# 后端开发（Backend Development）

后端开发关注**服务如何被实现**：并发模型、流量控制、幂等与状态管理、API 设计。它与相邻三个块各有分工——推理优化处理模型计算的效率，运维服务处理服务如何稳定运行，硬件构成提供物理基础；后端则处理"一个请求进来之后，服务端怎样正确、高效、可恢复地把它完成"。

这四块是**主视角而非互斥分类**，同一机制在不同层形态不同："并发"在硬件层是锁与内存屏障，在后端层是线程/协程与限流背压，在推理层是连续批处理与 KV cache 块共享，在运维层是多副本负载均衡与弹性伸缩。

## 并发 vs 并行

- **并发（concurrency）**：多个任务在重叠的时间段内推进，可能在同一核上交替执行——关注"如何组织任务以避免互相阻塞"。
- **并行（parallelism）**：多个任务真正同时执行，需要多核——关注"如何把工作分到多个执行单元"。

容量规划的基础关系（Little's Law）：`并发数 = 吞吐 × 平均延迟`，见 `../../computer-organization/performance/performance.md`。提高吞吐或降低延迟都会降低所需并发，反过来并发过高会推高延迟——这是限流与背压的理论依据。

## 并发模型

| 模型 | 特点 | 适合 |
|---|---|---|
| **多进程** | 内存隔离、故障隔离好；开销大、通信需序列化 | 强隔离需求、利用多核（如 Nginx worker、Prefork） |
| **多线程** | 共享内存、切换成本低；需同步、易竞态 | I/O 与 CPU 混合、共享状态场景 |
| **协程 / 异步 I/O** | 用户态调度、非阻塞 I/O、单机高并发；调试复杂、不能阻塞事件循环 | I/O 密集型高并发（网关、RPC 服务） |
| **事件循环** | 单线程 + 非阻塞 I/O + 回调 / async-await | 高连接数、轻计算 |

选择取决于负载性质：I/O 密集用异步/协程，CPU 密集用多进程或多核并行，混合场景常组合（如每核一个进程 + 进程内协程）。底层多核与一致性模型见 `../../computer-organization/parallel/parallel.md`。

## 流量控制

- **限流**：限制单位时间请求数，保护服务不被压垮。令牌桶允许一定突发，漏桶输出恒定速率。按用户、接口、租户等维度分别设限。
- **背压（backpressure）**：下游处理不过来时，让上游减速或拒绝，而不是让队列无限增长——无界队列最终转化为 OOM 或超时雪崩。
- **超时**：连接超时、读超时、整体超时；沿调用链传递**超时预算**，避免上游已超时而下游仍在烧资源。
- **重试**：只对幂等操作重试；用**指数退避 + 随机抖动**，并设重试上限，否则形成重试风暴。
- **熔断**：失败率超阈值时快速失败，给下游恢复窗口，避免持续打满故障服务。
- **降级**：返回简化结果、默认值或缓存，保证核心链路可用。

限流、熔断、重试同时是后端实现与运维稳定性手段——这里从服务实现视角讨论，运行侧的监控与容量治理见 `../devops/devops.md`。

## 幂等与状态管理

- **幂等性**：同一请求执行一次与多次效果相同。写操作带 `idempotency_key`（如支付、下单），重复请求返回首次结果而非重复执行。
- **乐观并发**：数据带版本号，更新时比较版本（CAS），冲突则重试；配合显式 ACK 与状态同步避免竞态与状态漂移。
- **无状态服务**：把会话外置（如 Redis），服务本身不持有状态，便于水平扩缩容与故障转移。
- **一致性取舍**：强一致、最终一致、因果一致的选择取决于业务约束；跨服务事务常以 sagas / 事件驱动替代分布式事务。

Agent 系统的工具写操作同样依赖幂等键、版本号与 `trace_id`，见 `../../ai/agent/tool/tool.md` 与 `../../ai/agent/multi/failure/failure.md`。

## API 与服务设计

- **交互风格**：REST（资源与 HTTP 语义）、gRPC（强类型、高性能、流式）、异步消息（解耦、削峰、最终一致）。
- **版本化与兼容**：新增字段向后兼容，破坏性变更走新版本；用消费者驱动的契约测试验证提供方的约定一致，见 `../quality/quality.md`。
- **可观察性基础**：结构化日志、请求 ID 透传、指标埋点——这些在服务内实现，数据由运维侧采集，见 `../devops/devops.md`。
- **边界与模块化**：服务内部保持清晰边界，避免单体退化为大泥球；架构风格与质量属性权衡见 `../architecture/architecture.md`。

## 与推理服务的关系

推理服务里的**连续批处理**本质是请求级并发调度的特例：slot 空出即插新请求，相当于后端"事件循环 + 排队"的 GPU 化版本。通用并发模型、排队、限流与背压在这里讨论；GPU slot 调度、KV cache 块共享与引擎选型是模型层的特化，见 `../../ai/model/inference/inference.md`。

## 常见失败模式

- **无界队列**：下游变慢时请求堆积，最终 OOM 或全链路超时。
- **重试风暴**：无退避、无上限的重试把故障放大为流量洪水。
- **非幂等重试**：重复扣款、重复下单——写操作没有幂等键。
- **线程池配置失当**：过大导致上下文切换开销，过小导致吞吐不足。
- **缺少超时**：一个慢下游阻塞整个调用链，故障沿依赖传播。
- **共享状态竞态**：乐观并发缺失导致状态漂移与丢失更新。
