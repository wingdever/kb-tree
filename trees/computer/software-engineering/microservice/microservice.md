# 微服务框架（Microservice Frameworks）

> 来源：microservices.io 模式目录、Apache Dubbo 官方文档、Istio 官方文档、gRPC 官方文档。框架能力矩阵与接口形态变化快，以官方文档为准。

微服务架构把应用组织为一组**可独立部署、松耦合**的服务，服务围绕业务能力组织，通常由小团队拥有。收益来自"独立部署"这一属性本身——独立发布节奏、独立扩缩、故障隔离；代价是网络失败、分布式一致性、可观测性与运维协调。如果组织并不需要独立部署节奏，引入注册中心、网关、熔断与分布式事务就是纯负债。

单体并非反模式：小团队小项目用单体往往更好。边界尚未稳定时过早拆分会造出**分布式单体**（distributed monolith），比单体更难改。务实路径是先把边界在单体里跑清楚，再选择性地把高变更、高扩展、跨团队的领域拆成服务，用绞杀者模式（Strangler Fig）渐进迁移。

## 服务边界

- **按业务能力拆分**：以业务能力（而非技术分层）定义服务，每个服务对应一项端到端能力。
- **按子域拆分**：用 DDD 的限界上下文/子域定义边界，边界内模型自洽、边界间显式转换。
- **自包含服务**：设计服务使其处理同步请求时不依赖等待其他服务响应，缩短同步调用链。
- **数据库私有**：每服务拥有私有数据库（Database per Service）是微服务一致性的前提；共享数据库会让服务边界名存实亡。

## 核心模式

服务发现回答"调用方如何找到实例"：客户端发现由调用方查注册表并自行选实例，服务端发现由路由器查注册表后转发；实例可自行注册或由第三方代注册，注册表保存实例位置。取舍在于把发现逻辑放在应用进程内还是基础设施里。

- **API 网关**：为外部客户端提供统一入口。按客户端类型拆分时形成 BFF（Backend for Frontend），避免一个网关被不同端的格式需求撕裂。
- **外部化配置**：数据库位置、凭据、开关等不写进代码；配置中心下发规则，实例监听变更。注册中心、配置中心、元数据中心在职责上可分，实践中常由同一组件承担。
- **可靠性**：熔断器在下游失败率超阈值时快速失败，避免故障沿调用链级联；限流站在服务提供者视角保护自身；熔断降级站在消费者视角，用预设降级结果替代直接失败。重试只对幂等操作生效，需指数退避与上限。
- **一致性阶梯**：优先用 API Composition（调用数据所属服务并在内存 join）解决读侧跨服务查询；写侧用 Saga（一串本地事务 + 补偿）；需要回放与审计再上 CQRS / 事件溯源。可靠性配套是 Transactional outbox / 事务日志挖掘 / 轮询发布，以及幂等消费者。选型时先问"能否重构边界避免跨服务事务"。
- **可观测性**：日志聚合、应用指标、审计日志、分布式追踪、异常跟踪、健康检查 API 是微服务必备的横切能力；没有追踪，跨服务延迟与失败点无法定位。

## 框架范式：进程内 SDK 与进程外代理

微服务框架的能力可以放在应用进程内（SDK 型），也可以移到进程旁的独立代理（Sidecar 型），这是最根本的选型轴。

**SDK 型（Dubbo、Spring Cloud 体系）**：服务发现、负载均衡、路由在客户端生效，无需额外代理进程，协议切换灵活。Dubbo 定位为云原生微服务开发框架，支持 HTTP/2、gRPC、REST、Thrift、TCP 等协议，内置加权随机（默认）、加权轮询、最少活跃、最短响应、一致性哈希、P2C 与自适应等负载均衡策略。其流量管控用 Router 链：每次调用请求流经一组 router，逐个收窄地址子集，随后才做负载均衡；由此可实现全链路灰度、金丝雀、按比例转发、同区域优先、重试与限流降级。代价是语言绑定与框架升级耦合。

**Sidecar 型（Istio + Envoy）**：控制面 Istiod 提供服务发现、配置与证书管理，把高层路由规则翻译成 Envoy 配置并下发给 Sidecar；数据面 Envoy 以 Sidecar 注入，中介所有入站出站流量，内置动态发现、负载均衡、TLS 终止、HTTP/2 与 gRPC 代理、熔断、健康检查、按比例流量分割、故障注入与丰富指标。最大价值是**无需改代码即可给存量部署加流量管控、mTLS 与遥测**；代价是资源成本、运维开销，以及注入需要重启 Pod。Istio 另提供 ambient 模式，用节点级 ztunnel 代理处理 L4，按需经 waypoint 获得 L7 能力，加入网格无需重启 Pod；还支持 Proxyless 形态接入同一控制面。

**平台接管趋势**：云原生部署下，注册中心、配置中心、元数据中心的部分职责正被 Kubernetes、Istio 等平台组件替代。已有平台能力时再叠加一套 SDK 注册中心，会形成双份服务视图。

## 通信协议

gRPC 基于 HTTP/2，默认用 Protocol Buffers 同时作为 IDL 与线上格式，由 `protoc` 生成各语言桩代码，支持四种通信模式（Unary、服务端流、客户端流、双向流）与可插拔认证，是 CNCF 孵化项目。优势是高频低延迟内部调用、强类型契约、原生流式、跨语言一致代码生成；代价是浏览器需 gRPC-Web 代理、默认不纳入 HTTP 缓存、二进制负载不可读。

REST 以资源与 HTTP 语义为中心，JSON 可读、调试工具成熟、浏览器直连与 HTTP 缓存天然可用；代价是契约可选、流式能力有限、负载体积更大。

更准确的问法不是全局二选一，而是**对外表面用哪个、对内调用用哪个**：可在同一架构里 REST 对外、gRPC 对内。Google API 设计指南同时适用于 REST 与 RPC，其 HTTP 映射支持 JSON/HTTP 与 Protocol Buffers/RPC 双向转码，即一份 proto 契约可同时产出两种表面。

## 选型判据

- 默认从小处开始：单体不是反模式，微服务的前提是组织确实需要独立部署节奏。
- 能力放进程内还是进程外：改代码成本与代理资源成本权衡；存量系统改造优先进程外。
- 是否已有平台接管发现与配置：避免重复建设，防止双份服务视图。
- 协议按内外表面分别选，不追求全局统一。
- 一致性按复杂度阶梯逐级上，先试边界重构。
- 团队规模决定能维护多少套基础设施：每多一层都要有人升级与排障。

## 常见失败模式

- 边界划错造出分布式单体，跨服务重构比单体昂贵得多。
- 过早拆分：边界未稳定就引入全套治理设施。
- 同步调用链过长：一个慢下游拖垮整条链路，超时预算未沿链传递。
- 非幂等重试：重复扣款、重复下单。
- 忽略可观测性：跨服务失败只能靠猜。
- 把 Saga 当默认方案，而不是先重构边界避免跨服务事务。
- 同时维护平台发现与框架注册中心，出现双份服务视图。
