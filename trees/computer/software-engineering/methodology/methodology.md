# 软件开发方法论（Software Development Methodologies）

方法论回答"工作如何排期与推进"，它约束的是**流程与反馈节奏**，而不是技术质量本身。选择取决于项目复杂度、需求清晰度、团队结构、风险承受度与业务目标。

## 主要方法

| 方法 | 特点 | 适合 |
|---|---|---|
| **Waterfall（瀑布）** | 线性顺序，阶段依次完成，关卡明确 | 需求明确、少变化（ERP、政府项目、硬件耦合） |
| **Agile — Scrum** | 固定时长冲刺、角色与仪式齐备、迭代增量 | 需求变化快、跨职能团队 |
| **Agile — Kanban** | 持续流、可视板、限制在制品（WIP）、拉动 | 运维、支持、变化频繁且难预测的工作 |
| **Lean（精益）** | 价值驱动、消除浪费、优化流动、延迟决策 | 追求效率与快速上市 |
| **Spiral（螺旋）** | 迭代 + 显式风险分析与原型 | 复杂大型系统（银行、航天） |
| **RAD（快速应用开发）** | 快速原型、用户反馈循环、时间盒 | 短周期、需频繁客户输入 |

## 共同内核

- **迭代与增量**：把大交付拆成可验证的小步，尽早暴露风险。
- **反馈闭环**：每个周期末用可工作的软件而非文档对齐干系人。
- **适应规划**：计划是随信息更新而演进的，不是一次性锁死。

## 规模化与混合

组织常在实践中混合：用瀑布的关卡满足合规，用 Scrum 的节奏推进开发，用 Kanban 管控运维与中断。规模化框架（SAFe、LeSS 等）试图把多团队协调起来，代价是流程复杂度——引入前应确认协调需求真实存在，而非为"看起来专业"。

## 选择依据

- 需求是否清晰、是否会频繁变化？
- 错误代价与合规要求有多高（决定关卡强度）？
- 团队规模与分布、是否需要跨团队同步？
- 用户对早期反馈与持续交付的需求？

## 常见失败模式

- 把 Agile 当成"没有计划与文档"的借口，缺少纪律的迭代退化为混乱。
- 机械执行仪式（站会、回顾）而不解决真实阻塞。
- 方法论之争掩盖了真正的问题：需求不清、边界不稳、反馈链断裂。
