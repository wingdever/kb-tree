# 文件完整性基线

快照的目的不是恢复，而是**判定变化**：先记录一份"当前应该是什么样"的指纹，之后每次比对产生的差异都必须被归入三类之一——可信、可疑、无法解释。归档的备份解决前一个问题，基线解决后一个问题。

## 基线是什么，不是什么

- 不是备份：只保存指纹，不保存内容。它回答"这个文件有没有被改"，不回答"怎么还原成原来的内容"。
- 不是一次性动作：基线需要随每次可信变更更新，否则差异会淹没在噪声里。
- 不是全量哈希：对系统每个字节做哈希，成本与收益不成比例；覆盖面取"改了会出问题"的部分即可。

指纹至少包含哈希、大小、权限、属主。单看修改时间不够——时间戳可以被伪造；单看大小也不够——等长替换很常见。

## 覆盖面

适合纳入的：系统配置目录、自启单元及其启用链接、系统二进制、定时任务、SSH 授权公钥、手工部署在系统路径下的脚本。

应当排除的：运行态与临时目录、日志、缓存、数据库运行文件、频繁重写的状态文件。这些位置天然持续变化，纳入只会制造噪声，而噪声会让真正的差异失去意义。

包管理器已登记的文件可以复用发行版自带的校验记录，不必自建哈希：包内文件的内容与权限有独立记录，可直接校验。**自建内容才是基线的重点**，因为它们没有任何第三方记录可以对照。

## 变化的三分类

- **可信**：包升级、已声明的变更窗口内、有对应部署记录或工单。特征是时间、位置、来源三者能对上。
- **可疑**：不属于任何变更窗口，或位置属于系统目录却由手工放入，或权限与属主出现异常放宽。
- **无法解释**：能确认发生了变化，但找不到来源。这类不进入"观察"，直接按入侵处理。

分类的关键不是差异本身，而是**能不能给出解释**。解释不了的部分，就是尚未查清的部分。

## 对齐流程

1. **先定性，再动文件**。差异出现时第一反应应是取证与解释，而不是把文件改回去——改回去会抹掉证据。
2. **可疑项取证**：保留样本与属性，查包归属与修改时间，与该位置的其他文件对比。
3. **可信项补登记**：确认来源后更新基线，并记录变更原因，使下一次比对不再报警。
4. **无法解释项处置**：隔离、清除、复核，之后重新建立基线；复核要确认差异没有在其他位置同步出现。

## 基线放在哪里

基线不能只放在被监控的机器上。攻击者获得足够权限后可以修改基线文件或校验数据库，使比对永远通过——这时基线本身成了掩护。

可行的做法：把基线摘要同步到版本库、对象存储或另一台主机；在本机只保留只读副本；按周期离线导出一份。基线文件的价值在于"外部有一份本机改不动的记录"。

## 噪声治理

- 部署与升级会集中产生差异：在变更窗口内重新生成基线，而不是逐条解释。
- 高频变化的文件要么排除，要么显式列入"允许变化"清单。
- 允许变化清单与例外清单一样会腐化，需要定期的到期复核。

## 与包归属的关系

包归属回答"这个东西该不该存在"，哈希基线回答"存在的东西有没有被改动"。两者互补：前者挡住陌生的新文件，后者挡住熟悉文件的可疑修改。

## 落地清单

- 先确定基线范围：系统二进制目录、配置目录、自启目录、授权公钥，范围一次定清，避免"每次凭感觉挑几个文件"。
- 生成基线时记录算法、时间与来源主机，哈希算法要选抗碰撞的，不要用已被淘汰的算法。
- 基线存两份：本机一份、主机之外一份；只存本机时，攻击者改文件顺手改基线，比对就失效。
- 比对按计划执行并与变更联动：正常变更后更新基线，未更新导致的告警会训练人忽略告警。
- 输出要可行动：报"哪些文件新增/修改/删除"，附文件路径与包归属，而不是只报一个总数。
- 基线不覆盖数据文件与日志，把范围控制住才能长期维护。
