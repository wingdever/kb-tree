# 自启动面

木马要活过重启，就必须被某个"开机时会被读的东西"登记。这类位置统称自启动面。监控它的理由很直接：**不重启也能跑的程序是运行态问题，重启还能跑的程序是资产问题**——后者不解决，处置就是临时的。

## 被登记不等于被信任

systemd 本身不校验来源，它只负责读目录、按依赖拉起。任何拿到写权限的人都可以往这些目录里放一个单元，systemd 会照章执行。所以"systemd 里的自启项都是认证过的"这个前提不成立：systemd 是登记表，不是审核机构。

真正能区分"谁放进来的"的判据只有**包归属**——文件由发行版包安装，说明它来自可信供应链；没有包归属，就需要有人为它负责。判断顺序永远是先看归属，再看行为与名称。

## systemd 不只是一张表

只查 `systemctl list-unit-files --state=enabled` 会漏掉相当一部分。至少五个入口：

- **单元文件搜索路径**：除常见目录外，还有运行期目录、本地安装目录与用户级目录。用户级单元由该用户的 systemd 实例拉起，不需要 root 也能做到持久化。
- **启用链接与依赖拉起**：一个单元即使没有启用，也可能被别的单元的依赖关系带起来。反过来，启用链接本身是独立文件，被改了位置就绕过了对单元文件的检查。
- **drop-in 覆盖**：包内单元完全合法，但同名的 `*.d/*.conf` 可以给它追加执行前动作。这是最容易漏的一类——单元名、包归属、启用状态全都正常，实际行为已经被改。
- **generator**：开机早期动态生成单元的脚本。生成出来的单元不在磁盘上，文件清单里根本找不到。
- **定时器、套接字、路径单元**：不是服务单元也会拉起进程；模板单元 `@实例` 让人只看模板文件就以为只有一个。

## systemd 之外

传统 init 脚本、cron 与 at、shell 启动文件、动态链接器预加载、内核模块加载清单、网络管理钩子、容器重启策略、SSH 与 PAM 配置——每一处都能独立完成持久化。只盯 systemd，等于只关了一扇门。

## 重启不常做验证

生产主机不会为了验证就重启。可行的替代是核对**开机时会读到什么**：单元集合、启用链接、drop-in、生成器、依赖图，以及上面那些非 systemd 位置。要真的验证持久化是否被清除，应在隔离环境或维护窗口做，而不是在线上赌一次重启。

## 检查节奏

自启动面适合跟着每次变更走：装包、加服务、改配置之后重跑一次并更新基线。日常则每天看"有没有新增的非包归属登记项"，每周看一次全量清单——新增项少，全量清单长，两者的读法不同。

## 落地清单

- 列全持久化面：系统与用户自启单元、定时任务、shell 启动脚本、预加载配置、授权公钥、开机脚本、容器重启策略，逐项确认归属。
- 每个持久化点都要能回答"谁装的、什么时候、为什么"。答不出来的就是待查项。
- 变更即记录：新增自启单元、新增定时任务、追加公钥都进变更日志，并与告警联动。
- 巡检优先看增量：与基线比对新增项，比通读全部条目更有效。
- 清理时按面逐项过，不要只删最显眼的那一个；残留的任意一处都会让清理失效。
- 季度复核持久化清单本身，业务新增的机制（容器、编排、代理）常带来新的持久化面。
