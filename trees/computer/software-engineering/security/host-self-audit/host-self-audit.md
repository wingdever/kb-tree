# 主机自我巡检与防护策略

单机防护不是一堆加固项的集合，而是一套按固定节奏重复执行的动作。它要同时回答三个问题：入口还有多少、尝试有没有代价、异常能不能被看见。三个问题对应三层，缺一层就会在别层留下漏洞。

## 三个层次

- **收敛**：把"可被利用的入口"减少到能逐一解释的数量。
- **计价**：让每一次失败尝试产生确定的时间成本，压掉自动化爆破的收益。
- **对照**：用一份可验证的"应该存在什么"清单，去比对"现在存在什么"。

前两层作用在攻击发生之前，第三层作用在发生之中与之后。前两层做得再好，也仍需要第三层，因为任何收敛都会有残余。

## 收敛：认证面

认证面的目标不是"加锁"，而是"减少需要保护的对象"：

- 关闭口令认证，只保留密钥。口令认证一旦开启，剩余防护全部压在一个字符串上。
- 超级用户不接受口令登录，只接受密钥。这消除了"一次命中即最高权限"的最短路径。
- 可登录账户收敛到白名单，业务与数据库身份不提供交互 shell。
- 管理类端口不绑定在全部接口上，需要时通过隧道进入。

若某处确实只能保留口令认证，那就退一步：长度与随机性足够、与其他位置不复用、定期核对是否外泄。这是妥协，不是等价方案。

## 计价：失败尝试

自动封禁的要点是**封禁时长与单位**，而不是封禁本身：

- **单位是来源地址**，不是账户。攻击者换账户比换地址便宜，锁定账户只会把正常用户一起挡在外面。
- **时长取"够用"而非"够狠"**。自动化爆破的重试窗口通常在分钟级，短时封禁就足以让它转向别的目标；永久黑名单则会积累误伤，并在某天把自己挡在外面。
- **递增**。同一地址反复触发时延长封禁，比一次性长封禁更省心，也更容易解释。
- **白名单先行**。自己的出口地址、跳板与监控探针必须在白名单里，否则第一次误封就发生在运维自己身上。

封禁只处理"尝试"，不处理"配置"。它与"关闭口令认证"是两件不同的事：前者降低噪声，后者取消可能性。

## 对照：白名单巡检

巡检的可信依据是**归属**：一个东西是否存在，可以由包管理器回答；一个东西是否正当，则要由人来解释。

- **自启单元**：凡是有包归属、且路径落在包安装目录的，可以视为基线；有单元但查不到包归属的，进入"待解释"队列。
- **系统目录可执行文件**：同理。系统二进制通常有归属、体积正常、动态链接；异常项按同一队列处理。
- **定时任务与授权公钥**：没有包归属概念，只能按"新增即告警、由人确认"处理，因此需要保留基线快照来定义"新增"。
- **待解释不等于恶意**。运维自建脚本、手工部署的服务都会进队列，处理方式是补一条显式例外并记录责任人与用途，而不是删掉了事。

白名单的敌人是腐化：例外只增不减、没人负责，半年后清单本身就失去了意义。例外需要过期复核。

## 巡检节奏

- **每日**：失败次数与来源、非白名单来源的成功登录、出入流量比例、待解释队列的增量。
- **每周**：全量的单元与可执行文件归属比对，授权公钥哈希比对。
- **每次变更后**：部署、扩容、加人，都视为一次基线变更，需要重新确认清单。

摘要必须离开主机，进入有人的通道。留在日志目录里的日报，和没有日报是同一件事。

## 边界与失败模式

- **自锁**：封禁与认证收敛都可能把运维自己关在门外，必须保留控制台或救援通道，并在改动前验证新连接可用。
- **只做封禁**：封禁降低了日志噪声，容易被误读为"已经安全"。
- **只做对照**：巡检能发现问题，但发现问题到处置之间仍需要有人负责，否则队列会一直增长。
- **以数据价值判断风险**：没有数据的机器同样会被征用为出口与算力，风险不随数据价值下降。
