# 软件生命周期（SDLC）

软件生命周期描述一项软件从"为什么做"到"上线后如何活下去"的全过程。常见阶段：**需求 → 设计 → 实现 → 测试 → 部署 → 维护**。现代团队很少把它做成单条直线——即使在受监管环境，也是在关卡（gate）内迭代：用户反馈、安全发现、生产事故、市场变化都会改变系统目标。**SDLC 是一个循环**：生产中的学习反哺下一轮需求与设计。

## 六个阶段

- **需求**：把模糊目标变成可验证陈述，区分功能需求与非功能需求，建立到测试和发布的追溯。详见 `requirements/requirements.md`。
- **设计**：把质量属性（安全、扩展、可维护、性能）显式化为架构决策；设计不只是"能跑"，还要能加固、扩展、维护。详见 `../architecture/architecture.md`。
- **实现**：选数据结构、API、库、运行时模式，写测试，互相评审，用 CI 在发布前编译、检查、扫描、演练。好团队让变更小到可理解，避免未评审的依赖升级、无文档的配置改动、不可重复的手工部署。
- **测试**：单元、集成、契约、系统、性能、安全、验收——没有哪种证明完美，每种从不同角度降低不确定性；测试直接映射到验收标准（"结账 2 秒内完成"对应性能测试，"API 返回正确 schema"对应契约测试）。详见 `../quality/quality.md`。
- **部署**：通过功能开关、金丝雀、蓝绿、回滚计划把软件送上生产。详见 `../devops/devops.md`。
- **维护**：更新、修 bug、增强功能、优化性能，让系统持续安全、可扩展、对齐业务。维护往往占软件全生命周期成本的最大头（常见估计 60%–80%）。

## 迭代与关卡

- **迭代式交付**：每个短周期都走完需求到部署的缩小版闭环，尽早暴露风险。
- **阶段关卡（gate）**：在强监管或硬件耦合场景，阶段之间存在评审与批准关卡；关卡不否定迭代，只是把"能否进入下一阶段"显式化。
- **反馈回路**：可观测性数据、事故复盘、用户行为、依赖升级与安全公告，都是下一轮需求的输入。闭环断裂的典型症状是"上线即失联"——没人知道真实使用情况。

## 常见失败模式

- 把 SDLC 当成一次性流水线，上线后没有维护与反馈通道。
- 测试只在末尾进行，缺陷发现越晚修复成本越高（左移可缓解，见 `../quality/quality.md`）。
- 需求不可验证（"系统要快""界面要友好"），导致验收时争议。
