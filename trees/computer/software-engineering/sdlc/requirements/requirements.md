# 需求工程（Requirements Engineering）

需求工程把模糊目标转化为**可验证陈述**。核心产出不是"愿望清单"，而是每一条都能被测试、被追溯到设计与发布的规格。ISO/IEC/IEEE 29148 是这一过程的参考标准。

## 两类需求

- **功能需求**：描述系统行为——建账户、计税、对账、发通知、导出报表。通常写成用例或用户故事。
- **非功能需求（质量属性需求）**：描述系统属性，必须尽量量化，否则不可验收：
  - 性能：p95 延迟 < 200ms（在 1000 并发下）
  - 可用性：月度可用性 ≥ 99.9%（约 43 分钟/月停机预算）
  - 隐私与合规：数据最小化、留存 90 天后自动删除、审计日志保留 1 年
  - 可访问性：符合 WCAG 2.2 AA
  - 韧性：单可用区故障时 5 分钟内切流
  - 可维护性、成本上限、可审计性

## 表达形式

- **用户故事**：作为<角色>，我想要<能力>，以便<价值>。质量用 INVEST 检验：独立（Independent）、可协商（Negotiable）、有价值（Valuable）、可估算（Estimable）、小（Small）、可测试（Testable）。
- **验收标准**：每条故事配 Given/When/Then 或检查清单，直接成为测试用例。
- **优先级**：MoSCoW（Must / Should / Could / Won't）或 Kano 模型，避免"都重要"导致的范围失控。
- **规格说明**：对硬约束（协议、算法、合规）用精确语言，不用形容词。

## 追溯矩阵

维护需求 → 设计决策 → 代码/组件 → 测试用例 → 发布版本的追溯关系。用途：

- 变更影响分析：改一条需求，立刻知道牵动哪些测试与文档。
- 合规审计：证明每条强制需求都被实现并验证。
- 验收覆盖：发现"写了需求但没人测"或"写了测试但无来源"的缺口。

## 常见失败模式

- **不可验证**："系统要快""界面要友好"——没有阈值与条件，验收时争吵。
- **过早锁定方案**：把实现手段当需求（"用 Redis"），限制更优解。
- **隐形需求遗漏**：非功能需求缺席，直到上线后被性能、安全或合规问题反噬。
- **追溯断链**：需求变更未同步到测试与文档，追溯矩阵迅速腐化——把它当交付物的一部分而非事后文档。
