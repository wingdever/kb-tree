# 软件架构（Software Architecture）

架构是**把质量属性显式化的地方**。功能"能跑"只是底线；能否加固、扩展、维护、部署，决定系统是否真正完成。架构决策的本质是权衡：没有银弹，只有"在这个约束下更合适"的选择。

## 质量属性驱动设计

把模糊的"要好"转成可检验的质量属性场景：**刺激源 → 刺激 → 环境 → 构件 → 响应 → 响应度量**。例："在 1000 并发下（环境），支付请求到达（刺激），系统在 p95 < 200ms 内返回（响应度量）"。

关键属性：性能、可扩展性、可用性/韧性、安全性、可维护性、可测试性、可部署性、成本。属性之间常冲突（强一致 vs 可用、加密 vs 延迟），架构是这些冲突的显式取舍，并把取舍理由记录下来。

## 架构风格谱系

| 风格 | 核心 | 适合 | 代价 |
|---|---|---|---|
| 分层架构 | 表现/业务/数据分层，依赖单向 | 通用业务系统 | 层间易僵化、产生"贯穿层" |
| 模块化单体 | 单部署单元，内部边界清晰、强模块 | 中小产品、早期创业首选 | 需要纪律维持边界，否则退化为大泥球 |
| 微服务 | 按业务能力拆分，独立部署与扩展 | 高变更频率、跨团队自治、差异化扩展 | 网络失败、分布式追踪、数据一致性、部署协调成本 |
| 事件驱动 | 组件通过异步事件解耦 | 实时分析、系统集成、松耦合工作流 | 因果链调试困难、最终一致性、消息重复与顺序 |
| CQRS / 事件溯源 | 读写模型分离，状态由事件流重建 | 复杂领域、审计与回放需求 | 显著复杂度，仅在收益大于成本处使用 |
| 清洁 / 六边形 | 业务核心与外部依赖隔离，依赖指向内部 | 领域复杂、需长期演进与测试 | 接口与适配层增多 |
| Serverless | 函数即部署单元，按事件与用量计费 | 事件驱动、波动流量后端 | 冷启动、状态管理、供应商锁定、调试困难 |
| 边缘计算 | 计算下沉到靠近用户处 | 全球用户低延迟、数据本地合规 | 部署与运维分散、一致性挑战 |
| 多云 / 混合 | 跨云与自建组合 | 合规、成本优化、避免单点锁定 | 抽象层复杂、运维与技能要求高 |

## 单体与微服务的现实取舍

微服务不是"更先进"的同义词，而是**用运维复杂度换团队自治与独立扩展**。常见误区：在边界尚未稳定时过早拆分——边界错误时，跨服务重构比单体内重构昂贵得多。务实路径往往是从模块化单体开始，把边界跑清楚，再**选择性地**把高变更、高扩展、跨团队的领域拆成服务。

## 架构决策记录（ADR）

每个重要决策写一份短记录：背景、决策、备选方案、后果（好与坏）。价值在于保存"当时为什么这么选"，避免半年后无人知晓约束来源、把决策当教条或盲目推翻。ADR 随代码进版本库，而非散落在聊天记录里。

## 常见失败模式

- 以"业界最佳实践"代替自身约束分析，照搬大厂架构。
- 架构文档与实现脱节，决策无人维护。
- 分布式引入的失败模式被忽略：网络分区、部分失败、时钟偏差、重试风暴。
- 只关注功能需求，质量属性缺席，上线后加固成本剧增。
