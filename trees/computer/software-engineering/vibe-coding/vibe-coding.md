# 氛围编程（Vibe Coding）

氛围编程由 Andrej Karpathy 于 2025 年 2 月提出：用自然语言描述想要什么，让 AI 写代码，你通过**运行结果的反馈**来引导下一步，而不是逐行编辑或审查。原始表述是"完全沉浸于感觉、拥抱指数级、忘记代码的存在"。

它的定义特征不是"用 AI 写代码"，而是**选择不逐行审查输出**。大量开发者重度使用 AI 但仍逐行读代码——那是 AI 辅助编程，不是氛围编程。2026 年 Karpathy 本人提议把需要设计、约束与人类判断的生产级工作改称 **agentic engineering**，把两者当作互补的两种模式。

## 核心理念

- **职责分离**：人负责"做什么"（需求、架构决策、质量把关），AI 负责"怎么做"（代码实现、语法细节、模式套用）。
- **心智负担转移**：从"记住 API 签名"转为"清晰表达意图"，从"逐行调试"转为"审查整体方案"；核心技能从打字速度转向需求分析与架构判断力。
- **工作单位是行为，不是函数**：说"下载最近 30 天的 Stripe 事件写成 Parquet 文件"，而不是"写一个接收日期范围的函数"——函数形状由 agent 决定。
- **验收靠执行**：跑起来符合预期就接受，不符合就描述问题让它重试。真正稀缺的能力是**清晰描述意图**和**分辨"真对"还是"表面能用"**。

## 与相邻方式的区别

| 方式 | 审查程度 | 适合 | 主要技能 |
|---|---|---|---|
| **Vibe coding** | 跳过或极少审查 | 原型、内部工具、绿地探索 | 描述意图、识别坏输出 |
| **AI 辅助编程** | 每个改动都审查 | 生产代码、既有代码库 | 传统工程 + 提示词熟练度 |
| **Agentic Coding** | 自主执行 + 人在关键处监督批准 | 完整任务交给 agent，目标导向 | 任务拆解、上下文、结果验收 |

详见 `../../ai/agent/coding/coding.md` 与 `../spec-driven/spec-driven.md`。

## 经验与实践

### 按风险切换模式（Vibe & Verify）

标准做法是保留"让 AI 写"的轻量，但在后端插入验证：

- **低风险**（个人工具、学习、一次性脚本）：可以全程 vibe。
- **中风险**（内部工具、MVP、可丢弃原型）：vibe + 冒烟测试 + 快速安全扫描。
- **高风险**（生产、客户数据、公开服务）：必须切到 agentic engineering——人工审查 + 自动安全扫描 + 补测试，即使是在 vibe 模式下写出的代码，上线前也要过这些关卡。

实用分界是**代码生命周期**：本周就能丢掉的，快速 vibe；要维护扩展数月以上的，先消除模糊性反而总成本更低。

### 让 vibe 保持可用的提示词模式

- 说清**成功标准**（怎么算做对了）。
- 设定**自主上限**（哪些操作必须先问人）。
- **先要计划再写代码**。
- 要求**最小 diff**，不要顺手重写无关部分。
- 请求**回滚路径**。
- 保持紧反馈循环：每次改动后跑测试，接受前扫 diff，命名不可变量让 agent 必须保持。

### 三件必做

1. **看 diff**：一次性代码可以不逐行看；共享代码至少扫一遍改动。
2. **跑安全 linter**：如 semgrep、bandit、truffleHog，机械检查密钥泄露、SSRF、XSS。
3. **让 AI 写测试**：每次生成后追加"为这段代码写测试"——没有测试的代码不算完成。

### 两条纪律

- **绝不 vibe secrets**：API key、数据库密码、生产 token 不交给 AI，也不让它写进代码；`.env` + `.gitignore` + 环境变量的纪律不可妥协。
- **别丢掉读代码的能力**：越依赖 vibe，越要偶尔停下来真正读懂代码——长期看这才是技能分水岭，出事故时尤其如此。

### 错误处理

AI 遇到报错默认会重试，往往是同一个错误反复出现。正确做法是**先分析根因，再制定修复方案**；把"报错必先分析根因、严禁盲目重试"写进全局规范。高风险操作（数据修改、文件系统操作、网络请求、执行危险命令）必须让 AI 先说明计划再执行，确认后再动手。

### 提交纪律

阶段性任务完成后提交（git add + commit），但**严禁自动 push**；提交信息用简短的 `type: description` 格式、中文描述，保持历史可读。全局规范可按四个维度制定：逻辑规范（先规划、高风险确认、报错查根因）、协作规范（何时提交/推送、信息格式）、环境规范（编码格式、文件过滤）、交付规范（禁止硬编码、依赖变更需确认、代码简洁）。

## 适用场景

- **适合**：一次性脚本、周末项目、落地页、内部工具、管理后台、绿地新项目、探索陌生 API、在你已理解的问题上学习。
- **不适合**：生产系统、涉及资金/PII/认证的代码、别人要维护的代码、你无法识别错误答案的问题、超出单次上下文的大改造、安全敏感与性能关键代码。

## 失败模式

- **错误累积**：每步 95% 可靠的 agent，在长链未审查步骤上仍会频繁失败——氛围编程按定义跳过了能及早发现的审查。
- **自信的 bug**：代码能编译、读起来漂亮，但做错事——比明显崩溃更难察觉。
- **安全缺口**：未转义输入、失效的鉴权检查、泄露的密钥，在演示里看着正常，到生产就出事。业界测试中，在允许选择安全方案时 LLM 约 45% 选了不安全实现；受测编码 agent 均引入过 SSRF 类问题，AI 生成代码相关 CVE 在 2026 年初数月内显著上升。
- **技能退化**：从不自己调试，能力逐渐流失，往往在事故中才发现。
- **维护债**：形成没人理解的代码库——能跑直到不能跑，然后没人知道为什么。
- **许可证风险**：生成代码可能近似有许可证约束的源码，商业使用需留意。

## 与 SDD 的关系

氛围编程与规格驱动开发不是对手，而是同一谱系的两端：**vibe 用来探索，spec 用来交付**。前期用氛围编程快速试错、把想法捏成形；一旦要进入生产、多人协作或需要审计，就切换到 `../spec-driven/spec-driven.md`，把已确认的意图固化成可审查的规格。判断切换时点的仍是风险与代码生命周期。
