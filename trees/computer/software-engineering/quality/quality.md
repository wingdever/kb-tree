# 软件质量与测试（Software Quality and Testing）

没有哪种测试能证明完美，每种测试从不同角度降低不确定性。质量不是测试阶段才产生的，而是贯穿需求、设计、实现的属性；测试的作用是**把变更风险压到可发布**。

## 测试金字塔

从底到顶：单元测试 → 集成测试 → 契约测试 → 系统/端到端测试。越往下越快、越稳定、越便宜、定位越准；越往上越能覆盖真实跨边界行为，但越慢越脆。健康结构：底部大量、顶部少量。反过来（"冰淇淋筒"）会导致反馈慢、维护成本高、CI 不稳定。

- **单元测试**：验证单个函数/类的行为，快、确定、无外部依赖。关注边界条件、异常路径、状态转换。
- **集成测试**：验证模块间协作（服务↔数据库、服务↔消息队列），发现"各自都对、接起来错"。
- **契约测试**：消费者驱动的契约（如 Pact）验证服务提供方与消费方对接口的约定一致，避免微服务间"我改了你不知道"。
- **系统/端到端测试**：从用户入口走完整流程，验证真实价值路径；保留少量冒烟级覆盖，不追求全量。
- **非功能测试**：性能测试（负载、压力、稳定性）、安全测试（渗透、依赖扫描、SAST/DAST）、可访问性测试、兼容性测试。

## 测试实践

- **TDD（测试驱动开发）**：红→绿→重构。先写失败测试再实现，显著提升质量、减少生产 bug，代价是初期节奏变慢与对重构纪律的要求。
- **BDD（行为驱动开发）**：用 Given/When/Then 把验收标准写成可执行规格，让技术与非技术干系人对齐。
- **ATDD（验收测试驱动）**：在需求阶段就确定验收测试，避免"做完了才知道验收标准"。
- **测试替身**：mock / stub / fake / spy 按需要选择；过度 mock 会让测试只验证自身假设。
- **代码评审**：不只是找 bug，更是知识传播、设计与可维护性把关，是专业成长 indispensable 的环节。评审应聚焦设计与可读性，格式交给自动化（linter / formatter）。

## 左移（Shift-Left）

把测试与安全前移到生命周期早期，由自动化支撑，追求快速反馈：静态/动态分析进 CI、依赖与许可证扫描、安全策略即代码、提交前本地跑快测试。缺陷发现越晚，修复成本越高——左移的经济学正在于此。

## 质量度量

- **缺陷逃逸率**：上线后发现的缺陷占比，反映测试有效性。
- **变更失败率 / 部署频率 / MTTR / 变更前置时间**：DORA 四项指标，衡量交付效能与稳定性。
- **测试覆盖率**：有用的信号而非目标；覆盖率 100% 不代表断言质量高。

## 常见失败模式

- 只追覆盖率数字，写没有断言价值的测试。
- 端到端测试过多，CI 缓慢且偶发失败，团队开始跳过测试。
- 测试与验收标准脱节：需求说"2 秒内完成"，测试却不测时间。
- 左移变成"把工作甩给开发者"而不给工具与自动化支撑。
