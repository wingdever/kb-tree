# DevOps 与站点可靠性工程（DevOps and SRE）

DevOps 的协作、自动化、共担责任仍是基础；SRE 用工程手段把可靠性变成可度量、可管理的对象。两者共同目标：**让变更频繁、快速、安全地流动**。

## CI/CD 流水线

提交后自动执行：编译 → 单元测试 → 静态分析/格式检查 → 依赖与许可证扫描 → 构建制品 → 部署到类生产环境 → 集成/契约测试 → 安全扫描 → 发布。原则：

- 每条提交触发同一条流水线，结果可复现。
- 制品只构建一次，在不同环境间 promotion（晋升）而非重新构建，避免"测试的和上线的不是同一个"。
- 快反馈优先：把最可能失败的检查放前面，让开发者几分钟内知道结果。
- 失败即停（fail fast），不允许带红构建继续发布。

## 部署策略

| 策略 | 做法 | 适用 |
|---|---|---|
| 滚动发布 | 逐批替换实例 | 通用，需处理新旧版本共存 |
| 蓝绿部署 | 两套环境切换流量 | 需要快速回滚、版本切换成本可控 |
| 金丝雀 | 小比例流量先上，观察指标再扩量 | 高风险变更、需要真实流量验证 |
| 功能开关 | 代码部署与功能发布解耦，按人群/配置开启 | 持续交付、灰度、A/B 测试 |
| 影子流量 | 复制生产流量到新版本但不返回结果 | 验证新版本行为与性能 |

**回滚计划是发布的一部分**：没有验证过的回滚路径，就不要发布。功能开关让"关闭功能"比"回滚代码"更快。

## 基础设施即代码（IaC）

用 Terraform / Pulumi 等声明式定义基础设施，版本化、可评审、可复现。价值：消除配置漂移、环境可重建、审计有据。配合理念：**宠物 vs 牲畜**——服务器可替换而非精心呵护；不可变基础设施——改配置靠重建镜像而非原地修改。

## 可观测性三大支柱

- **日志（logs）**：离散事件记录；结构化日志便于检索与聚合。
- **指标（metrics）**：可聚合的时间序列（Prometheus / Grafana），适合告警与趋势。
- **追踪（traces）**：请求跨服务的调用链（OpenTelemetry），定位分布式延迟与失败点。

三者互补：指标告诉你"出问题了"，追踪告诉你"在哪一步"，日志告诉你"为什么"。没有可观测性，事故响应只能靠猜。

## SRE 核心实践

- **SLI（服务级指标）**：对用户真正重要的量的度量，如请求成功率、延迟、可用性。
- **SLO（服务级目标）**：对 SLI 的明确目标（如月度可用性 99.9%）。
- **错误预算**：允许不可靠的上限（100% − SLO）。预算充足时可加快发布；预算耗尽时冻结风险变更，优先稳定性——这让"快"与"稳"有了可执行的仲裁机制。
- **消除 Toil**：把重复、手工、无长期价值的运维工作自动化。
- **事故响应与无责复盘（postmortem）**：关注系统与人因的改进，而不是追责个人；产出可跟踪的改进项。
- **容量规划与混沌工程**：主动验证系统对故障的韧性。

## 平台工程

越来越多组织设平台工程团队，提供自助基础设施与"黄金路径"：内部开发者门户、可复用 CI/CD 模板、标准化环境、内置合规与观测。目的是让产品团队专注于业务价值，而不必重复解决部署、环境、合规问题。

## DORA 四项指标

部署频率、变更前置时间、变更失败率、服务恢复时间（MTTR）。高效能团队在这些指标上同时表现更好——快速交付与高稳定性并不矛盾。

## 客户端自动更新

服务端 CI/CD 管的是“制品怎么发到服务器”，客户端自动更新管的是“已经装在用户机器上的旧版本怎么安全换新”。它多出版本协商、签名校验、原子替换、失败回滚与分批放量，不能用一个下载脚本代替。

## 常见失败模式

- CI 长时间红灯无人处理，团队形成"绕过检查"的习惯。
- 发布没有回滚演练，事故时手忙脚乱。
- 只监控 CPU/内存等系统指标，缺失用户视角 SLI。
- 错误预算无人执行，SLO 沦为装饰。
