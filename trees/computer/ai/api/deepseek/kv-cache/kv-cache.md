# 上下文缓存（Context Caching on Disk）

DeepSeek API 的**磁盘上下文缓存默认对所有用户开启**，无需修改代码即可受益。每次请求都会触发缓存构建；后续请求若与之前请求有重叠前缀，重叠部分从缓存读取，计为一次**缓存命中**。

## 命中规则：完整匹配缓存前缀单元

命中要求对应前缀已被「持久化」，即写入磁盘缓存。由于 Sliding Window Attention 机制，缓存前缀的存储与匹配方式不同于以往：**每个缓存前缀是独立完整单元，后续请求必须完整匹配某个缓存前缀单元才能命中**。部分重叠不算命中。

缓存前缀在三种时机被持久化：

1. **请求边界**：每个请求在「用户输入结束位置」与「模型输出结束位置」各产生两个缓存前缀单元，后续请求完整匹配其中任一即可命中。
2. **公共前缀检测**：系统检测到多个请求共享某段前缀时，把它持久化为独立单元。
3. **固定 token 间隔**：长输入或长输出会按固定 token 间隔切出单元，避免长前缀因为永远到不了结束位置而无法缓存。

## 两个典型例子

**多轮对话**：首轮 `A + B`，次轮 `A + B + C`。次轮完整匹配首轮的 `A + B` 单元，命中 `A + B`。

**长文问答**：首轮 `A + B`（系统提示 + 财报 + 摘要要求），次轮 `A + C`（同一财报 + 盈利分析）——`A + C` 与 `A + B` 不完整匹配，不命中；但系统检测到公共前缀 `A`，将其持久化为独立单元；第三轮 `A + D` 完整匹配 `A`，命中。

## 命中状态字段

响应 `usage` 增加两个字段。

- `prompt_cache_hit_tokens`：本次输入中命中缓存的 token 数。
- `prompt_cache_miss_tokens`：本次输入中未命中缓存的 token 数。

## 重要边界

- 磁盘缓存**只匹配用户输入的前缀**；输出仍由计算与推理生成，受 `temperature` 等参数影响，保留随机性。
- 缓存系统按 **best-effort** 工作，**不保证 100% 命中率**。
- 缓存构建耗时数秒；不再使用时自动清理，通常数小时到数天。
- `user_id` 可用于 KVCache 隔离与隐私管理。

## 一句话主线

**默认开启、按完整前缀单元命中、命中可观测但不保证——把稳定内容放在最前面，让请求尽量完整复用同一个单元。**
