# Agent 互操作与接口

这一组回答「Agent 怎么接外部世界」。四类接口各管一段：**工具**决定它能做什么，**协议**决定它跟谁对话，**技能**把知识与流程打包，**渠道**决定用户从哪里够到它。共同点是：接口一旦定下，能力上限和权限边界就同时被定下了。

## 四个接口的边界

| 接口 | 对面是谁 | 一旦定错，代价在哪 |
|---|---|---|
| 工具 | 函数、API、数据源 | 权限过大或粒度过粗，模型会在错误的地方乱试 |
| 协议 | 别的 Agent、编辑器、前端 | 选错协议，接第二个客户端时要重写整条线路 |
| 技能 | 可复用的知识与流程 | 打包不清，同一套判断在不同 Agent 上漂移 |
| 渠道 | 用户所在的平台 | 平台限制（消息长度、富媒体、鉴权）决定交互形态 |

## 选择时按「对面是谁」问

- 对面是**函数或数据源** → 工具，且先想清楚爆炸半径与幂等性。
- 对面是**另一个 Agent**，跨团队或跨厂商 → 标准协议，而不是私有 JSON。
- 对面是**编辑器** → 客户端协议；对面是**自有前端** → 事件流协议，两者解决的不是一件事。
- 对面是**用户所在的应用** → 渠道，先接受它的限制再设计交互，而不是反过来。

## 三条容易踩的坑

- **把协议当能力**。接上 MCP 不等于 Agent 变强，它只解决「拿得到工具」；工具好不好用是另一回事。
- **过早抽象**。只有一个客户端时自建私有协议更省事，但接第二个客户端时成本会一次性回来；判断依据是「半年内会不会有第二个入口」。
- **渠道倒逼产品**。先做网页再上 IM，会撞上消息长度与富媒体的限制；有 IM 需求时，交互要按 IM 的粒度设计。

## 决策顺序

先定工具契约，因为它同时决定能力与风险边界；再按「对面是谁」选协议；最后处理技能打包与渠道接入。做跨端产品时，先确定接入协议再定渠道——顺序反过来会返工。

## 一句话主线

工具定义能力与风险边界、协议定义对话对象、技能打包可复用的判断、渠道决定触达方式；一切都按「对面是谁」选，且接口选型要在第二个客户端出现之前想清楚。
