# 工具结果契约

工具设计的多数讨论停在输入 schema，真正决定 Agent 能不能自我纠错的是**返回什么**。同一个后端错误，写成一句 `Error: something went wrong` 会让模型原地重试三次；写成带错误码、可重试标记、建议下一步的结构化对象，模型一次就能换路。下面讲返回值的契约设计。

## 结果有两个读者

每次工具返回同时被两方消费，写法要同时满足：

- **模型**读自然语言部分：发生了什么、能不能重试、下一步该调什么、还缺什么参数。
- **程序**（中介层、评估器、UI、审计）读结构化部分：错误码、资源 id、版本号、耗时、计费。

混在一起的典型后果：把给程序看的错误码直接抛给模型（`ERR_409_CONFLICT`），模型只能猜；或者只给模型写一句人话，评估器无法统计失败类型。

## 成功返回的信封

一个稳定信封只要四个槽，多一个都是负担：

| 槽 | 内容 | 缺了会怎样 |
|---|---|---|
| `status` | `ok` / `partial` / `error` | 模型无法区分"没查到"与"查询失败" |
| `data` | 结果本体或资源指针 | 只能靠文本猜测结果 |
| `meta` | 版本号、耗时、计数、游标 | 无法续取、无法判断新鲜度 |
| `next` | 可选的续取方式（游标、offset、建议调用） | 大结果只能截断，模型以为已经拿全 |

`data` 里优先放**资源指针**而不是内容快照：`{"order_id": "o_123", "status": "paid"}` 比把整张订单 JSON 塞回去更有用——后续动作可以直接引用这个 id，而快照会过期、会膨胀上下文。只有内容本身就是答案时（一段文本、一张表的若干行）才直接返回内容。

`meta` 里的计数要写清是"总数"还是"本页数量"，否则模型会把 5 当成全部。计数与游标属于程序读者，但模型也需要看到"还有更多"这句话，两者都要有。

## 错误返回的六个字段

错误对象至少写清六件事，缺哪件都会导致错误的下一步：

| 字段 | 回答的问题 | 写法 |
|---|---|---|
| `code` | 哪一类失败 | 稳定枚举，不随文案改；如 `invalid_argument`、`permission_denied`、`conflict`、`rate_limited`、`unavailable`、`unknown` |
| `message` | 人/模型可读的原因 | 一句话说清哪个字段、哪个前提不满足 |
| `retryable` | 原样重试有没有意义 | 布尔值，由服务端判定，不让模型猜 |
| `retry_after` | 多久之后再试 | 仅 `retryable` 且已知等待时间时给；单位明确 |
| `scope` | 谁能修 | `caller`（改参数可修）/ `user`（需要用户授权或补充）/ `system`（等外部恢复） |
| `next_action` | 建议的下一步 | 具体到动作与参数，如"用 `list_orders(customer_id=...)` 重新取 id" |

一个可直接照抄的形状：

```json
{
  "status": "error",
  "error": {
    "code": "conflict",
    "message": "order o_123 已被更新，当前版本 v7，你提交的基于 v5",
    "retryable": false,
    "scope": "caller",
    "next_action": "先调 get_order(o_123) 取回最新版本，再重放这次修改",
    "details": {"resource": "order", "id": "o_123", "current_version": 7, "your_version": 5}
  }
}
```

`details` 是给程序与排障用的结构化补充，模型可以只读 `message` 与 `next_action`。两者不要互相替代：`message` 里堆 JSON 会浪费 token，`details` 里只放错误码会让模型看不懂。

## 把内部错误映射成模型能用的措辞

后端错误码通常面向开发者，需要一层翻译再交给模型。映射时保留原码给程序，另外生成一句动作导向的话：

| 内部情形 | 模型看到的措辞 | 模型该做什么 |
|---|---|---|
| 参数校验失败 | "字段 `due_date` 需要 ISO 日期（如 2026-11-30），你给的是 `下周五`" | 改参数重试一次 |
| 权限不足 | "当前账号没有该客户账单的读取权限，需要用户授权或换账号" | 停止重试，向用户说明 |
| 版本冲突 | "记录在你读取后被改过，先取回最新版本" | 先读后写 |
| 限流 | "该接口每分钟有调用上限，建议 30 秒后重试或改用批量接口" | 等待或换接口 |
| 依赖不可用 | "下游服务暂时不可用，已重试两次仍失败" | 换方案或转人工，不要死磕 |
| 未知结果（超时后状态不明） | "请求已发出但未拿到确认，请先查询该资源当前状态再决定" | 先查后动，禁止直接重放 |

> 判断：`retryable=false` 却让模型"再试一次"是最常见的契约错误——它把一次确定性失败变成了三次无意义调用，还可能在非幂等接口上造成重复副作用。

## 部分成功与批量

批量操作不要只返回一个成功/失败位，那会逼模型整批重放。正确形状是逐项结果加汇总：

- `status: "partial"`，`data.items[]` 每项带自己的 `status` 与错误对象。
- 顶层给出 `succeeded`、`failed`、`skipped` 三个计数。
- 明确"失败项是否已回滚"：要么全回滚（事务），要么逐项独立（已成功的保留），二者选一并写进契约。
- 提供只重试失败项的入口（按 id 列表），而不是让模型重放整批。

## 幂等重放的返回

带幂等键的写操作，重复调用有两种合法返回：

- **原结果重放**：同键同参，返回首次的结果，附 `meta.replayed: true`。Agent 看到这个标记就知道"上次其实成功了"，不该再改参数重试。
- **冲突**：同键不同参，返回 `conflict` 并说明"该幂等键已用于另一次请求"。这是调用方的 bug，不要静默接受新参数。

不带幂等键的写操作，超时后必须返回 `unknown` 状态并提示先查询，不允许返回"失败"——"失败"会诱导重试，而真实结果可能是已成功。

## 大结果怎么交

三种做法各有适用面，选一种写进契约，不要混用：

| 做法 | 适用 | 代价 |
|---|---|---|
| 游标分页 | 列表类、可稳定排序 | 模型要多次调用，需在 `next` 里给游标与剩余量 |
| 摘要 + 指针 | 单条记录过大（长文档、整表） | 模型看不到细节，需要另一次取数 |
| 截断并显式声明 | 兜底手段 | 必须写清"已截断、共多少、怎么取全"，否则模型当成完整数据 |

截断是最容易出错的一种：静默截断会让模型基于半份数据下结论。无论哪种做法，返回里都要有"完整性"字段（`complete: true/false`），程序据此判断是否需要再取。

## 契约演进

工具契约会随业务变，变更方式决定 Agent 会不会突然失灵：

- 新增字段一律可选，带默认值；不要新增必填。
- 枚举扩展要保守：模型可能把新值当未知值处理，扩展前确认下游能接受。
- 字段语义不能改（同名字段从"含税"改成"不含税"是最隐蔽的事故），要改就换新名字。
- 弃用分两步：先标记并在描述里写明替代方式，观察调用量归零后再删。
- 版本号进 `meta`，让评估与排障能对齐"这次跑的是哪版契约"。

## 反模式

- **把异常栈直接返回**：泄露内部路径，模型也无法利用。
- **`null` 当错误**：空结果是合法业务状态，出错必须走 `status: "error"`。
- **错误文案里带下一步的模糊建议**："请检查输入后重试"——检查什么、怎么改，都没说。
- **成功也返回 `error: null` 字段**：让模型误以为有错误分支要处理，增加误判。
- **人话与错误码各说一套**：文案说"稍后再试"，码是 `invalid_argument`，模型必然走错。

## 落地清单

1. 给每个工具定一个信封模板（四槽 + 错误六字段），先在注册表里写死，再写实现。
2. 把后端错误码整理成一张映射表：内部码 → 契约码 → 模型措辞 → 建议动作。映射表进代码，不进提示词。
3. 每个写工具检查三件事：幂等键、冲突返回、超时后的 `unknown` 语义。
4. 每个列表工具检查 `meta.total` 与 `next.cursor` 是否都给，且分页稳定（排序键唯一）。
5. 批量工具补逐项状态与"只重试失败项"入口。
6. 拿五条真实错误样本做模型侧验证：只给模型 `message` 与 `next_action`，看它下一步是否按预期行动；不按预期就改措辞，不要改提示词去迁就。
7. 在评估里加一项"错误恢复率"：注入可恢复错误后，Agent 在有限步内恢复的比例。

## 一句话主线

结果契约的价值不在"结构好看"，而在**让模型不需要猜**：成功时知道拿全了没有，失败时知道能不能重试、该改什么、该找谁——把这三件事写进返回体，纠错就从提示词工程变成了接口设计。
