# 工具检索与动态暴露

工具超过二三十个之后，问题会从"能不能调对"变成三件事：**schema 占满上下文**、**相似工具互相干扰**、**模型看不见的工具等于不存在**。这不是提示词能解决的，需要在架构上决定"这一轮让模型看到哪些工具"。

## 什么时候该管工具数量

先给几个触发信号，命中两个以上就该治理：

- 工具总数超过 20 个，或全部 schema 序列化后超过上下文窗口的 10%；
- 有一组名字相近、描述相近的工具（多个"搜索"、多个"读取"）；
- 工具选错率随工具数上升而上升（加工具反而让老任务变差）；
- 每轮都要发全量工具定义，缓存前缀无法稳定。

## 四种暴露策略

**1. 分层命名空间。** 按域分组（文件、检索、数据库、通信），名字带前缀（`db.query`、`fs.read`）。收益是模型可按前缀做粗筛，也便于按角色授权；代价是命名变长。

**2. 按阶段/角色限定工具集。** 规划阶段只给只读工具，执行阶段给写工具；子 Agent 只看到自己职责内的工具。这是效果最确定的一种——缩小选择空间比优化描述更有效。

**3. 按需检索（工具检索）。** 先把用户意图与工具描述做匹配（关键词 + 向量），只把命中的 5–10 个工具注入本轮上下文。适合工具库很大、单轮只用少数几个的场景。代价是多一次检索调用，且有误检风险——命不中时模型会"以为做不到"。

**4. 远端工具按需连接。** 通过 MCP 之类协议把工具挂在远端服务，按需连接、按需拉取清单，而不是启动时全部加载。收益是上下文与启动开销都降；代价是连接失败要能降级（返回"该能力暂不可用"而不是空工具列表）。

## 工具描述本身就是检索文本

无论用哪种策略，描述质量决定检索与选择的上限：

- **一句话说清"什么时候用它"**，而不是只写"它做什么"。模型选错多半是边界没写清。
- 写**反例边界**：不该在什么情况下用（"不要用它读本地文件"）。
- 参数描述里给**格式样例**，比形容词有效。
- 同族工具的描述要能区分：把差异点写在第一句。

## 动态暴露的代价

- **不可复现**：同一任务两次跑，工具集可能不同，轨迹无法直接对比。对策是记录本轮暴露的工具集版本，评估时固定。
- **缓存失效**：工具列表变化会打断提示缓存前缀。把稳定工具放前面、动态工具放尾部，或给动态部分单独做缓存块。
- **可见性即权限**：隐藏工具既是减负也是授权手段，但**不能只靠隐藏做权限**——模型可能通过其他工具间接达成同样动作，权限必须在执行侧再校验一次。
- **发现成本转移**：按需检索把成本从"每轮发全量"转到"每次检索"，工具库越大越划算，库小反而亏。

## 常见失败模式

- 隐藏了工具却没告诉模型"能力存在但需申请"，模型直接回答"我做不到"。
- 检索只按名字匹配，描述里的同义词搜不到。
- 工具集按会话动态变化，但轨迹没记录，线上问题无法复现。
- 权限靠"不给看"实现，执行侧没有二次校验。
- 工具数量爆炸后继续靠加描述、加示例硬扛，成本与错误率一起上升。
- 检索结果不稳定：同一意图两次召回不同工具集，行为漂移。

## 什么时候不用治理

工具在 10 个以内、单轮只用其中少数、schema 开销可忽略时，全量暴露最省事——动态暴露会增加一次调用与一类新故障。治理的收益随工具数增长，不必提前上。
