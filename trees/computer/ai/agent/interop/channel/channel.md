# Agent 渠道接入

Agent 的能力不只在模型循环里——它还要能被人从微信、QQ、Slack、CLI、Web UI 这些**渠道**触达。渠道接入是把外部消息系统桥接到 Agent 会话的一层，决定身份怎么来、会话怎么切、上下文怎么注入、限流与合规谁负责。

## 为什么单独成一个知识点

渠道选择和模型、工具、记忆是正交的：同一个 Agent 循环可以挂多个渠道，但不同渠道的**会话边界、身份语义、富媒体能力、合规风险**完全不同。把这些差异塞进 Agent 构建流程里会互相污染；独立出来才能单独选型、单独评估。

## 通用架构

```
用户 → 客户端 / 协议端或官方 API → 渠道适配层（插件或网关）→ Agent 会话 → 工具 / 记忆 / 技能
```

渠道适配层的职责：

- **入站**：把平台消息转成 Agent 能读的上下文，处理图片、语音（STT）、文件、引用与转发。
- **出站**：把 Agent 的回复转成平台消息，处理 Markdown 剥离、分句、图片/语音（TTS）、富卡片。
- **会话映射**：把账号、房间、会话 ID 映射成 Agent 的 session；私聊与群聊通常各自独立。
- **身份与准入**：白名单、拥有者判定、@ 提及或昵称触发、概率触发；非目标消息不进队列。
- **节奏与限流**：按房间串行、随机延迟、长度上限、每小时次数上限，避免轰炸和封号。
- **管理面**：人格 prompt、监听列表、用量统计、开关与试运行模式。

## 三类接入方式

| 方式 | 例子 | 优点 | 代价 |
|---|---|---|---|
| 官方 Bot API | 平台官方机器人接口 | 合规、稳定、能力有官方保障 | 受平台权限与审核限制，富媒体能力可能不足 |
| 协议端网关 | OneBot 11 + NapCat / Lagrange 等 | 能力接近真人客户端，图片语音文件齐全 | 非官方协议，账号风控与封号风险，需自担合规 |
| 自建前端 | Web UI、CLI、桌面应用 | 完全可控，无第三方协议风险 | 要自己做人机交互、鉴权与部署 |

## 与相邻知识点的关系

- **记忆**：按房间/账号隔离记忆，是跨渠道共享还是各自一份。
- **技能**：按房间决定技能可见范围。
- **工具 / MCP**：渠道注册的工具与 MCP 工具都进同一个工具面，但权限边界不同。
- **多智能体**：一个渠道房间可以对应一个 Agent 会话。

## 会话边界怎么定

渠道决定会话，而不是反过来。四种边界要提前定：

| 场景 | 边界 | 关键问题 |
|---|---|---|
| 私聊 | 一个用户一个会话 | 是否与群内发言共享记忆 |
| 群聊 | 一个群一个会话 | 是「群作为整体」还是「每人一条线」 |
| 话题 / 线程 | 一个话题串一个会话 | 跨话题是否继承上下文 |
| 多 Bot 同群 | 每个 Bot 独立 | 消息归属与互相打断 |

最常见的错误是把「群」当成一个人：群里十个人说话，Agent 把他们的偏好混成一份画像，于是给 A 的答复带着 B 的约束。

> 判断：会话边界应按「谁在跟 Agent 对话」定义，而不是按「消息从哪个房间来」定义。

## 身份映射

三层映射，缺一层就会在某个渠道上错乱：

1. **平台身份**：open_id / union_id / QQ 号 / Slack user id。
2. **应用身份**：用户在你的系统里的账号 id。
3. **权限身份**：租户、角色、可见范围。

三条纪律：显示名不能当主键（会改、会重名、可伪造）；平台身份要区分「同一用户在私聊与群聊」；跨渠道合并用户必须由用户显式绑定，不能靠昵称猜测。

## 入站归一化

| 消息类型 | 处理方式 | 失败时的降级 |
|---|---|---|
| 纯文本 | 直接进上下文 | — |
| 图片 | 存为引用 + 可选 OCR/描述 | 无视觉能力时告知用户 |
| 语音 | STT 转文本，保留时长与说话人 | 转写失败要求重发文字 |
| 文件 | 存引用，按需读取 | 超大文件只给摘要 |
| 引用 / 转发 | 展开被引内容，标注来源 | 无权限读取时标注「不可见」 |
| 表情 / 贴纸 | 丢弃或映射成语义标签 | 不要当文本解析 |
| 系统消息（入群、撤回） | 单独事件通道，不进对话 | 与用户消息分开处理 |

## 出站与分条

平台差异主要在长度、Markdown 支持与富媒体。三条通用做法：

- **按平台能力降级**：有卡片用卡片，没有就退回文本 + 链接。
- **主动分条**：超过平台上限按语义分（段落、列表项），不要硬截断。
- **保留可回溯标识**：回复里引用原消息 id，用户能看到「在回哪一句」。

## 限流与幂等

- 平台侧配额（按房间、按应用、按秒/分钟）必须先查清，再定发送节奏。
- **按房间串行**：同一个群的消息按顺序处理，避免 Agent 的回复互相覆盖。
- **按消息 id 幂等**：平台会重投，重复消息不能触发两次工具调用。
- 发送失败要退避重试；连续失败要熔断并在管理面报警，而不是无限重试到封号。

## 乱序与重投

渠道事件几乎不保证顺序。两条防线：

1. 每条入站消息带平台时间戳与单调序号，处理前先判「是否已处理」。
2. 回复与请求用消息 id 关联，不要假设「最后一条回复对应最后一条请求」。

## 合规与数据

- 留存：聊天记录与附件的保存期限要写清楚，并提供删除路径。
- 群管理授权：进群前要拿到管理员同意，退群要停止服务并清理会话。
- 敏感内容：图片、语音里的个人信息要按渠道策略脱敏。
- 未成年人场景：默认关闭或加限制，不要靠「用户自称成年」判断。

## 常见失败

| 失败 | 症状 | 修法 |
|---|---|---|
| 群当一人 | 偏好互相污染 | 按发言人分线 |
| 昵称当主键 | 改昵称后记忆断裂 | 用平台稳定 id |
| 重投触发两次工具 | 重复下单、重复发信 | 消息 id 幂等 |
| 硬截断长回复 | 句子断在半截 | 按语义分条 |
| 无限重试 | 账号被限流或封禁 | 退避 + 熔断 |
| 忽略系统消息 | 把入群提示当用户发言 | 独立事件通道 |

## 一句话主线

**渠道接入是「消息系统 → Agent 会话」的适配层：先选合规的接入方式，再定会话边界、身份准入与富媒体策略；模型循环本身不必改。**
