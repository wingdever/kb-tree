# 群聊知识沉淀

社区群聊里每天有大量答疑，但这些答疑默认是**消耗品**：回答完就沉底，下一个人再问一遍，答案随回答者的记忆和在线时间波动。沉淀的目标不是把聊天记录存下来，而是把"已经被验证过的结论"变成可检索、可引用、可更新的条目。下面讲一条从消息到知识的流水线，以及群聊这种载体带来的特殊约束。

## 沉淀的对象是结论，不是消息

一条消息进不了知识库，它缺上下文、缺适用条件，也可能是错的、过时的、半截的。能沉淀的最小单元是**一条结论**，具备四个要素：

- **问题**：用后来者会怎么问的措辞写，而不是当时那句口语。
- **答案**：被回答者确认过的口径，最好附操作步骤或判断依据。
- **适用条件**：什么版本、什么角色、什么情况下成立；不写条件，条目会在半年后误导人。
- **出处**：原始消息或讨论串的定位，能点回去看上下文。

## 什么样的消息值得沉淀

按信号筛，不按消息量筛。四类信号最值得抓：

| 信号 | 说明 | 容易漏掉的原因 |
|---|---|---|
| 重复提问 | 同一问题在一个时间窗里被不同人问多次 | 每次都被"随手答了"，没人觉得需要记 |
| 明确结论 | 有人给出带条件的定论、版本号、操作步骤 | 夹在闲聊里，没有标记 |
| 可复用流程 | 一段需要多步操作、且步骤稳定的做法 | 答得越详细越容易被认为是"一次性帮忙" |
| 资源与链接 | 官方文档、工具地址、模板文件 | 链接过期后无人维护 |

反面清单同样重要：情绪宣泄、一次性排障、涉及个人隐私的对话、未经验证的猜测、会被版本更新立即推翻的信息——这些进库只会增加检索噪声。

## 从消息到条目的五步

1. **分话题**。一段群聊往往同时跑三四个话题，先按"问题—回答"配对切开，再逐条处理。多人交替插话的段落要按引用关系还原，而不是按时间顺序硬切。
2. **配对问答**。锁定"谁问了什么、谁给出了有效回答"。同一问题有多人回答时，取信息最完整、且被提问者确认的那条；其余作为补充或反例保留。
3. **去重合并**。同一问题被答过多次，合并成一条，保留最新且最完整的口径；旧口径若仍有适用场景（如老版本），作为附注而不是并列条目。
4. **审核定稿**。自动生成只是候选，进库前要有人确认三件事：结论是否正确、条件是否写全、是否与现行口径冲突。
5. **入库带出处**。条目写清来源讨论串、时间、回答者角色；出处不是装饰，它是后续核对与更新的唯一起点。

## 群聊特有的三个难点

- **上下文缺失**。群里一句"照上次那样配就行"在记录里完全不可解。处理办法是要求条目自足：把"上次"展开成具体路径与参数，做不到就不入库。
- **多人接力回答**。答案可能由三个人拼成，任何单条消息都不完整。合并时要标注每一段的贡献，避免把 A 的结论和 B 的例外混成一句自相矛盾的话。
- **口头口径漂移**。同一件事在不同时间有不同说法，往往因为版本变化或回答者理解不同。发现冲突时不要二选一，而是拆成"旧版本做法 / 当前版本做法"，各带时间。

## 条目字段

一条知识建议固定这些字段，缺项就是待补而不是可发布：

| 字段 | 作用 |
|---|---|
| 问题 | 检索入口，用后来者的问法 |
| 结论 | 一句话可执行的口径 |
| 步骤/依据 | 需要多步时给出顺序；判断类给依据 |
| 适用条件 | 版本、角色、平台限制、前置状态 |
| 出处 | 讨论串定位与时间 |
| 维护人 | 谁负责在口径变化时更新 |
| 被问次数 | 排序与优先级信号，不公开引用次数本身 |

## 机器人怎么用这些条目

- **命中即引用**，并附出处：回答里带上"依据某日讨论"的定位，用户能自己核对。
- **未命中要承认**，并转人工或记录缺口：把"没查到"当成知识缺口的信号，而不是让模型自由发挥。
- **回答口径与库内一致**：模型改写可以，但不能改变条件、版本与结论方向。
- **缺口回流**：每次转人工的问题进候选池，按上面的信号重新筛选，形成闭环。

## 时效与失效

- 每条带**生效时间**；版本类知识在版本变更时主动复核，不靠读者发现。
- 结论被推翻时**保留历史并标注失效**，直接删除会让引用过它的回答失去依据。
- 消息被撤回、讨论被删除时，对应条目的出处失效，条目要降级为"待复核"。
- 定期清理：半年无人引用且条件已变的条目，合并或归档，避免库里堆着互相矛盾的旧结论。

## 平台约束

QQ 官方机器人的群聊能力有几条硬约束，直接决定沉淀流程怎么排：

- 群消息事件分"仅 @"与"全量接收"两种，全量接收要群主开启；没有全量权限时，未被 @ 的讨论根本收不到，沉淀只能覆盖被召唤的片段。
- 被动回复要带消息 id，群聊有效期 60 分钟、每条消息最多回复 5 次（机器人是群主或管理员时为 50 次）。超过窗口就不能再挂回原消息，长流程的追问要另起消息。
- 主动消息受频控约束：机器人维度与单群维度都有每分钟上限，且有每群每日条数上限；把"每日精华"做成主动推送要按额度排。
- 同一消息可能重复推送，必须按消息 id 去重，否则同一条讨论会被沉淀两次。
- 已发送消息超过两分钟不可撤回；机器人为管理员时可撤回成员消息，这条能力可用于清理误发内容，但不能替代审核。

## 失败模式

| 现象 | 原因 | 后果 |
|---|---|---|
| 库里条目很多，没人查 | 问题用的是当时的口语，不是后来者的问法 | 检索命中率低，等于没沉淀 |
| 同一问题有五个版本答案 | 只做采集不做合并 | 回答自相矛盾，用户失去信任 |
| 半年前的结论仍在生效 | 没有生效时间与复核 | 按旧版本操作导致故障 |
| 条目里出现成员隐私 | 采集时未脱敏 | 合规风险，且难以追溯删除 |
| 机器人答得头头是道但出错 | 未命中时自由发挥，而不是承认缺口 | 错误被当成知识再次沉淀 |

## 落地清单

1. 先定**候选信号**与排除清单，写进采集规则；不要先做"全量总结"。
2. 建一个只有"待审"和"已发布"两态的队列，自动生成一律进待审。
3. 给条目定字段模板，缺"适用条件"或"出处"的不能发布。
4. 每周固定一次合并与去重，把重复问答压成一条。
5. 给每条指派维护人；没有维护人的条目只算草稿。
6. 机器人回答强制带出处；未命中时输出"没查到 + 已记录"，并写入缺口表。
7. 每月看三个数：命中率、缺口新增数、失效条目数；三个都不动说明流程没跑起来。
8. 版本类知识绑定版本号，发版时触发复核任务。

## 一句话主线

群聊沉淀的难点不在采集，而在**把口语、半截、多人拼凑的对话压成一条带条件、带出处、能被后来者直接用的结论**；做不到这三点，存下来的只是聊天记录。
