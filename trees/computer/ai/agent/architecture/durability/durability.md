# 持久执行与恢复

Agent 的活儿经常比一次 HTTP 请求长：等文件解析、等人工审批、等第三方回调，中间还会崩。持久执行要解决的就是这件事——**进程可以死，任务不能丢**；恢复时既不能把已完成的外部副作用再做一遍，也不能把模型调用从头重跑一遍。

## 为什么不能"失败就从第一步重来"

重跑的成本不是线性的，有三个硬约束：

- **模型调用不可廉价重放**。同一提示两次调用的输出可能不同，轨迹分叉后再重跑，前面攒下的证据、工具结果、用户确认全部作废。
- **外部副作用不可重复**。下单、转账、发邮件、改库，重放一次就是两笔订单、两封邮件。
- **等待时间比计算贵**。人工审批可能要几小时，重跑意味着重新等一遍。

于是正确的模型不是"重试整个任务"，而是"从最后一个安全点继续"，并且要求副作用可去重。

## 三个核心机制

### 1. 步骤即状态，每步落检查点

把 Agent 循环拆成可寻址的步骤（图节点、活动、状态机迁移），每步结束时把**输入、输出、以及副作用结果**写进检查点。恢复读最后一条检查点，而不是读聊天记录。

- 粒度是权衡：每次模型调用后落盘最安全，写放大最贵；每 N 步或每类关键节点落盘便宜，但要接受重放若干步。
- 状态必须可序列化：别把数据库连接、文件句柄、闭包、客户端对象塞进去。它们的重建应由步骤自己完成。
- 检查点要带版本：prompt 版本、工具 schema 版本、模型名，一起记录。否则旧 run 用新规则恢复，行为会漂移。

### 2. 幂等键绑定外部调用

恢复的难点不在状态，在副作用。做法是给每个副作用一个稳定的键（`run_id` + `step_id`，或业务单号），调用下游时带上：

- 支付、下单、工单创建这类有单号的系统，天然可按业务键去重；
- 发消息、写文件这类无单号系统，需要本地记录"做过"的标记，或让下游按 `Idempotency-Key` 头去重；
- 无法幂等的操作（如"给客户打电话"）只能靠检查点里的完成标记 + 人工确认兜底。

一句话判据：**恢复路径上每个动作，都要能回答"再做一次会怎样"**。答不上来就不该放进可恢复任务里。

### 3. 暂停点是一等公民

人工审批、外部回调、定时等待，必须是引擎级的暂停，而不是"循环里 sleep 等"：

- 暂停时释放执行资源，恢复时用外部输入（审批结果、回调数据）接着跑；
- 等待期间任务状态要可查（等待中/已超时），否则运维看不到卡在哪；
- 超时是正常分支，不是异常：审批过期要有默认路径（放弃、降级、转人工）。

## 三种实现形态与语义差别

| 形态 | 恢复语义 | 代价 |
|---|---|---|
| 图执行引擎（检查点 + 会话 id） | 从最后检查点快照恢复，状态是一份序列化数据 | 状态要可序列化；图结构变更需兼容旧检查点 |
| 工作流引擎（确定性重放 + 活动） | 重放代码路径，跳过已完成的活动，活动需幂等 | 工作流代码必须确定（不能读随机数、当前时间做分支） |
| 队列 + 自己写状态机 | 完全自定义，最灵活 | 幂等、超时、并发、暂停全部自己实现，最易出错 |

选型看两点：状态里有没有大量非结构化上下文（有则快照型更顺手）、团队是否已有工作流基础设施（有则别自己造）。

## 常见失败模式

- **检查点不可反序列化**：线上跑一个月，恢复时才发现状态里塞了不可序列化对象。
- **副作用没幂等**：恢复把"已完成"的步骤又执行一次，产生重复订单。
- **状态漂移**：恢复时外部世界已经变了（价格、库存、权限），旧上下文却还在按旧事实推理。对策是恢复后对关键外部事实做一次重新校验。
- **长等待占资源**：把等待写成阻塞循环，几十个任务就把并发槽占满。
- **恢复风暴**：一次故障后大量 run 同时恢复，打爆下游限流。恢复要带抖动与并发上限。
- **版本混跑**：新旧 prompt/工具同时在跑，评估结果无法归因。

## 什么时候需要

需要：任务跨多次请求、有外部副作用、含人工审批或长时间等待、失败重来的成本高于一次快照存储。

不需要：单轮问答、纯只读检索、可随时整体重跑且没有副作用的一次性脚本。这类场景加重试与超时即可，上持久执行是过度设计。
