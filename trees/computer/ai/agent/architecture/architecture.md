# Agent 架构与编排

这一组回答「Agent 内部怎么组织」：谁决定下一步、状态放在哪里、失败怎么恢复、多个 Agent 怎么分工。真实系统里，少数几种循环与编排形态就覆盖了绝大多数需求——难点不在发明新架构，而在**按失败代价选形态**。

## 四个决策点，按顺序问

1. **循环长什么样**。任务一步能完成就不必上循环；需要在观察中调整 → 交错推理与行动；步骤可预判 → 先规划再执行；答案不确定、需要比较多条路径 → 树搜索。
2. **控制流要不要显式化**。把「下一步做什么」完全交给模型最灵活，但不可回放、不可审批、崩了只能重跑；一旦涉及不可逆动作或长任务，就该把关键控制流画成图，让状态与检查点落在代码里。
3. **单 Agent 够不够**。默认是单 Agent + 工具。拆成多 Agent 的主要正当理由是上下文隔离、权限隔离与并行度，不是「能力不够」——后者通常靠加工具与改提示解决。
4. **横切关注点挂在哪**。审计、限流、脱敏、人工审批这类逻辑应放在生命周期钩子或中间件里统一拦截，而不是写进提示让模型自觉遵守；写进提示等于把控制权交给模型。

## 一条反直觉的判断

模式不是从简到繁的升级路线，而是按**失败代价**分叉：

- 失败可回滚、可重试 → 让模型自主，省掉脚手架。
- 失败不可逆（写库、转账、删文件、对外发消息）→ 先把控制流显式化，再谈自主性。

这解释了为什么同一套模式在 demo 里「太重」、在生产里「刚好」——差别不在任务复杂度，而在一次错误的代价。

## 三种常见误判

- **把多 Agent 当默认**。多数「多 Agent 更好」的结论来自任务本身可并行，而不是协作机制有效；串行化的多 Agent 往往只是把一次调用拆成多次，成本翻倍、质量不变。
- **图式编排用得太早或太晚**。太早，灵活性被不必要的节点锁死；太晚，崩溃恢复与人工审批没有地方挂，只能在外层包一层脆弱的重试。
- **钩子里做业务判断**。模型看不到钩子的决策，行为会与提示描述不一致，排查时极难定位。

## 决策顺序

先按任务结构与失败代价选循环形态（一步可完成、边看边改、步骤可预判、答案不唯一），再判断单 Agent 是否足够；只有上下文、权限或并行度确有隔离需求时才拆多 Agent。涉及不可逆动作或长任务时，先把关键控制流显式化。编码、浏览器与桌面类任务的决定点在行动面：动作接口与权限边界，而不是推理模式。

## 一句话主线

用少数几种循环与编排模式搭起推理骨架，单 Agent 不够时再按协作模式扩成多 Agent，关键控制流交给状态图，横切关注点用 hooks 拦截；形态的选择依据是失败代价，不是任务大小。
