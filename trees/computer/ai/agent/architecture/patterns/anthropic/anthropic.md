# Anthropic 的 5 + 1 工作流模式

Anthropic 的《Building Effective Agents》命名了六个模式，已成为全行业通用词汇。前五个是 **Workflow**（控制流由你编写），第六个才是真正的 **Agent**（控制权交给模型）。按顺序阅读：每一个都增加自主性，也随之增加成本与测试负担。

## P01 Prompt Chaining（提示链）

把任务拆成固定步骤，每步输出喂给下一步；可在步骤间插入程序化检查（gate），输出不合规即停下。

- **何时用**：能干净地拆成阶段的任务——先列大纲、再核对、再扩写成文；先解析、再校验、再转换。
- **取舍**：用延迟换准确率。每次模型调用做的事更简单，更可能做对。
- **成本**：五个模式中最便宜（前提是链深度受限）。很多团队永远不需要离开这个模式。

## P02 Routing（路由）

先对输入分类，再分派到专门的处理路径。分类器可以是 LLM，也可以是确定性规则。

- **何时用**：不同输入类别的成本或质量要求差异明显——FAQ 用便宜模型、复杂查询用推理模型、边界情况转人工。
- **收益**：关注点分离。调整退款路径不会破坏技术支持路径，因为它们不共享提示词。
- **风险**：分类器本身成为单点故障，值得单独评估。每次输入增加一次分类调用。

## P03 Parallelization（并行化）

同时运行多个模型调用并聚合结果。两种变体：

- **分节（sectioning）**：把任务拆成独立子任务并行处理。
- **投票（voting）**：同一任务跑多次，取多样答案或多数决。

- **何时用**：子任务相互独立，或多视角/多次投票能提升置信度。一个实用做法是护栏：一个调用回答用户，同时第二个调用做内容安全审查。
- **成本**：随 N 线性增长；延迟受最慢的那次调用限制，而非各次之和。复杂任务中，每个考量点用独立 LLM 调用通常更好——专注注意力于单一方面。

## P04 Orchestrator-Workers（编排器-执行器）

中央模型拆解任务、把子任务分派给 worker 模型，再合并结果。与并行化的区别：**子任务不是预先固定的**，由编排器根据输入动态决定。

- **何时用**：复杂任务，子任务在输入到达前无法确定。Anthropic 的例子是涉及多个文件的代码改动。
- **成本**：五个模式中最贵。planner 可能过度拆解，值得给 worker 数量和单任务预算设上限。
- **生态**：多数多智能体框架围绕它构建。

## P05 Evaluator-Optimizer（评估器-优化器）

两个角色组成循环：一个模型生成候选，另一个评审并给反馈，生成者修订，直到评审通过或达到预算。

- **何时用**：质量比延迟更重要；评审方有清晰的验收标准；任务适合迭代改进。Anthropic 的例子是文学翻译。
- **两个适配信号**：人类能说清反馈时 LLM 输出可明显改善；LLM 本身能给出这类反馈。
- **成本**：可变，主要由迭代次数决定，务必封顶。评审那一半就是 LLM-as-judge。

## P06 Autonomous Agent（自主智能体）

第六个模式是完整 Agent：模型在循环中独立运行，用环境反馈决定下一步。

- **何时用**：开放式问题，无法预测步数。Anthropic 的例子是解决 GitHub issue——读代码、改代码、跑测试、再试。
- **执行流程**：从人类指令/对话开始 → 任务明确后独立规划执行 → 每步从环境获取"接地真相"（工具结果、代码执行）→ 检查点或受阻时暂停等人 → 完成或触发停止条件（如最大迭代数）时终止。
- **代价**：成本与风险的顶点。实现往往很简单——"只是 LLM 在循环中根据环境反馈用工具"，但正因如此工具集与文档必须精心设计与测试。

## 模式可组合

这些模式既能组合也能叠加（每个都会引入前一个没有的失败模式）：路由步骤可以把难题送进编排器-执行器系统，每个 worker 又可以是末尾带评估器的提示链，并行化可以嵌在任意模式内部。**架构就是组合**。多数生产系统组合两到三个模式。

关键原则：从最简单能解决问题的模式起步，仅在有证据表明改善结果时才加复杂度。

## 三个典型组合

模式名是零件，不是架构。看三个真实组合，能更快理解"组合"的含义：

| 场景 | 组合 | 为什么这样拼 |
|---|---|---|
| 客服分流 | 路由 → 各路径内部提示链 → 高风险动作前并行跑一个安全审查 | 分类决定路径，链保证每步可校验，护栏不占用主回答的那次调用 |
| 多来源调研 | 并行扇出（每个来源一个 worker）→ 汇总节点做冲突检测 → 评估器补一轮修订 | 来源彼此独立可并行，汇总与评估是质量瓶颈，单独成环节 |
| 代码修复 | 自主 Agent 主循环 → 每步观察后接验证器（跑测试） → 失败时回填结构化错误 | 验证是廉价的外部信号，用它约束自由度比限制步数更有效 |

## 常见误用

- **把 P06 当默认**：一上手就做"自主 Agent"，结果把可枚举的流程也交给模型随机决定。
- **模式堆叠当质量**：每个环节都加评估器与投票，成本翻几倍而质量不变——先证明瓶颈在哪。
- **丢掉 gate**：提示链的价值一半在步骤之间的程序化检查，只串提示不校验，等于把错误加速传递。
- **用模式名画架构图**：图上写"路由 + 编排器"，实际代码里是一个 200 行的 if/else 加一个大提示——模式名要对应可指认的代码结构。

## 一句话主线

这六个模式不是菜单，而是**自主性刻度**：从固定链到自主循环，每加一格都要用"有没有证据表明结果变好"来付账。
