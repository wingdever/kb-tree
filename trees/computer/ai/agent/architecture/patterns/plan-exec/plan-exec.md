# Plan-and-Execute：规划与执行分离

如果把"边想边做"看作微观管理，本模式就是授权：把规划器（Planner）与执行器（Executor）分离，前者决定做什么，后者负责做好。

## 结构

- **规划器**：能力强的前沿模型读取用户宏观目标，生成一个由子任务组成的有向无环图（DAG）。
- **执行器**：更小、更快、更便宜的模型领取子任务，用特定工具执行并返回结果。

示例：用户要求"研究竞品价格并写一份对比报告"。

- 规划器输出：`[任务1: 抓取竞品A], [任务2: 抓取竞品B], [任务3: 对比数据], [任务4: 写报告]`
- 执行器并行运行任务 1 和 2。

## 优势

- 更快：执行阶段可并行。
- 更稳：决策集中在一次规划里，执行阶段不再反复试探，不容易陷入死循环。
- 更省：把昂贵的规划集中在一次，执行用便宜模型。
- 适用：步骤有依赖、需要事先布局、执行路径可预测的任务。

## 局限

- 规划器一次性定好计划，**执行中看到意外数据不会调整**。
- 如果任务依赖观察结果逐步决定（每步都改变策略），不适合——此时应改用交错推理与行动，或让计划里保留可重规划的空位。
- 规划器失败没有重试逻辑时不可恢复。

## 与相邻形态的差别

同样是"先规划再执行"，差别在于**规划时看不看得到观察结果**：

| 形态 | 规划何时做 | 规划时能否看到执行结果 | 代价与收益 |
|---|---|---|---|
| 交错推理与行动 | 不做规划，边做边定 | 每步都看 | 上下文最贵、最易死循环，最适应意外 |
| 全盘规划后批量执行（本模式） | 一次，前置 | 看不到 | 规划集中一次，执行可并行、可用便宜模型 |
| 规划用占位符 | 一次，前置 | 看不到，执行结果回填占位符 | 比上一行更省 token，因为规划阶段不携带观察 |
| 多 Agent 层动态编排 | 运行时按输入定 | 编排者看得到 | 最灵活、最贵，子任务数量不可预算 |
| 分层分解 | 分层做 | 高层不看细节 | 轻量模型切高层、昂贵模型只做难步，按难度付费 |

> 判断：如果执行中"看到什么就该改主意"的概率很高，前置规划只会把错误固化；如果能事先列出大部分步骤，前置规划省下的 token 与稳定性远超它的僵化代价。

## 规划税（Planning Tax）

规划本身有成本，且存在任务复杂度阈值：低于阈值，规划是浪费；高于阈值，规划有帮助但收益递减。降低规划税的方向有四个：把规划压成一次前置调用（不在循环里反复规划）、复用相似任务的计划结构（计划缓存）、分层分解让便宜模型只做高层切分、限制推理 token 的思考预算。这些手段的收益随任务重复度上升，一次性任务上几乎为零。

## 计划怎么写才可执行

一份能执行、也能验收的计划，每一步要有四个要素：

| 要素 | 说明 | 缺失后果 |
|---|---|---|
| 动作 | 调哪个工具、传什么参数 | 执行器只能猜 |
| 输入 | 引用哪一步的产物 | 顺序错了才发现依赖 |
| 验收条件 | 怎样算这一步成功（可判定） | 无法判断该不该重试 |
| 失败处理 | 重试、降级还是中止 | 出错后原地打转 |

验收条件写成「看起来合理」等于没有。要写成可测的：文件存在、条数等于 N、金额与订单一致、schema 校验通过。

## 执行器不是转发器

执行器的三件事：执行前校验前置条件（输入齐不齐、依赖完成没有）、执行后核对验收条件、不符就标记失败并带着证据回到规划层。只把动作转发给工具的「执行器」，等于把计划变成建议。

## 重规划的触发与代价

四个触发点：验收失败、环境变化（工具不可用、数据变了）、新信息推翻假设、预算不足。

重规划最贵的不是再调一次模型，而是**要不要丢弃已完成的工作**。正确做法是保留已产出的产物，只重排剩余步骤；从头重跑会把副作用再做一遍。

## 与子 Agent 分派的关系

Plan-and-Execute 是单线的计划；把步骤分派给子 Agent 是并行化，多了一层合并契约：子 Agent 返回什么格式、失败如何汇总、产物如何拼接。没有合并契约就并行，最后会得到几份互相矛盾的中间结果。

## 常见失败

- 粒度过粗：一步里塞多个副作用，失败后无法判断哪部分生效。
- 计划没有依赖：并行执行时读到未完成的上游产物。
- 验收条件依赖模型自评：等于没有验收。
- 重规划无上限：每次失败都重排，成本超过直接转人工。
- 计划与提示强耦合：改一句提示就要重写整个计划模板。

## 一句话主线

Plan-and-Execute 用**一次前置规划**换执行阶段的并行、稳定与便宜；代价是计划一旦成型就看不见意外——所以它适合步骤能事先列出、每步可独立验收的任务。
