# 任务分解与依赖规划

多步任务失败，多数不是某一步做错，而是**一开始就拆错了**：子任务之间边界模糊、验收标准缺失、依赖关系被想当然地串成一条链。分解的质量决定了后面能不能并行、能不能验证、失败时能不能只重做一小块。

## 分解的单位是产物，不是动作

按"先查资料、再写代码、然后跑测试"这种动作序列拆，得到的是流程，不是可验收的工作。有效的子任务长这样：

- 有明确**输入**（从哪份数据、哪份上下文来）；
- 有明确**输出**（一个文件、一段结构化数据、一份结论，能指出位置）；
- 有**验收判据**（谁来判断做对了，依据是什么——测试通过、schema 校验、人工确认）。

判据缺失的子任务会退化成"看起来做完了"，最后由人兜底重做。经验规则：**写不出验收判据的子任务，说明还没拆到位**。

## 依赖是图，不是列表

子任务之间的关系有三类，混在一起就会把并行机会浪费掉：

- **数据依赖**：B 需要 A 的输出。真依赖，必须等。
- **资源依赖**：A、B 要改同一个文件、抢同一个配额、用同一个账号。不是逻辑依赖，但要串行或分区。
- **时间依赖**：只有先后顺序上的偏好（先写大纲再写正文），可以并行草拟后合并。

把这三类都画成 DAG，关键路径才是真正的最短耗时。常见错误是"伪依赖"——因为习惯性按步骤编号，把所有子任务串成链，明明可以并行的检索与素材整理被排成一列。

## 粒度：一次到数次工具调用

- 太细：每个子任务只做一次搜索，协调开销与上下文拼接成本超过执行本身，且中间产物碎到无法复用。
- 太粗：一个子任务覆盖半个项目，失败就要整体重来，也看不出错在哪。
- 合适的粒度：一个子任务的产出能独立被检查，且大致落在一次到数次工具调用的量级。

层级不要过深。三层以上（总目标 / 阶段 / 步骤 / 步骤内的动作）时，中间层往往只是在搬运上下文，没有增加判断，这时应该砍掉中间层，让子任务直接对齐可验收产物。

## 分解者与执行者

由规划者产出子任务、执行者各自完成，是常见结构；代价是规划者看不到执行现场。两个修正手段：

- **分解时读真实环境**：先探查文件结构、API 能力、数据规模，再拆。凭想象拆出来的计划，第一步就会撞上"这个接口不存在"。
- **让验收判据先落地**：先定测试或校验脚本，再分子任务，比先分任务再补验收更可靠。

## 重规划触发条件

计划一定会在执行中失效，关键是何时承认。给出可执行的触发条件，而不是"感觉不对就重来"：

- 同一子任务连续两次验收失败；
- 关键外部事实变化（库存、价格、权限、接口下线）；
- 预算消耗超过阈值而进度落后于关键路径；
- 出现计划里没有的新依赖（发现要改的文件被别的任务占用）。

重规划的范围要收窄：只重排受影响的子树，不要整棵树推倒重来，否则已完成的工作白费。

## 常见失败模式

- **无验收分解**：子任务只有动作描述，做完无法判断对错，靠人肉通读。
- **伪依赖串行化**：把可并行的工作排成队，交付时间翻倍。
- **隐藏依赖**：两个子任务都改同一个配置文件，并行后互相覆盖。
- **过深分层**：中间层只搬运上下文，判断力没有增加，反而每次都要重新讲一遍背景。
- **计划不可执行**：依赖不存在的能力、假设了错误的接口形态，第一步就卡住。
- **不重规划的执念**：明知路走不通仍按原计划推完，把预算烧在错方向上。

## 什么时候需要

需要：任务能拆成互不重叠、各自可验收的部分；子任务之间有明显的数据或资源边界；需要并行压缩交付时间。

不需要：任务强顺序耦合、每一步都依赖上一步的完整上下文（如逐段改写一篇长文）、总步数在两三步之内。这类任务直接线性执行，分解只会增加协调成本。
