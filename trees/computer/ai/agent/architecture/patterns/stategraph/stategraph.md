# 状态机与 DAG：别完全信任 LLM 自己管控制流

对于关键应用，2026 年企业级架构的标准做法是使用**显式状态图**（如 LangGraph）：把状态转移硬编码成图，定义节点（函数）和边（条件路由）。LLM 只决定走哪条边，**无法发明不存在的路径**。

## 核心思想

- 纯 Agent 循环（调用→调用→回灌）在进程崩溃时失效——对话与花掉的钱一起蒸发。
- 显式图把状态作为一等公民，每个 super-step 后存到检查点（checkpointer）。这一个改变免费换来：持久化执行、人在回路、时间旅行。
- 图把两类步骤混在同一张图里：边与手写节点由代码决定走向，Agent 节点由模型决定下一步动作——可控的部分与需要判断的部分各归其位。

## 人工审批节点

典型做法：如果 Agent 要先起草邮件再发送，就在"起草"和"发送"两个状态之间插入一个"人工审批节点"。图会在物理上暂停执行，等待 UI 的 webhook 响应后才继续。这是防止灾难性错误的方式——凡是写数据库、发邮件、转钱的动作都应先过审批节点。

## 关键机制

- **Reducer**：声明新值如何与旧值合并（如 `add_messages` 追加而非覆盖消息）——对话记忆的关键。忘记给列表状态加 reducer 是常见错误。
- **检查点（Checkpoint）**：每个 super-step 后序列化状态快照，以 `thread_id` 为键。崩溃后用同一 `thread_id` 再次 invoke 即从最后成功的节点恢复——没有特殊"恢复 API"。
- **条件边（Conditional edge）**：由状态函数决定走哪条边，可指回早期节点形成循环——这是 ReAct 循环在图里的实现方式。需设 `recursion_limit` 防止无限循环。
- **interrupt**：在节点内暂停、保存检查点、交还控制权；人工输入后用 `Command(resume=...)` 从精确点恢复。等待可持续数分钟到数天，因为状态持久在磁盘。

## 何时用图

- 控制流需要循环（ReAct、重试、自我批评）。
- Agent 必须能崩溃后恢复。
- 想要一等公民的人工审批门。
- 需要流式输出中间状态给前端。
- 工作流有 5+ 步骤且带条件分支。

**何时不用**：单次 LLM 调用 + 单次工具调用（直接用 SDK）；纯线性无分支（普通函数更清晰）。

## 图之前：先定状态契约

图的价值来自「状态是一等公民」，所以状态 schema 比节点函数更重要。一个可用的状态只放**跨节点必须传递**的东西：

| 字段类 | 内容 | 不该放什么 |
|---|---|---|
| 目标与约束 | 原始任务、硬性限制、验收标准 | 模型的中间推理长文 |
| 计划与进度 | 待办、已完成、当前步骤 | 每个工具的完整原始返回 |
| 结果引用 | 产物路径、记录 id、摘要 | 大文件内容、base64 |
| 控制信息 | 重试计数、预算消耗、错误码 | 临时变量、调试打印 |
| 人工输入 | 审批结果、补充信息 | 用户全量历史 |

两条硬约束：状态必须**可序列化**（检查点要落盘），且必须**可裁剪**（大对象放外部存储，状态里只留引用）。把 10MB 的网页正文塞进状态，二十步就是 200MB 的快照，恢复一次要几十秒。

## 图设计：四类节点，职责不能混

| 节点类型 | 做什么 | 不能做什么 |
|---|---|---|
| 路由 / 判定 | 读状态、选下一条边 | 产生副作用 |
| 执行 | 调工具、改外部世界 | 自行决定去哪 |
| 校验 | 可判定的检查（schema、存在性、金额） | 依赖模型自评 |
| 人工 | interrupt 等人 | 顺手改业务数据 |

路由与执行分开，是为了让重放安全：路由可以随便重算，执行必须幂等。混在一起的节点在崩溃恢复时最容易重复扣款、重复发信。

## 终止条件要显式

- 每条循环路径都要有**出口边**（完成、放弃、转人工），不要靠「没有下一步」隐式结束。
- 循环必须带**单调进度指标**（已完成步骤数、剩余预算、剩余待办），否则「再试一次」会变成永远。
- `recursion_limit` 是保险丝，不是控制手段。触顶应当归为失败并保留最后状态，而不是静默截断。

## 恢复语义的三个坑

1. **节点内副作用可能已执行**。检查点记的是「进入节点前」的状态，崩溃点若在副作用之后、写状态之前，恢复会重跑整个节点。执行节点必须幂等，或用 effect log 记录「这一步已提交」。
2. **interrupt 之后的临时变量会丢**。只有写进状态的东西能活过暂停；节点内的局部变量在恢复时是空的。
3. **不要重算路由**。恢复应直接采用检查点里保存的下一节点；重新跑一遍条件判断，可能因为状态微小差异走到另一条边，产生「恢复后行为变了」。

## 常见失败

| 失败 | 症状 | 修法 |
|---|---|---|
| 忘加 reducer | 列表状态被后一次写入覆盖 | 列表字段声明追加语义 |
| 状态塞大对象 | 快照暴涨、恢复变慢 | 外置存储 + 引用 |
| 副作用放在路由节点 | 重放时重复执行 | 拆分节点 |
| 条件边无默认分支 | 异常状态无路可走 | 兜底边指向失败处理 |
| 在 super-step 边界提交外部事务 | 半提交状态 | 提交放在节点内并幂等 |
| 检查点无 TTL | 存储无限增长 | 按线程生命周期清理 |
| 把 recursion_limit 当重试预算 | 掩盖死循环 | 单独的重试计数与终止条件 |

## 边界：图约束路径，不约束判断

图能保证「不会走到不存在的路径」，但不能保证节点内的判断是对的。开放任务（路径无法事先枚举）硬套图会僵化，图真正适合的是**路径可枚举、但需要可靠性**的场景。

还有一层常被忽略：图和提示、模型一样是版本化对象。改一条边、换一个节点的默认分支，都是行为变更，应当和提示版本一起记录，否则线上出问题时无法回答「当时用的是哪版图」。
