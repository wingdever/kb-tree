# ReWOO：无观察推理（Reasoning WithOut Observation）

ReWOO 把规划集中在一次前置调用中完成：规划器生成带占位变量的完整 DAG， worker 执行工具并代入观察， solver 读一次最终轨迹产出答案。**规划器永不看工具输出**。

## 要解决的问题：ReAct 的规划税

在 ReAct 循环里，每次工具观察都会回灌到规划器提示，供下一轮推理——token 成本随步数近似**平方增长**，因为每轮都携带此前所有轮次的轨迹。八步任务里，规划器把自己的草稿和所有先前观察重读七次，而多数重读并不改变计划（结构本可事先知道）。

## 三个角色

1. **Planner（LLM 调用 1）**：输出完整计划 DAG，步骤用变量引用，如 `t1 = Search(x); t2 = Summarise(#t1)`。`#E1`、`#E2` 是尚未知道的工具结果占位符。
2. **Worker（无 LLM）**：按依赖顺序执行工具，把观察代入证据变量。
3. **Solver（LLM 调用 2）**：读取解析后的轨迹（任务 + 紧凑的证据列表），产出最终答案。

模型总共只调用约 **2 次**，且从不读原始观察。

## 效果数字

- 论文摘要的口径：在六个公开基准上报告 **5× token 效率**，HotpotQA 上约 **4% 准确率提升**。
- HotpotQA 的具体数字（论文表格）：ReWOO 约 1986 token、42.4% 准确率；ReAct 约 9795 token、40.8% 准确率。也就是说 token 用量约是对照的五分之一，准确率略高。
- 六步任务的演示计算：ReAct ~9300 token vs ReWOO ~2800 token，约 3.3×；节省随步数增长（ReAct 近似平方，ReWOO 近似平坦）。

## 禁忌与权衡

- **放弃适应性**：计划在任何结果看到之前就固定。如果第三个工具返回意外数据（歧义实体、错误、空结果），僵化的计划无法察觉与改道。
- 占位符替换需要**类型化变量约定**。
- 计划正确率必须高；中途重规划会抵消节省。
- 适合：结构由任务决定而非由前一步返回决定的任务、高吞吐量批处理和（如数千文档做相同多步处理）。
- 不适合：探索性任务（每个观察真正改变策略）——用 ReAct/Reflexion 或混合。

## 在模式图谱中的位置

- **特化 Plan-and-Execute**：用占位变量 DAG 把规划与观察彻底解耦，比一般 Plan-and-Execute 更省。
- **被 LLMCompiler 泛化**：把 ReWOO 的 plan-as-DAG 用任务分发器并行执行独立步骤，原论文报告延迟最多提速 3.7×、成本最多省 6.7×。

## 计划 DSL：三个必须写死的约定

ReWOO 省 token 的前提是计划能被机器执行，而计划是自然语言时，worker 只能靠猜。需要三个约定：

1. **变量声明与依赖**。占位符只能引用**前面**已声明的步骤，形成 DAG；依赖要显式写出，worker 才知道哪些步骤可并行。
2. **工具签名绑定**。计划里写工具名与参数模板，worker 执行前先校验参数能解析、类型对得上；解析失败直接判该步失败，不要交给模型「再想想」。
3. **类型标注**。每个占位符声明类型（`list[str]`、`int`、`url`）。不标类型，solver 拿到的是字符串拼接，数值与列表都会被压平。

一个最小计划大致长这样：

```
t1 = search("2026 年 Q3 财报 营收")          #E1: list[doc]
t2 = fetch_top(#E1, n=3)                      #E2: list[text]
t3 = extract(#E2, field="revenue")            #E3: list[number]
answer = compare(#E3)
```

## Worker 执行：并发与单步失败

- **无依赖步骤并行**，有依赖按拓扑序推进；并行度受工具限流约束，不受计划结构约束。
- 单步失败只有三种正当处理：重试（仅限幂等工具）、用空值降级并在证据里标注「缺失」、中止并转 ReAct。
- **不要让 worker 自行改计划**。一旦 worker 开始「看着结果调整下一步」，就退化成 ReAct，token 优势当场消失，还多了一层不可见的控制流。

## Solver 的输入要裁剪

Solver 只需要四样东西：任务、每步的工具名与参数、证据摘要（按步截断，例如每步 500 字符）、失败与缺失标记。原始 JSON 不要进 solver——它会把 token 省下来的部分又花回去。

证据互相冲突时，**把两个来源并列交给 solver**，而不是先合并成一句「综合来看」。合并会掩盖冲突，让最终答案看起来比实际更确定。

## 一个可算的判据：结构熵

用不用 ReWOO，本质是问「任务的结构在开始前是否基本确定」：

- 结构熵低（步骤序列与工具选择基本可预判，比如「查三份文档再对比」）→ ReWOO 收益最大。
- 结构熵高（每一步的结果决定下一步做什么，比如排障、开放式调研）→ ReAct 或混合。
- **同构批处理**收益最高：一次规划模板复用到上千个输入，规划成本被摊薄到接近零。

## 实现清单

1. 计划 schema 化（不是自由文本），带依赖与类型。
2. worker 校验参数可解析，失败即判该步失败。
3. 占位符求值有明确顺序，禁止前向引用。
4. 证据按步截断，保留失败标记。
5. 单步失败策略预先声明（重试 / 降级 / 中止）。
6. 记录「计划是否被中途改写」——被改写就说明该换模式了。
