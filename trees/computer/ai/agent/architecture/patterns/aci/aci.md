# 设计三原则与 ACI（Agent-Computer Interface）

Anthropic 提出的实现 Agent 的三条核心原则：保持简单、优先透明、设计健壮的 ACI。遵循这些原则，才能创建不仅强大、而且可靠、可维护、被用户信任的 Agent。

## 1. 保持简单（Simplicity）

从简单提示开始，让评估驱动优化；简单、可组合的模式胜过重量级框架。许多模式几行代码就能实现。**只有在能明确改善结果时才增加复杂度**。

## 2. 优先透明（Transparency）

显式暴露 Agent 的规划步骤；不透明的黑箱系统难以维护与调试。

## 3. 设计健壮的 ACI

把工具定义与规格当作提示工程来对待，投入与整体提示词同等的注意力。经验法则：**你在人机界面（HCI）上投入多少精力，就准备在 Agent-计算机接口（ACI）上投入同样多的精力**。

### 格式很关键

同一个动作可以用多种方式表达（文件改动用 diff 还是整文件重写；结构化输出用 markdown 还是 JSON）。对软件工程这些差异可能只是表面，但对 LLM 而言：写 diff 需要提前知道块头里改了多少行，写 JSON 里的代码需要对换行和引号做额外转义——**有些格式对 LLM 难写得多**。

### 格式建议

- 给模型足够的 token 在"把自己写进死胡同"之前先思考。
- 让格式尽量接近模型在互联网文本中自然见过的样子。
- 避免格式开销（精确统计上千行代码、对写出的代码做字符串转义）。

### 设身处地

看工具描述和参数，模型能否一目了然？若你需要仔细想想，模型多半也需要。好的工具定义包含：示例用法、边界情况、输入格式要求、与其他工具的清晰边界。把参数命名与描述当作给团队里初级开发者写一份优秀 docstring——尤其在有许多相似工具时。

### 测试与防错（poka-yoke）

- 用大量示例输入测试模型怎么用你的工具，看它犯什么错再迭代。
- 通过改参数让错误更难发生。Anthropic 在构建 SWE-bench Agent 时，打磨工具花的时间**超过**打磨整体提示词——例如模型在离开根目录后用相对路径会出错，他们把工具改成始终要求绝对路径，模型从此完美使用。

## 框架取舍（Anthropic 立场）

- 框架简化标准底层任务（调用 LLM、定义解析工具、串联调用），让你快速起步。
- 但会引入额外抽象层，遮蔽底层提示词与响应、让调试变难，也容易在简单方案够用时诱发不必要复杂度。
- 建议**开发者先直接用 LLM API**——许多模式几行代码就能实现。若用框架，务必理解底层代码；对底层机制的错误假设是常见错误来源。
- 进入生产时，不要犹豫减少抽象层、改用基础组件构建。

## 工具描述要写六段

一份能被模型正确使用的工具描述，包含六段，缺哪段都会在真实任务里以错误形式暴露：

1. **一句话用途**：这个工具做什么，不做什么。
2. **何时用 / 何时不用**：与相邻工具的边界（最容易混淆的部分）。
3. **参数**：类型、单位、取值范围、默认值、是否必填。
4. **返回结构**：字段含义、是否分页、失败时返回什么。
5. **错误语义**：哪些错误可以重试，哪些必须换参数。
6. **一个最小示例**：真实可用的调用样例，比形容词有效。

## 错误信息是写给模型看的

错误信息不是给人排障的堆栈，而是**下一步动作的指令**。一条好的错误包含三件事：哪里错了（字段与期望）、为什么错（约束）、怎么改（可执行建议）。

差的写法：`Error: invalid request`。
好的写法：`path 必须是绝对路径，收到 "src/app.ts"；请改为 "/repo/src/app.ts"`。

经验：把「模型会犯的错误」逐条写成可操作的提示，比在系统提示里加十句「请小心」更有效。Anthropic 在 SWE-bench Agent 上的做法就是如此——模型离开根目录后相对路径出错，于是把参数改成只接受绝对路径，错误直接消失。

## 返回结构：为下游省事

- 列表要带总数与游标，不要只给前 N 条让模型猜还有没有。
- 长文本给摘要 + 引用（路径/URL），不要整篇塞回上下文。
- 二进制与图片给路径或引用，不要 base64。
- 成功与失败用同一个外层结构（`ok`、`data`、`error`），模型不必按状态码分支。

## 命名与粒度

- 名字用「动词 + 对象」：`read_file`、`create_issue`，不要 `file_tool`。
- 一个工具一个动作。把「读、写、删」塞进一个工具，会让权限与幂等都无法表达。
- 参数命名与真实世界一致：`recipient` 而不是 `arg2`；枚举值给出全部取值，不要让模型自由发挥。
- 相似工具要显式划界，或在描述里写「如果你要做 X，用另一个工具」。

## 让模型少做格式体操

同一个动作有多种表达，选对模型最省力的那种：

- 改文件：小改用 diff/替换，大改用整文件写；不要强制模型数行号。
- 结构化数据：能给 schema 就别要求手写 JSON 字符串。
- 代码：不要要求在 JSON 字符串里转义换行与引号——把代码放独立字段或用文件传递。

判断标准很简单：**这个格式要求，是在帮模型表达，还是在考模型的格式记忆力**。

## 防错清单（poka-yoke）

逐条问，任一为是就要改设计：

- 默认值是否危险（默认删除、默认覆盖、默认对外发送）？
- 参数是否可能指向错误对象（相对路径、模糊名称、可猜测的 id）？
- 重复调用会不会产生第二次副作用？
- 参数校验在服务端做，还是指望模型自觉？
- 失败后模型能否从错误信息里知道下一步？
- 权限是否按工具而非按角色授予？

## 怎么测 ACI

1. 用真实任务回放，统计错误类型分布（参数错、选错工具、格式错、语义错）。
2. 单独测「工具选择」：给一组相邻工具，看模型是否选对。
3. 两个版本盲测同一批任务，只看成功率与错误类型，不看描述写得多漂亮。
4. 把每次失败转成一条可复现用例，改完再跑——否则同一个坑会踩很多次。
