# 树搜索：ToT / GoT / MCTS / LATS

当单条推理链不够——多个路径看似都合理、第一个看似合理的路径并非最佳、走进死胡同时——把 Agent 循环提升为搜索树，配合价值函数与回溯。

树搜索不是"更好的推理技巧"，而是**把算力换成探索**：同一道题，多花几倍调用去覆盖分支，期望在第一条路径走错时还有第二条。因此它天然有适用条件，也天然有预算上限。

## Tree of Thoughts（ToT，Yao et al., NeurIPS 2023）

把线性 CoT 推广为对多个推理路径的显式探索：每步生成多个候选思路，对部分状态打分，剪掉弱分支，扩展有希望的分支，直到停止条件。

- 推理变成**有向导引的搜索**：回溯显式、分支质量可测、最终答案从竞争候选中选而非第一个轨迹。
- 关键依赖：**评估函数质量**决定性能。外部验证器（代码执行、测试）优于自我反思打分。
- 变体：BFS（穷举）、DFS（深度、内存有限）、Beam search（内存受限 + 好启发式）。
- 数字：论文在 Game of 24 上报告 CoT 约 4% vs ToT 约 74% 的成功率；代价是数十倍调用（论文未强调 token 倍数，但显式树显著贵于 CoT）。
- 语境：推理模型已在推理时内化大量这类探索，显式 ToT 更多留给"有外部验证器"的任务与非前沿模型。

## Graph of Thoughts（GoT，Besta et al., AAAI 2024）

树只允许分支与回溯（每个思路一个父节点）；图增加**聚合**——一个节点可有多个父节点（N 对 1 合并）与循环（精炼回路），部分解可以组合与改进。论文在可组合任务（如排序、集合合并）上报告 GoT 相对 ToT 质量提升约六成、成本下降约三成。

若子结果不能组合，图的额外机制买不到收益——这是用不用 GoT 的分界线，不是"图比树高级"。

## MCTS 与 LATS

**MCTS（Monte Carlo Tree Search）**：用模拟 rollout 与价值反向传播。不只是"有分数的 ToT"——它保存多次访问的统计，以树策略决定下一份搜索算力投向哪里（先探索少访问的分支，再收敛到高价值分支）。

**LATS（Language Agent Tree Search，Zhou et al., ICML 2024）**：统一 ReAct + Reflexion + MCTS。LLM 同时充当 agent、价值函数（给状态打分）、优化器（选最佳轨迹）。

- 节点保存：环境状态、动作历史、观察、反思、价值估计、访问统计。
- 迭代：Select → Generate candidate actions → Execute/Simulate → Observe → Evaluate & Reflect → Update statistics → Expand/Revisit/Backtrack。
- 环境反馈是核心：代码修复的"候选补丁→跑测试→观察失败→更新分支价值"，浏览器交互的"候选点击→新 DOM→衡量进展"。
- 数字：论文报告在 HumanEval 上 GPT-4 pass@1 达 **92.7%**，优于 ReAct、Reflexion、CoT、ToT；另在网页决策任务上报告无梯度平均分 75.9。代价是每道题要做多轮 rollout、价值评估与回溯，模型调用量比单次推理高一个数量级。
- 前提：有廉价可靠的价值函数。

## 成本结构

选树搜索之前先算清楚三笔账，任意一笔爆掉就不该用：

| 成本项 | 怎么涨 | 怎么压 |
|---|---|---|
| 模型调用 | 分支数 × 深度 × 每节点评估次数，近似指数 | 减分支宽度、提前剪枝、缓存相同前缀 |
| 状态存储 | 每个节点要保存观察与历史，长任务迅速膨胀 | 只存摘要 + 指针，节点按需重建 |
| 验证器 | 每个候选都要跑测试/编译，可能比模型调用更贵 | 分层验证：先廉价静态检查，再跑重验证 |
| 延迟 | 串行搜索直接放大人可感知的等待 | 并行扩展同层节点，但注意限流 |

> 判断：树搜索的性价比拐点通常在"验证器比模型便宜且可靠"的领域（代码、数学、结构化查询）。在需要人判断质量的开放写作类任务上，多采样几条让人挑，往往比建树更划算。

## 怎么落地

把论文方法变成能跑的实现，关键在四件事，而不在公式：

1. **状态表示**：节点存"到这里为止的结构化摘要 + 关键产物引用"，不存整段对话。状态越像对象、越不像聊天记录，评估与去重越好做。
2. **候选生成**：一次生成 N 个候选（N 取 3–5），要求它们在策略上不同而不是只换措辞；同质候选是浪费预算。
3. **评估与剪枝**：先定阈值而不是排名——低于阈值的整支剪掉，高于阈值的按分数保留前 K 个。没有绝对阈值时，模型会永远"都还行"。
4. **停止条件**：深度上限、总调用上限、连续 M 次无提升、找到满足验收标准的解，四者取先到者。

## 何时用 / 何时不用

**用**：复杂规划、数学、代码任务且第一条路径常失败；有好的评估函数或外部验证器；任务真正分支多；需要显式回溯。

**不用**：简单线性任务；延迟或 token 预算紧张（显式树显著贵于 CoT）；没有可靠评估信号（这时搜索只是把错误放大 N 倍）。

## 失败模式

| 失败 | 症状 | 处置 |
|---|---|---|
| 评估器偏差 | 总分高的分支实际是错的 | 用外部验证器替代模型自评，或双评估器交叉 |
| 多样性坍缩 | N 个候选几乎相同，搜索退化成重复采样 | 提示里要求策略差异，或按温度分层采样 |
| 上下文膨胀 | 节点带全量历史，几层后就触顶 | 节点只存摘要与产物引用 |
| 过度搜索 | 早就有可接受解，仍继续展开 | 设"满足验收即停"的出口 |
| 缓存不命中 | 前缀每次不同，成本翻倍 | 固定系统提示与工具描述，动态内容后置 |
| 评估与生成错配 | 能选出好候选，但生成器产不出好候选 | 先提升生成能力，判别能力的边际收益更小 |

## 最重要的前提

任何审慎搜索方法（ToT/GoT/MCTS）都依赖能廉价可靠地给部分状态打分。若无法用验证器、单元测试、启发式或价值函数产出该信号，搜索就是"在黑暗中探索"。**先建评估器，再建树**。

研究还发现：生成器比判别器重要得多——提升模型提出好思路的能力帮助大，提升其判断能力帮助有限。这与"树搜索靠评估器"并不矛盾：评估器决定能不能选出好解，生成器决定好解在不在候选里。

## 一句话主线

树搜索是**用预算换探索**的模式：评估器决定天花板，候选多样性决定收益，停止条件决定成本；三者缺一，树只会更贵而不会更准。
