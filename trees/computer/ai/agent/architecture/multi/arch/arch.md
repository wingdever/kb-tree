# 多智能体的架构模式

多智能体不是默认选项——单 Agent + 工具是基线。只有当单个工具齐备的 Agent 不够用时，才拆分。拆了之后首先要选的就是架构模式：决定请求怎么在 Agent 之间流动、谁拥有控制权。

## 请求如何流过系统（四阶段）

1. **任务分解与路由**：编排器接收请求，拆成子任务，路由给最合适的 Agent。客服请求可能拆成意图分类和数据检索两个子任务，发给两个不同 Agent。
2. **专门执行**：每个 Agent 独立处理自己的子任务，只用与自身角色相关的上下文和工具——这就是上下文效率收益的来源。
3. **消息传递与交接**：交接通常携带中间结果本身、置信度分数（帮助编排器决定继续下发还是打回重做）、人工复核标记（遇到超出范围的东西时触发验证 Agent 或人）。
4. **聚合与输出综合**：编排器或专门的综合 Agent 合并所有输出。这一遍也是捕获 Agent 间不一致的地方。

四阶段里最容易被低估的是第 4 步：**合并本身也要成本**，要读多份输出、判冲突、重排格式。很多多智能体方案在第一年就跑输单 Agent，原因不在拆分，在于合并没人认真做。

## 五种架构模式

| 架构 | 协调方式 | 最适合 | 主要代价 |
|---|---|---|---|
| **层级 / 监督者（Supervisor）** | 中央监督者分派并复核，对最终结果单点负责 | 需要问责的企业工作流；最常见的生产模式 | 监督者上下文成为新瓶颈 |
| **顺序 / 流水线（Sequential / Pipeline）** | 固定顺序，每步输出喂给下一步 | 步骤稳定、可重复：检索→摘要→格式化；简历筛选、发票解析 | 没有回退，早步错误向后传播 |
| **并行（Parallel）** | 多个角度同时处理同一问题，事后合并 | 时间敏感、需速度；用延迟换多样性 | 合并难、token 总量上升 |
| **网络 / 去中心化（Network / Swarm）** | Agent 直接协商，无单一控制者 | 大规模分布式 Agent 池 | 无全局视角、最难调试、易循环 |
| **创建者-验证者（Creator-Verifier / 对抗）** | 一个生成，另一个独立检查/挑战 | 高风险输出，需要内建复核 | 验证者与生成者共享同一盲区 |

## 补充模式

- **群体聊天 / 辩论（Group chat / Debate）**：共享会话中互相批评、辩论、投票。能提升推理密集型任务质量，但烧 token 且无强管理者会漂移。
- **黑板 / 共享状态（Blackboard）**：Agent 读写共享工作区而非直接消息传递，解耦好但状态管理复杂。是 1980 年代 AI 模式的复兴；arXiv 2510.01285 与 2507.01701 报告信息发现任务相对基线有明显提升，但工具不成熟，属**新兴方向而非生产默认**。
- **层级（Hierarchical）**：监督者的监督者，"团队之团队"。获得规模，但每一层都让延迟和 token 成本相乘——只有扁平监督者真的管不过来时才加层。

## 怎么选：四个判据

不要按"哪个模式先进"选，按四个约束排序：

| 判据 | 指向的模式 | 反向信号 |
|---|---|---|
| 需要单一问责点 | 监督者 | 每个子结果都要独立对外负责 → 流水线 |
| 步骤可预先枚举 | 流水线 | 输入类型会决定不同路径 → 监督者或路由 |
| 延迟是硬指标 | 并行 | 子任务互相依赖 → 并行只会白跑 |
| 输出风险高、错一次代价大 | 创建者-验证者 | 验证成本大于收益 → 单 Agent + 抽样复核 |

> 判断：优先选"控制权集中、路径可枚举"的模式，把自主性留在最需要开放判断的那一步。多智能体系统最难的部分从来不是"让 Agent 更自主"，而是"出问题时能定位到哪一跳"。

## 确定性 vs 自主性光谱

每个模式都落在从确定性到自主性的光谱上：

- **确定性端**：你编码流程——图、边、控制转移条件。可预测、可测试、易追踪。顺序流水线或手编码的编排图在此。
- **自主端**：LLM 决定谁下一步行动。管理者 Agent 看状态选 worker；网络 Agent 自由交接。更灵活、适应脏输入，但执行路径每次运行都变，难以评估。

实践规则：**可靠性重要的地方推向确定性控制，把自主性留给真正需要开放式判断的部分**。

## 失败模式

多智能体系统的失败有相当比例不是模型能力问题，而是协调问题。按发生位置分：

| 失败 | 发生位置 | 表现 |
|---|---|---|
| 规格不清 | 分解阶段 | 子任务定义模糊，两个 Agent 做出互斥的结果 |
| 交接丢信息 | 交接阶段 | 下游重复劳动，或推翻上游已确认的结论 |
| 验证缺口 | 聚合阶段 | 每份输出都"看起来对"，合起来不对 |
| 循环委派 | 协调层 | A 交给 B，B 交回 A，步数与成本失控 |
| 责任稀释 | 全局 | 出错时没有任何一个 Agent 或人被追责 |
| 一致性与格式漂移 | 聚合阶段 | 同一字段在不同子输出里命名、单位不同 |

对应的最小手段：子任务写验收标准、交接带固定字段、聚合阶段做冲突检测、交接计数设上限、明确单一负责人、聚合前统一 schema。

## 一句话主线

多智能体是**用协调成本换上下文效率**：拆得对，每个 Agent 只读自己该读的；拆得错，只是在多个上下文里重复同一场混乱。
