# 多智能体的架构模式

多智能体不是默认选项——单 Agent + 工具是基线。只有当单个工具齐备的 Agent 不够用时，才拆分。拆了之后首先要选的就是架构模式：决定请求怎么在 Agent 之间流动、谁拥有控制权。

## 请求如何流过系统（四阶段）

1. **任务分解与路由**：编排器接收请求，拆成子任务，路由给最合适的 Agent。客服请求可能拆成意图分类和数据检索两个子任务，发给两个不同 Agent。
2. **专门执行**：每个 Agent 独立处理自己的子任务，只用与自身角色相关的上下文和工具——这就是上下文效率收益的来源。
3. **消息传递与交接**：交接通常携带三样东西——中间结果本身、置信度分数（帮助编排器决定继续下发还是打回重做）、人工复核标记（遇到超出范围的东西时触发验证 Agent 或人）。
4. **聚合与输出综合**：编排器或专门的综合 Agent 合并所有输出。这一遍也是捕获 Agent 间不一致的地方。

## 五种架构模式

| 架构 | 协调方式 | 最适合 |
|---|---|---|
| **层级 / 监督者（Supervisor）** | 中央监督者分派并复核，对最终结果单点负责 | 需要问责的企业工作流；最常见的生产模式 |
| **顺序 / 流水线（Sequential / Pipeline）** | 固定顺序，每步输出喂给下一步 | 步骤稳定、可重复：检索→摘要→格式化；简历筛选、发票解析 |
| **并行（Parallel）** | 多个角度同时处理同一问题，事后合并 | 时间敏感、需速度；用延迟换多样性 |
| **网络 / 去中心化（Network / Swarm）** | Agent 直接协商，无单一控制者 | 大规模分布式 Agent 池；但无全局视角、最难调试、易循环 |
| **创建者-验证者（Creator-Verifier / 对抗）** | 一个生成，另一个独立检查/挑战 | 高风险输出，需要内建复核 |

## 补充模式

- **群体聊天 / 辩论（Group chat / Debate）**：共享会话中互相批评、辩论、投票。能提升推理密集型任务质量，但烧 token 且无强管理者会漂移。
- **黑板 / 共享状态（Blackboard）**：Agent 读写共享工作区而非直接消息传递，解耦好但状态管理复杂。是 1980 年代 AI 模式的复兴；arXiv 2510.01285 与 2507.01701 报告信息发现任务相对基线提升 13–57%，但工具不成熟，属**新兴方向而非生产默认**。
- **层级（Hierarchical）**：监督者的监督者，"团队之团队"。获得规模，但每一层都让延迟和 token 成本相乘——只有扁平监督者真的管不过来时才加层。

## 五种 recurring 模式（工业视角）

2026 年生产多智能体系统由五种反复出现的模式构成，每种对应不同的协调问题：

- **Hierarchical（监督者）**：企业中最常见，因为对最终结果保持单一问责点。
- **Sequential / Pipeline**：确定性、可测试、无递归风险，适合固定 SOP。
- **Parallel**：用协调简单性换速度，Agent 之间不互相等待。
- **Network（去中心化）**：可扩展但难调试，因为没有 Agent 拥有全局图景。
- **Creator-Verifier（对抗）**：捕获单个 Agent 无法在自己工作中发现的错误。

## 确定性 vs 自主性光谱

每个模式都落在从确定性到自主性的光谱上：

- **确定性端**：你编码流程——图、边、控制转移条件。可预测、可测试、易追踪。顺序流水线或手编码的编排图在此。
- **自主端**：LLM 决定谁下一步行动。管理者 Agent 看状态选 worker；网络 Agent 自由交接。更灵活、适应脏输入，但执行路径每次运行都变，难以评估。

实践规则：**可靠性重要的地方推向确定性控制，把自主性留给真正需要开放式判断的部分**。
