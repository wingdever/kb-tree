# 交接与通信（Handoff & Communication）

多智能体之间如何传递控制权与信息，是架构的血管。要分清两层：**框架内通信**与**跨框架/厂商通信**。

交接不是"把对话转过去"，而是一次**责任转移**：从这一刻起，另一个执行者要对这段目标负责，并带着自己的上下文与预算继续跑。转移得不干净，错误就会在边界上累积——上游以为已经交代清楚，下游以为还有人在管。

## 交接携带什么

一次 handoff 至少携带九样东西，缺哪样，下游就会自己猜，而猜错是静默的：

| 字段 | 内容 | 缺了会怎样 |
|---|---|---|
| 目标 | 这一跳要达成的具体结果，可判定 | 下游按自己的理解跑偏 |
| 已完成 | 已产出的中间结果与其位置 | 重复劳动，或覆盖上游成果 |
| 未完成 | 已知的缺口与待验证项 | 下游以为万事俱备 |
| 约束 | 口径、格式、禁用手段、时间窗 | 违反业务规则 |
| 工具边界 | 可用工具与数据范围 | 越权调用 |
| 预算 | 剩余步数、token、时间 | 一个节点吃光全局预算 |
| 验收标准 | 什么算通过、谁来判定 | 无法收口，无限往返 |
| 回传格式 | 结构化字段与失败码 | 结果无法被编排器消费 |
| 失败回退 | 失败时回给谁、怎么降级 | 失败在边界处消失 |

这些字段不必都写进提示词，但必须都存在于系统里：一部分在任务对象上，一部分在工具签名与权限里。**只写"请把上下文转交"的交接，等于把契约留在了口头。**

## 框架内通信

- **消息传递 + 共享图状态**（LangGraph）：Agent 通过图的共享状态交换信息。
- **显式 handoff**（OpenAI Agents SDK）：把对话历史转给另一个 Agent——被委派的 Agent 接收对话历史并接管，成为"当前活跃 Agent"直到该轮结束。
- **共享完整轨迹**：Cognition 的实践规则："共享上下文，共享完整 Agent 轨迹，而不只是单条消息"——丢掉轨迹的交接丢失了隐含决策。

三种方式的差别在**谁拥有状态**：共享图状态是"状态在编排层"，交接是"状态跟着控制权走"，共享轨迹是"状态谁都能读"。状态所有权不明确时，最常见的事故是两个 Agent 各自维护一份互相矛盾的版本。

## 什么时候该交接

拆分与交接的触发条件应该是具体的，而不是"任务看起来复杂"：

- **上下文互相污染**：两类工作需要的上下文差异极大（一个要读全部代码，一个要读全部客户记录），放一起会互相挤占。
- **工具域不同**：权限边界本就该分开，让一个 Agent 持有所有工具的权限，等于取消边界。
- **可以真并行**：子任务之间没有顺序依赖，能同时跑，交接是为了并发而不是为了分工。
- **需要独立验收**：某一段必须由另一个角色按其标准复核。

反过来说，三种情况不该交接：**能一次做完的**（交接的固定开销换不来收益）、**需要高频往返的**（每次交接都要重建上下文，来回几次比单 Agent 更贵）、**状态高度耦合的**（拆开之后每一步都要同步全量状态）。

## 跨框架/厂商通信

Agent 由不同团队、框架或公司构建时，跨边界那一跳必须落在标准信封上，不要自造消息格式——否则每接一个伙伴写一次适配器，鉴权、能力发现与长任务状态也没法复用。

跨边界能传的只有**显式声明的部分**：任务描述、输入产物、状态码、产物引用。不能传的是隐含状态——对方的记忆、工具会话、未落盘的中间推理。把这些当成"应该也在"的东西，是跨组织集成最常见的失败。

选型看三件事：对方是否用签名 Agent Card 做能力发现，是否支持 task 生命周期与状态回传，鉴权是否按 OAuth 资源服务器隔离。交接质量仍靠自己这一侧：验收标准写进任务描述，结果按可校验的 Artifact 收，失败按 task 状态收口。

## 共享状态与黑板模式

Agent 也可以通过读写共享工作区（黑板）而非直接消息传递来协作：

- 解耦好——Agent 不需要彼此知道对方存在。
- 代价是状态管理复杂，需要版本化状态、乐观并发、显式 ACK 来避免竞态与状态漂移。
- 黑板是 1980 年代 AI 模式的复兴；近年的公开实验报告在信息发现类任务上相对基线有明显提升（arXiv 2510.01285、2507.01701），但工具不成熟，属**新兴方向而非生产默认**。

> 判断：黑板适合"多个 Agent 各自贡献一块证据、最后由人合并"的场景；不适合有严格顺序与强一致要求的流程——那种场景下共享状态的冲突解决成本会高于拆分收益。

## 通信的可靠性

- 消息丢失：对关键消息要求显式 ACK（重试直到确认）。
- 消息被误解：要求结构化格式，不要自由文本。
- 信息过载：监控 token 数，截断或摘要。
- 上下文过时：给所有上下文打时间戳。
- 竞态：给 handoff 编号排序；共享资源加锁或排队。
- 重复投递：接收端用幂等键去重，否则重试会把同一动作执行两次。
- 顺序错乱：按单调序号判断新旧，晚到的旧消息直接丢弃而不是覆盖新状态。

## 失败模式

| 失败 | 表现 | 处置 |
|---|---|---|
| 契约不全 | 下游反复追问上游"你指的是哪个文件" | 九字段缺项检查，交接前校验 |
| 状态双写 | 两个 Agent 各有一份事实，结论互相矛盾 | 明确单一状态所有者 |
| 上下文淹没 | 把全量历史转过去，下游在中段丢失关键约束 | 转摘要 + 显式约束，原轨迹留引用 |
| 无验收 | 交接后没人判断完成，流程悬空 | 每个 handoff 绑定验收标准与回传格式 |
| 往返风暴 | A 交给 B，B 又交回 A，循环不停 | 交接计数上限 + 禁止回交同一目标 |
| 跨边界假设 | 以为对方有自己的记忆与会话 | 只依赖显式声明的输入产物 |
| 静默失败 | 下游失败但按"已完成"回传 | 失败码必填，缺失败码视为未完成 |

## 一句话主线

交接的难点不在"怎么传"，而在**传得足够让下一个执行者独立负责**：目标、已完成、未完成、边界、预算、验收，这六件事写清楚，多智能体才可能比单 Agent 更强。
