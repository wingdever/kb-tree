# 可靠多智能体系统的五大构建模块

每个可靠的多智能体系统都依赖五个架构构建块：不同的角色、结构化数据 schema、确定性工具、持久化记忆、验证检查点。配置得当时复杂工作流顺畅运行，不会累积错误。

| 模块 | 作用 | 缺失的失败模式 |
|---|---|---|
| **隔离的角色与提示** | 紧范围的系统提示：角色、目标、约束、输出格式 | Agent 试图做多件事、幻觉约束 |
| **标准化状态与交接 schema** | 用 JSON 等结构化格式传递，而非无格式散文 | 下游误读对话上下文 |
| **受控工具注册表** | 最小权限；接入 Agent 只需读文件工具，不该有 CRM 写权限 | 安全风险、意外系统修改 |
| **上下文隔离与选择性记忆** | 只传与当前子任务相关的数据 | token 膨胀、延迟尖峰、注意力退化 |
| **人在回路评估门** | 关键动作（发客户邮件、更新生产库、授权交易）前暂停人工确认 | 失控的数据泄露或错误自动动作 |

## 1. 隔离的角色与提示（Isolated Personas）

每个 Agent 需要紧范围的系统提示，定义角色、目标、约束、预期输出格式。给 Agent 一个宽泛的角色会削弱焦点、降低输出一致性。角色化示例：planner / critic / executor / verifier / researcher / writer。

## 2. 标准化状态与交接 schema

Agent 之间不交换无格式的散文。可靠系统用结构化 schema（JSON）传递数据，保证下游 Agent 收到清晰标注的输入。这也是 MetaGPT 等框架的核心做法：用结构化制品（需求文档、设计规格、带接口的代码模块）交换，减少自由对话里的误解，并天然产生可审计记录。

## 3. 受控工具注册表

不是每个 Agent 都能访问所有组织 API。工具访问遵循最小权限：接入 Agent 需要读文件工具，不该有 CRM 写权限。按阶段限定工具——规划数据库迁移的 Agent 不需要图像工具在上下文里。

## 4. 上下文隔离与选择性记忆

Agent 不需要读完整历史消息线程。只传与当前子任务相关的数据，既省 token 又避免注意力退化。这与单 Agent 的上下文工程一脉相承。

## 5. 人在回路评估门（HITL Gate）

关键动作必须暂停等待人工确认：发送外部客户邮件、更新生产数据库、授权交易。这一控制不是独立模式。

## 结构化制品作为审计轨迹

Hong et al. 2023（MetaGPT）把这件事做成流水线：需求、设计、接口各自成为一种制品，逐层交付。更重要的副作用是：结构化制品天然生成一份完整、可检查的系统决策记录——把"输入到输出之间"发生的每个失败变成可观测的。

## 交接契约该写什么

多 Agent 系统里，**交接是唯一的跨角色界面**，它比任何提示词都更能决定可靠性。一份能被机器校验的交接至少要九个字段：

| 字段 | 内容 | 缺失后果 |
|---|---|---|
| `task_id` / `parent_id` | 任务标识与来源 | 出了问题无法回溯是哪次委派 |
| `objective` | 一句话可验收的目标 | 下游按自己的理解做事 |
| `inputs` | 引用（文件路径、记录 id、URL），不是全文 | token 膨胀、下游读到过期副本 |
| `constraints` | 硬约束：不许做什么、必须满足什么 | 越权与合规风险 |
| `acceptance` | 怎样算完成（可判定） | 无法判断该不该重试 |
| `artifacts` | 产物位置与格式 | 结果交付靠口头描述 |
| `budget` | 剩余 token、时间、工具调用次数 | 子任务烧光总预算 |
| `failure_policy` | 重试、降级还是上报 | 失败后原地打转 |
| `trace_ref` | 关联的 trace / run id | 审计与回放断链 |

> 判断：没有 `acceptance` 的交接等于把验收责任推给了下游的猜测；没有 `budget` 的交接等于给了下游无限授权。

## 工具注册表怎么落地

「受控工具注册表」不是一份工具清单，而是三样东西的组合：

- **标识与 schema**：每个工具一个稳定 id、一份可校验的参数 schema、一份返回结构说明。
- **策略（policy）**：谁能调、在什么条件下调、单次与累计上限、是否需要审批。
- **代理句柄**：worker 拿到的是「可调用的句柄」，不是真实凭证；调用时由注册表服务端校验策略并代执行。

三条纪律：凭证永不进入注册表（用引用或短时令牌代替）；写操作默认不授，按角色显式开通；注册表按**角色**绑定，不按会话全局共享——否则一个 worker 被注入后就能拿到全部能力。

## 预算与扇出

每个 worker 都要带预算：token、墙钟时间、工具调用次数，三者任一触顶即返回「部分结果 + 已耗尽」。编排器侧的**扇出上限**同样重要：并发 10 个 worker、每个读 100k token，账单是单 Agent 的十倍，而收益往往只有一两个 worker 的贡献。

经验做法：先串行跑两个 worker 验证拆分是否有效，再放开并发；并发数按「合并者的上下文容量」倒推，而不是按机器核数。

## 失败升级路径

一条固定的四级路径，避免每个 worker 自行发明处理方式：

1. 本层重试一次（仅限幂等操作）。
2. 降级：返回部分结果，并在 `artifacts` 里标注「缺失/未验证」。
3. 上报编排器：由编排器决定改派、缩范围还是放弃。
4. 转人工：涉及不可逆操作或超出能力边界。

明确禁止两件事：worker 自行扩权（去调用没被授予的工具）、worker 自行改计划绕过失败。这两件事会让失败不可观测。

## 验收与审计

结构化制品要能回答四个问题：谁产出的、在什么预算下产出的、依据哪些输入、验收是否通过。做法是把 `trace_ref` 与产出物一起存，并把验收结果写成结构化字段（通过/失败/未验证），而不是散文。

## 五个模块的落地顺序

先 schema 与注册表，再角色划分，再上下文隔离，最后 HITL。理由是：没有交接 schema 与权限边界，角色划分只是话术；没有隔离，多个 Agent 会互相污染上下文；HITL 放在最后，是因为它需要前面四样东西提供「在哪一步、对什么对象、由谁批」的结构化信息。

## 常见反模式

- 用自由文本交接，下游靠解析散文取字段。
- 多个 worker 共享一个全局可变状态，互相覆盖。
- worker 之间直连通信，绕过编排器，拓扑变成网状后无法排障。
- 委派不带预算，单个子任务吃掉整轮额度。
- 把 HITL 放在流程末端，前面已经产生了不可逆副作用。
- 工具注册表按会话共享，一个被注入的 worker 拿到全部能力。
