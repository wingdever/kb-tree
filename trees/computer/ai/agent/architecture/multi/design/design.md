# 多智能体的设计判断

多智能体不是默认选项。这份笔记汇总"要不要拆、怎么拆、拆到什么程度"的判断框架。

## 基线：单 Agent + 工具

**单 Agent + 工具是基线**——每个设计都应拿来对比的诚实起点。它不是多智能体，但它是衡量一切多智能体方案的标尺。只有当单个工具齐备的 Agent 被证明不够用时，才拆分。

> 在更简单的模式跑通之前上多智能体，只是装饰。

## 拆分的三种形状

拆开之后，请求怎么流动有三种基本形状；先选形状，再选框架，比反过来省事：

| 形状 | 子任务怎么来 | 适合 | 主要代价 |
|---|---|---|---|
| **静态流水线** | 开发期写死步骤与顺序 | SOP 稳定、每步输入输出固定 | 没有回退，早步错误向后传 |
| **动态编排** | 运行时由规划者按输入拆 | 子任务数量随输入变化（多文件改动、多来源调研） | 规划者可能过度拆解，成本最不可控 |
| **并行扇出** | 同一问题的多个角度同时跑 | 延迟敏感、需要多样性 | 合并难，token 总量上升 |

> 判断：三种形状的自主性依次升高，测试负担也依次升高。能写死就别动态，能静态扇出就别引入运行时规划。

## 使用前的判断清单

1. 单个 Agent 是否已经无困惑地处理了负载？若是，不要拆。
2. 不同请求类型是否真的需要各自的循环、提示、工具或模型？
3. 子任务的数量是否随输入变化、无法在开发期列出？（若是，用动态编排；若否，用静态流水线或固定扇出。）
4. 能否为每条边写清确定性条件？不能则小心——难以调试。
5. 是否已为高风险动作设了审批门、为循环设了上限？

## 何时值得拆

- **上下文隔离收益**：不同子任务需要各自的上下文与工具，单个 Agent 会被干扰 token 淹没。
- **角色专门化**：分类、验证等任务需要不同提示，优化一条路径不应伤害另一条。
- **并行需求**：独立子任务可同时执行，降低延迟。
- **问责需求**：需要 verifier Agent 独立复核高风险输出。
- **规模化需求**：可加新专家而不重建整个系统。

注意：上下文效率是**质量收益而非成本节省**——多个 Agent 一起跑的总 token 通常比一个 Agent 更高。

## 何时不该拆

- 任务步骤固定、可预测 → 用 workflow。
- 所有 Agent 都在一个应用、一个框架里 → 框架自带 handoff 可能足够。
- 对端是确定性微服务 → 普通 REST 客户端即可，不需要 A2A。
- 还没测出单 Agent 的瓶颈 → 先别引入复杂度。

## 成本意识

- 单 Agent 作基线记 1×：投票约 3×（每个 Agent 一票）、陪审团约 4×（各出一轮 + 一个裁判）、三轮辩论约 9×。
- 五个 Agent 的并行系统可达单 Agent 的 10–50× token——成本本身是失败模式。
- 给 worker 数量、单任务预算、迭代次数设上限。
- 按步骤选模型：简单路由用小模型，真正推理才用前沿模型。

## 失败模式先行

2026 生产实践：把失效模式当作设计输入。你的架构不算"够好"，直到你能对着 MAST 的每个类别说出部署了哪种缓解措施。

## 一句话主线

多智能体设计的核心不是"拆不拆"，而是**拆出来的每一块能不能独立验收**：能验收的拆分换来上下文隔离与并行，不能验收的拆分只是把一次失败复制成五次。
