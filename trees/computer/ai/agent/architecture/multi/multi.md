# 多智能体系统

多智能体不是默认选项。**单 Agent + 工具是基线**，是每个设计都该拿来对比的诚实起点。拆分的正当理由只有三个：上下文必须隔离、权限必须隔离、执行必须并行。除此之外，「让多个专家协作」通常是叙事而非收益。

## 这一组要回答的六个问题

1. **该不该拆**。先算一遍单 Agent 的可行解，再看拆分能省什么——多数场景拆完总 token 变多、延迟变长、调试变难。
2. **拆成什么形状**。中心编排、层级、流水线、群聊、黑板，形态决定了谁有控制权、失败如何传播。
3. **谁控制对话**。控制权在编排器手里最可控，在 Agent 之间轮转最灵活也最不可预测；这直接决定可观测性与成本。
4. **信息怎么传**。交接要携带目标、约束、已完成部分与未决问题；只传一句「你接着做」等于让下一个 Agent 重新猜。
5. **分歧怎么收敛**。投票、评审、辩论各有适用面，也各有方差问题——同样的输入两次跑出不同结论，比结论错更麻烦。
6. **会怎么坏**。多 Agent 的典型失效不是能力不足，而是协调失败：任务重复、信息丢失、互相等待、无限委派。

## 三个容易被忽略的判断

- **拆分不等于并行**。串行拆分会把一次调用变成多次，成本翻倍而质量不变；只有能真正并发、或上下文必须隔离时才划算。
- **上下文隔离是主要收益**。多 Agent 最实在的好处是每个 Agent 只看到自己该看的东西——这既是能力提升，也是安全边界。
- **协调开销随 Agent 数量超线性增长**。三个 Agent 两两通信是三对关系，五个是十对；超过某个数量后，编排本身就成了瓶颈。

## 决策顺序

先做单 Agent + 工具的基线，确认拆分确实能换来上下文隔离、权限隔离或并行度；再按控制权归属选架构与编排形态；最后用失效模式清单做上线前自查。跨组织协作才引入标准协议，同团队内部用框架自带的通信机制就够。

## 一句话主线

先用单 Agent + 工具做基线并证明它不够，再按上下文、权限、并行度三个理由拆分；形态决定控制权归属，交接决定信息是否丢失，共识机制决定结论是否稳定，而失效模式清单决定这套系统能不能上线。
