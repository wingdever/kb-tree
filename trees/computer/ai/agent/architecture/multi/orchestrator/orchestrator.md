# 编排器-执行器（Orchestrator-Workers）

这是最常用的多智能体模式：主导 Agent（监督者/编排器）协调流程，把子任务委派给专门的子 Agent（worker），每个 worker 完成后控制返回监督者，由监督者综合结果。

## 为什么是最常用

Anthropic 的研究系统是典范："主导 Agent 协调流程，同时把任务委派给并行运行的专门子 Agent"。控制集中在监督者、工作并行展开，是生产中最常见且稳健的模式。它对应的场景是：**子任务无法事先静态确定**——比如一次代码改动涉及哪些文件，编排器读了请求才知道。

## 两个变体

- **经典监督者**：主导者路由工作、收集结果。worker 作为独立 Agent 运行，返回文本结果。
- **工具调用式 / 管理者变体**：每个 worker 作为工具暴露给主导者，工具调用模型选择调用哪个。LangChain 在 2026 年推荐这个变体，因为它能更紧地控制**每个 Agent 看到什么上下文**。OpenAI Agents SDK 称为 "manager" 模式："当专家只需帮忙处理有界子任务、但不该接管面向用户的对话时使用"。

两者区别的关键在**对话所有权**：专家是否应该接管面向用户的会话？若只是后台处理有界子任务，用 manager（工具调用式）；若需要自主与用户对话，用经典 handoff。

## 层级扩展

层级（Hierarchical）把监督者变成"监督者的监督者"——团队之团队：

- LangGraph 文档："你可以通过让一个 supervisor 管理多个 supervisor 来创建多层级系统。"
- CrewAI 的 hierarchical process 自动分配 manager agent，委派任务并在继续前校验结果。
- 收益是规模——可以组合很多专家而不让一个监督者淹没在决策里；代价是每一层都让延迟与 token 成本相乘。

## 与并行化的区别

编排器-执行器与并行化（Parallelization）在拓扑上相似，关键差异在**灵活性**：

- 并行化的子任务是**预先固定**的（sectioning 分块、voting 投票）。
- 编排器-执行器的子任务**由编排器根据输入动态决定**。

因此编排器-执行器是五个模式中最贵的，planner 可能过度拆解——务必给 worker 数量和单任务预算设上限。

## 实现要点

- worker 应有隔离的角色与提示。
- 子任务结果用结构化 schema 回传，不要无格式散文。
- 编排器失败在没有重试逻辑时不可恢复——加重试与幂等。
- 给 worker 计数和预算上限，防止过度拆解烧光预算。
- 人在回路审批门可挂在监督者的综合输出之后。

## 委派前的三问

不是所有任务都该拆。委派之前先问三件事：

1. **子任务能否独立验收**？如果只能整体判断对错，拆开后的中间结果没人能验，错误会在合并时才暴露。
2. **上下文能否隔离**？子任务是否需要完整对话才能做对。需要共享大量隐式上下文的任务，拆出去反而失真。
3. **并行是否真的省时间**？串行依赖的任务拆开只会增加一次委派与合并开销；真正省时间的是「互不依赖且都耗时」。

三问里任一为否，优先留在单 Agent 里做。

## 扇出与合并

扇出（fan-out）是成本放大器，需要三个上限：并发 worker 数、单 worker 预算、总委派深度。合并（fan-in）有三种方式，选错会让前面的工作白做：

| 合并方式 | 适合 | 风险 |
|---|---|---|
| 拼接 | 结果彼此独立（多份资料汇总） | 冲突未处理，读者自己判断 |
| 投票 / 一致性 | 同一问题多路求解 | 多路同错时 unanimous 假象 |
| 重写综合 | 需要统一口径的最终答案 | 合并本身要一次 LLM 调用，成本常被漏算 |

合并者必须看到：每个 worker 的目标、关键结论、置信或未验证标记、产物引用。不需要看到每个 worker 的完整推理过程——那会把隔离省下的 token 又买回来。

> 判断：合并是编排模式里最容易被低估的一步。很多「多 Agent 效果不好」，实际是合并时把互相矛盾的结论揉成了一句话。

## 上下文传递：给什么，不给什么

给：原始任务、子任务目标、硬约束、上游产物引用、验收条件。
不给：完整对话历史、其他 worker 的中间草稿、编排器自己的内部推理。

传「引用」而不是「全文」，是为了让 worker 按需读取，也避免副本过期。

## 失败与重试

四类失败要分别处理：

- **worker 超时**：先判是否仍在推进（有心跳或进度事件），再决定等待还是取消。
- **worker 部分成功**：把已完成部分标为可用，缺失部分显式标注，不要整单丢弃。
- **编排器误判**：拆出了无法完成或重复的子任务。需要「重复检测」——比较子任务目标与输入，发现重叠就合并。
- **无限委派**：A 派给 B、B 又派回 A。用委派深度上限与「同一目标哈希」双重拦截。

## 观测

每次委派记一条 span：谁派的、派了什么、给了多少预算、花了多少、返回了什么、验收结果。没有这层观测，多 Agent 的成本与失败都无法归因——只能看到总账单和最终答案。

## 何时不用

- 单步任务或线性流程：直接调工具。
- 强顺序依赖：拆开只会增加交接开销。
- 需要共享大量隐式上下文（同一次调试、同一段代码的连续修改）。
- 预算极紧：编排器的规划与合并本身就是两次额外调用。

## 常见失败

| 失败 | 症状 | 修法 |
|---|---|---|
| 过度拆解 | 十几个 worker 各做一点，合并后仍不完整 | 先串行验证拆分，再放开并发 |
| 重复子任务 | 两个 worker 做同一件事，结果冲突 | 目标+输入哈希去重 |
| 合并失真 | 最终答案抹平了分歧 | 合并输入带「未验证/冲突」标记 |
| 上下文泄漏 | worker 看到了不该看的其他任务数据 | 按子任务裁剪输入 |
| 预算失控 | 总成本是单 Agent 的数倍 | 扇出与深度双上限 |
| 编排器无重试 | 一次委派失败整轮报废 | 幂等重试 + 降级路径 |
