# 计算机操作 Agent（Computer Use）

Computer Use 让多模态模型**像人一样操作图形界面**：看截图，输出点击、输入、滚动等动作，由 harness 执行后返回新截图。它用于**没有 API 的系统**——遗留桌面应用、厂商门户、只给界面不给接口的工作流。

## 感知—行动循环

```
截图 → 模型对照目标选动作 → harness 执行坐标/按键 → 新截图验证 → 循环，直到完成或触顶
```

- **感知**：每次截图按图像输入计费（约 1000–1800 input token）；历史每轮重发，长任务成本陡增。
- **动作**：Anthropic 的工具集涵盖截图、鼠标、键盘、滚动、缩放等；模型输出的是**坐标**，harness 负责执行。
- **验证**：靠下一张截图判断动作是否生效；失败动作（误点）不会自动回滚。

**坐标对齐是高频 bug**：模型返回的是它收到的那张图的像素坐标，任何缩放/裁剪都要映回真实屏幕；Gemini 用 1000×1000 归一化网格，需自行缩放；OpenAI 的循环持续到不再返回 `computer_call`。

## 与相邻方案的边界

| 方案 | 怎么行动 | 适合 | 不适合 |
|---|---|---|---|
| **API / MCP 工具调用** | 结构化调用，按 schema | 任何有 API 或 MCP server 的系统 | 覆盖不到的功能 |
| **Browser Use** | 对页面结构写选择器或让 Agent 驱动浏览器 | 稳定的 Web 流程；DOM 可读的页面 | 桌面应用、canvas、无语义界面 |
| **RPA**（UiPath 等） | 开发者预先录制/编排步骤 | 高稳定、高频、任务型流程 | 界面多变、需要推理的任务 |
| **Computer Use** | 截图 + 坐标 + 按键 | 无 API、界面多变、遗留系统 | 有 API 却不用——慢且贵 |

选择顺序：**有 API 就用 API；稳定 Web 流程用脚本；只有没有接口且界面多变时才上 Computer Use**。量级差别也很大：结构化接口调用是毫秒级，而视觉操作每步要"截一张图 + 跑一次推理 + 执行一次动作"，通常在数百毫秒到数秒，且步数越多越慢。

## 厂商方案与部署形态

三家的分歧在「鼠标放在哪里」：

| 方案 | 表面 | 部署 | 特点 |
|---|---|---|---|
| **Claude Computer Use** | 完整桌面 | 你的 VM / 容器 / 远程桌面 | 唯一的全桌面路线；一次性 VM + 快照回放是强隔离模式 |
| **OpenAI Operator / CUA** | 仅 Web | 托管沙箱里的 Chromium，画面回传 | 容器化安全模型，人在回路接管 |
| **Gemini Computer Use** | 浏览器标签页 | Google 基础设施，绑定登录会话 | 低延迟、DOM 感知；作用域限于浏览器 |

开源侧有 Agent S、Fara-7B 等。MCP 在三者之下作为共享工具层：密钥、识图、数据查询等辅助能力注册一次，各家都能调用，避免绑定单一 harness。

## 基准与代价

- **OSWorld / OSWorld-Verified** 是跨 Ubuntu / Windows / macOS 的电脑控制基准；分数随**步数预算**和任务长度剧烈变化，只应在同设置下比较。
- 2026 年公开报道的数值跨度很大（从 20% 上下到 80%+），同一模型在不同类别差异显著：文件操作、浏览器任务、表单填写、跨应用编排各有强弱。**按你的任务类别切分看，不看总分**。
- 长流程仍然容易失败；即使高分模型，多步任务仍有相当比例失败。
- 成本来自每步图像 token + 重发历史；后段步骤延迟可达前段的数倍。

## 安全边界

- **隔离优先**：一次性 VM / 容器、快照回滚、独立账号、限定凭据；出问题能整段重放和撤销。
- **不可逆动作要确认**：支付、提交、删除等必须人在回路；高风险金融门户不要无人值守。
- **不可信页面是输入**：网页可能藏提示注入劫持目标；把屏幕内容当工具结果，不当事实指令。
- **最小权限**：域名白名单、工具动作白名单、敏感值单独传入且不在轨迹里回显。

## 长任务的三个工程约束

短任务（几步填个表单）能跑通不代表能用；超过二三十步之后，三件事必须提前设计：

- **检查点**：每个阶段结束保存一次"现在屏幕应该长什么样 + 已完成到哪一步"。恢复时校验实际屏幕与预期是否一致，不一致就重来这一段，而不是继续往下点。
- **步骤幂等**：重试一次点击可能是二次提交（重复下单、重复发信）。对提交类动作，先查"是否已经成功"的痕迹再决定重试。
- **可重放**：把每步的截图、动作、判断理由留档。没有这段轨迹，失败只能靠人肉复现，长任务的偶发失败基本无解。

## 怎么评估

Computer Use 的分数极度依赖设置，评估口径本身比分数重要：

- **按任务类别分开看**：文件操作、浏览器任务、表单填写、跨应用编排的强弱完全不同，总分对选型没有意义。
- **固定步数预算与屏幕分辨率**：步数上限、是否允许重试、图像缩放比例都会显著改变结果，跑之前写进报告。
- **补三类指标**：完成率之外，看**平均步数**（成本）、**人工接管率**（可用性）、**不可逆动作拦截率**（安全）。
- **用自家真实界面做小样本**：公开基准里的应用未必和你的一样，10–20 条真实任务的自测比排行榜更有用。

## 浏览器与桌面的感知差别

浏览器页面有 DOM 与无障碍树，可以把"这里有个按钮、它叫什么"结构化地喂给模型；桌面截图只有像素，模型必须靠外观猜。这带来两个后果：

- 界面元素长得像（两个同样的"保存"按钮）时，纯视觉会点错，需要额外线索定位（相邻文字、窗口标题、序号标注）。
- 同一功能在不同分辨率/主题/语言下外观变化，会让固定坐标与固定视觉特征一起失效，所以要每次从新截图重新定位，而不是缓存坐标。

## 常见失败模式

| 症状 | 常见根因 | 对策 |
|---|---|---|
| 点空、点错位置 | 坐标未从模型图映回真实屏幕，或缩放/裁剪未还原 | 统一坐标约定，执行前换算并断言落在屏幕内 |
| 反复重试同一动作 | 动作没生效但没有验证，模型不知失败 | 每次动作后强制截图比对预期状态 |
| 任务半途卡死 | 弹窗、权限询问、加载态未被识别 | 维护"异常界面"清单，命中即走固定处理分支 |
| 重复提交 | 重试不幂等 | 提交前查痕迹，提交后立即确认回执 |
| 成本爆掉 | 历史截图全量重发，步骤又多 | 只保留最近若干张 + 一份阶段摘要 |

## 一句话主线

**Computer Use 是「没有 API 时的最后一招」：截图感知、坐标行动、逐步验证；用隔离 VM 与审批门兜住风险，能走 API 或稳定脚本就别走它。**
