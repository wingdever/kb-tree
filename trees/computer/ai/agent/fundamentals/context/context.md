# A2 上下文工程

上下文工程是"在正确时刻把正确信息放进模型有限的上下文窗口"的学科。核心认知：**上下文窗口是稀缺资源**——加更多 token 可能降低而非提高质量。

> 很多看起来像模型弱点的失败，其实是上下文管理失败，且只在真实负载下暴露。

## 三种失败模式

### 1. 上下文腐烂（Context Rot）

定义：**随输入长度增长而可测量的输出质量下降**。这是结构性问题，不是措辞问题。

- 注意力在长窗口中被摊薄，模型对中间部分权重不足，呈 **U 型曲线**：开头和结尾表现好，中间差。
- Chroma 测试 18 个前沿模型，全部随输入变长而退化，即便简单任务如此。
- Stanford 研究：检索文档堆到二十篇左右时，准确率明显下降，且答案落在上下文中段的文档最容易被忽略。
- **阈值效应**：超过最大窗口的某个比例后，准确率可能骤降而非渐变。
- 编码 Agent 尤其暴露：长任务周期累积大量干扰 token。

### 2. 上下文坍塌（Context Collapse）

定义：Agent **反复重写自己的上下文**时出现。每次重写趋向更简短、丢失领域细节，多次迭代后上下文被侵蚀，Agent 失去让它有用的具体知识。

- 与 rot 不同：rot 由上下文过长引起，collapse 由有损重写/摘要引起。
- 关键教训：**增量的、追加式的上下文更新优于整体重写**。

### 3. 工具与检索干扰（Tool & Retrieval Distraction）

太多工具或太多检索块挤占信号。不如 rot/collapse 出名，但在真实构建中同样常见。

- 每个暴露的工具定义都消耗 token 并增加干扰；臃肿的工具列表拉走注意力、抬高错误率。
- GeoEngine 基准：量化后的 Llama 3.1 8b 在 46 个工具时失败，19 个工具时成功。
- 规划数据库迁移的 Agent 不需要图像工具在它的上下文里。

## ACE：Agentic Context Engineering

arXiv 2510.04618，ICLR 2026。直面 context collapse，提出修复方案：

- 把上下文表示为**结构化的、逐条列举的 bullet 集合**，增量更新，而不是重写整块。
- 三个角色：**Generator（生成）**、**Reflector（反思）**、**Curator（管理）**，共同在一个演进的"剧本（playbook）"中添加和精炼条目——既保持细节又保持紧凑。
- 更广的启示：上下文是演进的、逐条的剧本，增量更新而非整体重写。

## 生产环境模式

> 生产上下文工程是**架构问题**，不是提示词调优问题。

### 1. 把窗口当预算

预先决定多少 token 给系统提示、检索、历史、工具，并强制执行。预算紧张时，**有意识地**压缩或丢弃某些内容，而非意外发生。

### 2. 建记忆层级（类似缓存层级）

| 层级 | 内容 | 存放 |
|---|---|---|
| **热** | 任务内即时状态 | 留在窗口 |
| **温** | 近期上下文 | 移到可压缩的摘要 |
| **冷** | 持久事实 | 推到长期存储，按需检索 |

### 3. 到极限前压缩，不是之后

在窗口填满**之前**摘要旧轮次，让 Agent 永不触及 rot 阈值。但要验证摘要保留了任务依赖的细节——简洁偏差正是 collapse 的成因。

### 4. 按阶段限定工具

只暴露与当前任务阶段相关的工具。

### 5. 把推理卸载到文件

让 Agent 写持久笔记并读回，使工作记忆跨压缩存活。这是**长运行 Agent 最可靠的单一升级**。

### 6. 在上下文增长下测试

用真实的大窗口规模评估，而非只在短 happy-path 输入上。多数 Agent 在 5,000 token 看着很好，80,000 token 就崩。不测长场景就是发布故障。

## 五种核心技术与权衡

| 策略 | 做什么 | 何时用 |
|---|---|---|
| **压缩 Compaction** | 用保留决策与约束的摘要替换详细历史 | 长对话，旧轮次不再重要但结论重要 |
| **外部记忆** | 把重要状态写到文件/数据库/草稿本，步进检索 | 必须超越单个上下文窗口的工作流 |
| **子智能体隔离** | 把聚焦任务交给独立上下文的子 Agent，只返回结果 | 中间推理会污染父 Agent 的多步工作 |
| **按需检索而非预加载** | 提供检索工具，需要时才取 | 大语料，每次决策只相关一小片 |
| **提示缓存** | 缓存稳定前缀（系统提示、工具、规则），动态尾部每轮重算 | 长周期 Agent 每轮重发相同上下文 |

Manus 把文件系统描述为"大小无限、天然持久、可直接操作的上下文"，输入:输出 token 比约 100:1。Anthropic 研究系统用子 Agent 隔离——每个子 Agent 以干净上下文开始，只返回简短摘要。

## 提示缓存的经济学反转

提示缓存对重复前缀的降本幅度取决于各家的计价规则：缓存读取通常显著便宜于新 token，同时改善首 token 时间；具体折扣以官方计价页为准，不要按单一比例做预算。

但缓存改变了一个判断：

- 摘要/转换上下文会改变 token 序列 → 缓存失效，转换后的 token 按全价计费。
- 有实验估算：在已有缓存折扣的前提下，压缩未必划算——压缩本身要再调用一次模型，省下的 token 可能抵不过这次调用，还不算质量损失。
- 在 AI 导师实验中，**保留完整历史**在召回、成本、延迟上均优于生产默认的压缩方案。
- 也有相反方向的研究（ByteIota）：提示缓存反转了经济学，主张默认不要压缩，保留完整历史直到窗口真的满；且指出长运行 Agent 存在"上下文惯性"——在 200K–300K token 处做**硬重置 + 显式状态交接**（新 Agent 继承代码库、环境和简短笔记，而非摘要），比压缩更能摆脱死胡同假设。

遇到障碍时应综合判断：缓存便宜时倾向保留；本地小窗口硬件必须用检索或压缩；关键决策是**检索什么、记住什么、丢弃什么**——这些始终属于构建 Agent 的团队。

### 缓存的反模式

把变化的工具结果放进稳定前缀 → 破坏缓存，使后面全部失效。正确做法：稳定前缀（系统提示、工具定义、规则）缓存，动态工具结果放在尾部。

## 六类战术（Breunig 归纳，跨三个时代不变）

1. **增强（Augmentation）**：RAG 与技能系统。
2. **工具装载（Tool loadout）**：过滤哪些工具出现——某企业团队发现每位工程师加载 600 个技能，选择性过滤解决了性能问题。
3. **隔离（Quarantine）**：子 Agent 以空白历史在共享环境工作。
4. **修剪（Pruning）**：移除不再相关的轮次（Claude Code 自动做）。
5. **摘要（Summarization）**：压缩成简报，但要先做相关性过滤。
6. **卸载（Offloading）**：把状态存文件和数据库，而非携带在上下文里。

与 2024 年的区别：这六类现在都**属于代码**，而非提示词指令。

## operational context：文档和日志之外

| 来源 | 能回答 | 不能回答 |
|---|---|---|
| Runbook / wiki | 写文档时的流程是什么 | 现在是否仍适用 |
| 工单历史 | 以前发生了什么 | 之后改了什么 |
| 遥测（Datadog/Grafana） | 被配置采集的告警、指标、日志 | 没人想到要埋点的值 |
| 运行上下文（实时证据） | 哪条路径跑了、某字段当时的值、什么变了 | 需要对运行系统的安全只读访问 |

行业调研普遍显示：多数工程负责人认为自家 Agent 对生产运行状态的可见性不足，几乎没有团队说自己完全看得见。不少用 AI SRE/APM 工具调查生产问题的案例，失败原因是执行级数据从未被采集。

## 写作原则（设计期决定大部分质量）

- **指令写在恰当的高度**：具体到能指导行为，又灵活到给模型强启发式。Runbook 解释决策规则，而不是 40 步脚本。
- **工具集最小化**：如果人都说不清某场景该用哪个工具，Agent 同样会挣扎。
- **让失败可见**：抹掉失败就移除了模型适应所需的证据。
- **闭环验证**：Agent 改了文件要重读、写了测试要运行、发了 API 要检查响应。可靠性来自"行动→观察→对照目标验证→纠错"，而非假设成功。
