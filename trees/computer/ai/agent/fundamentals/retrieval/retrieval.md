# 检索实现与 RAG

检索是把外部资料变成**模型能当场读到、事后能核对**的那一段上下文。它不只是"搜一下"：搜到的东西会占用窗口、会参与推理、会成为回答的依据，所以每个环节都在做"选什么进窗口"的决定。

## 一条检索链的六个环节

1. **查询构造**：把用户这句话变成可检索的查询。原始问句通常不适合直接检索——它含指代、含口语、含多意图。
2. **召回**：从索引里取候选，通常取几十到上百条，宁可多取。
3. **融合**：把多路召回的结果合成一个排序（关键词一路、向量一路，往往还要加元数据过滤）。
4. **重排**：用更贵的模型给候选重新打分，只留少数几条。
5. **组装**：把留下的片段拼进提示，附带来源标识与必要的上下文边界。
6. **回链**：回答里标注依据来自哪一段，让人能点回去核对。

第 1 步与第 4 步最容易被省略，也最影响效果：查询不改写，召回就靠运气；不做重排，前面的噪声会直接进窗口。

## 查询构造：先改写再检索

- **指代消解**：把"它""这个""上次那个"替换成具体对象，否则检索词里全是代词。
- **多意图拆条**：一句话里问了互不相关的两件事，拆成两条查询分别召回，再合并。
- **补全隐含条件**：用户只说"退款"，要补上产品线与地区限定，否则召回一堆无关政策。
- **假设性答案（HyDE）**：先让模型写一段"可能的答案"，用这段文本去检索。适合问句与文档措辞差异大的场景（用户口语问、文档术语写）。
- **术语归一**：把用户的口语映射到文档里的正式说法（"封号"→"账号封禁"），词表可以很小，但必须维护。

> 判断：查询改写是性价比最高的环节——它不改索引、不改模型，只改一两条提示，却能同时改善召回与重排的效果。检索效果差时先动这里，别先换向量模型。

## 混合召回：单一向量检索不够用

| 通道 | 擅长 | 明显失效的场景 |
|---|---|---|
| **关键词（BM25 一类）** | 精确词、编号、错误码、产品型号、专有名词 | 同义改写、跨语言、口语提问 |
| **稠密向量** | 语义相近、换一种说法、跨语言 | 罕见专名、编号、否定与限定条件 |
| **元数据过滤** | 时间、版本、租户、文档类型 | 无法表达语义相关性 |
| **结构化查询** | 精确聚合（"上季度华东退货率"） | 开放问答 |

融合的常用做法是**倒数排名融合（RRF）**：不看原始分数（两路分数不可比），只看各自排名，按 `1/(k + rank)` 累加。它简单、不需要调权重，适合先跑起来。

> 判断：只要语料里有编号、错误码、型号、法规条款号，就必须保留关键词通道。纯向量检索在这类查询上会稳定地漏掉最该命中的那一条。

## 重排与窗口预算

- **重排是"用贵模型做便宜筛选"**：召回几十条，用 cross-encoder 或小模型逐条打分，只留 3–8 条进窗口。
- **条数不是越多越好**：检索文档堆到二十来篇时，模型对中间位置内容的利用率明显下降（Lost in the Middle 的结论），首尾更有优势。
- **预算按任务定**：事实问答留 3–5 条；需要综合多份材料时留 8–10 条并做摘要；超过这个量，应该先压缩再进窗口。
- **截断要讲道理**：按段落边界截，不按字符数硬切；被截断的段落要标注"已截断"，否则模型会把半句当完整结论。

## 引用回链怎么做

- **片段级标识**：每段带 `doc_id#chunk_id`，回答里引用它，而不是只写文档名。
- **引用粒度与断言对齐**：一条结论对应一处引用；一句话里塞三个来源等于没有来源。
- **冲突要显式**：两份资料说法不一致时，回答里要指出"这里有两种口径"，而不是挑一个看起来合理的。
- **找不到就说不确定**：检索为空或分数过低时，允许回答"资料里没有"，比编一个更像答案的回答安全。
- **回链可达**：引用要能点回原文位置；只给文档首页链接，核对成本仍然很高。

## 检索够不够用的三个信号

不必等评测集，线上三个指标就能看出问题：

1. **空召回率**：查询有结果但重排后全被丢弃，说明查询与索引措辞对不上。
2. **引用密度**：回答里带引用的断言占比。长期偏低，说明模型在凭记忆答，检索只是摆设。
3. **重复召回**：同一段内容反复出现在不同查询里，通常是切分过碎或索引重复。

## 失败模式

| 症状 | 常见根因 | 对策 |
|---|---|---|
| 答非所问但语气笃定 | 召回错了却照样生成 | 低分时拒答；强制引用 |
| 关键词查不到 | 只有向量通道 | 加关键词通道与 RRF 融合 |
| 多跳问题答不全 | 只做单轮检索 | 按子问题拆查询，分轮检索并合并证据 |
| 上下文被塞满 | 召回条数过多、片段过长 | 重排后限量、按段落截断、先压缩 |
| 版本过期 | 索引未随文档更新 | 增量更新 + 文档版本元数据 + 失效标记 |
| 引用指向错段 | 片段 id 拼接错误或重排后未回填 | 引用随片段走，重排不得改写 id |

## 什么时候不需要 RAG

- 语料很小（几十页以内）且变化慢：直接放进系统提示，比维护索引便宜。
- 问题只需精确查询：给一个 SQL/API 工具，让模型自己查，比检索更准。
- 任务是生成而非回答：写作、改写不需要外部证据，检索只会引入噪声。
- 已经有高质量工具接口：能直接调接口拿事实，检索是绕远路。

## 一句话主线

检索工程的重心不在"用哪个向量库"，而在**查询怎么构造、候选怎么融合、留下的证据能不能被核对**：把这三步做对，换模型与换库的收益才显现。
