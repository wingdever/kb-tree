# Prompt 提示词工程

提示词工程已从"写 clever 提示"演化为一门软件工程学科——把提示词当代码：结构化格式、版本控制、测试、监控。对 Agent 而言，提示词是 harness 的一部分，但**很多事情不能靠提示词解决**（如权限、PII、合规），那些要靠中间件、工具与护栏。

判断一页提示词写得好不好，只看三件事：它约束了**形状**（输出能不能被程序消费）、管住了**预算**（token 花在哪、缓存能不能命中）、留下了**回归**（改了以后怎么知道没变差）。口吻与"聪明程度"排在后面。

## 推理技巧

| 技巧 | 适合的信号 | 代价 |
|---|---|---|
| 思维链（CoT） | 多步算术、逻辑、规划；中间量需要外部可见 | 输出变长，简单查找任务反而引入推理错误 |
| 自洽性（Self-Consistency） | 单一可验证答案，准确性优先于吞吐 | 采样 N 条链，成本线性上升 |
| 思维树（ToT） | 需要探索多条路径并剪枝的搜索型任务 | 多次调用 + 显式评估，工程复杂度高 |
| ReAct 式交错 | 需要边查边想、依赖外部信息 | 工具延迟进入关键路径，循环可能不收敛 |
| 宪法式自我批评 | 有明确可陈述的规则集，希望模型自查 | 多一轮生成，规则本身要维护 |

- **思维链**：zero-shot（"Let's think step by step"）或 few-shot 展示推理过程。在多步算术、逻辑、规划上明显提升；**在简单查找任务上有害**——多出来的推理步骤就是多出来的出错机会。
- **自洽性**：高温采样多条推理链，对最终答案多数决。GSM8K 上比单样本 CoT 高 17.9 分；代价是 N 倍 token，且只对"答案可比较"的任务有效。
- **思维树与搜索**：把候选推理状态当节点，显式打分、剪枝、回溯。收益在需要试错的题上，不在需要直答的题上。
- **ReAct**：推理与工具调用交错，每步观察回填上下文。它把"想"和"查"绑在一起，适合信息在外部、且不知道要查几次的任务。
- **宪法式 AI（Constitutional AI）**：定义原则 → 让模型批评自己的输出是否违反 → 修订。规则必须短、可判定，否则批评会退化成另一种风格意见。

> 重要：**扩展思考模型**（o 系列、Claude extended thinking、Gemini thinking）原生做逐步推理，别再加"think step by step"（冗余开销无收益）——用 `reasoning_effort` 等 API 参数控制思考深度。

> 判断：推理技巧是**按题分配**的，不是全局默认。同一套系统里，分类节点不需要思维链，规划节点需要；把"请一步步思考"塞进所有节点，等于给简单任务加错误率、给所有任务加账单。

## 系统提示结构

- **保持精炼**：150–300 词起步。超过 3000 token 注意力明显稀释；只在出现具体失败模式时才加规则，一条规则对应一个真实事故。
- **注意边界**：注意力在上下文首尾最强——核心指令与静态规则放开头，动态数据放中间，关键执行指令放末尾。长上下文里中段内容最容易被忽略。
- **四块结构**：角色/目标 → 约束 → 上下文/数据 → 任务指令（末尾）。四块的顺序不要随手改，它是位置效应与缓存前缀共同决定的。
- **正面表述优于否定**："别用要点 jargon" 让模型先处理被禁概念（粉红大象问题）→ 改写成"用连续段落、清晰易懂的术语"。
- **XML 标签分隔**：用 `<context>`、`<rules>` 等显式分隔组件，防注入、防上下文串味、帮模型解析动态载荷。OWASP LLM Top 10 把提示注入列为 #1 风险。

三类内容不要混在同一段里：**身份与目标**（长期稳定）、**行为规则**（较少变动）、**本次任务数据**（每次都变）。混在一起既难维护，也会让缓存前缀每次失效。

> 判断：规则数量与遵循率不是线性关系。十一条并列规则里，模型通常只会稳定执行前几条和最相关的几条；与其加第十二条，不如把重复出现的失败合并成一条可判定的规则，或干脆交给代码校验。

## 提示管不了什么

提示词是"偏好与口吻"的杠杆，不是"能不能做"的开关。四类事情必须由提示词之外的东西承担：

| 要保证的事 | 该由谁负责 |
|---|---|
| 不许调某类工具、不许读某类数据 | 权限与工具白名单（执行层拒绝） |
| 输出能被程序解析 | JSON Schema / 结构化输出 API + 解析器 |
| 事实与数值正确 | 检索、工具返回值、对源数据校验 |
| 一定不泄漏 PII、一定合规 | 中间件、脱敏与策略引擎 |
| 每一步一定按某个顺序走 | 代码编排，不是"请严格按步骤" |

把"请不要"写成提示词，得到的是一句期望；写成执行层拒绝，得到的是一条约束。两者都要有，但不能互相替代。

## 结构化输出

不要靠"返回 JSON"的自然语言请求——相当一部分调用会失败并破坏下游解析器。做法：用 Pydantic/Zod 定义精确 schema，再用 provider 的 structured output API（OpenAI response_format + JSON schema、Anthropic tool definition）。**JSON mode 只保证语法有效，strict structured output 才约束形状**；两者都不证明提取值真实，要对源数据校验。

解析失败按四类分开处理，别一律重试：

- **截断**（超 max_tokens）→ 提高上限或让模型先说结论再补细节，重试同一提示通常还是截断。
- **前后有多余文字** → 提示里明确"只输出对象"，或直接用 strict 模式。
- **字段缺失/多字段** → schema 太宽或必填项太多，收窄 schema 比加提示词有效。
- **类型或枚举越界** → 给枚举而不是自由字符串，并在提示里列全合法值。

Repair 循环要有上限：带错误信息重试 1 次，仍失败就降级（走默认值、转人工、返回上一节点的原始文本），不要让 repair 无限递归吃掉预算。流式场景下 JSON 不是逐 token 可用的，要等完整对象或按事件协议分片。

## 示例怎么选

few-shot 的收益几乎全来自"例子选得对不对"，与数量关系不大：

- **按失败模式选例**，不是按"典型输入"选。想修的错是格式，就给格式边界例；想修的错是漏字段，就给字段最全的例。
- **3–8 条**足够。再多通常只是把上下文变长、把缓存前缀变贵；如果还在变差，问题多半在指令而非例子数量。
- **示例必须与 schema 一致**。示例里出现的字段、格式、口吻会被模型当契约照抄；示例写错了，schema 拦不住语义。
- **正例 + 反例**。反例要标注"为什么错"，只贴一个错误输出会让模型学成"另一种风格"。
- **警惕示例污染**：示例里带真实日期、真实品牌、真实人名，模型会把这些当默认值带进新输入；示例里的捷径（比如恰好一步算出）也会被照搬。
- **动态示例**按输入相似度检索，能提升边缘输入的表现，但要防"照抄示例"——相似度太高时模型会复用示例的答案结构而不看当前输入。

## 上下文预算与缓存

- **静态前缀在前，动态内容在后**。人格、业务规则、固定 schema、长 few-shot 都属于前缀；用户输入、检索结果、时间戳放后面。
- **缓存命中的前提是前缀逐字节一致**。在开头插一个日期、一个会话 id、一个随机排序的工具列表，后面全部失效——这类"顺手加的元信息"是缓存最常见的杀手。
- Anthropic 缓存 token 收正常输入价的 10%（省 90%），OpenAI 收 50%（省 50%）。对大文档 + 多次调用（仅用户输入变化）价值最大；一次性调用没有意义。
- **长文档先摘要再拼**，不要整篇塞进上下文。摘要在离线或缓存阶段做，把稳定的摘要放前缀，把需要原文核对的片段放末尾。
- **预算要给每个节点**，不是给整条链路。单节点超预算就截断检索结果、降 few-shot 数量，而不是让某个节点悄悄吃掉整条链路的余量。

## 版本与回归

- **提示版本控制**：存 Git，语义化版本（major=格式破坏、minor=新特性、patch=措辞），带元数据（model/temperature/max_tokens），维护 changelog。
- **A/B 测试**：明确成功指标，流量均分，每变体 500+ 样本达统计显著。指标要先定，改完再找指标等于自证。
- **评估驱动**：建 50–100 条代表性输入的 golden set + ground truth，每次提示改动跑自动回归（LLM-as-judge 或规则）。Stage 2→3（加质量指标与 A/B）是投入回报最大的跃迁；Stage 4（DSPy 自动优化）需要稳定评估标准 + 50+ 标注样例 + 高量重复。
- **提示漂移监控**：模型版本升级、上下文变长、工具列表变动都会改变行为。上线后持续抽样比对输出分布，比上线前的一次评估更能发现问题。
- **失败样本回流**：线上失败对话转成回归用例，标注"错在哪一步"而不是只标"整体错"，否则修复只能靠猜。

## 常见失败模式

| 失败 | 症状 | 处置 |
|---|---|---|
| 规则堆叠 | 规则越多越不遵守，前后冲突 | 合并成可判定规则，其余交给代码 |
| 用提示做权限 | 模型"答应不调"，偶尔还是调 | 执行层白名单拒绝 |
| schema 有形状无真值 | 解析全过，数值是编的 | 对源数据校验，或改成抽取+工具 |
| 缓存不命中 | 成本曲线无故上扬 | 检查前缀是否逐字节稳定 |
| 示例过拟合 | 新输入被套成示例形状 | 减例子、换按失败模式选例 |
| 中段丢失 | 长上下文里的关键约束被忽略 | 关键约束前置或重复在末尾 |
| 模型升级后行为漂移 | 同一提示输出风格突变 | 版本固定 + 回归集 + 漂移监控 |

## 技术选择七问

1. 任务有单一可验证正确答案？→ Self-Consistency。
2. 涉及空间关系/逻辑依赖？→ Chain-of-Symbol。
3. 生产运行 >500 次？→ 投资 DSPy 编译。
4. 成本是硬约束？→ 低 reasoning effort + zero-shot。
5. 需探索多解路径？→ ToT（收益抵得上成本时）。
6. 给便宜模型生成提示？→ 用前沿模型 Meta-Prompting。
7. 输出格式不稳定？→ 加显式 schema + 角色约束。

## 自检清单

1. 这段提示约束的是形状、预算，还是口吻？三者的手段不同，别混着写。
2. 每条规则能否对应一个真实失败模式？对应不上的删掉。
3. 前缀是否逐字节稳定、缓存能否命中？
4. 输出是否由 schema 约束，失败四类是否有各自的处置？
5. 有没有哪条规则其实该由权限、工具或校验承担？
6. 改动之后，跑的是哪一套回归集？

## 一句话主线

提示词不是"把话说清楚"，而是**把不确定性收进可验证的形状**：能交给代码判的交给代码，剩下必须由语言表达的，才写成规则、示例与结构化契约。
