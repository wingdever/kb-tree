# 工作流（Workflow）

工作流是确定性 DAG——节点、分支、转移在开发期固定，LLM 只是其中一个处理节点，**不控制流程**。可配置节点如 text2sql（自然语言转数据库查询）、translate（翻译）等。

确定性的真正含义不是"代码写死的"，而是**给定同一输入与同一外部状态，走同一条路径**。这条性质换来三样东西：可复现、可审计、成本可预算——也正因为这三样，工作流撑得住正式的生产与 ToB 交付。

## 本质分界线：谁决定下一步

- **Workflow**：流程由开发者/代码预写 → 固定 DAG、分支预配置、结果可复现、易审计。
- **Agent（ReAct）**：运行时控制权交给 LLM → 动态生成路径、目标驱动自主探索、不可预测。

标签滥用是 2026 的普遍问题："用了 LLM 的多步工具链"未必是 Agent。用**确定性光谱**思考更清晰：

| 阶段 | 形态 | 特点 |
|---|---|---|
| 1 | 确定性代码 | 无 LLM，路径固定、输出可复现、成本有界 |
| 2 | AI 增强工作流 | 固定管线 + 若干 LLM 节点，LLM 做窄而受限的工作 |
| 3 | 含 Agent 节点的工作流 | 编排仍确定性（人画图），某些节点有能动性——**多数生产"多 Agent"实在此阶段** |
| 4 | 自主 Agent | 模型自己决定编排，路径运行时涌现 |
| 5 | 多智能体系统 | 多个自主 Agent 协调，交接、共享状态、涌现行为 |

> 判断：阶段 1/2 易治理，阶段 4/5 易扩展；没有全局正确答案，只有针对具体问题的答案。选阶段的依据是"中间步骤能不能在开发期列出来"，不是"哪个听起来更先进"。

## 工作流的四个要素

一张能跑起来的工作流图，必须把四件事都写死，缺一件就会在线上以意外形式补回来：

| 要素 | 要写死什么 | 缺失后的表现 |
|---|---|---|
| 节点 | 输入输出 schema、超时、重试策略、模型与温度、成本上限 | 某个节点悄悄变慢或变贵，链路整体劣化 |
| 边 | 条件表达式、默认分支、最大跳数 | 条件不覆盖时流程卡死或走错分支 |
| 状态 | 哪些字段跨节点传递、谁可写、schema 版本 | 节点之间靠约定传字段，改一个就崩一串 |
| 契约 | 失败如何上报、重试几次、能否补偿、何时转人工 | 失败被吞掉，或重试把副作用放大了几倍 |

图本身是代码：进版本控制、有测试覆盖、改动走评审。旁挂一份画在文档里的图而不维护代码里的图，两边迟早不一致。

## 节点契约

节点是工作流里唯一可以"出错并被定位"的单位。一个节点该带的字段：

- **输入 schema 与输出 schema**：下游只读 schema 字段，不读自然语言句子。
- **超时**：按 P99 的 2–3 倍设，不是按平均值。超时后进入失败分支而不是继续等。
- **重试策略**：只对瞬时错误重试（限流、超时、5xx），指数退避 + 抖动；确定性错误（schema 不符、参数非法）重试无意义。
- **幂等性声明**：这个节点有没有外部副作用、幂等键是什么。没声明过的节点默认不可重试。
- **成本上限**：token 与调用次数上限，超限降级或转人工，避免一个节点吃光整条链路预算。
- **失败语义**：抛出什么类型的错误、下游据此走哪条边。

提示词属于节点配置，随节点版本一起走：改了提示等于改了节点行为，要跑该节点的回归用例，而不是跑整条链路碰运气。

> 判断：节点粒度以"失败能归因"为准。一个节点里塞了检索、改写、生成三件事，线上出错时无法判断是哪一步；拆成三个节点，代价是多几次编排开销，换来的是可定位。

## 分支怎么判

路由是工作流里最容易退化的地方——一开始是 `if`，半年后变成一张靠自然语言猜的规则表。

- **能用代码判的不用模型**：字段是否存在、数值是否超阈值、枚举是否命中、上游是否返回空结果。这类判断写成表达式，成本为零且可测。
- **必须模型判时，做成分类器节点**：封闭标签集（不给自由文本）、低温度、输出"标签 + 一句理由"、标签之外一律落到默认分支。
- **默认分支必须有**：任何分类器的输出都要有兜底边，否则新出现的输入类型会直接卡住流程。
- **分支数量设上限**：超过 5–6 个并列分支时，改成配置表驱动（一张 `条件 → 目标节点` 的表），代码只负责查表，不再堆 `if/elif`。
- **条件写在边上，不写在节点里**：节点只产出结构化字段，由边决定去哪。节点内部偷偷决定下一步，等于把 DAG 变成了隐式状态机。

一个典型的分支设计：上游抽取节点输出 `doc_type`（枚举四类）+ `confidence`；边按 `doc_type` 分流，`confidence < 阈值` 或枚举外的值走"人工复核"边。整条规则可以用三个表达式写完，也能写单测。

## 重试、补偿与部分失败

工作流真正的难点不是成功路径，而是"做了一半失败了"：

- **幂等键先于重试**。写外部系统（下单、发消息、建工单）必须带幂等键；没有幂等键的重试是在制造重复副作用。
- **重试只解决瞬时错误**。超时、限流、连接重置可以重试；业务拒绝（余额不足、参数非法）重试只会重复失败并放大账单。
- **不可撤回的副作用用补偿**，不是重试。已经扣了款、发了消息、建了记录，后续节点失败时要走补偿节点（退款、撤回、作废），按反向顺序执行。
- **检查点续跑**。长流程在每个节点完成后落一次检查点（节点 id + 输出 + 时间），恢复时从最后一个成功节点继续，而不是从头重跑整条链路。
- **部分成功要显式表达**：批量任务里 8 条成功 2 条失败，输出应是"成功列表 + 失败列表 + 失败原因"，而不是一个笼统的失败状态。

> 判断：补偿逻辑的复杂度与外部副作用数量成正比。工作流里每多一个"对外写入"节点，就要多一条补偿路径；能推迟到最后一步统一写入的，就别在中途分散写。

## 人工门放在哪

人工门不是"多加一个确认"，而是把不可逆的决策挪到人手里。该设门的边有四类：

1. **写外部系统**：改客户记录、发对外消息、建合同、动账。
2. **花钱**：下单、退款、超额调用付费 API。
3. **改权限**：授权、提权、共享数据范围。
4. **不可撤回的对外沟通**：群发、公告、对外报价。

门要显示的不是一句"是否继续"，而是决策所需的最小证据集：**提议的动作**（将要调什么、写什么）、**依据**（上游输出与引用片段）、**变更 diff**（改前/改后）、**影响范围**（涉及多少条记录、哪些对象）、**超时策略**（不处理时是阻塞、自动拒绝还是转交）。

- 门是阻塞点，工作流停在边上等人，不做"先跑完再补审批"。
- 审批结果要落成结构化字段（批准/拒绝/修改后批准），下游按字段分支，不靠自然语言解读。
- 拒绝要带原因，原因回流成分类器与提示的改进依据。

> 判断：门的密度与流程可信度成反比。处处设门会让审批人形成"无脑通过"的肌肉记忆，反而降低整体安全性；只在不可逆的边上设门，其余用可回滚的自动动作。

## 何时用工作流

流程标准化、步骤可完全列出、要求高稳定性：简历筛选、批量文档解析、数据清洗、审批流、固定格式报告、固定 RAG 问答链、标准客服回复管线。优势：成本稳定、易灰度、异常监控简单、适合正式 ToB 生产。

**"多步陷阱"**：5 步 ETL 永远是工作流，绝不应该是 Agent——Agent 用于中间步骤无法预先确定的任务。

每次调用成本：工作流比 Agent 便宜约 5–10×（不需要每步重复 LLM 调用），所以**即使多步任务也先从工作流起步，遇到需要适应的边缘情况再加 Agent**。

选型时可以按四个问题打分：

| 问题 | 偏工作流 | 偏 Agent |
|---|---|---|
| 中间步骤能否在开发期列全 | 能，且稳定 | 不能，随输入变化 |
| 边缘情况占比 | 低，可枚举并单独分支 | 高，无法预先分类 |
| 审计与合规要求 | 强，需要逐步可解释 | 弱，结果导向 |
| 失败代价 | 高，必须可回滚可复现 | 可接受重试与重来 |

## 何时用 Agent

只能定义最终目标、无法预先预测完整步骤：市场调研、多维数据分析、旅行规划、代码排障、开放式研究、需自由组合多工具持续收集信息推理。

判断标准不是任务"看起来复杂"，而是**路径是否真的无法在开发期确定**。一个每次都要走同样五步的"复杂任务"，仍然是工作流。

## 企业最佳实践：混合架构

**Workflow 做骨架，Agent 做局部节点的大脑**：

- 外层 Workflow 建立业务边界、主流程、异常捕获、人工兜底，保证全局可控。
- 把 Agent 嵌入流程内需要灵活推理的复杂子节点；Agent 只在指定范围自主探索，不突破整体框架。
- 例：智能竞品分析——外层固定流程"拉数据 → [Agent 竞品挖掘分析节点] → 报告模板填充 → 推送"，仅在"信息挖掘"子节点允许 Agent 自由调用搜索与统计工具，任务的起止、输出规范、超时都由外层控制。

嵌入 Agent 节点时，外层必须给它三样东西：**范围**（可用的工具与数据边界）、**预算**（步数与 token 上限）、**出口**（输出 schema 与超时后的降级值）。缺任何一样，Agent 节点都会成为整条链路里唯一不可预算的部分。

多数业务流程 80% 是固定管线、20% 是开放推理——只在那 20% 嵌入 Agent 是落地实战路径。

## 温度与架构协同

- Workflow 场景（严谨业务）低温 0.1–0.3，稳定统一输出、减少随机波动。
- Agent 场景谨慎升温——Agent 本就动态决策，过高随机性易诱发幻觉与无效循环。
- 具体到节点：分类与抽取用 0–0.2，结构化改写 0.2–0.4，创意与多方案生成 0.7 以上。
- 温度是**节点参数**，不是架构变量。用温度去弥补流程设计缺陷（比如靠升温让模型"更灵活地"处理没覆盖的分支），只会把不可复现引进来。

## 可观测与回放

- 图确定性 → 每次运行可复现，存精确提示、响应、工具调用、分支、耗时与 token。
- **成本归因到节点**：每个节点的 token 与调用次数单独记账，才能回答"这条链路为什么贵"。
- **延迟定位到边**：节点耗时与排队耗时分开记，边上的等待（尤其人工门）常是长尾来源。
- **失败可重放**：给定记录下来的输入与外部响应，能重跑出同一条路径；重放不一致说明某处有未记录的隐式依赖（当前时间、随机数、未落盘的外部状态）。
- 每次事故都该沉淀成一条回归用例，而不只是修一次代码。

## 工程要点

- **先画图再写提示**：每个流程在 LLM 介入前先映射为节点与边的有向图。节点是固定 schema 的 LLM 调用、固定契约的工具调用、或人工门；边是上游输出的 condition。
- **每个 LLM 节点约束输出**：绑定 JSON Schema 的结构化输出；下游分支读 schema 字段而非自然语言句子。输出畸形时同一节点带 repair 提示重试。
- **节点不要巨型化**：一个节点一件事，失败可归因；需要"顺手做点别的"时，宁多加一个节点。
- **LLM 真正挣得价值的场景**：流程本身开放、设计图成本高于运行 Agent 成本（研究、探索式数据分析、一次性信息收集）。

## 常见失败模式

| 失败 | 症状 | 处置 |
|---|---|---|
| 双图不一致 | 文档里的图与代码里的图各说一套 | 图由代码生成或图即代码，改动走评审 |
| 自然语言路由 | 分支条件写在提示里，靠模型"判断" | 改成分类器节点 + 表达式分支 + 默认边 |
| 重试放大副作用 | 一次下单变成三次 | 幂等键 + 只重试瞬时错误 + 补偿路径 |
| 节点巨型化 | 报错无法定位到具体步骤 | 拆分节点，按失败归因定粒度 |
| 失败被吞 | 上游失败下游照常跑，产出半成品 | 失败态显式传递，部分成功单独表达 |
| 人工门泛滥 | 审批人无脑通过 | 只在不可逆边上设门，其余自动可回滚 |
| 无检查点 | 长流程失败必须从头重跑 | 每节点落检查点，从最后成功点恢复 |

## 落地顺序

1. 把流程画成图，标出每个节点的输入输出与副作用。
2. 给每个节点定 schema、超时、重试与幂等声明。
3. 把能用代码判的分支全部代码化，剩下的才做分类器节点。
4. 在不可逆的边上加人工门，写清证据集与超时策略。
5. 接上检查点、成本与延迟记账，再用真实流量跑一轮灰度。

## 一句话主线

工作流的价值不在"用了 LLM"，而在**把每一步的可预测性买回来**：路径、形状、成本、失败后的退路都在开发期定好，LLM 只在被划定的小格子里做它擅长的事。
