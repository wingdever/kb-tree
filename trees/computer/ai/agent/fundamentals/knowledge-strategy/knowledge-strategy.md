# 知识与记忆方案：什么时候用哪个

> 本页回答一个决策问题：面对具体需求，该把信息放在哪里——模型权重、上下文、外部系统、检索索引、记忆存储，还是只做成本优化。只给选型依据，不展开机制；入口指向细节。

## 方案全景

| 方案（信息所在） | 适合 | 时效 | 可溯源 | 更新成本 |
|---|---|---|---|---|
| 模型参数知识（权重） | 训练截止前已学到的常识与能力 | 静态 | 无 | 极高，需重训 |
| 提示词 / 长上下文（窗口） | 少量稳定、无需溯源的当前上下文 | 即时 | 弱 | 极低 |
| 工具 / API 实时查询（外部系统） | 数据已在外部系统且要求实时 | 跟随上游 | 取决于上游 | 低，无索引 |
| RAG（检索索引） | 海量外部事实、需要引用溯源与权限隔离 | 索引可更新 | 强，可返回来源 | 中，需维护索引 |
| 检索即工具（索引，按需调用） | 让 Agent 自己决定何时检索 | 同 RAG | 同 RAG | 同 RAG |
| Text-to-SQL / 语义层（数据库） | 结构化数据、受治理的确定性指标 | 随库更新 | 强，SQL 与指标定义可查 | 中 |
| 知识图谱 / GraphRAG（图） | 跨文档实体关系与多跳推理 | 图更新慢 | 强，路径可追溯 | 高 |
| 共享本体 / 语义契约（规范） | 跨 Agent 的稳定命名、含义与动作边界 | 演进需审核 | 强，定义可版本化 | 中高 |
| LLM Wiki（编译制品） | 知识要积累、每个声明可见来源与纠错 | 一次编译、增量维护 | 强，带来源与编辑历史 | 中 |
| 持续预训练 / 全量微调（权重） | 把新知识系统写入模型 | 极慢 | 无 | 极高 |
| SFT / LoRA（权重） | 输出风格、格式、行为与拒答边界 | 中等 | 无 | 中，需样本 |
| 项目约定文件（仓库） | 编码 Agent 的长期项目约定 | 随文件改 | 中，Git 历史 | 低 |
| 持久化记忆库（记忆存储） | 用户偏好、稳定事实跨会话留存 | 即时写、按需召回 | 弱到中 | 中，需治理 |
| 检查点 / 状态持久化（运行存储） | 长运行失败恢复、人工交接 | 每次运行写 | 中 | 低 |
| ACE 增量上下文更新（会话） | 长时间运行中的上下文维护 | 追加式 | 中 | 低 |
| 技能 / 程序性记忆（文件） | 重复工作流、可复用的操作知识 | 随技能文件改 | 中 | 低 |
| 多 Agent 交接（传递） | 上下文与共享状态在 Agent 间流转 | 按交接写 | 弱 | 中，需信任边界 |
| 反思沉淀（轨迹） | 从执行轨迹自评、修正、积累 | 按运行积累 | 中 | 中，需评估信号 |
| 上下文缓存（服务端） | 重复前缀的成本优化 | 自动 | 无 | 低 |

缓存只改变成本，不改变模型知道什么；它叠加在其它方案上，不占一个「知识来源」的位置。

## 决策路径

按顺序问，遇到匹配项即停：

1. **要改的是行为还是补事实？** 行为、格式、语气、拒答边界 → SFT / LoRA。补事实 → 下一问。
2. **事实存在哪里？** 结构化数值与指标 → Text-to-SQL / 语义层；跨实体关系与多跳推理 → 知识图谱 / 共享本体；非结构化文档 → 下一问。
3. **是否已在外部系统且要求实时？** 是 → 工具 / API；否 → 下一问。
4. **要不要可溯源与长期积累？** 要即时溯源 → RAG；要跨会话积累成可读制品 → LLM Wiki；只要少量当前上下文 → 提示词 / 长上下文。
5. **要不要跨会话留住东西？** 稳定事实与偏好 → 记忆库；长运行恢复 → 检查点；重复工作流 → 技能；上下文易坍塌 → ACE。
6. **前缀是否高度重复？** 是 → 在已选方案上叠加上下文缓存，不替换上面的选择。

## 典型组合

方案之间通常是叠加关系，不是单选：

- **客服问答**：RAG（产品文档）+ 工具（实时查订单）+ 记忆库（用户偏好）+ 缓存（重复系统提示）。
- **编码 Agent**：项目约定文件 + 工具（文件与命令）+ 技能（重复工作流）+ 检查点（长任务恢复）；事实性语料少用 RAG。
- **企业分析**：语义层 / Text-to-SQL（算得准）+ 共享本体（含义一致）+ 图（关系追问）。
- **长运行研究**：LLM Wiki（知识沉淀）+ 检索即工具（Agent 自决检索）+ ACE（上下文维护）+ 反思沉淀（从轨迹改进）。

## 选型陷阱

- 把微调当成动态知识注入——知识会过时且更新昂贵，微调的主场是行为与格式。
- 把长上下文当成检索的替代品——成本、规模、延迟、上下文腐烂四个维度同时吃亏。
- 把记忆库当成训练——向量检索只是语义召回，不会改变模型权重。
- 不断加工具和检索块——干扰会挤占信号、抬高错误率。
- 把一次性问答做成 Wiki——没有持续维护者的语料，编译制品会退化为过期笔记。
- 把缓存当成知识方案——命中率再高也只是少付重复前缀的钱。

## 验证选型

- 检索质量 → RAG Triad、四层评估方案。
- Agent 行为 → 三层评估与 LLM-as-judge。
- 记忆是否引入污染 → 记忆治理与相关性召回。
- 成本是否真降 → 用 `usage` 字段核对缓存命中与 token 计费。

## 一句话主线

**先问信息放在哪里，再按时效、可溯源与更新成本取舍；方案通常叠加而非互斥，选完还要用评估验证。**
