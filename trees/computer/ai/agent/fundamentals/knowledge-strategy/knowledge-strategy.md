# 知识与记忆方案：什么时候用哪个

> 本页回答一个决策问题：面对具体需求，该把信息放在哪里——模型权重、上下文、外部系统、检索索引、记忆存储，还是只做成本优化。只给选型依据，不展开机制；入口指向细节。

## 方案全景

| 方案（信息所在） | 适合 | 时效 | 可溯源 | 更新成本 |
|---|---|---|---|---|
| 模型参数知识（权重） | 训练截止前已学到的常识与能力 | 静态 | 无 | 极高，需重训 |
| 提示词 / 长上下文（窗口） | 少量稳定、无需溯源的当前上下文 | 即时 | 弱 | 极低 |
| 工具 / API 实时查询（外部系统） | 数据已在外部系统且要求实时 | 跟随上游 | 取决于上游 | 低，无索引 |
| RAG（检索索引） | 海量外部事实、需要引用溯源与权限隔离 | 索引可更新 | 强，可返回来源 | 中，需维护索引 |
| 检索即工具（索引，按需调用） | 让 Agent 自己决定何时检索 | 同 RAG | 同 RAG | 同 RAG |
| Text-to-SQL / 语义层（数据库） | 结构化数据、受治理的确定性指标 | 随库更新 | 强，SQL 与指标定义可查 | 中 |
| 知识图谱 / GraphRAG（图） | 跨文档实体关系与多跳推理 | 图更新慢 | 强，路径可追溯 | 高 |
| 共享本体 / 语义契约（规范） | 跨 Agent 的稳定命名、含义与动作边界 | 演进需审核 | 强，定义可版本化 | 中高 |
| LLM Wiki（编译制品） | 知识要积累、每个声明可见来源与纠错 | 一次编译、增量维护 | 强，带来源与编辑历史 | 中 |
| 持续预训练 / 全量微调（权重） | 把新知识系统写入模型 | 极慢 | 无 | 极高 |
| SFT / LoRA（权重） | 输出风格、格式、行为与拒答边界 | 中等 | 无 | 中，需样本 |
| 项目约定文件（仓库） | 编码 Agent 的长期项目约定 | 随文件改 | 中，Git 历史 | 低 |
| 持久化记忆库（记忆存储） | 用户偏好、稳定事实跨会话留存 | 即时写、按需召回 | 弱到中 | 中，需治理 |
| 检查点 / 状态持久化（运行存储） | 长运行失败恢复、人工交接 | 每次运行写 | 中 | 低 |
| ACE 增量上下文更新（会话） | 长时间运行中的上下文维护 | 追加式 | 中 | 低 |
| 技能 / 程序性记忆（文件） | 重复工作流、可复用的操作知识 | 随技能文件改 | 中 | 低 |
| 多 Agent 交接（传递） | 上下文与共享状态在 Agent 间流转 | 按交接写 | 弱 | 中，需信任边界 |
| 反思沉淀（轨迹） | 从执行轨迹自评、修正、积累 | 按运行积累 | 中 | 中，需评估信号 |
| 上下文缓存（服务端） | 重复前缀的成本优化 | 自动 | 无 | 低 |

缓存只改变成本，不改变模型知道什么；它叠加在其它方案上，不占一个「知识来源」的位置。

这张表容易被读成"越往下越高级"，其实不是。**表里每一行都对应一个不同的信息所有者**：权重归训练方，上下文归本次会话，外部系统归业务方，索引归维护团队，记忆库归产品，检查点归运行时。选型的本质是选"谁负责让这份信息保持正确"。

## 五个取舍维度

方案之间的差异，可以归到五个维度上。前三个决定"能不能用"，后两个决定"养不养得起"：

| 维度 | 怎么量 | 常见误判 |
|---|---|---|
| 时效 | 数据多久变一次、能容忍多久过期 | 用微调解决"每周更新的政策文档" |
| 可溯源 | 是否需要给出处、能否回到原始片段 | 用长上下文做合规问答，答案无出处 |
| 一致性 | 同一问题在不同会话是否必须同答 | 用记忆库承担"权威口径"，各会话越答越散 |
| 更新成本 | 一次内容变化需要动几个人、几套流水线 | 低估索引重建与评测回归的连带成本 |
| 治理与权限 | 谁能读、谁能改、谁能删、如何审计 | 把全公司文档塞进一个索引，权限靠提示词约束 |

> 判断：多数选型失败不是选错了方案，而是**没指定信息所有者**。索引没人重建、记忆没人清理、语义层没人复核口径，方案本身再好也会在三个月内退化成过期缓存。

## 决策路径

按顺序问，遇到匹配项即停：

1. **要改的是行为还是补事实？** 行为、格式、语气、拒答边界 → SFT / LoRA。补事实 → 下一问。
2. **事实存在哪里？** 结构化数值与指标 → Text-to-SQL / 语义层；跨实体关系与多跳推理 → 知识图谱 / 共享本体；非结构化文档 → 下一问。
3. **是否已在外部系统且要求实时？** 是 → 工具 / API；否 → 下一问。
4. **要不要可溯源与长期积累？** 要即时溯源 → RAG；要跨会话积累成可读制品 → LLM Wiki；只要少量当前上下文 → 提示词 / 长上下文。
5. **要不要跨会话留住东西？** 稳定事实与偏好 → 记忆库；长运行恢复 → 检查点；重复工作流 → 技能；上下文易坍塌 → ACE。
6. **前缀是否高度重复？** 是 → 在已选方案上叠加上下文缓存，不替换上面的选择。

这套顺序有意把"最便宜的方案"放在后面才排除：先确认不能用轻方案，再上重的。反过来问（"我们有向量库，能用在哪"）几乎总会得到一个过度设计的答案。

## 迁移路径

方案是可以按成本升级的，不必一次到位。一条常见的爬坡路线：

1. **提示词里写死事实** —— 量小、变化慢、错了也不致命。上线最快。
2. **改成工具/接口查** —— 事实在业务系统里、要求实时、需要权限隔离。这一步通常比建索引便宜。
3. **加检索索引** —— 文档量大、需要引用与片段级溯源、需要按权限过滤。
4. **加结构化层** —— 数值类问题要算得准，改成语义层或 SQL，而不是让模型读表格。
5. **加记忆与沉淀** —— 出现跨会话的偏好、重复踩坑、知识需要积累时才做。
6. **动权重（SFT / LoRA）** —— 只在行为、格式、拒答边界需要系统性改变时。

每一步的触发条件应该写成可观测信号：检索命中率长期偏低、答案无出处被投诉、同类问题每周重复、口径不一致被审计指出。没有信号就升级，等于用工程预算买心理安慰。

## 成本与延迟的量级

不同方案的成本结构完全不同，混着比"贵不贵"没有意义：

- **上下文**：按 token 线性计费，随对话长度增长；延迟随输入长度上升，且长上下文的中段信息更容易被忽略。
- **检索索引**：一次性建库 + 持续增量，查询侧按 token 计费但量小；延迟多一跳检索，通常几十到几百毫秒。
- **工具/接口**：几乎不耗 token，成本与延迟由上游系统决定，瓶颈常在限流与权限。
- **语义层/图**：查询便宜且可缓存，贵在建与维护（口径评审、实体对齐、图更新）。
- **微调**：一次性训练成本高，推理成本可能更低；但每次数据变化都要重训+回归，隐性成本在流程上。
- **记忆库**：写入便宜，贵在治理——错记忆会长期污染，且很难归因到某次写入。

> 判断：缓存与检索优化的收益都有上限，真正的成本杠杆通常不在"再省一点 token"，而在"少让模型做它不该做的事"——把确定性计算交给 SQL、把固定流程交给代码。

## 治理与失效

每种方案都有它特有的腐烂方式，选型时就该把"怎么发现它坏了"一起定下来：

| 方案 | 典型失效 | 早期信号 |
|---|---|---|
| RAG 索引 | 文档更新但索引没重建，检索到旧版 | 答案引用日期早于文档更新日 |
| 记忆库 | 错记忆被反复召回，越用越偏 | 同一用户多次纠正同一事实 |
| 语义层 | 指标口径变更未同步，数值对不上 | 同一指标在不同报表差一位 |
| 知识图谱 | 实体逐渐重复、关系过期 | 同一实体多个别名并存 |
| LLM Wiki | 无人维护，编译制品退化为过期笔记 | 页面更新日期停滞 |
| 技能文件 | 环境变化后步骤失效 | 按技能执行连续失败 |
| 上下文缓存 | 前缀被无关信息污染，命中率骤降 | 成本上升但流量未变 |

治理的最小配置是三件事：**负责人**（谁在内容变化时动手）、**复核节奏**（多久抽查一次）、**删除路径**（发现错误时如何撤回而不是覆盖）。第三件最常被漏掉——只增不删的索引与记忆，最终都会变成噪声源。

## 典型组合

方案之间通常是叠加关系，不是单选：

- **客服问答**：RAG（产品文档）+ 工具（实时查订单）+ 记忆库（用户偏好）+ 缓存（重复系统提示）。
- **编码 Agent**：项目约定文件 + 工具（文件与命令）+ 技能（重复工作流）+ 检查点（长任务恢复）；事实性语料少用 RAG。
- **企业分析**：语义层 / Text-to-SQL（算得准）+ 共享本体（含义一致）+ 图（关系追问）。
- **长运行研究**：LLM Wiki（知识沉淀）+ 检索即工具（Agent 自决检索）+ ACE（上下文维护）+ 反思沉淀（从轨迹改进）。

## 选型陷阱

- 把微调当成动态知识注入——知识会过时且更新昂贵，微调的主场是行为与格式。
- 把长上下文当成检索的替代品——成本、规模、延迟、上下文腐烂四个维度同时吃亏。
- 把记忆库当成训练——向量检索只是语义召回，不会改变模型权重。
- 不断加工具和检索块——干扰会挤占信号、抬高错误率。
- 把一次性问答做成 Wiki——没有持续维护者的语料，编译制品会退化为过期笔记。
- 把缓存当成知识方案——命中率再高也只是少付重复前缀的钱。
- 把"能检索到"当成"答得对"——检索命中率与答案正确率是两件事，前者高而后者低，通常是拼装与指令的问题。

## 验证选型

- 检索质量 → RAG Triad、四层评估方案。
- Agent 行为 → 三层评估与 LLM-as-judge。
- 记忆是否引入污染 → 记忆治理与相关性召回。
- 成本是否真降 → 用 `usage` 字段核对缓存命中与 token 计费。
- 时效是否守住 → 抽样比对答案引用的时间与源数据更新时间。
- 权限是否真的隔离 → 用越权查询做红队测试，而不是读配置。

## 一句话主线

**先问信息放在哪里、归谁维护，再按时效、可溯源、一致性、更新成本与治理成本取舍；方案通常叠加而非互斥，选完还要用评估与治理信号验证它没有悄悄过期。**
