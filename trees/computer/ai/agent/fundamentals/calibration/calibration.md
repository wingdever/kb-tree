# 不确定性与弃权：让 Agent 知道自己不知道

模型的语气是均质的：猜对时说「是」，猜错时也说「是」。这不是措辞问题，而是**没有把内部不确定性映射到外部行为**。Agent 比单轮问答更危险，因为它会把一个不确定的判断带进下一步操作——先猜错订单号，再基于错误的订单号发起退款，整条链都显得很有把握。

这一页讲三件事：不确定性从哪来、怎么估、什么时候该停下来交给人。

## 一、校准：说的和做的一样准

校准（calibration）衡量的是「声称 80% 把握时，实际对的比例是不是 80%」。两个常见指标：

- **期望校准误差（ECE）**：把置信分桶，比较每桶的平均置信与准确率。
- **Brier 分数**：预测概率与真实结果的均方误差，对过度自信惩罚更重。

现代深度网络普遍**过度自信**，大模型在分布外输入上更明显：训练时见过的题型校准尚可，一旦换到没见过的任务形态，置信度仍然很高，准确率却掉下来。

> 判断：模型自己说「我有 90% 把握」这句话本身几乎不构成证据。要么有外部验证，要么有多路一致性，要么什么都不算。

## 二、四种不确定性，对应四种动作

把它们混成一句「不确定」，就找不到正确的处理方式：

| 来源 | 典型表现 | 正确动作 |
|---|---|---|
| 输入歧义 | 「那个订单」指哪一笔？ | 澄清提问，不要猜 |
| 知识缺失 / 过期 | 政策上月改过，模型不知道 | 检索、查权威源；查不到就明说 |
| 执行不确定 | 工具超时、返回不完整、状态未知 | 重试、查状态、用幂等键确认 |
| 能力边界 | 任务超出可完成范围 | 缩小范围、拆解、转人工 |

前两类是「信息问题」，中一类是「系统问题」，最后一类是「范围问题」。只有第一类适合直接问用户，第二类问用户往往也没用（用户不知道政策细节），第四类问用户是浪费。

## 三、怎么表达，别给用户一个概率小数

「我有 73% 的把握」对人没有意义：人无法把 73% 映射到行动，而且这个数字通常不准。可用的表达是**分级 + 依据 + 选项**：

- 分级：确定 / 较确定 / 不确定 / 未知。
- 依据：依据是什么（查到的文档、看到的界面、历史先例）。
- 选项：不确定时给两三个可选解释，让用户一句话就能纠正。

> 判断：给用户看的应该是「我基于什么、还缺什么、你可以怎么选」，而不是一个伪精确的分数。分数留在日志里给系统用。

## 四、弃权的四种形态

弃权不等于拒绝服务。按代价从低到高：

1. **标注不确定并继续**：结果照给，但标明哪部分没把握、依据是什么。适合低风险、可事后纠正的场景。
2. **只给建议不执行**：把方案摆出来，动作留给用户点。适合不可逆操作。
3. **缩小范围**：只做能确定的那部分，其余明确留给人工。适合长任务中段发现信息不足。
4. **明确转人工**：说明缺什么、已经做了什么、建议谁来接手。适合高风险或能力边界外。

四种形态的适用条件不同：把第 1 种用在高风险场景等于没弃权；把第 4 种用在低风险场景会让用户觉得系统很废。

## 五、什么时候必须弃权

用三个维度做矩阵，任一维度触顶就升级处理：

| 维度 | 低 | 高 |
|---|---|---|
| 影响 | 只读、可撤销 | 涉钱、对外发声、不可逆 |
| 可验证性 | 能当场核对 | 只能事后才知道 |
| 知识覆盖 | 有权威来源可查 | 只能靠推断 |

- 高风险 + 低可验证性 → 必须事前弃权，不执行。
- 高风险 + 高可验证性 → 可以执行，但要有校验与回滚。
- 低风险 + 低知识覆盖 → 标注不确定继续，别打断。

## 六、六种校准手段

按可靠性排序，越靠前越值得依赖：

1. **外部验证**：schema 校验、业务规则、单元测试、查权威源。最可靠，因为它不依赖模型自省。
2. **多路一致性**：多次采样或不同提示下答案是否一致；语义层面的分歧比字面分歧更有信号（同义表述算一致，结论相反才算不一致）。
3. **检索命中强度**：检索到的片段是否直接支持结论、是否有冲突来源。命中弱就是知识缺失的信号。
4. **历史先验**：同类任务在这个 Agent 上的历史成功率，按任务类型分桶。冷启动阶段不可用。
5. **结构化自评**：让模型先列依据再给结论，比直接问「你有多确定」略好，但仍不可靠。
6. **直接问置信度**：最弱。模型在 RLHF 后倾向给出让人满意的答案，过度自信是常态。

> 判断：能外部验证的，就别问模型自不自信。自评只在没有验证手段时作为兜底，且不能单独决定高风险动作。

## 七、多步会放大不确定

单步 95% 的可靠度，十步串起来是 \(0.95^{10}\approx 0.60\)。Agent 的错误不是均匀分布的，它会在中途某个判断上分叉，然后一路自我一致地错下去。

两个应对：

- **设可验证锚点**：在关键分叉处放一个能当场核对的检查（订单号是否存在、文件是否存在、金额是否匹配），把不确定性截断在这一步。
- **失败要能回退到锚点**：不要从第一步重跑，那会重复已完成的副作用。

## 八、评测：弃权也要被评

只测准确率会奖励「什么都敢答」。需要三个层面：

- **校准指标**：ECE、Brier，按任务类型分桶看，整体数字会掩盖长尾的严重过度自信。
- **风险—覆盖曲线**：横轴是覆盖率（回答了多大比例的问题），纵轴是已回答部分的准确率。曲线要单调——覆盖率上升时准确率应当下降。这条曲线能直接回答「弃权阈值定在哪」。
- **应弃权样本集**：专门构造不可回答、信息不足、超出范围的问题，测「该弃权时是否弃权」。没有这个集，弃权能力无法评估。

还要防两个反向指标恶化：

- **过度弃权**：把难题全推给人，覆盖率暴跌。弃权率本身不是越低越好，也不是越高越好。
- **弃权通胀**：提示太多太泛，用户学会忽略，等于没有提示。按风险分级提示，低风险不提示。

## 九、反模式

- 用「请注意核实」这类通用免责声明代替具体的不确定性标注。
- 把置信度当作路由依据，却没有校准过。
- 不确定时反复追问用户，而问题本身用户也答不上来（该去查文档）。
- 弃权后不交代已做了什么，用户只能从头再来。
- 只在末端判断要不要弃权，中途已经产生了副作用。
- 用单次采样的一致性当置信度（采样温度与次数都会影响结论）。

## 十、落地顺序

1. 先做**外部验证**：schema、规则、存在性检查，把可判定的错误挡在出口。
2. 再给结果加**分级标注 + 依据**，低风险场景先用起来。
3. 对高风险动作强制走**建议不执行**，把决策权交回人。
4. 建**应弃权样本集**，测该弃权时是否弃权。
5. 最后才谈阈值调优与校准指标；没有第 4 步，阈值只是拍脑袋。
