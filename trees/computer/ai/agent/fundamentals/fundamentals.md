# Agent 基础

这一组回答「Agent 是什么、什么时候该用、有限窗口怎么用、外部知识怎么取回来」。前三个问题在开工前必须回答，否则后面所有的架构选择都建在沙子上；最后一个决定 Agent 是凭记忆作答，还是能给出可核对的依据。

## 三个必须先定的问题

1. **它到底是不是 Agent**。一条固定的调用链是工作流，一个只会回答的是聊天机器人；只有当系统自己决定下一步调用什么、并根据结果调整时，才是 Agent。这条边界决定了你要不要做循环、要不要给工具、要不要做审批。
2. **注意力预算怎么分**。上下文是有限且昂贵的资源：系统提示、工具定义、历史、检索结果、当前任务都在抢同一块空间。默认顺序是「指令 > 任务 > 必要证据 > 背景」，越靠后的越该被压缩或外置。
3. **知识放在哪**。能进提示的就别建检索，能进检索的就别微调；判断依据是变化频率与规模，而不是技术时髦度。

## 三条容易被低估的判断

- **提示是设计，不是文案**。同一个模型下，提示的结构（角色、约束、示例、输出格式）比措辞更能决定质量；改措辞是在做微调，改结构才是做设计。
- **上下文越长不一定越好**。无关内容会稀释注意力，位置也会影响召回——中间段的信息最容易被忽略。
- **外部知识的第一价值是「可溯源」**，其次才是「更准」。能指向原始文档的回答，出错时能查、能修；只靠模型记忆的回答，错了只能重问。

## 怎么读这一组

先读 Agent 的定义与边界，确认你要做的确实是 Agent；再读提示与上下文，把窗口当成预算来分配；然后读知识策略，决定外部知识是走检索、走文件、还是走微调；最后读检索实现，把"该检索"落成"检索得对、引得出、更新得动"。这一组的结论会被后面所有方向引用，值得慢读。

## 一句话主线

先分清 Agent 与工作流、聊天机器人的边界，再把上下文当预算分配（指令优先、证据其次），最后按变化频率决定知识放提示、放检索还是放权重。
