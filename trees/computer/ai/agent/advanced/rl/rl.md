# A10 Agent 训练与强化学习

Agentic RL 是后训练（post-training）的前沿：在多轮、使用工具的轨迹上做强化学习，把"能聊天的模型"变成"能可靠调用工具的 Agent"。

## 基础模型为什么不够

基础模型能**谈论**工具，但不能可靠地决定何时调用、传正确参数、工具出错时恢复。RL 训练的是这些行为本身。

## RLHF vs RLVR

- **RLHF（人类反馈强化学习）**：SFT → 训练奖励模型（人类偏好对）→ PPO 优化策略。适合无法用规则捕捉的细微人类偏好（同理心、语气），但需要偏好数据、奖励模型和精细训练基础设施。
- **RLVR（可验证奖励强化学习）**：任务可算法验证时（代码通过测试、数学等于真值、工具参数合规、JSON 合法、CLI 命令正确、模拟结果成功），**直接用验证器当奖励信号**，跳过奖励模型。近年推理模型的主流做法，公开配方里 DeepSeek R1 一类都以可验证奖励为主，Nemotron 系列也在同一方向上。

> 判断：2022 年的 RLHF 配方（SFT → 奖励模型 → PPO）在今天的生产环境大体已被「可验证奖励 + PPO/GRPO」取代，原因不是 RLHF 失效，而是**验证器比人类偏好便宜、稳定、可扩**——凡是有判定器的任务，都不该再绕一层奖励模型。

## 关键算法

| 算法 | 需要价值网络？ | 奖励形式 | 最适合 |
|---|---|---|---|
| **PPO** | 是（critic） | 每步/每轨迹标量 | 通用、稳定；但 critic 让训练/服务的模型数翻倍，算力与调参成本高 |
| **GRPO** | 否（组相对） | 一组采样输出 | 可验证奖励任务；开源推理后训练的主流 |
| **DPO 类** | 否 | 偏好对 | 离线偏好调优；便宜，但不适合多步工具使用 |
| **RLVR** | 不适用（是设置而非优化器） | 可验证 0/1 | 代码、数学、可检查任务 |

### GRPO 的核心技巧

去掉价值网络；对同一输入采样一组输出，用组内相对表现计算优势——好样本上推、弱样本下压。内存约为 PPO 一半，去掉一个出了名的不稳定来源。核心就是组内归一化：

```python
import numpy as np

def grpo_advantages(rewards):
    """组内相对优势：在采样组内归一化奖励，无需价值网络。"""
    r = np.asarray(rewards, dtype=float)
    return (r - r.mean()) / (r.std() + 1e-8)

# 胜者为正，败者为负
```

源于 DeepSeekMath 论文。GRPO 与可验证奖励天然配对，驱动了 2026 多数推理 Agent 工作。

**新变体**：DAPO（动态采样策略优化）——在 GRPO 上加动态采样与非对称裁剪，保留有用学习信号与探索多样性；GSPO（组序列策略优化）——在序列级而非 token 级优化，提升训练稳定性，尤其对 MoE 模型。

## 端到端 RL 循环的七个部件

1. **策略模型**：被训练的模型。
2. **任务**：模型接收的输入。
3. **动作**：模型输出——工具调用、代码补丁、命令、多步轨迹。
4. **环境**：执行动作并反馈的系统。
5. **验证器**：判定成功或产生奖励的信号。
6. **Rollout**：当前模型采样的尝试。
7. **策略更新**：提高更好输出概率的训练步。

**训练前先评估**：在留出任务集上跑当前模型、检查失败、剖析验证器/奖励函数，再更新权重。RL 在"模型有时能做对但不够稳定"时最有效。**奖励错了，RL 就会优化错的行为**。

## 奖励设计

混合**硬可验证奖励**与**稠密塑形信号**，惩罚浪费动作；保持简单——复杂奖励更难调试、更容易被 gaming。

代码 Agent 给定失败测试的奖励草图：

- 最终补丁让所有测试通过：+1.0
- 链中每次正确函数调用：+0.3
- 每次冗余工具调用：-0.1（惩罚 churn）
- 从初次失败中恢复：+0.2

具体数字不重要，**形状**重要：引导学习的稠密信号 + 门控最终奖励的硬验证检查。

可验证任务的中间奖励（2025–2026 论文常见）：

- 工具调用成功/失败（API 是否干净返回）
- 工具调用有用性（模型是否用了结果）
- 计划一致性（动作是否符合声明的意图）
- 长度效率（惩罚冗余工具调用的轨迹）
- 校准（置信度是否匹配准确率）

**奖励稀疏是陷阱**：若 99% rollout 得 0，GRPO 没有信号 → 加中间奖励或课程学习。**奖励黑客**：Agent gaming 弱验证器 → 始终配留出对抗评估。**KL 过低**：策略漂移离 SFT 基座，英语退化 → 常见起点把 `kl_coef` 设在 0.02 附近，再按模型规模与任务调（经验值，不同配方差别很大，不当作固定超参）。

## 验证器决定训练的上限

「奖励错了，RL 会优化错的行为」可以再往前推一步：**验证器本身就是能力的天花板**。模型再强，也强不过一个只会说"通过/不通过"的判定器。

| 坏法 | 表现 | 训练结果 |
|---|---|---|
| 太松 | 几乎任何轨迹都通过 | 学到"随便试试就交" |
| 太严 | 99% 轨迹得 0，无中间信号 | 梯度消失，训练停滞 |
| 可被 hack | 只查文件是否存在、日志是否打印 | 学会满足检查而非解决问题 |
| 太慢 | 验证耗时高于生成耗时 | 吞吐塌陷，训练成本失控 |
| 不稳定 | 同一轨迹多次判定结果不一致 | 奖励变噪声，策略来回摆 |

> 判断：验证器上线前做三项体检——**通过率分布**应落在 20–80%（太低没有信号、太高没有区分度）；**一致性**上同一轨迹重判三次结果应相同；**作弊面**上显式喂一个"看起来通过但没解决问题"的补丁，看它能否识破。三项都过再投算力，比训完再找问题便宜一个数量级。

## 多轮 Rollout 基础设施

这是真正的工程难点。单轮 rollout 引擎（vLLM/SGLang）每条提示生成一个补全；多轮 rollout 引擎：

1. 生成部分补全直到模型发出工具调用（如 function-call token）
2. 暂停生成，解析工具调用
3. 在沙箱中执行
4. 把工具结果追加到上下文
5. 恢复生成，重复直到最终答案或轮次预算

verl、OpenRLHF、（部分）TRL 在 2025 开始加多轮支持，模式仍在演进。

**沙箱吞吐是绑定约束**：每次 rollout 可能执行 5~50 次工具调用；G=8、batch=256 提示时，每训练迭代 1万~10万次工具执行。每次执行几秒就是数小时沙箱时间。真实 RL 基础设施在沙箱吞吐、隔离与缓存上投入巨大。

**跨轮缓存复用**：每轮新 prefill 含之前所有轮次；vLLM/SGLang 前缀缓存有帮助，RadixAttention 尤其强（缓存结构天然逐轮扩展）。

## 信用分配：轨迹级 vs 步级

- **轨迹级 GRPO**：简单、可用的默认；多数开源配方使用；稀疏信号。
- **步级信用分配**：开放研究问题。PRM（过程奖励模型）和内在奖励是候选方案——需要逐轮信号（PRM 标注），否则用内在塑形有奖励黑客风险。

## 五阶段实践流水线

1. **策展有可验证结果的任务数据**：选成功可检查的任务；训练修 bug Agent 就收集真实 issue 及其通过的测试。奖励信号的上限是你的验证能力。
2. **设计奖励函数**：硬可验证奖励 + 稠密塑形；简单为上。
3. **建沙箱环境**：模拟器、容器或 mock API——Agent 能在这里安全失败一千次。
4. **选算法**：成本敏感的推理与工具用 GRPO；最大对齐质量且算力充足时 PPO 仍是强默认。
5. **评估→检查失败→重复**：闭环。

常见配方：**SFT（格式与冷启动）→ DPO 类偏好调优（对齐）→ RLVR + PPO/GRPO（推理与工具使用）**。很多团队把 rollout 生成与梯度更新解耦、异步运行，避免昂贵的多步 rollout 拖住训练。

## Agentic RL 需要环境，不只是数据集

单轮静态数据集够用：`{"prompt": "...", "answer": "..."}`。跨单步/多步/多轮的 Agentic RL 需要一个环境定义：**数据集 + Agent harness + 验证器 + 状态**。

长运行编码 Agent 可能需要多次工具调用才让测试通过；数据分析 Agent 要检查文件、跑查询、生成图表、验证结果；科学 Agent 要搜文献、调模拟器、修正假设。环境可以简单（数学的解析器 + 答案检查器）或复杂（带工具、文件、轮次限制和任务特定成功标准的沙箱）。

[NVIDIA NeMo Gym](https://github.com/NVIDIA-NeMo/Gym) 提供可扩展、可复现的环境构建方式，覆盖单步、多步、有状态、真实世界、LLM-as-judge 环境。合成数据扩覆盖：生成任务变体、边界案例、工具调用场景和期望输出，再用验证器、奖励模型或 LLM-as-judge 过滤。**合成数据不是真值**：保留人工质量种子集、激进去重、留出评估任务、使用前检查失败案例。

## 何时不该上 RL

- 任务没有可验证信号且无法承担偏好数据基础设施。
- 闭源 API：RL 需要完整梯度访问；闭源 API 只暴露 SFT + DPO。
- 更简单的方法（提示、上下文工程、工具设计）还没跑通——先把正常路径做对。

> 一条实用主线：需要时先 SFT → 用可验证奖励做 GRPO → 评估 → 检查失败 → 重复。奖励是核心：验证器决定下游一切。
