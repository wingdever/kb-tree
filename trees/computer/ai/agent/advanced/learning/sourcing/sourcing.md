# Agent 开发资料的获取

获取资料不是“收藏一堆链接”，而是把一个工程问题变成可核对的证据链：先知道要找什么，再找到一手材料，最后把材料压成能指导实现或判断的结论。资料越多不等于越懂；没有版本、没有证据、没有复现路径的资料，只会增加判断噪声。

## 先定义要找什么

先写一句“我要做什么决定”，再决定找哪类材料。不同问题对应不同的材料形态：

| 要解决的问题 | 优先找什么 | 典型证据 |
|---|---|---|
| 循环怎么停、怎么重试 | 官方文档、框架源码、设计说明 | 停止条件、最大轮数、错误分类、重试策略 |
| 工具怎么描述、怎么调用 | 工具规范、SDK 文档、协议规范（MCP、A2A） | schema、参数校验、错误返回、权限边界 |
| 上下文怎么组装 | 工程博客、源码、评测记录 | 上下文预算、压缩策略、缓存命中条件 |
| 效果是否真的提升 | 论文、基准、评测集、轨迹日志 | 对照实验、失败案例、成本与延迟 |
| 线上为什么坏 | issue、事故复盘、安全公告 | 复现步骤、根因、修复版本 |

问题越具体，搜索词越短。不要一上来搜“Agent 开发”，那会得到大量课程广告和概念复述；搜“agent loop stop condition”“tool call retry idempotency”“context window overflow”这类带构件名的短语，命中一手材料的概率高得多。

## 资料分层：一手、二手、噪声

| 层级 | 典型材料 | 正确用法 | 主要风险 |
|---|---|---|---|
| 一手 | 官方文档、规范、源代码、release note、论文、基准仓库、事故复盘 | 作为事实与实现的最终依据 | 版本会变，需要锁定日期或 commit |
| 二手 | 工程博客、课程、社区回答、视频讲解、中文解读 | 当地图、术语表和线索，帮你找到一手材料 | 转述会丢条件，结论可能被简化 |
| 噪声 | 营销稿、榜单稿、无来源的“最强”“颠覆” | 只提取可核验的数字、限制与发布时间 | 把宣传当能力，把个例当规律 |

二手转述、版本过期、营销稿不必一律拉黑，但要降级使用：

- **二手转述**：可以用来发现术语、争议和原始出处；它本身不是证据。看到一句关键结论，回到它引用的官方文档、论文或代码再确认一次。
- **版本过期**：只用于理解历史形态或做前后对比，不能拿来解释当前 API。旧文章里正确的设计，可能已经被新版本的限制条件推翻。
- **营销稿**：只取其中可量化的部分——价格、配额、延迟、上下文长度、并发限制；对“业界最强”“效率提升十倍”这类没有口径的断言，直接丢掉。

这就是“取其精华”的具体做法：保留线索、术语、失败案例和可核验数字，丢掉没有出处的结论与情绪化判断。

## 检索路径

按“离实现越近越优先”的顺序找：

1. **官方文档与规范**：产品文档、API reference、协议规范、迁移指南、release note。先看目录和 changelog，再看具体页；不要从搜索结果的第三页开始读。
2. **源代码与仓库历史**：README 只说明项目想做什么，源码、测试、issue 和 commit 才说明它实际怎么做。用 `git log -S"关键词"` 找某个机制是什么时候引入的，用 release tag 对齐文档版本。
3. **论文与基准**：arXiv、会议论文、基准仓库、评测榜单。先读摘要、实验设置与限制，再决定要不要读方法；不要只看榜单名次。
4. **工程博客与会议演讲**：厂商工程团队、框架维护者、真实项目复盘。它们常给出官方文档不写的取舍和失败模式，但仍要回到代码或数据核对。
5. **中文社区**：知乎、微信公众号、B 站、掘金等适合找线索和中文术语，不适合作为最终证据。把中文说法翻译成英文构件名，再回到一手来源。

常用的查询式：

- 精确短语：`"agent loop" "tool calling" "stop condition"`
- 限定站点：`site:github.com "checkpoint" "interrupt" agent`
- 限定文件：`filetype:pdf "agent evaluation" survey`
- 限定时间：`after:2025 "context engineering" agent`
- 代码搜索：在 GitHub 搜 `max_turns`、`tool_call_id`、`context_window`、`checkpoint`、`human_in_the_loop`，再按语言和仓库筛选
- 历史定位：`git log -S"max_turns" --oneline`，确认某个参数是原生设计还是后补的兼容层

搜索时同时准备中英文词表。Agent 领域的同一概念常有多个叫法：harness、scaffold、agent runtime；tool、function、action；trace、trajectory、span；上下文工程会写成 context engineering，工具协议会写成 MCP 或 Model Context Protocol。只搜一个词会漏掉一半材料。

## 版本与时效核对

Agent 资料最容易错在“内容是对的，但版本已经不对”。拿到材料后先核对五件事：

| 核对项 | 怎么查 | 不合格信号 |
|---|---|---|
| 发布时间 | 文档页脚、文章日期、release note | 只有“最近更新”，没有具体日期 |
| 代码版本 | release tag、commit SHA、`package.json` / `pyproject.toml` | 示例代码没有版本，或引用已删除的 API |
| 模型版本 | 模型卡、定价页、版本公告 | 把上一代模型的能力当成当前默认 |
| 适用范围 | 文档的限制、地区、配额、权限说明 | 只讲能力，不讲限制和失败方式 |
| 许可与安全 | LICENSE、security advisory、依赖公告 | 代码无许可证，或让你关闭沙箱/校验 |

核对顺序：先看日期与版本，再看代码能否运行，最后看结论是否有对照。三者缺一，资料就只能当线索，不能当依据。

## 从资料到可用知识

读到一段材料后，不要直接复制摘要；先拆成三层：

- **事实**：文档写了什么、代码实际做了什么、数据是多少。必须能指回原文、行号、commit 或表格。
- **机制**：它为什么这样工作，依赖哪些前提。用自己的话解释因果链，不照抄术语。
- **判断**：在什么条件下该用、什么条件下不该用，代价是什么。判断要署名，写成“我认为/我建议”，不要伪装成官方结论。

一份可用的笔记至少包含：定义、机制、边界、失败模式、最小例子、验证方法。最小例子可以是一段十行代码、一条可复现命令、一张对照表或一个最小评测集；没有它，笔记只是读后感。

记录来源时保留这些字段：标题、作者或机构、发布时间、版本或 commit、URL、许可证、访问日期。引用只摘短句并注明出处；大段复制既丢上下文，也可能违反许可。

## 一套可执行流程

1. **写问题单**：一句话说明要做的决定、使用场景和不做什么。问题单决定搜索边界。
2. **建词表**：列中文叫法、英文叫法、构件名、可能的旧名。每个词后面标注“官方/社区/猜测”。
3. **广搜候选**：官方文档、GitHub、论文、规范、工程博客各收 3–5 条；先只记元数据，不急着读全文。
4. **分层初筛**：把候选标成一手、二手、噪声；二手只保留能指向一手的线索，噪声只保留可核验数字。
5. **核对版本**：对一手材料锁定日期、release tag 或 commit；跑一次示例或查一次源码，确认它现在仍然成立。
6. **压成结论**：写成“事实—机制—判断—边界—验证”五段；每条事实带来源，每条判断带条件。
7. **建观察清单**：订阅 release、changelog、security advisory，给易变结论设复查日期；API、价格、配额、模型能力都属于易变项。

时间有限的快速版：十分钟读官方文档的目录与限制，十分钟看源码或 issue 里的真实用法，十分钟做一次最小验证；三件事都完成，再决定要不要继续深读。

## 常见失败

- **链接囤积**：收藏了几百条，真要做决定时一条也回不到原文。资料的价值在证据链，不在数量。
- **把二手当证据**：二手博客说得再顺，也要回到官方文档、论文或代码；转述者的省略往往正是失败条件。
- **按 star 数排序**：star 衡量关注度，不衡量可维护性、许可、测试覆盖和与当前版本的匹配度。
- **忽略版本**：拿两年前的教程套当前 SDK，报错后以为是能力问题，实际是接口已经换了。
- **只读结论不读边界**：论文的适用域、产品的配额、框架的权限模型，通常写在最不显眼的位置，却决定能不能用。
- **把营销指标当能力**：没有口径的“提升”无法复现；只取有单位、有基准、有对照的数字。

## 一句话主线

**从可决策的问题出发，先拿一手材料，再用二手材料当地图；每条结论都带版本、证据和一次可复现的验证。**
