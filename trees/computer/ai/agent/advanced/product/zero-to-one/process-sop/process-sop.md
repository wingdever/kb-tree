# 场景到 SOP 与流程

需求发现回答“做什么”，流程拆解回答“怎么做”。前者产出场景清单，后者把场景变成一张能交给平台搭建的图。

这篇实战把流程拆解分成两层：先粗后精。粗流程用来确认方向，精流程用来生成节点。跳过粗流程直接画细图，容易在错误方向上精益求精。

## 粗流程：先看全貌

粗流程只写主干：谁发起、先做什么、后做什么、在哪里结束。它不关心每个按钮怎么点，只确认三件事：

- 起点和终点是否清楚；
- 中间是否漏了关键环节；
- 哪些环节必须由人判断。

案例的粗流程是：看到好文章 → 复制链接 → 发给智能体 → 抓取正文 → 总结与打标签 → 写入表格 → 以后检索。到这一步，已经能判断它是不是一个值得做的闭环。

## 精流程：拆到节点

精流程把每个步骤拆成“输入—处理—输出—负责人”。案例里的精流程是：

1. 用户提交 URL；
2. 抓取网页，拿到标题与正文；
3. 模型总结正文，提取核心观点；
4. 模型打标签；
5. 组装成表格需要的字段；
6. 写入飞书多维表格；
7. 返回保存结果。

每一步都要能回答：

- 输入是什么形态？字符串、JSON、文件还是列表？
- 输出字段叫什么？类型是什么？
- 谁执行？模型、插件、代码还是人？
- 失败时走哪条边？重试、跳过还是转人工？

拆不到这个粒度，后面的工作流节点就会靠猜。

## 人机分工表

精流程旁边要配一张三列表：工作内容、AI 协助、人工来做。它不是礼貌性的“人机协同”，而是责任划分。

案例里的分法：

| 工作内容 | AI 协助 | 人工来做 |
|---|---|---|
| 发现文章 | 接收链接、触发流程 | 判断这篇文章是否值得收藏 |
| 抓取正文 | 自动抓取、提取标题与正文 | 遇到验证码或反爬时人工处理 |
| 总结 | 生成摘要与核心观点 | 判断摘要是否失真 |
| 打标签 | 根据内容生成候选标签 | 偶尔修正不准确的标签 |
| 写入表格 | 调接口写入 | 首次授权、处理权限过期 |
| 异常 | 自动重试、返回错误 | 收到告警后决定是否补录 |

这张表决定了哪些节点可以全自动，哪些节点必须加确认门。**判断质量、决定取舍、承担对外责任**的步骤，默认留给人。

## SOP 是流程的骨架

SOP（Standard Operating Procedure，标准作业流程）回答“在什么情况下、按什么顺序、做到什么程度、异常怎么办”。它比流程图多两样东西：触发条件和完成标准。

- 触发条件：什么输入会启动这条流程？不满足时怎么拒绝？
- 完成标准：什么状态算成功？是“写进表格”还是“人确认摘要可用”？
- 异常路径：抓取失败、模型输出不合 schema、表格权限失效，各自怎么处理？

有 SOP，流程拆解才是可复现的；没有 SOP，节点只是把人的即兴操作画成了图。

## 业务流程图

业务流程图用框和箭头描述步骤、顺序与信息流向。画图不是形式主义，它逼你把三件事显式化：

- 顺序：哪些步骤必须串行，哪些可以并行；
- 分支：什么条件走哪条路，默认分支是什么；
- 交接：哪一步的输出交给下一步，字段是否对得上。

画图时容易犯两个错：一是把“判断”画成一个框，却不写判断依据；二是把“异常”画成注释，而不是一条真实的边。异常边不画出来，上线后就会以“卡住”的形式出现。

## 从图到节点

低代码平台里的工作流，基本就是把流程图变成节点图。图上的一个处理框，通常对应一个节点：

- 接收输入 → 开始节点；
- 抓网页 → 插件节点；
- 总结与打标签 → 大模型节点；
- 组装 JSON → 代码节点；
- 条件分流 → 选择器节点；
- 写表格 → 插件节点；
- 返回结果 → 结束节点。

所以流程拆得越准，平台搭建越快。反过来，如果在平台里一边拖节点一边想流程，通常会在中途推翻重来。

## 输出物

流程拆解的交付物是一套四件套：

- 粗流程：一页纸能看懂的主干；
- 精流程：节点级步骤与输入输出；
- 人机分工表：谁做什么、谁确认什么；
- SOP：触发条件、完成标准、异常路径。

这四样东西直接决定下一步选什么平台、搭什么节点、写什么提示词。

## 边界

- 流程拆解不是越细越好。细到“鼠标点哪里”对 Agent 没有帮助，细到“输入输出与失败路径”才有用。
- 流程图不能替代真实数据测试。图上跑得通，不代表脏输入能跑通。
- 人机分工要在需求阶段定，不要等上线后才发现某个高风险动作没人负责。
- 业务流程有例外时，先画主路径，再用异常边补；不要为了覆盖所有例外把主路径淹掉。

## 一句话主线

**先把场景收敛成一条有起点、终点和完成标准的 SOP，再拆成带输入输出与失败路径的节点，最后用业务流程图检查顺序、分支与人机交接。**
