# 商用 Agent 从 0 到 1

这篇实战给出的不是又一套 Agent 理论，而是一条**从岗位痛点走到可发布智能体**的低代码路径。它的价值在于把“我要做一个 Agent”拆成七个可交付阶段，并用一个“文章素材收集”案例把每个阶段落到具体输入、节点和输出上。

案例主线很短：

**记录工作流水账 → 让 AI 识别可提效场景 → 选一个场景细化流程 → 画业务流程图 → 选平台、模型与工具 → 在工作流里搭节点 → 创建智能体并挂载工作流 → 测试后发布。**

这条线适合快速验证一个具体场景，不等于生产级系统的全部工程；它解决的是“从想法到能跑”，生产化还要补评测、权限、观测与成本控制。

## 七个阶段

作者把商用 Agent 的开发归为七步：

| 阶段 | 要回答的问题 | 主要产物 |
|---|---|---|
| **需求梳理** | 哪个岗位、哪段工作值得交给 AI？ | 场景清单、优先级、边界 |
| **软件选型** | 用低代码平台、代码框架，还是自研？ | 平台、模型、工具的组合 |
| **提示工程** | 模型扮演什么角色、按什么格式输出？ | 系统提示、用户提示、输出 schema |
| **数据库** | 业务数据存哪、怎么读写？ | 表结构、字段、权限 |
| **构建 UI 界面** | 用户从哪里进入、看到什么？ | 对话入口、表单、结果页 |
| **测试评估** | 怎么判断它真的能完成任务？ | 测试用例、失败样例、验收标准 |
| **部署发布** | 发布到哪个渠道、怎么运维？ | 发布配置、监控、迭代计划 |

这篇文章的实操重点落在**需求梳理、流程拆解、软件选型、工作流搭建、智能体装配与发布**；数据库与 UI 只在案例中按需出现（例如飞书多维表格充当素材库与人工可读界面）。七步是框架，不是每步都必须做成重工程。

## 案例：一个素材收集智能体

起点是一个自媒体编辑的日常工作流水账：看数据、找选题、收集素材、写稿、送审、发布。让模型按 MECE 原则拆分后，得到一组可独立提效的场景：数据监控、热点追踪、选题策划、素材库、AI 写作、协同审阅、智能发布等。每个场景都可以是一个 Agent，合起来才像一个“数字员工”。

案例只取其中最窄的一段：**看到一篇好文章，把链接发给智能体，自动抓取正文、总结、打标签，写进飞书多维表格。**

这段之所以能落地，是因为它满足四个条件：

- 输入单一：一个 URL。
- 步骤可列全：抓取 → 提取 → 总结 → 打标签 → 组装数据 → 写入表格。
- 成功可判定：表里出现一行标题、摘要、标签、原文。
- 人工兜底清楚：抓取失败、标签不准、授权过期时，人能接手。

## 第一步：需求梳理

不要从“我想做一个 Agent”开始，从“我每天到底在干什么”开始。让岗位上的一个人或多人把工作写成流水账，细到每一步操作、看的每个网站、判断的每个依据；再让模型识别哪些段落可以被 AI 辅助，最后由人筛出可落地场景。

关键不是 AI 给了多少建议，而是人有没有用一组标准去筛：频率、耗时、判断难度、错误代价、数据可得性、是否必须人工拍板。高频率、低风险、输入输出清晰的场景先做；低频率、高责任、依赖隐性经验的场景后做。

## 第二步：流程拆解与 SOP

粗流程只说明“先做什么、再做什么”；精流程要拆到**每个节点都有输入、处理、输出、负责人**。把工作内容分成三列：AI 协助、人工来做、需要人工确认。然后把步骤画成业务流程图——图上每个框，基本就是低代码平台里的一个节点。

SOP（标准作业流程）是这一步的骨架：在什么情况下、按什么顺序、做到什么程度、异常怎么办。没有 SOP 的流程拆解，最后会变成“模型自己猜步骤”；有 SOP，才能把隐性经验变成可测试的节点契约。

## 第三步：软件选型

选型不是选“最强平台”，而是选“当前约束下最快能验证的平台”。三个维度先定：

- **平台形态**：Coze、Dify 这类低代码平台适合快速搭工作流与发布；LangChain、CrewAI 这类代码框架适合深度定制与自托管；自研适合有特殊权限、数据或规模要求时。
- **模型按节点选**：总结、打标签、分类这类窄任务不必用最贵的模型；需要复杂推理的节点再上强模型。同一个提示在不同模型上表现可能不同，选模型和写提示要一起测。
- **工具按接口选**：平台内置插件、开放 API、RPA、代码节点各有用处；能走稳定 API 就不优先用页面抓取，能用一个工具合并的节点不要拆成三个。

案例选的是 Coze + DeepSeek：低代码负责编排与发布，模型只负责总结与打标签。选型结论要写成“平台 + 模型 + 工具 + 理由”，而不是一句“用了 Coze”。

## 第四步：工作流节点

工作流是确定性的图：开始节点接收参数，中间节点处理，结束节点返回结果。常见节点类型包括：

- **开始 / 结束**：定义输入变量与返回方式，必选且不能孤立。
- **插件节点**：调用外部能力，例如抓取网页、写飞书表格。
- **大模型节点**：总结、分类、抽取、生成。
- **代码节点**：做数据转换、清洗、拼装 JSON。
- **选择器 / 分支**：按条件走不同边。
- **循环 / 批处理**：对列表逐项处理。
- **变量聚合 / 输入输出**：把多路结果合并或显式暴露。

每个节点都要写清输入输出：上游给什么字段、下游要什么字段、字段类型是否匹配、失败时返回什么。节点之间的连线不是装饰，而是数据流与控制流；开始与结束之间没有连线，流程根本跑不起来。

## 第五步：提示词契约

案例里的提示词分成两层：

- **系统提示词**：角色、技能、输出格式、限制。它定义“你是谁、你能做什么、你必须怎么回、你不能做什么”。
- **用户提示词**：只放本次任务的具体变量，例如标题与正文；变量用平台占位符引用上游输出。

结构化输出要写成契约：JSON 字段名与下游节点完全一致，给出示例，要求只输出 JSON，不要额外解释。模型返回后再做解析与校验；字段缺失、类型不符时走失败分支，而不是把脏数据写进表格。

提示词不是越长越好。它要能把“任务边界 + 输出结构 + 失败方式”说清楚；剩下的知识应该放在工具、检索或数据里，而不是全部塞进提示。

## 第六步：数据连接

案例的数据链是：抓取插件返回标题与正文 → 大模型返回 summary 与 tags → 代码节点组装成飞书多维表格要求的 `records.fields` 结构 → 保存插件写入表格。

这段最容易出错的地方不是模型，而是**接口契约**：

- 插件要的 `app_token`、`table_id`、`records` 分别是什么类型，字段名是否与表格列名一致。
- 写入前是否做了类型转换；数组、对象、字符串不能靠拼接硬凑。
- 令牌是否最小权限、是否泄露在日志或提示词里。
- 写入是否可重试、是否会产生重复行；失败时是否能把错误返回给用户。

能走 API 就不要走页面点击；必须走页面抓取时，要把反爬、验证码、页面结构变化当成正常失败来设计。

## 第七步：智能体装配

工作流是“固定管线”，智能体是“入口与调度”。案例里的智能体做三件事：

1. **人设与回复逻辑**：告诉它这是素材收集助手，只处理 URL，不闲聊无关话题。
2. **挂载工作流**：用户发链接时调用素材收集工作流；如果未来有视频、播客工作流，智能体根据输入类型选择。
3. **调试与发布**：在预览区用真实链接测试，确认抓取、总结、写入都成功，再选择发布渠道。

智能体的“自主”不等于“什么都让它决定”。在这个案例里，流程是固定的，智能体主要负责识别意图、路由工作流、组织回复；真正需要开放探索的任务，才把更多控制权交给模型。

## 发布与运营

发布前至少检查六件事：输入是否校验、令牌权限是否最小、失败是否有提示、写入是否幂等、单次成本是否可接受、日志是否能定位问题。

发布渠道可能包括智能体商店、豆包、飞书、抖音小程序、微信生态、API 与 Chat SDK；不同渠道对插件、模型与授权的要求不同，不能假设“一处发布、处处可用”。

发布不是终点。上线后要看四类信号：任务成功率、人工接管率、平均耗时、单次成本；再把失败样例回流成流程分支或提示修正。

## 哪些知识可以复用

- **需求侧**：工作流水账、MECE 拆场景、SOP、业务流程图、人机分工表。
- **平台侧**：低代码平台与代码框架的边界、按节点选模型、插件/API/RPA 的取舍。
- **编排侧**：工作流节点、输入输出契约、分支与失败路径、变量引用。
- **模型侧**：系统提示与用户提示分层、结构化输出 schema、模型与提示联合调试。
- **数据侧**：JSON 转换、外部 API 字段映射、权限与幂等。
- **交付侧**：智能体人设、工作流挂载、测试、发布渠道与上线信号。

这些不是“Coze 专属技巧”。换成 Dify、LangChain 或自研，需求梳理、流程拆解、节点契约、结构化输出和发布检查仍然成立；变的只是实现工具。

## 边界

- 这是一条**低代码快速验证路径**，不是生产级架构的完整答案。高并发、多租户、审计、灰度、回滚要另做工程。
- 案例只覆盖“素材收集”，不能证明同一套流程能处理开放式研究、多步决策或高风险操作。
- “让 AI 分析工作流水账”会给出看似合理的场景清单，但优先级仍要人按业务价值与风险判断。
- 平台内置插件有配额、权限与稳定性限制；关键链路要准备替代方案。
- 发布到第三方渠道要过平台审核与数据合规，不能把“能发布”当成“可商用”。

## 一句话主线

**先用工作流水账找到值得做的场景，再用 SOP 把场景拆成有输入输出的节点，选一个够用的平台与模型，把节点连成工作流，用提示词与 schema 约束模型，用插件与代码接通数据，最后用智能体做入口、用发布渠道触达用户。**
