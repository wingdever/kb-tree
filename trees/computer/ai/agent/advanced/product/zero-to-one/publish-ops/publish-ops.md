# 智能体发布与运营

发布不是把按钮点一下，而是把“能跑”变成“有人用、出错能兜、成本可控”。案例的发布段很短，但它暴露了几个真实约束：不同渠道支持的能力不同，插件与模型不一定通用，介绍与开场白要重新写。

## 渠道不是复制粘贴

同一个智能体，发布到不同渠道会遇到不同限制：

- **智能体商店 / 豆包**：可能只支持部分模型与插件；部分插件不支持分享，发布后仅自己可用。
- **飞书**：适合内部协作与群聊，但权限与组织范围要配置。
- **抖音小程序 / 微信生态**：需要单独授权、配置与审核。
- **API / Chat SDK**：适合接进自有产品，但要自己做鉴权、限流与前端。
- **网页 / 独立应用**：自由度最高，运维责任也最大。

发布前要列一张渠道能力表：支持哪些模型、哪些插件、什么鉴权、有没有配额、审核要多久。不要假设“主平台能跑，所有渠道都能跑”。

## 上线前检查

至少检查八项：

1. **输入校验**：空输入、非 URL、超长文本是否被拒绝或处理；
2. **权限最小化**：令牌只读写必要的表，不暴露在提示词与日志里；
3. **失败提示**：抓取失败、模型失败、写入失败，用户能否看懂；
4. **幂等**：重复提交会不会写重复行；
5. **配额**：单用户、单日、单次执行是否有限制；
6. **成本**：一次任务调用多少模型、多少插件，单价是否可接受；
7. **日志**：能否看到每个节点的输入输出与错误；
8. **回滚**：出问题能否下线、换版本或切回人工。

这八项里，任何一项缺失，发布都可能变成“演示很顺，上线就崩”。

## 发布文案也是能力边界

智能体介绍、开场白、预设问题，不只是营销文案，它们会塑造用户预期：

- 介绍要写清“输入什么、输出什么、不做什么”；
- 开场白给一个具体示例，降低首次使用门槛；
- 预设问题覆盖成功路径与边界场景；
- 不要写“全能助手”“什么都能做”，否则第一次越界就会失去信任。

案例的介绍是“内容总结助手，能准确提炼 URL 页面信息”；开场白是“发我一个链接，我帮你总结并保存”。这句话同时说明了输入与动作，比“我是你的智能助手”有用。

## 上线后的四个信号

发布后至少看四类信号：

| 信号 | 说明 | 异常时先查 |
|---|---|---|
| 任务成功率 | 成功完成的比例 | 抓取、模型 schema、写入权限 |
| 人工接管率 | 用户放弃或转人的比例 | 失败提示、能力边界、输入形态 |
| 平均耗时 | 从提交到返回的时间 | 模型长度、插件超时、排队 |
| 单次成本 | 模型 + 插件 + 存储 | 重试、长上下文、无效调用 |

再加两类定性信号：用户重复使用率、失败反馈内容。重复使用说明场景选对了；失败反馈是最便宜的评测集。

## 迭代闭环

上线后的每一次失败，都应该进入一个闭环：

1. 记录失败输入、节点输出、错误码；
2. 判断是切流程、改提示、换模型、修插件，还是能力边界没写清；
3. 只改一个变量，重跑同一组样例；
4. 把新样例加入回归集；
5. 版本化发布，保留回滚。

不要一次改五处。改多了，成功时不知道是哪一处起了作用，失败时也不知道是哪一处造成的。

## 运营不是加功能

第一版跑通后，最容易犯的错是“再加一个功能”。每加一个工作流、插件或渠道，都会增加路由、权限、配额与测试面。

扩展前先问：

- 新功能解决的是高频失败，还是想象中的需求？
- 现有流程能否通过改一个节点解决？
- 新渠道是否支持现有插件与模型？
- 成本与权限是否仍然可控？

能在一个工作流里加节点解决的，不要新开一个智能体；能在一个渠道跑好的，不要同时铺五个渠道。

## 边界

- 平台审核与渠道规则会变化，发布能力不是永久承诺。
- 低代码平台的配额与插件稳定性有限，关键业务要有替代与降级。
- 发布后的数据涉及用户隐私与合规，日志与记忆要按最小必要留存。
- “上线”不是产品化完成；SLA、计量、责任边界仍要按产品化方法补齐。

## 一句话主线

**发布前按渠道能力、权限、失败、幂等、配额、成本、日志与回滚做检查；发布后用成功率、接管率、耗时与成本迭代，不要用加功能代替修问题。**
