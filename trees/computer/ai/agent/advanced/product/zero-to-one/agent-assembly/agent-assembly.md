# 智能体装配

工作流是管线，智能体是入口。装配阶段要回答：用户怎么进来、它怎么识别意图、调用哪条工作流、失败时怎么回复。

案例的智能体很简单：一个人设、一段回复逻辑、一个挂载的素材收集工作流、一个预览测试区。它的“智能”不在于自由规划，而在于**把用户输入正确地路由到固定管线**。

## 人设与回复逻辑

人设不是写一段“你是一个专业、热情、严谨的助手”，而是写清四件事：

- **服务对象**：谁在用，用来做什么；
- **输入范围**：接受什么形态的输入（链接、文件、文字）；
- **能力边界**：能做什么、不能做什么、越界时怎么拒绝；
- **回复风格**：给结果、给步骤、给失败原因，还是给下一步建议。

案例的人设是“内容总结助手”：用户发 URL，它抓取、总结、打标签、写表；不处理与 URL 无关的闲聊；总结要精炼、突出重点。

人设要和工作流能力一致。人设说“我能分析视频”，工作流却只支持文章，第一次遇到视频就会露馅。

## 技能与工具

智能体的技能面板决定它能调用什么：

- **插件**：直接调外部 API；
- **工作流**：调用固定管线；
- **知识**：挂知识库或文档；
- **记忆**：短期对话、长期偏好；
- **触发器**：什么事件启动它。

案例只挂了素材收集工作流，没有堆一堆用不上的插件。这是对的：技能越多，路由越容易混乱，权限面也越大。

装配时按“最小能力集”原则：先挂完成核心任务所需的最少工具，跑通后再加。每加一个工具，都要问它解决哪一个具体失败，而不是“以后可能用得上”。

## 工作流挂载与路由

一个智能体可以挂多条工作流。路由可以按：

- **输入类型**：URL 走文章收集，视频链接走视频转写，文件走文档解析；
- **用户意图**：总结、收藏、检索、发布；
- **显式命令**：用户选择某个功能，或输入固定前缀。

路由要可解释。用户发一个链接，智能体应该能说“我按文章流程处理”，而不是黑箱地猜。路由错了，用户要能纠正；纠正结果要能被记住或写进规则。

案例只有一个工作流，路由退化为“收到 URL 就调用”。这反而降低了第一版复杂度。多工作流是后续扩展，不是第一版必需。

## 知识与记忆

- **知识**：领域资料、模板、规则。能放知识库就不要塞进系统提示。
- **记忆**：用户偏好、历史任务、常用标签。短期记忆放对话，长期记忆放数据库或平台记忆区。
- **状态**：任务进行到哪一步、哪些字段已填。长任务要能恢复，不能靠模型“记得”。

案例用飞书表格充当外部记忆：素材写入表格，下次可按标签检索。这比让模型记住所有文章更可靠，也让人能直接查看与修正。

## 预览与调试

发布前必须在预览区用真实输入跑：

- 一条正常文章链接：确认抓取、总结、标签、写入全部成功；
- 一条抓取不到的文章：确认失败提示清楚；
- 一条非 URL 输入：确认不会误触发工作流；
- 一条超长文章：确认截断或分段策略生效；
- 一条重复链接：确认不会写重复行。

调试时看每个节点的输入输出，不只看最终回复。最终回复说“已保存”，不代表表格里真的有数据。

## 发布配置

发布时要补：

- 智能体介绍：一句话说清它能做什么；
- 开场白：给用户一个具体起点；
- 预设问题：降低首次使用门槛；
- 发布渠道：哪些平台可用、哪些插件不支持；
- 权限与配额：哪些用户可用、每天能用多少次。

案例发布时由平台自动生成介绍与开场白，作者再按实际情况修改。自动生成是起点，不是终稿；介绍里必须写清输入形态与能力边界。

## 自主与路由的边界

“智能体”常被理解成“模型自己决定一切”。在这个案例里，流程是固定的，模型主要负责理解输入、调用工作流、组织回复。真正自主的部分很少。

这不是缺点。任务越确定，越应该把控制权放在工作流；任务越开放，才把更多决策交给模型。装配阶段要明确：哪些路由由代码/规则决定，哪些由模型判断，哪些必须用户确认。

## 边界

- 挂太多工作流会让路由与权限变复杂；第一版只挂核心管线。
- 人设不能替代权限控制；越界操作要靠工具白名单与审批，不靠提示词。
- 平台记忆区有容量与隐私限制；敏感信息不要写入长期记忆。
- 预览通过不等于发布可用；不同渠道的模型、插件与配额可能不同。

## 一句话主线

**智能体负责入口、人设与路由，工作流负责确定性执行；先挂最小能力集跑通，再用真实输入调试，最后按渠道补发布配置与权限边界。**
