# Agent 软件选型

流程拆完，下一步不是立刻打开某个平台，而是回答三个选型问题：

1. **平台**：低代码、代码框架，还是自研？
2. **模型**：整条链路用一个模型，还是按节点分工？
3. **工具**：用平台插件、开放 API、RPA，还是代码节点？

选型的目标不是“最强”，而是“在当前的交付时间、数据权限和团队能力下，最快跑通并可维护”。

## 平台：先看约束，再看功能

| 形态 | 代表 | 适合 | 代价 |
|---|---|---|---|
| 低代码平台 | Coze、Dify | 快速搭工作流、可视化调试、直接发布到渠道 | 平台配额、插件能力与导出受限，深度定制受制于平台 |
| 代码框架 | LangChain、LangGraph、CrewAI | 需要自定义状态、工具、路由与部署 | 要自己搭工程、观测、权限与发布 |
| 自研 | 自有服务 + 模型 API | 特殊数据、权限、规模或合规要求 | 成本最高，所有基础设施自己承担 |

案例选 Coze，理由很具体：要在一个具体场景上快速验证“抓取 → 总结 → 写表”，低代码的节点、插件和发布能力刚好覆盖；不值得为此先搭一套自研服务。

选平台时要问的不是“功能多不多”，而是：

- 我需要的工具它有没有，没有能不能用 API 或代码补；
- 数据能不能留在允许的位置，权限能不能最小化；
- 配额、并发、单次执行时长够不够；
- 出错时能不能看到每个节点的输入输出；
- 以后迁移，工作流与提示词能不能导出或重建。

低代码的锁定量体现在三处：插件生态、发布渠道、配额策略。选之前先确认这三处不会成为硬约束。

## 模型：按节点分工

案例里只有两个需要模型的动作：总结正文、打标签。它们不需要最贵的推理模型，一个稳定的通用模型就够；真正需要复杂规划的任务，才把强模型放到关键节点。

按节点选模型的三个判断：

- **任务复杂度**：抽取、分类、格式转换用中小模型；多步推理、代码生成、长文分析用强模型。
- **输出约束**：需要严格 JSON 的节点，优先选指令遵循稳定的模型；输出格式比“文采”重要。
- **成本与延迟**：高频、短输出的节点用便宜模型；低频、关键判断的节点用强模型。

同一个提示在不同模型上表现可能不一样。选型不是“先定模型再写提示”，而是“模型 + 提示 + 测试集”一起定。

## 工具：按接口稳定性选

工具是 Agent 接触外部世界的接口。优先级大致是：

1. **稳定 API**：字段清楚、有文档、有错误码，最可控。
2. **平台内置插件**：省开发，但受平台配额与版本影响。
3. **代码节点**：适合数据转换、清洗、拼装，不适合替代有状态的外部服务。
4. **RPA / 页面自动化**：没有 API 时的最后手段，脆弱且难维护。

案例里“抓取网页”和“写飞书表格”都用插件：前者输入 URL、输出标题与正文；后者输入表格标识与记录数组、输出写入结果。中间的 JSON 组装用代码节点，因为这是纯数据变换，交给模型反而不可控。

工具选型要看四件事：输入输出是否结构化、失败是否可重试、权限是否最小、调用是否计费。一个工具如果只能“点页面”，就要预期它会因页面改版而失效。

## 选型输出

选型结论不要写成“用了 Coze + DeepSeek”，而要写成一张可复核的表：

| 项 | 选择 | 理由 | 替代方案 |
|---|---|---|---|
| 平台 | Coze | 快速验证、内置发布 | Dify / 自研 |
| 模型 | 通用模型 | 总结与打标签足够 | 强模型用于复杂节点 |
| 抓取 | 网页抓取插件 | 输入 URL、输出标题正文 | 自建抓取服务 |
| 存储 | 飞书多维表格 | 人可读、API 可写 | 数据库 + 管理后台 |
| 通知 | 平台回复 | 先跑通闭环 | 邮件 / IM 机器人 |

这张表让后来的人知道“为什么这么选”，也知道出问题时可换什么。

## 边界

- 低代码平台适合验证与中小规模交付，不适合假设它能无限扩展；配额、并发和插件限制要提前压测。
- 按节点选模型会增加配置复杂度，节点少时收益有限；先跑通，再拆模型。
- 插件不是免费基础设施：它有配额、权限、版本和稳定性风险，关键链路要有替代。
- 选型不是一次性决定。场景、数据量、合规要求变化后，平台与模型都要重评。

## 一句话主线

**平台按交付约束选，模型按节点任务选，工具按接口稳定性选；选型结论要写成“选择 + 理由 + 替代方案”，而不是一句品牌名。**
