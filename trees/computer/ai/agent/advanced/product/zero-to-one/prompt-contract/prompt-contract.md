# 提示词契约

在这类低代码 Agent 里，提示词不是“跟模型聊天的几句话”，而是**节点之间的契约**：上游给什么变量，模型按什么角色处理，输出什么字段，字段怎么被下游消费。

案例的系统提示写得很典型：角色、技能、输出格式、限制。它没有把整篇业务规则塞进去，而是只写这个节点需要模型做的事。

## 系统提示的四段结构

一个可维护的系统提示通常分四段：

1. **角色**：你是谁、服务谁、在什么场景下工作。
2. **技能**：你能完成哪几类动作，每类的输入输出是什么。
3. **输出格式**：返回 JSON、Markdown 还是纯文本；字段名、类型、示例。
4. **限制**：不能做什么、遇到不确定时怎么办、拒绝时怎么回复。

案例的角色是“中文文章总结助手”；技能是“总结正文、提炼标签”；输出格式明确要求 JSON，给出 `summary` 与 `tags` 的示例；限制是“只处理提供的文章内容、不回答无关话题、按给定格式组织”。

这四段里，**输出格式**最容易被写虚。只写“请输出 JSON”不够，要写出字段名、类型、嵌套结构和示例；否则模型会自由发挥，下游解析必失败。

## 用户提示只放变量

系统提示定义“怎么干”，用户提示提供“这次干什么”。案例的用户提示只有两行：

```text
文章标题为：{{title}}
文章内容为：{{content}}
```

`{{}}` 是平台变量占位符，值来自上游抓取节点。用户提示里不再重复角色与格式要求，避免同一套规则写两遍、改一处漏一处。

如果用户提示里塞满业务规则，系统提示就会退化成一句“你是助手”，模型对任务边界的理解会随每次输入漂移。

## 结构化输出契约

案例要求模型返回：

```json
{
  "summary": "文章总结内容",
  "tags": "标签1,标签2,标签3"
}
```

字段名必须和下游代码节点、表格列名一致。三个常见错误：

- 模型多包一层 `{"data": {...}}`，下游按顶层字段取不到；
- `tags` 有时是数组、有时是逗号字符串，类型不稳定；
- 模型在 JSON 前后加解释文字，解析器直接报错。

处理办法是“提示约束 + 代码校验”双保险：提示里给示例、要求只输出 JSON；代码节点解析后检查字段是否存在、类型是否正确，不合法就走失败分支。

## 模型与提示一起调

同一个提示在不同模型上表现不同。案例特别提醒：先选定当前场景合适的模型，再写系统提示与用户提示；换模型要重跑同一组测试。

调试顺序建议：

1. 用一条真实输入，确认模型能产出合法结构；
2. 用三条边界输入（空内容、超长内容、非目标语言），确认失败方式可控；
3. 用下游真实消费方验证字段是否对得上；
4. 再调措辞、示例与温度，不要一上来就堆形容词。

提示词不是越长越准。把“任务、格式、边界、失败方式”写清楚，比写一大段“请你专业、严谨、细致”有用。

## 提示词不该承担什么

- **不该承担知识**：领域知识放检索、知识库或工具，不要塞进系统提示。
- **不该承担权限**：权限由代码与平台管，不能靠一句“不要访问敏感数据”。
- **不该承担确定性转换**：字段改名、类型转换、拼 JSON 交给代码节点，模型只做语义判断。
- **不该承担事实校验**：模型说“已保存”不等于真的保存；写入结果要看插件返回。

## 边界

- 提示词能改善输出质量，但不能修复缺失的数据、错误的流程或没有权限的工具。
- JSON 模式不是万能的：模型仍可能漏字段，必须做 schema 校验。
- 低代码平台的“提示词优化”功能可以给措辞建议，但业务字段与失败语义仍要人定。
- 多语言、长文、表格类输入需要单独测试，不能假设中文短文的提示能直接复用。

## 一句话主线

**系统提示写角色、技能、输出格式与限制，用户提示只放变量；结构化输出要字段级对齐下游，并用代码校验兜住模型的不稳定。**
