# 对外接口设计：把 Agent 暴露成一个可靠的服务

Agent 内部可以很乱，但对外只有一套契约。这套契约要同时满足三类调用方：等人回答的聊天前端、跑批处理的后端、以及要把 Agent 嵌进自己流程的第三方。三者对延迟、断线、重试的要求完全不同，所以接口不能只有一种形态。

这一页讲契约本身，不讲传输层怎么建连。

## 一、先定资源模型

接口的稳定性来自资源模型，而不是端点数量。Agent 服务至少有五个对象：

| 对象 | 生命周期 | 说明 |
|---|---|---|
| Agent | 长期 | 配置与能力的集合（提示、工具、模型、策略） |
| Thread | 长期 | 一条对话/任务上下文，跨多次运行存在 |
| Run | 一次执行 | 对某个 Agent 的一次调用，是最核心的计费与观测单位 |
| Step | 运行内 | 一次模型调用或一次工具调用 |
| Artifact | 长期 | 产出物（文件、报告、图片），挂在 Run 或 Thread 上 |

**Run 是一等公民**。所有状态查询、取消、重试、计费、审计都围绕 Run 展开。把「一次请求」当成无状态的函数调用，后面所有长任务、断线恢复、进度查询的需求都会无处安放。

## 二、三种形态，语义必须一致

| 形态 | 交互 | 适合 | 主要代价 |
|---|---|---|---|
| 同步 | POST 后等响应 | 秒级内的问答、分类、抽取 | 超时即失败，长任务不可用 |
| 异步任务 | 创建 Run → 查状态 → 取结果 | 分钟级以上的任务、批量 | 需要状态存储与轮询/webhook |
| 事件流 | 创建 Run 后订阅事件 | 聊天、需要过程可见 | 连接管理、断线续传、多端一致 |

三种形态应是同一套底层语义的不同投影：同一个 `run_id`，同样的状态机，同样的错误码。分别实现三套会导致「同步接口成功、流式接口报错」这类无法解释的不一致。

> 判断：先定 Run 的资源语义，再选形态。反过来先写端点，早晚要为「流式接口没有 run_id」重做一遍。

## 三、Run 的状态机

```
queued → running → succeeded
                 → failed
                 → cancelled
                 → expired
        running → requires_action → running（人工响应后）
```

四条纪律：

- **终态不可回退**。已 `succeeded` 的 Run 不能再变 `failed`；需要补充结果时新建一个 Run。
- **每次状态变化有单调序号**。客户端据此判断是否漏事件，也用于断线续传。
- **状态必须可查询**。不能只靠流事件告知结果——连接断了，客户端要能凭 `run_id` 补回全量状态。
- **`requires_action` 是显式状态**，不是「正在等」。等待人工的 Run 要能被列出、超时、取消，否则会永久挂起。

## 四、创建与重试的幂等契约

创建 Run 是唯一有副作用的核心写操作，必须幂等：

- 客户端生成 `Idempotency-Key`，同一逻辑请求重发时携带同一个键。
- 服务端在窗口内（如 24 小时）返回首次结果，不重复执行。
- 键的作用域是「租户 + Agent」，不能全局，否则会互相碰撞。
- 重试只对**可重试错误**生效：5xx、超时、限流（带 `Retry-After`）。4xx 里的参数错误重试一万次也一样。

查询类接口一律 GET 且无副作用，可以随便重试。取消接口要幂等：取消一个已取消的 Run 返回成功，不是 404。

## 五、流式：事件是主体，连接不是

流式接口最容易犯的错，是把「连接活着」当成「任务在跑」。

- **事件带 `id`**（单调序号或全局事件 id），客户端记录最后收到的 id。
- **续传用 `Last-Event-ID` 或显式 attach 端点**，服务端补发缺失事件。补不全时给一个 `SNAPSHOT` 事件让客户端重建状态。
- **保活靠注释帧**，不靠业务事件。长时间无事件的 Run 也要发心跳，否则中间层会掐连接。
- **连接断开不代表 Run 结束**。Run 继续跑，客户端重连后接着收。
- **一个 Run 允许多个订阅者**（多端、审计、监控），但写入只有一路；订阅者之间通过事件序号对齐。
- **慢消费者要有策略**：丢弃中间事件并标记「已跳过」，或断开并让其重连取快照。不要无限缓冲。

> 判断：流式接口的正确性标准是「断线任意次、乱序重连、重复投递，最终状态仍然一致」。

## 六、错误契约

错误是接口的一部分，需要和成功一样被设计。

- **稳定错误码**：机器可读的 `code`（如 `run_not_found`、`quota_exceeded`、`tool_timeout`），不随文案变化。人类可读的 `message` 可以改。
- **分类决定客户端行为**：`invalid_request`（改参数）、`rate_limited`（退避）、`upstream_error`（可重试）、`agent_failed`（业务失败，别重试）、`quota_exceeded`（找管理员）。
- **携带 `request_id` 与 `run_id`**：没有这两个 id 的报错，支持工单无法定位。
- **不要把模型/工具失败包装成 500**。模型拒绝回答、工具超时都是**业务结果**，应体现在 Run 状态与结果字段里，而不是 HTTP 层。
- **部分成功要显式表达**：长任务跑了 8 步、第 9 步失败，返回 `failed` 但同时给 `partial_result` 与已完成步骤，别让客户端以为什么都没有。

## 七、人在环接口

`requires_action` 需要两个端点：列出待处理动作、提交响应。

- **动作要有类型与参数 schema**，客户端才能渲染出正确的确认界面（批准、选择、补充信息）。
- **响应带 `action_id` 与幂等键**：用户重复点击不能触发两次执行。
- **超时策略明确**：超时后 Run 进入 `expired`，而不是继续挂起。
- **多端一致**：一端响应后，其他端的待处理项要同步消失；这依赖事件流，而不是各端轮询。

## 八、版本与兼容

- **API 版本放在路径或头**，不放在字段名里。
- **新增字段与新增事件类型不算破坏性变更**；删除字段、改变语义、收紧校验才算。
- **Run 记录里要存「它当时用的是哪个版本」**：Agent 配置版本、提示版本、模型版本、策略版本。否则三个月后无法解释某次结果。
- **弃用要有窗口**：先标记、双写、监控调用量，再下线。直接删字段是最常见的线上事故来源。

## 九、鉴权与配额

- 服务间用 API key 或 OAuth client credentials，用户侧用短期 token；不要把长期 key 塞进前端。
- 租户 id 必须来自鉴权上下文，**不能来自请求体**——否则一个参数就能越权读别人的数据。
- 配额用响应头表达：剩余额度、重置时间、限流速率的 `RateLimit-*` 头，让客户端能自适应而不是撞墙。
- 每个 Run 的计费口径要在文档里写死：按 token、按步数、按工具调用、还是按墙钟时间。

## 十、反模式

- 只有同步接口，长任务靠客户端超时硬扛。
- 流式接口不返回 `run_id`，断线后无法找回。
- 用连接断开作为取消信号。
- 错误统一返回 `500` 或统一 `{"error": "failed"}`。
- 幂等键由服务端生成。
- 租户 id 放在请求体里。
- 状态只有 `running` 和 `done`，没有 `requires_action` / `expired`。
- 模型版本不进 Run 记录。

## 十一、落地顺序

1. 定 Run 资源与状态机（含终态与序号）。
2. 同步接口 + 查询接口（最小可用）。
3. 幂等键 + 错误契约。
4. 异步任务形态（创建/查询/取消/webhook）。
5. 事件流与断线续传。
6. 人在环端点与多端同步。
7. 版本化、弃用流程、配额头。

前三步完成后，接口已经能被后端稳定集成；流式是体验层，不是正确性层。
