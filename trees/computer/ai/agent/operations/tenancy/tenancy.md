# 多租户隔离

一套 Agent 服务同时服务多个客户时，隔离不是"加个 tenant_id 字段"就完事。真正会出事故的是四处：租户身份从哪来、数据在哪分区、缓存与索引会不会串、删租户时能不能真的删干净。

## 租户身份必须来自可信来源

- 从**已签名的凭据**里取（token claim、session 断言），不要把 `X-Tenant-Id` 这类请求头当依据——它可由客户端任意伪造。
- 租户 id 与用户身份要分开校验：用户属于哪个租户属于服务端事实，不能让模型或前端自行声明。
- 一次请求只允许一个租户上下文；出现"跨租户查询"要有独立的、显式审批的内部接口，而不是复用用户请求通道。

## 数据面分区

按存储形态分区，而不是靠"查询时记得过滤"：

- **关系型**：独立库或独立 schema 优先；共享表时用行级安全（RLS）等强制机制，让过滤在数据库层完成，应用漏写条件也不会泄露。
- **向量索引**：一租户一分区或一 collection，检索时带强制过滤条件。共享索引里只做元数据过滤，一旦忘了带条件就是全库召回。
- **对象存储**：前缀按租户划分，签名 URL 绑定租户，避免拿到一个 URL 就能读别人的文件。
- **缓存**：键里包含租户；提示缓存尤其危险——前缀相同的请求可能跨租户命中，绝不能把 A 的文档片段放进共享前缀。
- **记忆与工作区**：会话记忆、检查点、临时文件都按租户命名空间隔离；长任务的恢复也要校验租户未变。
- **模型侧**：微调数据、评测集、少样本示例不跨租户混用；给某租户定制的提示模板不要把别家内容带进去。

## 配额与噪声邻居

共享资源必须按租户设上限，否则一个客户的重任务会拖垮所有人：

- token 与费用上限（按日/按月，触发降级或拒绝）；
- 并发任务数与工具调用速率；
- 存储与索引规模；
- 长任务的最大墙钟时间与最大轮次。

配额触发要可观测：限流、降级（缩小上下文、换小模型）、拒绝，三种策略要按场景选，并且让租户看得见自己被限的原因。

## 生命周期：开通、导出、删除

- **开通**：租户初始化要幂等，重复开通不产生第二套数据面。
- **导出**：按租户导出对话、产物、记忆，格式要能脱离平台读。
- **删除**：真正的难点在"删干净"——向量条目、缓存键、备份、日志、派生的索引与摘要都要覆盖；删除请求要有可核对的完成报告。
- 删除与在途任务冲突时，先冻结租户，再终止任务，最后清理数据。

## 审计与排障

日志、追踪、指标一律带租户维度，且能在聚合视图里按租户切片。排障时最常问的两句是"这是哪个租户的"和"这个租户的调用打到了哪些下游"，缺了租户标签就只能全量搜。

## 常见失败模式

- 租户 id 取自可伪造的请求头，等于没有隔离。
- 共享表忘记加过滤条件，一次全表召回把别家数据带进答案。
- 缓存键不含租户，提示缓存跨租户命中。
- 索引重建时按全库重跑，旧租户数据被带进新索引。
- 只删业务表，向量与缓存残留，等于删了壳没删内容。
- 配额只设总量不设单租户，噪声邻居拖垮平台。
- 内部员工工具复用生产通道却没有显式越权标记，审计上分不清是运维还是客户行为。

## 什么时候需要

需要：一个部署服务多个互不信任的客户；或同一企业内部多个部门之间有数据边界。单租户自建部署、内部小团队共用一套凭证的场景，做好权限即可，不必引入完整租户体系。
