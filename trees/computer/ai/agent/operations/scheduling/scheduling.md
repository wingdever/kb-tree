# 调度与并发：当多个请求抢同一份状态

单用户的 Agent 几乎不需要调度：来一个请求，跑一遍。一旦并发上来，问题全部集中在**共享资源**上——同一个会话、同一个工作区、同一份预算、同一个有速率限制的工具。这些冲突不会自己消失，只会在某个深夜以「状态被覆盖」「额度莫名用光」「两个 worker 各执行了一半」的形式爆发。

这一页只讲运行时调度，不讲任务怎么拆。

## 一、先分清三种请求

调度策略取决于请求要不要碰状态：

| 类型 | 例子 | 能否并行 | 关键约束 |
|---|---|---|---|
| 无状态任务 | 单轮问答、翻译、总结 | 可以 | 只受资源与配额约束 |
| 有状态会话 | 多轮工具调用、需要记忆的任务 | 同一会话内不可并行写 | 单写者 |
| 长任务 | 批量处理、监控、构建 | 可以并行，但占资源久 | 配额、公平性、可取消 |

> 判断：只有「读」能并行，「写」必须串行。想并行写同一会话，先证明写入之间没有依赖——多数情况下这个证明不成立。

## 二、一次请求的完整生命周期

```
准入 → 排队 → 获取租约 → 执行（带检查点）→ 提交 → 释放
```

每一环都要有超时与失败出口：

- **准入**：判预算够不够、租户配额还有没有、当前是否处于熔断。不满足就在这里拒，别让请求跑一半才发现超预算。
- **排队**：有上限，有可见的排队位置。无限队列等于把内存当磁盘用。
- **获取租约**：拿不到就等或降级，不能「先干起来再说」。
- **执行**：每个可中断点放检查点，便于取消与恢复。
- **提交**：副作用落地的最小临界区，尽量短。
- **释放**：无论成功失败都要释放，包括异常与超时路径。

## 三、单写者：会话并发的唯一硬规则

同一会话在同一时刻只允许一个写者。理由不是性能，而是**一致性**：两个写者各自基于旧状态推理，最后一方覆盖另一方，用户看到的是「Agent 忘了刚才说的话」。

实现有三档，按复杂度递增：

| 方式 | 机制 | 优点 | 代价 |
|---|---|---|---|
| 进程内串行 | 单进程队列按 thread 串行 | 最简单 | 无法多 worker |
| 粘性路由 | 按 thread id 哈希到固定 worker | 无需锁，延迟低 | 热点会话压单机；worker 挂了要迁移 |
| 分布式租约 | 抢租约 + 心跳续租 + fencing token | 弹性最好 | 复杂，需处理脑裂与续租失败 |

分布式租约的关键不是「加锁」，而是**防旧持有者写入**：租约带一个单调递增的 fencing token，写存储时把 token 一起提交，存储端拒绝 token 小于当前已见值的写入。否则一次 GC 停顿就足以让过期持有者把新状态覆盖掉。

**用户可见的并发**（多端同时打开同一会话）用另一套语义：不是锁，而是**租约 + 显式接管**。一端持有租约，另一端只能看；接管需要用户确认，接管后旧端降为只读并收到提示。

## 四、队列：优先级、公平、背压

严格优先级必然导致低优请求饥饿。可用的组合是：

- **基础优先级**（付费等级、任务类型）+ **老化**（等待越久权重越高）。
- **按用户轮转**而不是按请求轮转，避免一个用户批量提交占满队列。
- **并发度按租户分配**，不按全局分配，防止单租户拖垮所有租户。

背压要在三个位置做，缺一个都会雪崩：

1. **入口**：队列长度上限 + 每用户在途请求上限，超了直接 429/503，并给出重试建议。
2. **执行中**：下游工具限流时，降低拉取速率而不是攒内存；工具返回 429 要退避，不能立即重试。
3. **预算**：接近上限时降级（缩短上下文、换便宜模型、拒绝非必要工具），而不是硬跑到爆。

> 判断：背压的目标是让系统在过载时**变慢**，而不是**变错**。宁可拒绝，也不要超时后写一半。

## 五、幂等与去重

重试是必需品，副作用是敌人。三个概念要分清：

- **幂等键（idempotency key）**：客户端或网关生成，同一逻辑请求重发时携带同一个键。
- **去重窗口**：键 + 时间窗（如 24 小时），窗口内重复请求直接返回首次结果。
- **执行记录（effect log）**：每次有副作用的工具调用落一条记录，键为「run id + step id」，重放时先查记录，命中则跳过执行。

语义上只能做到**至少一次**投递，所以每次副作用都要自带「可判定是否已执行」的依据：

| 副作用类型 | 判定依据 |
|---|---|
| 创建订单 | 业务唯一键（外部单号） |
| 发消息 | 消息 id + 发送方幂等键 |
| 写文件 | 内容哈希 + 版本号 |
| 转账 | 请求幂等键 + 外部流水号 |

> 判断：幂等键必须由调用方生成。让服务端自己生成，重试时就变成了两次不同请求。

## 六、预算并发记账

多任务同时花钱，最容易出的事故是「每个任务都觉得自己还有额度」。正确做法是**预留—结算**：

1. 准入时按估算值预留（reserve），从可用额度里扣掉。
2. 执行中按实际消耗更新，不超预留太多。
3. 结束时结算（settle），多退少补。

预留要留余量，估算偏低会导致执行中被迫中断；估算偏高会让并发度虚假受限。经验值是按同类任务的历史 P90 预留，而不是均值。

预算维度至少四个：token、工具调用次数、墙钟时间、外部 API 费用。任一维度触顶都要能优雅收尾——把已有结果整理成部分交付，而不是直接报错丢弃。

## 七、取消与抢占

- **协作式取消**：在循环的每个边界检查取消信号，而不是硬杀线程。硬杀会留下写了一半的文件与已扣费的调用。
- **不可中断区**：副作用提交阶段（写库、发消息、扣款）必须走完或明确回滚，不能在半途被打断。
- **抢占策略**：高优请求到达时，是否可以抢占低优长任务？多数系统不该抢占，而该排队——抢占带来的补偿逻辑远比省下的等待时间贵。
- **取消后的收尾**：释放租约、结算预算、写一条「被取消」的终态记录、通知订阅方。取消不是「消失」，是一个正常终态。

## 八、该看哪些指标

| 指标 | 说明 | 异常信号 |
|---|---|---|
| 队列等待 P50 / P99 | 准入后的等待时长 | P99 远高于 P50，说明有长任务阻塞 |
| 租约冲突率 | 抢锁失败比例 | 持续偏高，说明热点会话或租约过短 |
| 租约持有时长 P99 | 单次持锁时间 | 接近 TTL，说明续租机制有问题 |
| 去重命中率 | 重复请求比例 | 偏高说明客户端重试策略有问题 |
| 最大饥饿时长 | 某请求最长等待 | 超过 SLA 说明老化策略失效 |
| 取消完成时间 | 从信号到资源释放 | 过长说明检查点太稀 |

## 九、反模式

- **无上限队列**：过载时把内存耗尽，最后整机重启。
- **锁代替单写者设计**：加锁只是补丁，正确做法是让写入路径天然串行（按 thread 分区）。
- **重试不带幂等键**：一次超时变成两次扣款。
- **租约无 fencing**：脑裂时旧持有者仍能写。
- **预算按均值预留**：一半任务执行中被截断。
- **取消靠杀进程**：残留半写状态，恢复时无法判断是否已提交。
- **优先级无老化**：低优请求永久饥饿，且没人发现。

## 十、落地顺序

1. 会话内单写者（进程内队列足够）。
2. 入口背压与队列上限。
3. 幂等键 + 执行记录（先覆盖有副作用的工具）。
4. 预算预留—结算。
5. 多 worker 时再上租约与 fencing，不要一开始就做分布式锁。

前三步完成，多数系统的并发事故就消失了；第四、五步是在规模与弹性上的投资。
