# 云端 Agent 运行

云端 Agent 的形态是：**Agent 跑在远端机器上，客户端只是入口**。用户从浏览器、桌面端或移动端连上去，看到的是同一份工作区与同一段对话；关掉客户端，任务还在跑。这与"本地跑一个 Agent、调用远端模型"是相反的分工——算力、文件、凭据、进程都在云侧，客户端只负责输入、渲染与少量本地桥接。

## 与本地 Agent 的四个实质差别

- **生命周期解耦**：客户端连接是短暂的，会话与任务可以是长时间的。用户午休时关掉页面，回来还能看到进度——这要求会话状态不挂在连接上。
- **环境是产品的一部分**：本地 Agent 用用户自己的机器与安装，云端必须提供一个可复现的镜像、固定的依赖、明确的资源上限。用户不该关心"云机上装了什么"。
- **并发与配额成为一等问题**：一个用户可能开多个会话，多个用户在共享集群上跑任务，CPU/内存/磁盘/并发都要计量与限制。
- **数据驻留变了**：代码、文档、密钥从用户设备转移到了云侧，删除、导出、审计、合规都成为运行时设计的一部分，而不是事后补。

## 三种运行形态

| 形态 | 特征 | 适合 | 代价 |
|---|---|---|---|
| 一次性任务沙箱 | 每个任务起一个干净环境，结束即销毁 | 批量改造、测试、数据分析等无状态任务 | 每次冷启动；无长期上下文与工作区 |
| 常驻工作区 | 用户有一个长期存在的云端空间，会话在里面反复开合 | 持续开发、长期项目、需要保留文件与环境 | 状态治理复杂；空闲资源与成本 |
| 混合 | 常驻工作区 + 每次任务起子沙箱执行危险动作 | 既要连续性又要隔离的团队场景 | 两套生命周期要协调 |

选择取决于"用户是否需要回来接着干"。不需要就做一次性，简单得多；需要就必须正面处理持久化、版本与配额。

## 关键判断：连接不等于会话

云端 Agent 最容易犯的错，是把会话状态绑在连接上：连接断开就认为任务结束，重连就重跑。正确的分层是三层各自独立：

- **连接层**：客户端与网关之间的长连接，可断可重连，允许同一会话多条连接。
- **会话层**：一段有状态的对话与任务，由服务端持有，有 id、有事件日志、有所有权。
- **工作区层**：文件与进程，可能比会话活得更久，也可能随会话销毁。

三层分开之后，"用户换了设备""网络抖了一下""客户端崩了"都只是连接层事件，不影响任务本身。

## 典型链路

客户端 → 网关（鉴权、租户路由、限流）→ 会话服务（编排、事件分发）→ 运行时（容器或微虚拟机里的 Agent 进程）→ 工具与外部系统。

其中三处最容易出问题：网关的鉴权是否把租户与用户身份带全、会话服务的事件是否可重放、运行时的资源是否有硬上限。

## 公网入口

把服务从内网推到公网，会多出三道独立约束：入口层要受浏览器信任，客户端要满足安装条件，主机所在地要满足备案要求。入口层解决连接可信，客户端解决交付形态，备案解决主机合规；任意一层缺失，都不能由另外两层补上。

## 什么时候不该用云端形态

- **必须访问本地资源**：内网数据库、本地 GPU、用户机器上的私钥、需要人工插拔的设备。
- **数据不能出域**：合规要求数据不离开用户设备或指定机房。
- **延迟敏感且交互密集**：每步都要毫秒级反馈的场景，远端往返本身就是瓶颈。

这些场景更适合本地 Agent + 远端模型，或边缘部署。

## 常见失败模式

- 会话状态挂在连接上，断线即丢，用户回来发现任务重跑了一遍。
- 每个任务都拉全量镜像，冷启动几十秒，交互式体验崩坏。
- 工作区无配额，一个会话写满磁盘影响整台云机。
- 客户端承担了业务逻辑，换端行为不一致。
- 云端进程用长期高权凭证，用户之间权限边界模糊。
- 没有"会话结束"的明确定义，进程与存储长期泄漏。
