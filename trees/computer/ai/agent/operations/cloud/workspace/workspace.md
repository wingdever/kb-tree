# 云端工作区与持久化

云端 Agent 的"工作区"是用户真正在意的东西：代码、笔记、产物、装好的依赖。它比会话活得更久，也比运行时更该被认真设计。核心问题是三句：**从哪个镜像起、改变写到哪一层、结束时留下什么**。

## 镜像是契约，不是细节

- **镜像要固定版本**：`python:3.12-slim@sha256:…` 这种带摘要的引用，而不是浮动 tag。否则某天上游更新，用户的任务莫名其妙开始失败。
- **基础镜像尽量薄**：只装运行时与常用工具，语言级依赖由工作区自己装。镜像越大，冷启动越慢，攻击面也越大。
- **预装热路径**：把高频依赖（包管理器缓存、常用 CLI、模型 tokenizer）做进镜像或挂载缓存层，能把首次任务的几十秒降到几秒。
- **镜像变更要有版本号**：用户能查到"我这次用的是哪版环境"，也能选择固定在旧版本上。

## 文件系统分层

典型的组织方式：

- **只读基础层**：镜像内容，所有人共享，不写。
- **会话可写层**：overlay 上的上层，任务期间的写操作落在这里，销毁即消失。
- **持久卷**：用户要长期保留的目录（项目源码、产物、配置），独立挂载，跨会话复用。

判断某个目录该放哪层，只看一个问题：**用户下次回来还需要它吗**。需要就进持久卷，不需要就留在可写层随会话消亡。

## 快照与恢复

- **快照点**：任务开始前、危险操作前、会话结束时。三处各有用途：回滚、审责、留存。
- **快照要能单独恢复**：按用户/工作区粒度恢复，不能只支持整机恢复——否则一个租户的数据损坏要牵连所有人。
- **快照不等于备份**：快照在同一存储上，误删会被一起带走；重要数据要有异地备份。
- **恢复的语义要写清**：恢复到哪个时间点、在途任务怎么处理、外部副作用（已发出的邮件、已下的单）是否需要人工对账。

## 配额与清理

工作区是最容易失控的资源：依赖缓存、日志、模型权重会无声地涨。

- **磁盘配额按工作区**（项目配额或独立卷上限），写满只影响自己。
- **文件数量上限**同样重要，几百万小文件会让备份与扫描崩溃。
- **缓存目录要可回收**：包缓存、编译产物、临时文件设 TTL，或按最近使用淘汰。
- **清理要可解释**：删了什么、为什么删、用户能否找回（回收站或快照），三件事都要有交代。
- **空闲工作区**：长期不用的工作区应归档（压缩冷存）而不是直接删除。

## 产物导出与交付

任务产出的文件不能只留在云端：

- 显式**导出白名单**（目录、扩展名、体积上限），而不是整目录打包；
- 导出物要有**清单与校验**（路径、大小、哈希），下游才能确认拿到的是同一份；
- 大文件走**临时签名 URL**，绑定租户与过期时间；
- 交付形态要跟用户预期一致：预览用网页，下载用归档，长期保存进用户自己的仓或云盘。

## 与本地同步的取舍

"云上有一份、本地也有一份"听起来自然，实际最容易出问题：

- **单向优先**：云端为主、本地只读拉取，或本地为主、云端只读同步，冲突面最小。
- **双向同步的代价**：需要冲突检测、合并策略、删除传播，还要处理"离线修改"与"云端并发任务改同一文件"。多数产品低估了这部分工作量。
- **代码场景**：优先用版本控制（git）做同步与合并，而不是自研文件同步；工作区里保留一个远端，用户随时可推可拉。

## 依赖装得上、装得对

工作区里最容易"今天能跑、明天跑不起来"的不是代码，是依赖：

- **锁定文件进版本库**：`package-lock.json`、`poetry.lock`、`requirements.txt` 带精确版本；只写 `>=` 等于把复现权交给了上游。
- **缓存层与安装解耦**：包缓存挂成单独卷，重建会话时复用，既省时间也减少对外网依赖；缓存损坏要能一键清空重建。
- **安装失败给可读原因**：区分网络不可达、版本冲突、缺少系统库，三种失败的处理方式完全不同；笼统报"安装失败"会让用户反复重试。
- **系统级依赖进镜像**：编译工具链、图形库这类需要 root 的东西放进镜像，不要指望任务中 `apt install`。

## 多租户隔离的四个面

一个工作区出问题不该影响别人，隔离要在这四处同时成立：

| 面 | 做法 | 漏掉的后果 |
|---|---|---|
| 文件系统 | 每会话独立挂载点与路径命名空间 | 路径穿越读到他人文件 |
| 进程与用户 | 独立 uid、独立进程组 | 一个失控进程压垮整机 |
| 网络 | 出网策略与私有网段隔离 | 工作区之间可互相扫描 |
| 资源 | CPU/内存/磁盘/文件数配额 | 单个租户吃满配额拖垮宿主 |

> 判断：隔离强度要按"工作区里跑的是谁的代码"来定；用户能自己执行命令，就当作不可信代码处理，而不是当作自己的服务。

## 常见失败模式

- 用浮动镜像 tag，某次上游更新后大量任务失败且无法复现。
- 所有东西写可写层，会话一销毁，用户一天的产出全没了。
- 持久卷无限增长，磁盘写满拖垮整台云机。
- 快照只支持整机回滚，单用户误操作只能全量恢复。
- 导出不做体积限制，一次把几十 G 传给客户端。
- 双向同步没有冲突策略，本地与云端互相覆盖。
- 删除工作区时漏掉缓存、快照、导出副本，数据"删了还在"。

## 什么时候可以简化

一次性任务、产物只有一个小文件、用户不需要回来接着干的场景：用完即销毁的临时目录 + 结果上传，是最省事也最安全的做法。工作区持久化的复杂度只在"用户会回来"时才有必要付。

## 一句话主线

工作区设计的核心是**分清"会消亡的"和"要留下的"**：能重建的交给镜像与可写层，只有用户真正在意的东西才进持久卷——判错一处，要么数据丢，要么磁盘满。
