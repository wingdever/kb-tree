# 移动端推送通道

移动端推送看起来只是“服务器把通知发给客户端”，真正难的是：**手机通常没有公网地址，服务器不能主动连它；App 进程又会被系统冻结或杀死。** 所以“服务器直推”只在客户端保持连接、且进程还活着时成立。要在 App 退到后台甚至被杀后仍然收到消息，就必须借助一条系统级的常驻通道。

## 移动端为什么不能只靠服务器直推

手机在 NAT 后面，没有固定公网 IP。服务器无法主动向手机发起 TCP 连接，只能由客户端先连服务器，并维持一条出站连接。

这条连接有三个天然弱点：

- App 进入后台后，进程会被系统限制、冻结或回收；
- 省电策略会切断长时间空闲的网络连接；
- 用户手动清理、厂商清理、低内存回收都会杀掉进程。

因此，移动端有两条路：

1. **App 自己维持长连接**：前台可靠，后台取决于系统是否允许进程活着；
2. **使用系统推送通道**：由系统或厂商的常驻服务维持连接，收到消息后唤醒 App。

真正稳定的推送通常两条都用：在线走 App 长连接，离线走系统推送，打开 App 后再做一次增量同步。

## 两层连接：App 长连接与系统推送

| 层 | 谁维持连接 | 连接对象 | 主要限制 |
|---|---|---|---|
| App 长连接 | App 进程 | App 自己的服务器 | 进程被杀即断；后台受省电、自启动、厂商清理限制 |
| 系统推送 | 系统或厂商的推送守护进程 | 厂商推送服务 / FCM | App 只能注册 token；能否使用取决于设备、系统、应用商店与签名 |

App 长连接是“应用自己保活”。Android 允许前台服务维持连接，但会带来常驻通知、耗电和用户体验代价；普通后台进程不可能长期稳定。系统推送则是另一条连接：App 不拥有它，只拿到一个设备 token，由系统服务在收到消息时唤醒 App。

这也是“中心化”的来源：**不是数据必须集中，而是唤醒路径必须经过一个长期在线的推送服务。** 这个服务可以是华为、小米、OPPO、vivo 等厂商的推送服务，也可以是 FCM，或者是用户自建的 UnifiedPush 分发器。

## 国内 Android 的推送通道

国内 Android 没有统一的系统推送协议。常见通道包括：

- 华为 Push Kit、小米推送、OPPO / vivo / 荣耀等厂商推送；
- 个推、极光等第三方聚合推送；
- FCM：依赖 Google Play services，主要用于海外或有 GMS 的设备；
- UnifiedPush / ntfy：由用户或组织自建分发器，App 通过标准接口接收；
- 前台服务 + WebSocket / SSE：只在 App 存活时可靠。

FCM 不是“Android 推送的唯一正确答案”。国内很多设备没有 GMS，网络也不稳定，FCM 不能作为大陆主通道。反过来，厂商推送也不是统一协议：每一家都有自己的 SDK、token、服务端 API、限流规则和上架要求。

## 大厂为什么看起来“永远在线”

微信、QQ、钉钉、飞书这类应用的稳定到达，通常不是单靠一条 App 自建连接，而是多层组合：

- 应用自己的长连接，负责在线实时消息；
- 厂商系统推送，负责 App 被杀后的唤醒；
- 后台白名单、自启动权限、预装或系统级合作，保证长连接更容易存活；
- 打开 App 后按游标同步，补上离线期间的消息；
- 专门的推送中台处理多厂商、重试、去重、设备失效和到达率。

> 判断：普通 App 可以复制“长连接 + 系统推送 + 增量同步”的架构，但复制不了厂商白名单、预装、系统签名合作这些后台存活特权。把“微信级稳定”当成默认目标，会低估系统权限的差距。

即使有大厂体量，后台保活也不是绝对的：系统仍可能杀进程、用户仍可能关闭自启动、厂商策略会随版本变化。所以大厂也不会只依赖长连接，系统推送和离线同步始终是兜底。

## 推送只负责唤醒，正文走同步

稳定的移动推送通常不把完整消息塞进通知，而是发一个很短的唤醒信号：

```text
用户服务器 → 推送通道 → 唤醒 App → App 回连用户服务器 → 按游标拉增量消息
```

这样做有三个好处：

- 推送服务看不到完整正文，数据仍留在用户自己的服务器；
- 消息不会因为推送丢失而永久丢失，App 打开后可以补拉；
- 多设备、多端在线时，用同一套游标与去重逻辑收敛，不依赖推送的到达顺序。

通知栏可以展示摘要，但正文、附件、会话状态仍以数据服务为准。推送是“提醒”，不是“消息存储”。

## 自建多服务器的三条路线

当用户自己配置服务器时，推送的难点不是“怎么发”，而是**App 级推送凭据放在谁手里**。FCM 项目、厂商 AppKey、包名和签名都绑定这个 App，不属于某个用户服务器。

| 路线 | 谁持有凭据 | 适用 | 代价 |
|---|---|---|---|
| 官方 relay | App 方 | 公共产品、普通用户 | 引入中心服务；服务器只发唤醒请求 |
| 每服务器自带凭据 | 各服务器管理员 | 高级自建、单用户 | 配置复杂；secret 分发风险高；App 要多项目适配 |
| 不做原生推送 | 无 | MVP、前台使用 | 后台不保证实时；可用 UnifiedPush / ntfy / 前台连接兜底 |

官方 relay 的典型分工是：用户服务器把“唤醒设备”的请求发给 relay，relay 持有 FCM / 厂商凭据并负责路由；relay 只看到设备 token 和节点标识，不接触消息正文。这样既保留数据自建，又不需要把 service account 发给每个节点。

每服务器自带凭据在技术上可行，但把 FCM service account 或厂商 secret 分发到所有自建节点，等于让任一节点泄露就影响全量设备；同时 App 还要按节点初始化多个推送项目、维护 token 映射。它适合少数愿意承担配置责任的管理员，不适合作为普通用户默认路径。

不做原生推送时，仍可以用 UnifiedPush / ntfy 让用户自建分发器，或在前台用 WebSocket / SSE。前者需要安装 distributor，后者一退后台就不可靠；产品上要明确这是“打开 App 才实时”，不是“永远在线”。

## 工程判据

先回答四个问题，再选推送方案：

- 通知必须在 App 被杀后到达吗？不需要，就前台连接足够。
- 目标用户主要在大陆吗？是，就不能把 FCM 当主通道。
- 是否坚持完全自建？是，就只能走用户自建 UnifiedPush / ntfy，或接受后台不实时。
- 谁持有 App 级推送凭据？公共产品需要官方 relay；高级单节点可以让管理员自带。

一个可落地的分层是：

1. 应用内 SSE / WebSocket 保证前台实时；
2. 推送抽象成 `PushProvider`，不让业务代码直接依赖 FCM；
3. 海外构建接 FCM，国内构建接厂商通道或聚合推送；
4. 自建场景保留 UnifiedPush / ntfy 作为可选；
5. 推送只发唤醒信号，正文永远回源到用户服务器拉取。

## 常见失败模式

- 把 FCM 当成 Android 的唯一推送标准，国内设备直接收不到。
- 把 FCM service account 或厂商 secret 放进客户端、二维码或每个自建服务器。
- 以为写了双进程、守护进程就能保活，忽略系统后台限制和厂商清理。
- 只做 App 长连接，不做系统推送，App 被杀后消息全丢。
- 推送携带完整正文，推送服务变成数据旁路。
- 没有 token 失效清理，设备换机后持续向旧 token 发送。
- 没有增量同步与去重，推送重复或乱序时客户端出现重复消息。
- 把“通知送达”当成“消息已消费”，没有已读 / 游标确认。

## 一句话主线

移动端推送的本质不是“服务器直连客户端”，而是**用一条系统级的中心化通道唤醒客户端，再让客户端回源自建数据服务做增量同步**；能自建的是数据与分发器，不能自建的是手机厂商对后台进程的许可。
