# 会话生命周期与重连

云端 Agent 的用户体验八成取决于会话模型是否做对。做错的典型症状：切换一次网络就从头再来、手机锁屏五分钟回来任务没了、两个窗口看到不同的进度。根因都是**会话状态被绑在连接上**。

## 五个阶段

**1. 创建**：拿到会话 id，绑定租户、用户、工作区、运行时实例。创建要幂等——同一请求重复到达不能产生两个会话。

**2. 接入（attach）**：客户端连上并声明"我要观察这个会话"。接入时服务端要下发两样东西：当前状态快照、以及从某个事件序号开始的增量。客户端据此渲染，不必重放全部历史。

**3. 运行**：Agent 在运行时里执行，产生的每一类事件写入会话日志——用户输入、模型文本增量、工具调用与结果、状态变更、错误、产物生成。

**4. 空闲**：无连接、无任务时的等待态。要区分"可回收"与"必须保留"：工作区可能需要长期保留，运行时进程通常不该长期占资源。

**5. 结束与回收**：正常结束（任务完成、用户主动结束）、超时结束、异常结束。结束时必须固化产物（文件、报告、日志），写清结束原因，并释放运行时资源。

## 事件日志是可重放的核心

会话日志按单调递增序号追加，每条事件带：序号、类型、时间、载荷、来源（用户/模型/工具/系统）。它带来三个能力：

- **断线重连**：客户端带上"我处理到第几条"，服务端只补发之后的增量。序号缺失即报错，而不是静默跳号。
- **多端一致**：新接入的设备先取快照再追加量，不会看到半截状态。
- **复盘与审计**：一条任务的完整轨迹可回放，也是评估与归因的数据源。

关键细节是**幂等**：重连补发时客户端可能已处理过部分事件，事件必须带可去重的标识（序号天然满足），且客户端重复处理不能造成重复副作用（例如重复执行工具）。

## 连接管理与弱网

- **心跳**：双向心跳用于发现半开连接（TCP 已死但双方都以为还在）。只靠 TCP 超时要等几分钟，交互体验无法接受。
- **重连退避**：指数退避 + 抖动，避免故障后所有客户端同时重连打垮网关。
- **增量优先**：文本增量、状态变更都按小块推送；整段重发既费流量又会让界面闪回。
- **可降级**：弱网时先保证"状态与关键结果"到达，暂停高频的中间过程渲染。

## 谁有权写这个会话

一个会话可以有多个观察者，但**写者必须唯一**：

- 观察者只读，可随时接入退出；
- 写者持有一个带过期时间的租约，切设备时做一次显式"接管"；
- 接管时旧连接收到明确的"你已被接管"事件，而不是静默失效；
- 用户输入要带来源标识，事后能分辨是哪台设备、哪次操作。

没有唯一写者的系统，会在两端同时发消息时产生交错的工具调用与自相矛盾的上下文。

## 结束语与超时的分寸

- **空闲超时**：只回收运行时，保留工作区与会话记录；用户回来能接着聊，而不是重新开一个。
- **任务超时**：长任务要有墙钟上限与"阶段性产物已保存"的保证，否则超时等于全丢。
- **硬删**：涉及数据删除时，先冻结会话、终止任务、清理向量与缓存，再删记录，最后给出可核对的完成报告。

## 常见失败模式

- 会话 id 与连接 id 混用，重连即新会话。
- 事件不带序号，客户端只能全量重拉，延迟与流量双高。
- 补发事件时未去重，工具被重复执行。
- 多端同时写入，上下文交错，模型行为漂移。
- 空闲只断连接不回收进程，云机上堆满僵尸会话。
- 超时直接销毁工作区，用户半小时的工作消失。
- 结束不写原因，事后无法区分"用户取消"与"系统崩溃"。

## 什么时候可以简化

单用户、单端、任务短于一次连接的场景（例如一次几分钟的批处理），可以不做事件日志与重连——直接把结果当响应返回即可。会话模型的价值随"任务时长 × 端数量 × 网络不确定性"增长，三者都低时不必上。
