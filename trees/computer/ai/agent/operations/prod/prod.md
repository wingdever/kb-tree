# 07 生产实践与避坑

## 常见陷阱与缓解

| 陷阱 | 描述 | 缓解 |
|---|---|---|
| **幻觉** | 模型自信地陈述虚假内容 | RAG；只从检索上下文回答；引用；事实性评估 |
| **工具错误与误用** | 调错工具或传错参数 | 少而描述清晰的工具；严格校验；可推理的错误；工具调用测试 |
| **失控成本与循环** | Agent 永不停下 | 迭代/token/时间硬上限；成本告警 |
| **评估缺口** | 凭轶事发布 | 上线前建评估集；从生产失败中扩充 |
| **提示注入** | 用户输入或检索文档中藏恶意指令 | 输入清洗；最小权限工具访问；敏感动作人工审批 |
| **过度工程** | 过早使用多智能体架构 | 从简单开始；仅在确有可测收益时加复杂度 |
| **无可见性** | 无法解释失败运行 | 从第一天起做完整追踪 |

## 成本与延迟控制

单次请求可能触发多次模型调用：

- 封顶循环（迭代、token、时间）
- 按步骤选模型：小快模型做分类/路由，前沿模型做真正推理
- 缓存嵌入、频繁检索、重复提示前缀
- 裁剪上下文：摘要历史 + 只留最相关检索块（更短的提示更便宜也往往更准）
- 并行化无依赖的步骤

并行化模式的一个妙用：一个调用回答用户的同时，另一个调用并行做内容安全筛查——花的是 token，不是额外的墙钟时间。

## 可观测性：系统的控制面板

> 可观测性不是可选工具，而是整个系统的控制面板。

- **追踪**：提示词、推理、工具调用与结果、token、延迟，每次运行全记录。
- **指标**：成功率、单次成本、延迟、工具错误率、token、循环次数，并对异常告警。
- **反馈闭环**：用户标记坏答案 → 直接进入评估集。
- **发布**：feature flag、窄范围、人工介入、即时回滚。

## 三条核心原则（Anthropic）

1. **简单**：成功的 Agent 依赖简单、可组合的模式，而非重量级框架。从最简单方案开始，仅在有证据时加复杂度，并权衡延迟与成本。
2. **透明**：暴露 Agent 的规划步骤；黑箱系统难以维护。
3. **ACI（Agent-Computer Interface）**：工具文档与提示工程同等重要。在构建 SWE-bench Agent 时，Anthropic 发现打磨工具花的时间超过打磨提示词——例如修复目录切换后的相对路径失败问题。

## 构建 vs 合作

**自建**适合：有 ML 与后端工程师能负责评估与运维；Agent 是产品核心；能承诺持续维护。

**合作/借助外部**适合：追求速度；内部缺乏检索、评估与 LLM 可观测性经验；想避免昂贵的早期错误。好的合作方不只交付 demo，还应提供评估框架、护栏、监控和知识转移。

## 贯穿全过程的判断准则

- 工作流优先：能用确定性工作流解决的，不要交给 Agent。
- 评估是永久设施，不是上线前的某个阶段。
- 护栏是你拥有的确定性代码，不是对模型的请求。
- 工具设计=接口设计；先修工具，再调提示词。
- 先让正常路径跑通，再考虑样式美观，最后才考虑恶劣条件下的健壮性。
- 把 Agent 当微服务架构：路由层、执行层、记忆存储、严格护栏。掌握架构后，底层模型是可替换的。

## 一句话总结

> 把任务收敛清楚 → 能用工作流就不用 Agent → 审慎选模型 → 亲手掌握循环 → 像设计 API 一样设计工具 → 用 RAG 接地业务数据 → 谨慎管理记忆 → 加护栏 → 把评估做成永久系统 → 全链路追踪 → 控制成本延迟 → 窄范围带人工监督发布。

把评估与监控当作一等公民而非附加品的团队，才是那些 Agent 能活过 demo 阶段的团队。
