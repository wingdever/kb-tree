# 生产实践与避坑

## 常见陷阱与缓解

| 陷阱 | 描述 | 缓解 |
|---|---|---|
| **幻觉** | 模型自信地陈述虚假内容 | RAG；只从检索上下文回答；引用；事实性评估 |
| **工具错误与误用** | 调错工具或传错参数 | 少而描述清晰的工具；严格校验；可推理的错误；工具调用测试 |
| **失控成本与循环** | Agent 永不停下 | 迭代/token/时间硬上限；成本告警 |
| **评估缺口** | 凭轶事发布 | 上线前建评估集；从生产失败中扩充 |
| **提示注入** | 用户输入或检索文档中藏恶意指令 | 输入清洗；最小权限工具访问；敏感动作人工审批 |
| **过度工程** | 过早使用多智能体架构 | 从简单开始；仅在确有可测收益时加复杂度 |
| **无可见性** | 无法解释失败运行 | 从第一天起做完整追踪 |

## 上线门禁：八项证据

发布不是"功能跑通了"，而是"能证明它在真实流量下可控"。八项证据缺一项，灰度就等于赌博：

| 门禁项 | 最低要求 | 证据形式 |
|---|---|---|
| 评估集 | 覆盖真实分布，含历史失败样本 | 跑分报告 + 逐条失败归因 |
| 正常路径 | 端到端跑通，产物可核对 | 录制的完整轨迹 |
| 边界输入 | 空、超长、格式错、恶意注入各有用例 | 用例清单与结果 |
| 预算上限 | 轮次、token、墙钟三重上限生效 | 触发上限时的收口行为演示 |
| 成本基线 | 每成功任务成本与 P95 延迟有基线值 | 压测或回溯统计 |
| 可观测 | 能按会话 id 还原一次失败 | 一条真实失败的回放 |
| 回滚方案 | 关开关即回到旧版，无需改数据 | 演练记录 |
| 值班人 | 发布窗口内有明确责任人 | 排班表 |

> 判断：缺评估集与回滚方案的两项，其他六项做得再好也不该发——它们决定的是"出事能不能停"。

## 灰度怎么分档

- **分档顺序**：内部账号 → 1% → 5% → 25% → 全量。每档停留足够长（至少覆盖一个业务周期），因为很多失败是低频的。
- **每档看四个数**：任务成功率、人工接管率、每成功任务成本、P95 延迟。任一显著劣化就停在这一档查，不带着问题扩大流量。
- **按维度切流量**：优先放量到风险低的租户或任务类型，而不是随机抽样——随机抽样会把高风险用例均匀撒到全量。
- **冻结变更**：灰度期间不同时改提示词与工具，否则无法归因。

## 事故处理：先止血，再归因

事故现场最常见的错误是边查边改，把可复盘的现场破坏掉。固定顺序：

1. **关入口**：拉掉开关或限流，先止住新增影响。
2. **保现场**：保存会话轨迹、输入样本、当时版本号，再动手修。
3. **降级**：给用户可用的替代路径（退回旧版、转人工、返回部分结果），而不是一直转圈。
4. **回滚**：确认旧版可用再回滚，回滚后验证四项核心指标恢复。
5. **归因**：拿到轨迹后定位到具体环节（提示、工具、检索、编排），再决定修复还是重构。

分级按影响面而非技术难度：全量不可用或产生错误对外动作是最高级，需要立即人工介入；单租户劣化可排队处理。

## 值班与告警

- **告警必须可行动**：每条告警对应一个处理动作与一个负责人；做不到的告警删掉，否则团队会对告警脱敏。
- **runbook 写"第一步做什么"**：不是写原理，是写"先看哪个面板、先拉哪个开关"。
- **区分症状与噪声**：成功率下跌是症状，单次工具超时是噪声；后者聚合后再告警。
- **静默窗口要留痕**：维护期静默必须记录时间与范围，事故复盘时否则无法解释指标缺口。

## 变更管理：提示词与配置也是代码

Agent 线上行为的一半由非代码资产决定：系统提示、工具描述、检索配置、模型版本、采样参数。这些不进版本管理，就是不可复现的漂移源。

- **版本化**：提示词、工具 schema、路由规则与代码同一套版本号，随发布一起打 tag。
- **一次只改一类**：同时改提示词与检索，出问题时无法归因。
- **可回退**：提示词回退要能像回滚代码一样一键完成，且不依赖重新部署。
- **模型升级按发布处理**：换模型版本等于换了一个系统，必须重跑评估集与灰度，不能只当参数调整。
- **配置快照**：把"这次运行用的是哪版提示、哪个模型、哪些工具"写进轨迹，复盘时才有据可查。

> 判断：如果一次线上行为变化无法回答"当时用的是哪一版配置"，这个系统就已经不可运维了。

## 复盘只写能改的

- 结论落到**可执行的变更**：改哪个提示、加哪个校验、加哪条评估用例，每条带 owner 与日期。
- 只写"加强监控""提高意识"的复盘没有价值，下次照样复发。
- 同一个失败出现第二次，说明上次的 action 没落地，先追旧账再开新单。

## 自建还是借助外部

**自建**适合：有 ML 与后端工程师能负责评估与运维；Agent 是产品核心；能承诺持续维护。

**合作/借助外部**适合：追求速度；内部缺乏检索、评估与 LLM 可观测性经验；想避免昂贵的早期错误。好的合作方不只交付 demo，还应提供评估框架、护栏、监控和知识转移。

## 贯穿全过程的判断准则

- 工作流优先：能用确定性工作流解决的，不要交给 Agent。
- 评估是永久设施，不是上线前的某个阶段。
- 护栏是你拥有的确定性代码，不是对模型的请求。
- 工具设计=接口设计；先修工具，再调提示词。
- 先让正常路径跑通，再考虑样式美观，最后才考虑恶劣条件下的健壮性。
- 把 Agent 当微服务架构：路由层、执行层、记忆存储、严格护栏。掌握架构后，底层模型是可替换的。

## 一句话主线

生产化的分水岭不在功能多少，而在**能不能停、能不能退、能不能查**：有开关、有回滚、有轨迹，才谈得上规模；评估与监控是一等公民，不是上线前的过场。
