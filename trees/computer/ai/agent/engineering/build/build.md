# 05 从零构建 Agent：九个步骤

这是一条生产导向的构建路径。核心观点：构建生产级 Agent 更依赖有纪律的工程，而不是聪明的提示词。

## 第 0 步：先判断该不该做

最便宜的 Agent 是你不必构建的那个。先问：任务真的开放式吗？有清晰可检查的成功定义吗？错误行动的代价可控吗？若流程已确定或必须保证正确性，用 Workflow。

## 第 1 步：定义任务与成功标准

把 Agent 的工作写成一句利益干系人能认出的话，并用可衡量的方式定义"做对了什么"。

> 模糊的目标会产生游荡并烧掉 token 的 Agent。

具体范围应包含：

- **范围**：Agent 确切处理什么、明确不处理什么。
- **输入与输出**：请求的形态、可接受答案的形态，最好有 schema。
- **成功标准**：如何给一次运行打分（通过/失败）。
- **护栏**：Agent 绝不能做的动作、需要人工批准的动作。
- **非目标**：v1 刻意不解决的相邻问题。

> 如果你描述不出来，就无法评估 Agent，只能"凭感觉"发布。

**具体建议**：在写 Agent 代码之前，收集 **10~30 个已知正确答案的真实样例**。它们成为你的第一个评估集。这一步感觉慢，却是杠杆最高的一步。

## 第 2 步：选择模型

模型选择是成本、延迟、控制、能力的权衡，不是忠诚度比赛。三条路径：

- **托管前沿 API**（Anthropic Claude、OpenAI、Google）：推理与工具使用最强、上手最快、无基础设施负担；代价是每 token 成本与数据驻留考量。多数团队第一个 Agent 的正确起点。
- **开放权重模型**（Llama、Mistral、Qwen）：可自托管或通过推理服务使用；控制更强、敏感数据可留在自己环境、规模化可能更省；运维负担更重。
- **微调**：只在提示与检索遇到瓶颈之后再用。适合格式、语气、窄分类；对知识类问题通常不是第一步（RAG 更便宜、更易维护）。

实用选型模式：用最强模型做原型并证明可行 → 测试更小/更便宜模型在评估集上是否保持质量 → 把简单步骤路由给小模型、难题留给前沿模型。模型选择是**持续优化，不是一次性决定**。

## 第 3 步：设计 Agent 循环

循环是系统的心跳：接收目标 → 模型推理并选工具 → 执行工具 → 把观察反馈给模型 → 重复，直到模型给出最终答案或触发停止条件。

关键设计决策：

- **停止条件**：对迭代次数、总 token、时间/超时设硬上限。没有上限的 Agent 会无限循环并烧钱。
- **状态传递**：决定每轮模型看到什么。不要永远传全部历史（贵且终将溢出上下文）；用摘要、裁剪、选择性传递。
- **错误处理**：工具总会失败。循环要能捕获失败、把干净的错误反馈给模型、让它重试或换路，而不是让整个系统崩溃。
- **确定性**：尽量把非确定性的模型调用包围在确定性的、可测试的代码中。即使后来采用框架，也先亲手写一次循环。

## 第 4 步：用 Function Calling 给 Agent 工具

工具让 Agent 能影响世界：查数据库、调内部 API、搜索网页、发消息、跑代码。现代模型原生支持结构化函数调用。一个工具包含：

- 名称
- 描述
- 带类型的参数 schema

模型返回结构化调用，你的代码验证并执行。

> 工具设计就是接口设计（ACI），很多 Agent 在这里悄悄失败。

工具设计规则：

- **能力边界清晰**：把重叠动作合并成一个入口，模型才不会在相似工具之间反复试错。
- **为模型写描述**：清楚说明工具做什么、何时用、返回什么。
- **参数视为不可信输入**：模型产出的每个字段先过类型、范围与权限检查，再交给执行器。
- **让结果可推理**：返回模型能理解的错误（如"未找到该 ID 的客户"），而不是原始堆栈。
- **门禁危险动作**：涉及转账、删数据、联系客户，需显式确认或人工批准。

Anthropic 对工具设计的补充：工具定义与文档要和提示词一样精雕细琢。注意格式选择——文件改动用 diff 还是整文件重写、输出放在 markdown 还是 JSON，对 LLM 的难度差别很大（写 diff 要提前算好行数，JSON 里写代码要转义换行和引号）。给模型足够的 token 先"思考"再动手；格式尽量贴近它在互联网文本中自然见过的样子；避免让它做精确统计或字符串转义这类格式开销。把工具文档当作给初级开发者的 docstring：包含示例用法、边界情况、输入要求、与其他工具的边界。还要**防错（poka-yoke）**：通过改参数设计让错误更难发生——Anthropic 在 SWE-bench Agent 中把工具从允许相对路径改为强制绝对路径，模型从此不再出错。

## 第 5 步：用 RAG 接入数据

若 Agent 需要业务知识，就需要检索。生产级流水线：摄入与切块 → 嵌入与向量库（监控索引新鲜度）→ 检索质量（混合搜索 + 重排序）→ 接地与引用（只从上下文回答、不知道就说不知道、返回来源）。

## 第 6 步：处理记忆与状态

分三层设计：

- **工作记忆**：当前任务对话、草稿纸、中间状态；保持精简，用摘要控制成本。
- **长期记忆**：持久化事实（客户等级、过往决策、稳定偏好）；存数据库或向量库，相关时检索，不塞满提示词。
- **状态与检查点**：长运行 Agent 持久化状态，支持失败恢复与人工交接后继续。

隐私：只存能改善结果的最少内容，明确留存与删除策略。

## 第 7 步：构建护栏与评估

> 无法衡量就无法改进，无法约束就无法信任。

**评估**：把第 1 步的样例变成自动化评估套件，每次有意义的改动后都跑。混合使用：结构化答案的精确检查、开放式输出的评分量表、针对明确标准的 LLM-as-judge、工具调用正确性检查。**要评估工具调用，不只是最终答案**。每次生产失败都应加入评估集。评估不是阶段，而是永久设施。

**护栏**：用确定性安全层包裹 Agent——输入校验、提示注入防御、输出过滤（策略与格式）、按上下文的工具白名单、高风险动作人工审批。

> 护栏是**你拥有的代码**，不是你希望模型遵守的指令。

## 第 8 步：部署、监控、可观测性

> 看不见内部的 Agent，就无法运维。

- **追踪（Tracing）**：捕获每次运行的完整轨迹——提示词、模型推理、工具调用、工具结果、token、延迟。出问题时靠轨迹定位原因。
- **指标与告警**：成功率、每次运行成本、延迟、工具错误率、token 用量、循环次数；对异常（如循环次数突增）告警。
- **发布策略**：从窄范围开始、保留人工介入、随证据积累扩大自主性、用 feature flag 发布、支持即时回滚。
- **反馈捕获**：让用户标记坏答案，并把这些案例直接送入评估集。

## 第 9 步：控制成本与延迟

单次用户请求可能触发多次模型调用，需主动控制：

- **封顶循环**：迭代、token、时间硬上限。失控账单大多来自不会停的 Agent。
- **按步骤选模型**：简单分类/路由用小快模型，真正推理才用前沿模型。
- **缓存复用**：缓存嵌入、频繁检索、重复提示前缀；提示缓存能降本降延迟。
- **裁剪上下文**：摘要历史、只留最相关的检索块；更短的提示更便宜且往往更准。
- **并行独立工作**：无依赖的步骤并行执行，降低端到端延迟。

## 上线前检查清单

- [ ] 任务范围收敛到一个清晰工作，并有明确非目标
- [ ] 成功标准已写出且可衡量
- [ ] 已有真实样例构成的评估集并能自动运行
- [ ] 模型经过审慎选择，且在评估集上测过更便宜的备选
- [ ] Agent 循环对迭代、token、时间有硬上限
- [ ] 工具少、描述清楚、输入校验、最小权限
- [ ] 危险动作需人工批准
- [ ] 检索有接地、有引用、相关性被度量
- [ ] 记忆留存最少、有意为之、兼顾隐私
- [ ] 护栏能处理提示注入与不良输出
- [ ] 已接入完整追踪、成本/延迟/错误指标与告警
- [ ] 发布从窄范围开始、feature flag、保留人工介入
