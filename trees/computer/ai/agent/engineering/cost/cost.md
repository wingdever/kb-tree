# 成本与延迟工程

Agent 的成本不在模型单价上，而在"为了做成一件事花了多少次调用"。一个 20 轮的任务，即使单价便宜，成本也是单轮问答的二十倍；延迟同理——用户感知的是最后一个字出现的时间，而它是每轮串行累加的结果。

## 先看清成本的七个来源

1. **输入 token**：系统提示、工具 schema、对话历史、工具返回结果、检索片段。通常占比最高，且随轮次平方级增长（每轮都要重发前文）。
2. **输出 token**：推理过程、工具参数、答案正文。
3. **缓存读写**：命中缓存的输入便宜，未命中的贵；缓存写入有时单独计价。
4. **工具调用本身**：搜索 API、数据库、第三方计费接口。
5. **检索**：embedding 调用、向量查询、重排模型。
6. **执行环境**：沙箱运行时间、GPU 占用、文件存储与带宽。
7. **重试与浪费**：失败的调用照样计费，重复的探索是纯损耗。

优化前先量一遍这七项各占多少，否则容易在只占 5% 的地方使劲。

## 预算要分层，而不是只有一个总上限

- **每次请求**：最大输入 token、最大轮次、最大工具调用次数、最大墙钟时间。命中上限要优雅收口（给部分结果 + 说明），而不是硬断开。
- **每个任务**：多次请求组成的任务要有总预算，超支时降级而不是静默烧钱。
- **每个租户/用户**：日或月配额，触发后限流或降级。
- **告警线**：单任务成本超过 P95 的历史值就记一条异常，用于发现失控循环。

## 一次成本核算怎么做

不要凭直觉估，四步就能拿到可用结论：

1. **取样**：从生产轨迹里按任务类型抽样（每类 20–50 条），不要只取成功的，失败与重试才是浪费的大头。
2. **拆解**：每条按七项来源打标，算出中位数与 P95。中位数告诉你典型成本，P95 告诉你失控循环的代价。
3. **归因**：按"模型 / 工具 / 检索 / 执行环境"聚合，找出占比最高的那一项——通常不是你以为的那项。
4. **定预算与告警**：用 P95 的 1.2–1.5 倍作单任务告警线，用中位数的倍数作配额，而不是拍一个整数。

核算频率与迭代节奏对齐：改提示、换模型、加工具之后必须重算，否则基线会悄悄过期。

## 降本的五个有效杠杆

**1. 上下文治理优先于换便宜模型。** 工具结果截断、历史摘要、按需检索代替全量塞入——这些不牺牲能力。把"每轮都重发的静态内容"压缩到最小，收益线性复现。

**2. 缓存前缀要稳定。** 提示缓存按前缀命中，顺序上应把系统提示、工具定义、长期资料放最前，用户输入与临时结果放最后；一旦前缀里插入了时间戳、随机 id、变化的工具列表，命中率立刻归零。

**3. 按难度路由模型。** 意图分类、摘要、检索改写用小模型；规划、复杂工具编排用大模型。关键是判据：路由错误要能被下游发现（工具报错、校验失败），否则省下的钱会以失败重试还回去。

**4. 减少轮次比减少单价更有效。** 合并可并行的工具调用、把"先查再确认"的两轮合并成一次带约束的调用、用结构化输出减少往返——轮次是成本的乘数，砍轮次的收益通常比换模型更大。

**5. 让失败更便宜。** 便宜模型先试，失败升级；工具调用前先校验参数（schema、权限、目标存在），避免"错调用 + 错结果 + 重试"三份开销。

## 降本的三档风险

降本动作按"是否可能损伤能力"分三档，顺序反过来做最容易翻车：

| 档位 | 典型动作 | 风险 | 上线方式 |
|---|---|---|---|
| **无损** | 上下文治理、前缀缓存、并行化、参数预校验 | 几乎不损能力 | 可直接上，但要监控命中率与成功率 |
| **可测有损** | 模型降档路由、历史摘要、工具结果截断 | 能力可能下降，但评估集能测出来 | 必须带评估对照，劣化超阈值即回滚 |
| **不可测有损** | 砍掉整个历史、去掉检索、压缩工具描述到失去语义 | 失败方式随机、评估集测不全 | 不要做；宁可保留成本 |

> 判断：省下来的钱如果要用"更高的失败率 + 更多人工接管"来还，那不是降本，是转移成本。看每成功任务成本，不看单次调用价格。

## 延迟的五个观察点

- **首字节时间**：流式输出能显著改善体感，即使总时长没变。
- **关键路径**：并行化独立步骤；串行链路上每一个"等模型想完"都在叠加。
- **工具往返**：网络与外部 API 的 P95 往往比模型推理更不稳，要给超时与降级结果。
- **冷启动**：沙箱拉起、向量索引加载、连接池预热，长任务里这些固定开销不能忽略。
- **排队**：并发上限与限流策略决定了高峰期实际延迟，压测要看排队时间而不是只看单次推理。

## 度量：看"每成功任务成本"

- **每成功任务成本**（cost per successful task）：只优化单价会鼓励"便宜但失败"，这个指标才能对齐真实目标。
- **P95 延迟**与超时率：平均值会掩盖长尾，用户抱怨的通常是 P95。
- **缓存命中率**、**重试率**、**每任务轮次分布**：三项异常往往先于成本异常出现。
- **归因**：把成本按"模型 / 工具 / 检索 / 执行环境"拆开，才知道该动哪一块。

## 常见反模式

- 为了省 token 砍掉关键上下文，任务成功率下降，总成本反而上升。
- 缓存前缀里放动态内容，命中率长期为 0 却没人发现。
- 无单任务预算上限，一个死循环在夜里烧掉一个月额度。
- 全量路由到小模型，复杂任务失败率升高，人工接管成本被忽略。
- 只压推理单价，不看工具调用与沙箱时长。
- 优化指标只看平均值，长尾延迟持续恶化。

## 什么时候不必优化

内部低频工具、每天几十次调用、单次成本以分计的场景，投入成本工程不划算——把预算上限设好、把失控循环挡住就够了。成本工程的价值在规模化之后才显现。

## 一句话主线

成本工程的抓手不是单价，而是**每做成一件事消耗掉多少调用**：先把成本量清楚、把预算分层立起来，再动上下文、缓存与轮次——换便宜模型永远是最后一步。
