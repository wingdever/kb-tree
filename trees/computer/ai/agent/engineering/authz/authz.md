# 授权与委托

Agent 的危险能力和它的价值来自同一处：**它能替人做事**。于是每个动作都要回答三个问题——哪个 Agent 在动、它代表谁、被允许碰什么资源。这三个问题的答案组成授权三元组（服务身份 / 终端用户 / 作用域），任何一项含糊，都会在真实业务里变成越权或背锅。

## 三种典型错法

- **一把服务账号包打天下**：所有用户共用后台高权账号。审计日志里只有"某个 Agent 干了什么"，没有"谁让它干的"；一个提示注入就能以全员权限读数据。
- **把用户 token 原样透传**：Agent 和下游工具拿到的是完整权限的用户 token，既能读全部邮件，也能转账。出问题时无法区分是用户操作还是 Agent 判断。
- **审批只做"确认"不做"限定"**：界面弹一句"是否继续"，用户看不清具体参数；批准一次后同一权限沿用整天，等于没有控制。

## 委托链怎么设计

### 1. 区分三个身份

- **Agent 身份**：服务自己的凭证，代表"这套程序"，只用于访问平台自身资源（日志、配置、模型网关）。
- **用户身份**：终端用户的凭证，代表"谁授权了这件事"。
- **委托凭据**：由用户身份换取、绑定本次会话的短期凭证，权限范围比用户本身窄。

下游系统应当同时看到"执行者"和"主体"，而不是只看到其中一个。

### 2. 用 token exchange 而不是复制 token

按 OAuth 的令牌交换思路（RFC 8693），用用户的授权换一个**新的、降权的** token：`sub` 仍是用户，`act`（代理）是 Agent，`scope` 只含本次任务要用的能力，有效期以分钟计。好处是撤销时只需吊销委托凭据，不影响用户本人的登录态。

### 3. 作用域按能力与资源收窄

- 按**工具**授权，而不是按上游服务授权：拿到"发邮件"不等于拿到"读全部邮件"。
- 按**资源实例**授权：能操作订单 `#12345`，不等于能操作全部订单；能读这个仓库的这个文件，不等于能读整个私有仓。
- 默认只读，写操作单独授予；批量与外发类操作（群发、导出、对外付款）要再上一档。

### 4. 审批是授权的一种形式

审批的价值在于把"不可逆动作"从自动执行里摘出来。要做出效果，三条必须同时成立：

- **看得见**：审批卡片展示具体动作与参数快照（发给谁、发什么、金额多少），而不是"Agent 想执行一个操作"。
- **管得窄**：批准只对这一条动作有效，参数变了就失效；不做"本次会话内全部同意"。
- **分得清风险**：低风险自动、中风险单次确认、高风险双人或双因素；否则所有动作都弹窗，用户必然闭眼点同意，审批就退化成噪声。

### 5. 临时提权与自动降权

遇到权限不够时，走"申请 → 限时授予 → 用完即撤"的流程，而不是让人去后台改配置。授予要带到期时间与用途说明，过期自动失效，避免长期漂移的宽权限。

## 三种权限模型的取舍

同样是"授权"，落到实现有不同形状，选错会让后面每加一个功能都很别扭：

| 模型 | 怎么表达 | 适合 | 代价 |
|---|---|---|---|
| **静态角色**（RBAC） | 把用户归到角色，角色对应一组固定权限 | 人员结构稳定、权限集合小 | 角色会膨胀；临时需求只能加角色，越加越宽 |
| **按能力**（capability） | 每个动作是一个能力，授权即发能力令牌 | 工具种类多、动作粒度细 | 需要维护能力清单与组合关系 |
| **按资源实例**（scoped grant） | 授权绑定到具体对象（订单号、文件路径、仓库） | 多租户、单条业务数据敏感 | 每次操作要构造资源标识，实现更重 |

实践上三者是叠加而非互斥：角色决定"能申请哪类能力"，能力令牌决定"这次能做什么动作"，资源作用域决定"能对哪个对象做"。缺第三层是越权最常见的来源——权限对了，对象错了。

## 判定放在哪一层

- **网关/中间件统一判定**：所有工具调用先过一道策略检查。优点是口径统一、易于审计；缺点是拿不到业务语义，只能看粗粒度字段。
- **工具内部判定**：最了解参数含义，能拦住"路径穿越、任意 URL、越权对象 id"这类藏在参数里的越权。缺点是每个工具都要实现，容易漏。
- **模型自检**：可以作为提示，**不能作为控制**。模型判断"这个操作是否需要审批"会被提示注入直接说服。

> 判断：粗粒度拦截交给网关，细粒度与语义相关的拦截必须落在工具内部；两处都做才算闭环。只在网关做，等于假设参数永远干净。

## 撤销与审计

- **撤销要覆盖在途任务**：用户取消授权、离职、退订之后，正在跑的长任务必须停下；依赖检查点恢复的任务，恢复前要重新校验授权是否仍有效。
- **审计字段**：主体（用户 id）、代理（Agent 版本）、动作与参数、凭据 id、授权范围、结果、时间。缺"主体"与"凭据"的日志，事后无法定责。
- **不可抵赖**：高风险动作的记录要能导出给对方系统（对账、合规检查），不能只留在自家日志里。

## 怎么测授权

授权错误很难在生产里被发现（默认路径能跑通，错的那条没人走），所以负向用例要和正向一样多。四个必测场景：

1. **换主体**：拿 A 的委托凭据访问 B 的资源，必须被拒，而不是"只读放行"。
2. **换实例**：权限写着"可操作订单 #12345"，换成 #12346 必须被拒。
3. **参数夹带**：工具参数里塞入 `../`、外部 URL、他人资源 id，必须在工具层被拦。
4. **过期重放**：用已过期的委托凭据重放一次请求，必须被拒而不是"缓存命中放行"。

这四条的期望值都是"拒绝"，实现里最容易写成"记录但不拦"。把它们放进常规回归，比事后审计有效得多。

## 常见失败模式

- 权限继承链断裂：A 委托给 B、B 再委托给 C，最后没人说得清 C 的权限来自谁。对策是限制委托深度，并要求每层显式声明。
- 审批疲劳：弹窗过多导致用户不再阅读，等于无控制。
- 权限过宽后无人回收：为跑通 demo 授的宽 scope 一直留在生产。
- 只校验入口不校验出口：工具参数里夹带越权目标（路径穿越、任意 URL）时，入口鉴权形同虚设。
- 撤销滞后：token 有效期设得过长，事故发生时"已经删了权限"但旧凭据还能用。

## 什么时候需要

需要：多用户、会写数据、跨系统操作、有合规或财务要求。只读的内部工具、单用户本地脚本，用一把受限凭证即可，不必上委托链。

## 一句话主线

授权的关键不是"给 Agent 多少权限"，而是让每一次动作都能回答**谁在动、代表谁、碰什么**；三元组里任何一项含糊，越权和背锅就会同时发生。
