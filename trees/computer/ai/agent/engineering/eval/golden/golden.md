# 线上轨迹造黄金集

手写评测集只能覆盖你想到的情况；线上轨迹里有你没想到的。但把日志直接倒进评估集同样不行——轨迹不可复现、失败原因混在一起、标签来自投诉而不是判据。下面讲一条可执行的流水线：**采集 → 复现 → 最小化 → 定判据 → 分层冻结**。

## 为什么不能用"日志即用例"

一条生产轨迹包含用户输入、工具返回、环境状态、并发时序。直接拿来回放，多数情况下会得到与当时不同的结果：

- 外部依赖变了（接口升级、数据被修改、凭证过期），失败无法重现。
- 同一句输入在不同上下文里含义不同，单条抽取会丢掉关键前提。
- 失败轨迹里往往同时有多处问题（提示词、工具、检索），不拆开就无法定位。

所以轨迹是**原料**，不是用例；用例是经过复现与裁剪的可判定单元。

## 采集：一条轨迹至少要留什么

| 类别 | 字段 | 为什么必须 |
|---|---|---|
| 输入 | 用户原话、会话前几轮摘要、上传文件内容或哈希 | 复现的前提；只看最后一轮常常无法理解意图 |
| 模型与提示 | 模型快照 id、系统提示版本、工具定义版本 | 分数变化要能归因到具体改动 |
| 轨迹 | 每步的模型输出、选中工具、参数、返回、耗时 | 定位到具体一步，而不是"整体不行" |
| 环境 | 依赖服务版本、关键数据快照或种子、时区与语言 | 没有这些，回放会漂移 |
| 终态 | 业务系统里实际发生的结果（订单、工单、记录） | 判对错的唯一硬证据 |
| 信号 | 用户是否重问、是否转人工、是否投诉、是否有纠正 | 这些是"值得进集"的线索，但不是判据 |

采集时就把敏感字段脱敏（姓名、手机号、地址、凭证、内部 id），并保留可还原的映射旁路，否则用例进不了共享仓库。

## 从轨迹到用例：三步裁剪

1. **复现**。把环境固定下来（工具桩、数据快照、模型快照），重跑一遍，确认失败仍出现。重跑不出来的轨迹直接丢弃——它无法作为门禁。
2. **最小化**。删掉与失败无关的轮次、工具、文件，直到"再删一步就不再失败"。最小化后的用例通常只有原轨迹的一小段，但定位价值高得多：它直接指出是哪一步坏了。
3. **定判据**。写清"什么算对"：终态断言（数据库/系统状态）、必须出现的证据、禁止发生的动作。判据要能被机器判定；判不了的样本不进黄金集，进人审队列。

最小化还有一个副作用值得利用：同一根因的多条轨迹会收敛成同一条用例，天然去重。

## 分层：别让一个类型淹没整集

线上流量天然偏斜，热门场景会占满样本。按"影响 × 稀有度"分层配额：

- **主流程**：量最大，决定基线分数，占比可以高，但不要高到掩盖其他层。
- **边界输入**：空输入、超长、跨语言、格式异常。量小但必测。
- **已知事故**：每次线上事故至少进一条，作为不再犯的证据。
- **高危动作**：涉及资金、对外发送、删除。哪怕从未失败也要常驻，用负例验证"该拒绝的确实拒绝了"。
- **长尾意图**：低频但合理的请求，用来发现分布漂移。

配额的意义在于**让分数变化可解释**：某一层变差时，整体分数可能只掉一点点，分层看才知道是哪类用户受伤。

## 标注：谁定对错

- **判据优先于标签**。能写成断言的（终态、字段、动作序列）就不要交给人或模型打分。
- **双人标 + 仲裁**：主观样本至少两人独立标注，分歧样本由第三人或规则裁决，并记录裁决理由。
- **标"为什么错"而不只是"错"**：错误类型（理解错、工具错、检索错、策略错、环境错）决定后续修哪里。
- **模型预标只做排序**：用模型给候选样本排优先级（哪些更像真失败），不要用模型当最终判据，否则评估集继承模型的偏见。
- **用户投诉不等于错**：用户不满意可能是预期管理问题；判据没被违反就不该进"失败"类，可以另建体验类样本。

## 冻结与更新

- **冻结集**（frozen set）：一经定版不再改动，用于跨版本比较。任何修改都另建版本，旧版本保留。
- **开发集**：可随时增删，用于迭代调试，分数只作参考。
- **更新节奏**：按固定周期从线上抽样补入，并同步淘汰已失效用例（依赖已下线、判据已过时）。
- **变更留痕**：新增/删除/改判据分别记，否则分数变化说不清是用例变了还是系统变了。

> 判断：冻结集越小越要保护。几条核心用例被悄悄改掉，跨版本对比就失效了，而这种失效不会报警，只会让团队得出错误结论。

## 污染防护

- **评估集不进提示词、不进微调数据**：一旦泄漏，分数虚高且不可逆。用哈希黑名单在训练数据构建时拦截。
- **防止模型"背题"**：同一用例换措辞的变体留在开发集，冻结集只保留原始表述。
- **公开基准要防训练污染**：用公开基准前查其发布时间与模型训练截止时间的关系；自家基准不要发布原始样本。

## 常见失败模式

| 现象 | 真实原因 | 修法 |
|---|---|---|
| 评估集分数很高，线上仍差 | 样本来自演示与手写，不含真实长尾 | 按上文流水线从轨迹补样本，先补边界与长尾 |
| 同一改动两次跑分数不同 | 环境未固定（温度、工具桩、数据快照） | 固定种子与桩，记录模型快照与工具版本 |
| 修了一个 bug，另一类变差没人发现 | 集内样本偏斜，某层几乎没有样本 | 分层配额，按层看分数 |
| 团队对"这条算不算失败"反复争 | 判据含糊，靠人主观 | 把判据写成断言；判不了的移出黄金集 |
| 用例越加越多，跑一次要很久 | 没有最小化与淘汰机制 | 最小化轨迹、定期淘汰失效用例、按风险分层抽样跑 |

## 落地清单

1. 先在日志里定一条"值得进集"的筛选规则：出现转人工、重问、投诉、工具连续失败、终态与预期不符，命中即进候选池。
2. 给每条候选轨迹补齐六类字段（输入、模型与提示版本、轨迹、环境、终态、信号），缺项的直接丢弃而不是猜。
3. 写一个回放脚本：固定模型快照与工具桩，能一键重跑候选轨迹并输出终态对比。
4. 人工过一遍候选池，做最小化并写判据；判不了的进人审队列，不进冻结集。
5. 按五层配额组集，冻结一版并打标签；开发集与冻结集物理分开存放。
6. 把冻结集接进 CI，分数按层输出，而不只报一个总分。
7. 每月从线上补一批候选、淘汰一批失效用例，记录变更。

## 一句话主线

线上轨迹造集的难点不在"收集"，而在**把不可复现的经历变成可判定、可最小化、可冻结的样本**：复现不了的不进集，判不了的不进冻结集，没分层的集读不出结论。
