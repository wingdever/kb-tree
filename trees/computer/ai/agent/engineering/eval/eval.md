# A1 Agent 评估与测试

Agent 不是聊天端点——它会行动、调用工具、循环。评估 Agent 意味着评判**轨迹**，而不只是答案。

## 为什么传统评估失效

传统 LLM 评估给单次输出打分。Agent 产生的是一条轨迹：多个步骤、工具调用、观察结果、最终结果。同一任务可以通过不同路径成功；一个"正确"的最终答案可能掩盖浪费或危险的轨迹。

三个评估对象：

- **结果（Outcome）**：任务是否真的完成？最简单也最重要的信号。
- **过程（Process）**：工具用得是否合理？有无死循环、无谓 API 调用、破坏性动作？
- **效率（Efficiency）**：步数、token、耗时。两个 Agent 都能完成，成本可能差 10 倍。

## 三层评估

| 层 | 评什么 | 特点 |
|---|---|---|
| **最终答案层** | 最后一条消息对照期望结果 | 每个基准和多数教程都停在这里；必要但不充分——答案对，路径可能错、贵、不安全 |
| **轨迹层** | 产生答案的步骤序列 | 工具选对了吗？参数对吗？3 步的任务用了几步？循环了吗？工具失败后恢复了吗？20 步达成且中途两次违规调用的答案是失败轨迹 |
| **逐轮层** | 生产中每一轮的含义 | 越狱尝试、系统提示泄露、策略违规、用户沮丧——这些都不改变状态码、延迟或 token 数，对日志和追踪不可见 |

> 陷阱：把第一层当成全部。留出集 pass/fail 可以是绿的，同时轨迹一团糟、三轮漂移出策略。真正推动改进的信号在第二、三层，在真实流量上。

## 六个关键指标

| 指标 | 衡量什么 | 怎么算 | 易错点 |
|---|---|---|---|
| **任务完成率 / 成功率** | 是否到达正确终态 | 验证结果数据库/系统状态，而非只看最终文本（tau-bench 同时检查答案和 DB 状态） | 只看文本会放过"嘴上说订了机票其实没订"的 Agent |
| **工具调用准确率** | 选对工具、传对参数 | 逐次对照 schema 或参考检查（Phoenix 的 function-calling eval、DeepEval 的 span 级） | 低准确率说明 Agent 不理解可用能力 |
| **步数 / 循环数** | 效率与循环 | 实际步数 vs 最少所需；标记重复动作 | 在 trace 总数里不可见——20 步和 3 步都只返回一个答案，必须按步归因成本才看得出循环 |
| **轨迹匹配** | 步骤序列是否符合参考 | 对照参考轨迹（AgentEvals 的 trajectory-match evaluator，strict/superset 模式） | 固定期望路径会惩罚有效的替代解法 |
| **成本与延迟** | 每任务 token、美元、墙钟时间 | 按步归因，让 20 步循环可见而非埋在总数里 | 成本/成功任务才是暴露低效 Agent 的指标 |
| **接地性（Groundedness）** | 论断是否有检索上下文支撑 | 无参考 RAG 指标：faithfulness、context precision/recall、answer relevancy（Ragas） | 高幻觉率低恢复率的 Agent 推理强但错误处理脆弱 |

诊断组合：低幻觉率 + 低恢复率 = 推理强但错误处理脆弱；高工具准确率 + 低轨迹效率 = 知道该做什么但浪费资源。

## 离线 vs 在线评估

两者不是竞争关系，回答不同问题，可靠的 Agent 两者都要。

| 维度 | 离线（留出集） | 在线（生产流量） |
|---|---|---|
| 输入 | 已知答案的固定任务集 | 真实请求，没有任何数据集覆盖的长尾 |
| 时机 | CI、发布前、每次提示词改动 | 持续，真实轮次发生时 |
| 抓什么 | 已知用例的回归 | 漂移、新失败、沮丧用户、越狱 |
| 可复现 | 是，每次输入相同 | 否，流量变化；需打标后聚合 |
| 打分者 | LLM-as-judge、代码检查、抽样人工 | 足够便宜、可每轮运行的分类器 |

离线告诉你 Agent 在昨天的任务上没变差，可复现、属于 CI。它无法预见没见过的输入、漂移的多轮对话、只在真实系统发生的工具失败。在线评估通过给真实流量打分补齐：但打分者是瓶颈——LLM-as-judge 太慢太贵不能每轮跑，规模化在线评估需要毫秒级返回标签的分类器。**回报在于**：每个被打标的生产轮次都能回流到离线集、微调数据和奖励函数。这个闭环（而非更大的留出集）才是让 Agent 进步的东西。

## LLM-as-judge 及其失败模式

LLM-as-judge 是 LangSmith、Braintrust、Phoenix、DeepEval 的默认打分器：给模型输出和评分量表，返回分数。灵活、适合留出样本上的离线打分，但有四种失败模式：

1. **长度/冗长偏差**：系统性地给更长更详细的答案更高分，与正确性或相关性无关。
2. **位置偏差**：成对比较中，先出现或最后出现的答案因位置占优；交换顺序可能翻转结论。
3. **自我偏好**：与自身写作风格和模型家族匹配的答案得更高分，不管对错。
4. **成本与非确定性**：每次判断都是一次完整模型调用，太贵不能每生产轮次跑；同一轨迹跨运行可能得分不同。

实践结论：适合留出样本上的离线打分（成本和方差有界，可对边缘案例做集成或人工复核）；**不适合逐轮打标**——那需要确定性的、便宜的每轮标签，是分类问题，该用分类器。

## 逐轮分类器闭环

逐轮评估就是分类：取一轮，返回一个标签。标签是 trace 和最终答案分数都漏掉的语义事件：`jailbreak_attempt`、`is_agent_looping`、`policy_violation`、`is_user_frustrated`，或你产品特有的信号。分类器一次前向传播完成，因此每轮运行可负担。

每个逐轮标签同时喂给三件事：

- **评估**：打标轮次加入离线集，下一次回归运行覆盖它。
- **微调**：Agent 从纠正后的行为中学习。
- **RL 奖励项**："不要循环""不要泄露系统提示"变成梯度，而非愿望。

信号以 API 响应而非面板返回，因此可与任何评估栈组合：把标签写成 LangSmith/Braintrust span 的属性、在 CI 中作为发布门禁、从 Slack 告警、或在线路由。

## 框架与基准（2026）

### 框架（指向你自己的 Agent 打分）

| 框架 | 评什么 | 许可 | 免费层要点 |
|---|---|---|---|
| **LangSmith** | 轨迹评估、LLM-as-judge、启发式检查、标注队列；与 LangChain/LangGraph 一方集成 | 闭源 | Developer：5k traces/月、1 席、14 天留存 |
| **Braintrust** | 评估优先：LLM-as-judge、autoevals、自定义代码打分、人工复核 | 闭源 | 1GB 数据、10k 分数/月、14 天留存、无限席位 |
| **OpenAI Evals** | 基于注册表的可复现基准式评估；工具调用 Agent 的 Completion Function Protocol | MIT | 开源；2026-10-31 后托管平台只读 |
| **Arize Phoenix** | OpenTelemetry 原生追踪 + 评估：幻觉、Agent 函数调用、毒性、RAG | Elastic License 2.0（source-available） | 自托管，无事件上限 |
| **DeepEval** | pytest 风格本地评估；50+ 指标（G-Eval、任务完成、faithfulness）；span 级 | Apache 2.0 | 完全开源，本地运行 |
| **Ragas** | 无参考 RAG 指标：faithfulness、context precision/recall、answer relevancy | Apache 2.0 | 完全开源 |

### 基准（固定任务集，用于比较模型）

- **tau-bench**：客服（零售、航空），多轮工具调用 + 策略遵循；同时检查最终答案**和结果数据库状态**，而非只看工具调用语法。
- **tau²-bench**：客服 + 电信排障，双控制设置，用 pass^k 衡量重复尝试的可靠性（不只是一次成功）。
- **SWE-Bench**：2,294 个真实 GitHub issue，执行式——运行打补丁后仓库的测试。
- **AgentBench**：多环境（OS、DB、web、游戏）的推理与决策。

严肃基准的共同点是**执行式验证**。只检查工具调用语法或最终文本的基准，会放过"看起来对、实际做错"的 Agent。对你自己的框架也用同一标准：验证终态，而非最后一条消息。

## 实用评估配方

1. 建 20~30 个带清晰 pass/fail 的脚本化任务（结果层）。
2. 记录每次运行的完整轨迹。
3. 加过程检查：最大步数、禁用动作（删除、消费）、工具调用合理性。
4. 在轨迹之上（而非仅最终答案）用 LLM-as-judge 打分。
5. 跟踪"每成功任务成本"——暴露低效 Agent 的指标。

黄金数据集：从 50~100 个开始（含正例、关键边界、已知失败模式），持续纳入生产问题，第一季度末增长到 500+。100 个结果明确的精选用例，胜过 1000 个结果不确定的随机生成用例。每个 PR 都跑黄金集。

企业评估成熟度五级：实验（手工评审）→ 试点（离线+回归）→ 生产（在线监控+轨迹评估）→ 企业规模（治理、可观测性、自动化）→ 自主 AI（多 Agent 生态的持续运行时评估与优化）。

## 常见错误

- 只评最终答案：隐藏循环与浪费。
- 固定期望路径：惩罚有效的替代解法。
- 无沙箱：拿生产数据评估一个有破坏性的 Agent。
- 用旧黄金集：语料翻倍、查询分布漂移后仍相信六个月前的准确率数字。
- 把能自我打分当成可信：LLM-as-judge 需用人工标注切片校准，且只在离线样本上使用。
