# 评测仿真

单轮问答可以用静态数据集评，Agent 不行：它的任务是**多轮的、会改变环境的**。要评这类任务，必须再造两个东西——一个会回应的「用户」，一个可复现的「世界」。这两件事做不好，评测就会系统性偏乐观。

## 为什么静态集不够

一个 Agent 完成「帮我把这笔订单退款」要经历：问清订单号、查状态、确认政策、执行退款、告知结果。静态集只能验最后一句话像不像，无法验证过程中问了该问的、没问不该问的、退款的金额对了、且没有顺手做了别的写操作。

多轮任务的核心评测对象是**终态**（数据库里发生了什么），不是**措辞**。τ-bench 这类基准的设计逻辑正是如此：给 Agent 一套工具、给模拟用户一个目标，最后检查环境状态与目标是否一致。<RichMediaReference>["https://arxiv.org/abs/2406.12045"]</RichMediaReference>

## 三件必须模拟的东西

| 模拟对象 | 作用 | 关键风险 |
|---|---|---|
| 用户 | 提供多轮输入、追问、改主意、表达不满 | 模拟器比真人更配合、更耐心、说话更清楚 |
| 环境 | 工具返回值、数据库状态、外部 API | 不可复现：时间、随机、第三方状态一直变 |
| 事件与时间 | 超时、并发、外部通知、跨天流程 | 真实世界的时序被打平，长任务问题测不出来 |

缺任何一件，评测都只覆盖了「理想路径」。

## 用户模拟器：最难做对的部分

常见做法是让一个 LLM 扮演用户：给它目标（「你想退掉上周买的耳机」）、给它信息边界（「不知道订单号，需要被问出来」）、给它性格（耐心 / 急躁 / 含糊）。它按目标回应，直到任务完成或轮次用尽。

三个必须处理的偏差：

- **配合偏差**。模拟器天然愿意配合、主动补全信息，导致 Agent「问得少也能成功」；真实用户往往含糊、答非所问、中途改需求。
- **能力偏差**。模拟器语言过于标准，Agent 的分辨能力被高估；真实输入有错别字、口语、方言、多语言混用。
- **可被讨好**。被测 Agent 会学会用特定话术让模拟器给高分（「您看这样行吗？」），这是评测特有的过拟合。

抑制手段：用真人对话记录反推模拟器提示；给模拟器加「不主动提供未被问到的信息」的硬约束；抽样人工复核模拟器的行为；把「模拟器与真人判定一致率」当成指标长期盯住。

### 它到底怎么跑

模拟器由四样东西定义，缺一样就会退化成「随便聊」：

| 要素 | 作用 | 反例 |
|---|---|---|
| 目标 | 想达成什么，决定什么时候算结束 | 只写「你在买耳机」，Agent 做什么都能算完成 |
| 信息边界 | 知道什么、不知道什么、什么只有被问才说 | 把订单号写进开场白，问题直接被绕过 |
| 行为风格 | 耐心、含糊、改主意、情绪 | 永远礼貌配合，测不出追问能力 |
| 终止条件 | 达成 / 轮次用尽 / 主动放弃 | 没有上限，失败样本会一直聊到超时 |

运行循环是：Agent 发消息 → 模拟器按人设回应 → 环境返回工具结果 → 回到 Agent，直到终止。判定与模拟器**分离**：模拟器只负责扮演，判分交给终态检查与规则。

同一个场景，有边界和没边界的差别很大：

- **没有边界**：模拟器开场就说「帮我退订单 20251101 的耳机」——Agent 一句都不用问就通关，实际什么都没测到。
- **有边界**：模拟器说「我想退上周买的那个耳机，你帮我弄一下」——Agent 必须先问清是哪一笔，多轮追问、确认金额、说明退款周期，能力才真正被考到。

三种实现方式各有取舍：

- **脚本化**：预设台词树，最稳定可复现，但只能覆盖想到过的路径。
- **LLM 自由扮演**：能应对意外输入、覆盖广，但同一输入可能每次不同，结论不稳。
- **混合（主流）**：LLM 扮演 + 硬约束（不许透露未被问到的信息、不许替 Agent 做决定）+ 温度 0 + 轮次上限。

> 判断：模拟器像单测里的 mock——它的价值在于**稳定地制造压力**，而不是逼真地聊天。宁可台词僵硬，也不要每次表现不同。

## 环境仿真：可复现优先于真实

- **工具打桩**。按请求指纹返回录制好的响应，同一输入永远同一输出；改变状态的操作走可快照的本地实现。
- **数据快照**。评前重置数据库，评后丢弃；不要让上一轮的副作用污染下一轮。
- **时间可控**。把「现在」注入为可配置参数，才能测跨天、到期、超时这类流程。
- **故障注入**。按比例注入 429、5xx、超时、部分失败，专测重试与降级路径——这些路径在正常流量里几乎跑不到。
- **副作用隔离**。真实的下单、发邮件、转账接口一律不接真实环境；沙箱里可以随便炸。

> 判断：环境仿真的目标是「同样的输入永远得到同样的世界」，真实性排第二。宁可世界简化，也不要不可复现。

## 判定：终态检查优先

评测最容易做错的地方是「怎么算通过」：

- **终态判定**优于过程判定。查数据库/文件/消息队列的最终状态是否符合目标，而不是查 Agent 说了什么。
- **允许多条正确路径**。达成目标的方式不止一种，判定应该是「终态满足 + 无禁止副作用」，而不是「步骤与我们设想的一致」。
- **显式检查「不该做的事」**。漏掉这一步，一个把用户数据删了但答得很漂亮的 Agent 会拿满分。
- **检查中断恢复**。在关键步骤强制中断再恢复，验证不会重复执行已完成写操作。
- **设成本与轮次上限**。达标但用了三倍预算，同样应判不合格。

## 该盯的指标

- **模拟器—真人一致率**：同一批任务，模拟器判通过而真人也判通过的比例。低于某个水平时，评测结论不可信。
- **pass@k 与方差**：同一任务跑 k 次通过几次。方差大说明系统不稳定，均值好看也没意义。
- **假阳/假阴**：把失败判成通过（最危险）与把通过判成失败（浪费排查）的比例，两者要分开统计。
- **成本随轮次曲线**：轮次增加时成本增长是否失控。

## 常见反模式

- 只用单轮静态集，然后声称「多轮能力已验证」。
- 模拟器把答案直接说出来，Agent 只需复述。
- 环境不可复现：评测结果每天不一样，团队逐渐不信评测。
- 只判最终文本，不判副作用——危险操作也能「通过」。
- 把模拟器当裁判又当用户，同一个人演两边。
- 从不校准模拟器，指标连续上涨，上线后体验不变。

> 判断：模拟器也是被测系统的一部分。先花力气证明它「够难但不作弊」，再拿它的结论做决策。
