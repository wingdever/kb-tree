# 数据飞轮：把线上事故变成可复用的资产

飞轮不是「把日志存下来」。日志堆在那里不会自己变成能力。真正的闭环是六步：**运行 → 识别失败 → 归因到层 → 做成可复现用例 → 修复并验证 → 回到线上监控**。少了归因，得到的是噪音；少了复现，得到的是无法验证的传说；少了回线验证，得到的是自我感觉良好。

这一页讲这条链上每一步的判据。

## 一、先解决「采什么」

只存对话文本的日志，事后无法归因。需要存的是**一次运行的完整因果链**：

- 输入：用户原话、附件、会话历史摘要、注入的记忆。
- 决策：模型选择、检索到的上下文、工具选择理由（若有）。
- 执行：每次工具调用的参数、原始返回、耗时、状态码。
- 校验：schema 校验、业务规则校验、重试次数。
- 结果：最终输出、是否被采纳、后续用户行为。
- 元信息：策略版本、提示版本、模型版本、租户与风险级。

> 判断：日志要能回答「为什么这一步这么走」，而不只是「说了什么」。缺参数的 trace，事后只能猜。

采集本身有两个成本要提前定：存储（trace 比消息大一个数量级）与隐私（工具返回里常有个人信息）。采样策略按风险级分层：高风险全采，低风险按比例采。

## 二、信号从哪来：弱标签

线上很少有你想要的干净标签。可用的都是**弱信号**，可信度差别很大：

| 信号 | 通常意味着 | 可信度 | 陷阱 |
|---|---|---|---|
| 用户重试同一请求 | 上次结果不可用 | 高 | 可能是网络或超时 |
| 用户中途改写需求 | 理解偏差 | 高 | 有时只是需求变了 |
| 用户放弃 / 关闭会话 | 体验失败 | 中 | 可能只是下班了 |
| 人工接管 | Agent 无法完成 | 高 | 接管人可能越权兜底 |
| 校验失败 / 重试 | 输出不合规 | 高 | 也可能规则本身过严 |
| 用户明确纠正 | 事实或偏好错误 | 很高 | 样本稀少 |
| 用户点赞 / 采纳 | 可用 | 中 | 幸存者偏差，只覆盖简单任务 |

> 判断：`没有负反馈`不等于成功。绝大多数失败是静默的——用户直接换了个工具。所以飞轮不能只靠信号驱动，必须配主动抽检。

## 三、归因：先分到层，再谈修法

同一个失败现象，修错层等于白改。分诊表按「最可能的责任层」排序：

| 失败现象 | 责任层 | 典型修法 | 验证方式 |
|---|---|---|---|
| 答非所问、漏掉约束 | 提示 / 上下文 | 改指令、补示例、调整上下文顺序 | 回归集对比 |
| 检索到无关内容 | 知识层 | 改切块、改检索策略、补语料 | 检索命中率 + 端到端 |
| 参数格式错、字段缺失 | 工具 / schema | 收紧 schema、加约束解码、改描述 | 单测 + 失败样本重放 |
| 工具返回被误读 | 工具 / 文档 | 改返回结构、补字段说明 | 重放同一 trace |
| 多步任务走偏 | 策略 / 流程 | 加检查点、改分解粒度、加终止条件 | 轨迹级评估 |
| 该会却不会 | 模型能力 | 换模型、加工具、拆任务 | 同集换模型 AB |
| 事实错误且检索也查不到 | 知识层 / 数据 | 补知识、标注时效 | 事实核查集 |

> 判断：先问「换个人来做，需要什么信息」，再问「模型有没有这个信息」，最后才问「模型够不够聪明」。顺序反了，会把上下文问题误判成模型问题，然后花几周换模型。

## 四、从 trace 到用例：六步

原始 trace 不能直接进评测集，它太长、含隐私、且不可复现。要压成最小用例：

1. **脱敏**：替换姓名、地址、单号、密钥；保留结构与长度特征。
2. **裁剪**：只留复现所需的最小上下文，删掉无关历史。
3. **固化环境**：工具返回打桩（固定为当时的值），否则用例会随外部系统变化而失效。
4. **写期望**：不是写「标准答案」，而是写**可判定的验收条件**（必须问到订单号、退款金额等于 X、不得调用删除接口）。
5. **去重**：语义相似度聚类，同一类失败保留 2–3 个不同变体，不要 50 个。
6. **分层标注**：难度（单步 / 多步 / 长任务）、风险级（只读 / 写 / 对外）、来源（线上 / 合成 / 人工构造）。

**不可复现的用例只能当参考，不能进门禁**。门禁里放不可复现的用例，结果是随机红灯，团队很快学会忽略它。

## 五、五类资产，门槛不同

| 资产 | 用途 | 门槛 |
|---|---|---|
| 评测集 | 衡量能力与回归 | 可复现、可判定、覆盖失败类型 |
| 门禁用例 | 阻断发布 | 稳定、快、失败原因明确 |
| 提示 / 策略补丁 | 直接修复线上 | 必须过回归集，且记录触发它的 case |
| 工具与文档修整 | 消除系统性误用 | 需重放同一批 trace 验证 |
| 训练 / 微调数据 | 改变模型行为 | 最严：授权、去偏、去重、留出集隔离 |

顺序很重要：**先用提示与工具修，修不动再考虑训练**。多数「模型不行」的案例，最后是靠 schema 收紧和补一个工具解决的；反过来先训模型，会把本可以在提示层解决的问题固化进权重，之后更难改。

## 六、飞轮转速

飞轮的效率取决于三个时间：发现（事故到被看见）、归因（看见到知道为什么）、修复（知道到上线验证）。多数团队的瓶颈在**归因**，不在采集。

小规模团队不建议一上来就做全自动管线。更有效的起步形态是：

- 每周固定抽 20–30 条失败 trace，人工分诊并归因。
- 每周只修其中最高频的 2–3 类，其余进待办池。
- 每修一类，补 3–5 条用例进门禁。

这个节奏下，两个月能得到 40–60 条高质量用例和一份真实的失败分布，比一条自动聚类管线有用得多。

## 七、六类失败

| 失败 | 表现 | 后果 | 防线 |
|---|---|---|---|
| 只采不消费 | 日志齐全，没人看 | 存储成本上升，能力不变 | 定抽检节奏与责任人 |
| 只修不验证 | 改完就上线 | 修一处坏一处 | 每次修复附来源 case |
| 过拟合评测集 | 集内全绿，线上照旧 | 指标失真 | 留出集 + 定期换血 + 线上抽检 |
| 分布污染 | 用线上高频样本反复调 | 长尾能力退化 | 按难度与风险分层，长尾保底配额 |
| 隐私与授权 | trace 直接进数据集 | 合规风险 | 采集即脱敏，训练数据单独授权 |
| 幸存者偏差 | 只看有反馈的样本 | 系统性低估失败 | 主动抽检 + 静默失败探测 |

## 八、飞轮健康度

四个数字能判断飞轮是否在转：

- **事故复发率**：同类失败再次出现的比例。这是飞轮有没有效的唯一硬指标。
- **用例增长与覆盖**：新增用例数、覆盖的失败类型数、长尾占比。
- **发现到修复的中位时间**：按风险级分开看，高风险必须显著更短。
- **线上与评测集的分布差距**：任务类型、难度、工具使用分布的 KL 距离或分桶对比；差距扩大说明评测在过期。

> 判断：飞轮的产出不是「数据量」，而是「复发率下降」。数据量涨而复发率不降，说明在收集，没在闭环。

## 九、落地顺序

1. 结构化 trace（含参数与校验结果），按风险级采样。
2. 每周人工分诊 20–30 条，写出失败分布。
3. 把最痛的 3 类做成可复现用例，进回归门禁。
4. 修复并回线观察复发率。
5. 稳定后再考虑自动聚类、自动归因、训练数据生产。

第 2 步是分水岭：没有人工分诊，后面全是自动化幻觉。
