# 版本管理与灰度

Agent 的行为由六样东西共同决定：模型、提示词、工具 schema、工具实现、检索索引、策略阈值。改其中任何一样都等于发布新版本，但很少有人把它当发布来管——于是线上出现"昨天还好好的，今天答错了"，却找不到改了什么。

## 什么算一次版本变更

把这些一起冻结成一个 `agent_version`，写进每条轨迹：

- **模型**：名字 + 具体快照（厂商换底模时，同名模型的输出分布会变）。
- **提示词**：系统提示、工具描述、少样本示例——工具描述改一个词就能显著影响调用准确率。
- **工具契约**：参数 schema、错误语义、超时与重试策略。
- **工具实现**：同一 schema 下后端换了逻辑，行为也变了。
- **检索侧**：embedding 模型、切块策略、索引版本。
- **策略参数**：轮次上限、置信阈值、审批门限。

只记录 model 和 prompt 是不够的，出问题时最常见的原因恰恰在工具与索引这两侧。

## 变更分级

按影响面分三级，走不同流程：

| 级别 | 例子 | 流程 |
|---|---|---|
| 热修 | 提示词里错字、工具描述补一句边界说明 | 改完即发，但要留版本标记，事后可归因 |
| 常规 | 换模型、调阈值、改工具实现 | 离线评估集跑通 + 小流量灰度 |
| 结构性 | 换检索方案、改工具集合、改架构模式 | 影子流量对比 + 分阶段放量 + 明确回滚预案 |

分级的价值是防止"所有改动都走重流程"导致团队绕过流程，也防止"什么改动都直接上"造成事故。

## 灰度与影子流量

- **灰度**：按用户或会话稳定分桶（同一用户始终命中同一版本，否则体验会来回跳），逐步从 5% 到 100%。观察指标要同时看质量（任务完成率、人工接管率）与成本（token、延迟、工具调用次数）。
- **影子流量**：新版本只跑不交付，用同一批真实输入对比新旧输出。适合结构性变更，能在没有用户风险的情况下暴露退化。
- **对照要可判**：没有评估集就没有灰度判据。灰度前先确定"什么算变好、什么算变差"，否则只是把噪声放大了。

## 回滚

- **配置级回滚**优先：版本化配置能一键切回旧值，秒级生效。
- **状态级回滚很难**：检查点、索引、写入的记忆都带着新版本的痕迹，回滚代码不会回滚数据。所以结构变更要能双写或保留旧索引，直到新版本确认稳定。
- **在途任务**：切换版本时正在跑的长任务，要么用旧版本跑完（需要恢复时能取到旧版本），要么显式取消并重排。两条路都要在切换预案里写明。

## 常见失败模式

- **只版本化 prompt**：模型或索引悄悄换了，问题却归到提示词上。
- **轨迹不带版本**：线上异常无法定位到具体变更，只能全量回滚。
- **模型升级未重测工具**：新模型对工具描述的敏感度不同，原本调对的工具开始被误用。
- **索引换了没重调切块与召回**：embedding 一换，旧的分块大小和阈值全部失配，召回率静默下降。
- **灰度分桶不稳**：同一会话在两个版本间跳，上下文与风格来回变。
- **回滚只回代码**：配置文件、索引、缓存没回，实际行为仍是新的。

## 什么时候需要

需要：有真实用户、有质量或成本压力、迭代频率高于每月一次、变更会引起行为差异（几乎所有 Agent 都符合）。

不需要：内部一次性脚本、原型验证阶段、无状态单轮问答且错误代价极低。这些场景记一个 git commit 就够。
