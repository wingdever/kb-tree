# 执行沙箱与代码执行环境

让 Agent 跑代码是能力跃迁——能跑测试、能处理数据、能装依赖；也是风险跃迁：**模型生成的代码等于不可信输入**。沙箱要同时满足两个目标：让代码真能跑起来，让跑坏的代价有上限。

## 威胁模型

先列出"能坏成什么样"，再决定隔离到哪一层：

- **破坏宿主**：删文件、改系统配置、拉起挖矿进程、fork 炸弹打满进程表。
- **读走密钥**：环境变量里的 API key、挂载的凭证文件、宿主上的 `.env`。
- **外联泄数据**：把读到的文件、对话上下文发到外部地址；或反过来拉入恶意载荷。
- **被注入驱动**：网页、文档、工具返回里的隐藏指令诱导 Agent 执行危险命令——这是 Agent 特有的入口，普通 CI 没有。
- **供应链**：运行时 `pip install` 默认从公网拉包，装进来什么不可控。
- **资源耗尽**：磁盘写满、GPU 被占、长任务永不退出。

## 隔离层级与代价

从便宜到贵，隔离强度与启动成本同向变化：

| 层级 | 机制 | 启动成本 | 适用与边界 |
|---|---|---|---|
| 进程级 | `seccomp` 限制系统调用、`landlock` 限制文件访问、cgroup 限 CPU/内存 | 毫秒 | 同一宿主内的"半可信"代码；内核共享，逃逸风险仍在 |
| 容器 | namespace 隔离 + 只读根文件系统 + 丢弃 capabilities + 非 root 用户 | 百毫秒 | 主流选择；要能跑测试与装包时足够 |
| 微虚拟机 | 独立内核（Firecracker 一类），或用用户态内核（gVisor）拦截系统调用 | 百毫秒到秒 | 需要内核级隔离、或要跑不可信二进制；GPU 直通通常更麻烦 |
| 远端托管沙箱 | 厂商提供的隔离执行环境，SDK 起停 | 秒级 | 不想自建、需要横向扩容；数据出域与网络策略要审 |

选择顺序：**先问要跑什么**（纯 Python 数据处理 → 容器够；要跑内核模块、要跑 Docker-in-Docker → 微虚拟机或托管），**再问谁能忍多久启动**。

## 五个必须做对的控制

### 1. 默认断网，按域名放行

出网是最常见的泄漏路径。默认拒绝，按需放行到具体域名（包索引、业务 API），并记录每次外联目标。需要浏览网页的场景单独开一个带代理的浏览器沙箱，不与代码执行沙箱共用网络策略。

### 2. 密钥永不进沙箱

正确姿势是代理注入：沙箱内的进程访问一个本地代理，代理持有凭证并只在允许的域名上附加。这样即使代码被诱导打印环境变量，也拿不到真 key。备用凭证要短期、可撤销、权限收窄到单一用途。

### 3. 文件系统分层 + 产物白名单

镜像只读，会话写在一层可写 overlay 上，任务结束即销毁；需要带出的产物走显式导出（按路径白名单 + 体积上限），不允许整目录回传。否则一次误操作会把宿主目录或临时密钥文件打包出去。

### 4. 资源硬上限

CPU、内存、进程数、磁盘、墙钟时间五项都要设上限，超限直接杀，不靠进程自觉。没有墙钟上限的沙箱迟早会攒出一堆僵尸任务。

### 5. 全量审计

命令、输入、stdout/stderr、退出码、网络目标全部留痕，绑定 `run_id`。出事后能复盘"它到底做了什么"，也是评估与回归的数据来源。

## 与工具设计的接口

代码执行工具的返回值决定模型能不能用好它。三条实践：

- 结构化返回：`exit_code`、截断后的 `stdout`/`stderr`、生成的文件列表、耗时，而不是一整段乱序文本。
- 输出截断要有策略：头尾各留一段 + 中段提示"已截断 N 行，全文在 path"，否则长日志会把上下文吃光。
- 失败分型：语法错误、依赖缺失、超时、权限拒绝是不同信号，模型据此的修复动作不同；混成一个"执行失败"会让它反复瞎试。

## 什么时候不需要

只调用自家固定 API、不执行生成代码的场景，沙箱是多余的复杂度——用受限工具集 + 参数校验更简单。沙箱的复杂度只有在"必须执行不可信代码"时才值得付。

## 怎么验证沙箱真的隔离

隔离配置写完不等于隔离成立。定期跑一组"故意越界"的演练，比读配置可靠：

1. **读宿主敏感文件**：尝试读 `/etc/shadow`、宿主 `~/.ssh`、`~/.git-credentials`，期望的结果是"不存在或拒绝"。
2. **连外网**：尝试直连一个未放行的域名与一个 IP 直连，期望被拒；再试 DNS 解析，确认不是只挡了 HTTP。
3. **打满资源**：起一个 fork 炸弹与一个写满磁盘的循环，确认被硬杀且宿主不受影响。
4. **挂载面检查**：确认沙箱内看不到宿主 Docker socket、宿主 home 目录、其他租户的卷。
5. **审计完整性**：跑一段命令后检查日志里是否有命令、退出码、网络目标、文件变更——缺一项就说明审计有洞。

演练结果要留档并在每次镜像或配置变更后重跑。**没演练过的隔离，只是配置看起来像隔离。**

## 常见失败模式

- 把宿主 Docker socket 挂进沙箱：等于给了宿主 root。
- 容器以 root 运行、根文件系统可写、capabilities 不裁剪。
- key 以环境变量形式直给，且沙箱能出网。
- 只做了隔离、没做资源限制，一次死循环拖垮整台机器。
- 超时不杀进程，只让 API 返回超时，后台继续跑。
- 审计只留 stdout，没有命令与文件变更记录，事后无法定责。
- 复用同一个长期沙箱跑多个用户的代码，状态与数据互相污染。

## 一句话主线

沙箱的本质是把**"不可信代码"的失败半径限制在一个可丢弃的盒子里**：隔离层级按威胁模型选、密钥与网络从设计上就不给它、资源上限不是建议而是硬杀；能只调 API 就不该给代码执行权。
