# Agent 工程与验证

这一组回答「怎么搭起来、怎么证明它行」。顺序不是「写完再评」，而是**每一步都留下可验证的痕迹**：任务定义写清成功标准，实现时留好 trace，上线前有回归集，安全护栏嵌在工具与权限里而不是提示里。

## 工程上的四个必经环节

1. **定义成功标准**。先写「什么算做对了」，再写提示与工具。定义含混时，后面所有评测都会变成主观打分。
2. **跑通最小闭环**。一个模型、一个循环、两三个工具，端到端跑通一次真实任务；闭环不通时加框架只会放大问题。
3. **建评估集与门禁**。黄金集覆盖已知的坏 case，回归集覆盖历史事故；每次改提示、换模型、加工具都要过门禁。
4. **把护栏放进系统**。权限、审批、沙箱、输出审查属于架构与工程，不属于提示词；靠提示「不要做危险操作」等于没有护栏。

## 三条经验判断

- **框架要「挣得自己的位置」**。框架的价值在持久化、中断恢复、可观测性这些硬能力上；只为「少写几行循环」引入框架，通常换来的是更难排查的抽象。
- **评估器比模式重要**。没有评估时，加模式与调提示都只能凭感觉；有评估时，很多「看起来需要多 Agent」的问题会变成一次提示修改。
- **安全的第一杠杆是权限，不是措辞**。能删库的工具即便提示写得再严，也不该给模型直接调用的权限；最小权限加人工确认，比任何提示都可靠。

## 推进顺序

按「定义成功标准 → 跑通最小闭环 → 建评估门禁 → 嵌护栏」四步推进；每一步都留下可验证的痕迹。已经在跑的系统，优先补评估与回归，这是把「感觉变好了」变成「确实变好了」的唯一环节；示例只在需要对照实现细节时使用。

## 一句话主线

先写清成功标准，再用最小闭环跑通，然后建评估集与回归门禁，最后把权限、审批、沙箱嵌进工具与运行时；框架与模式只有在能证明质量提升时才值得引入。
