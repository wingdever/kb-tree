# 01 什么是 Agent

## 一句话定义

**AI Agent 是一个系统：其中的大语言模型（LLM）在运行时自主决定下一步做什么，以达成某个目标。**

关键在于它不只是模型本身，而是一个由多部分组成的系统：

- 语言模型（推理核心）
- 控制循环（决定下一步）
- 工具集（行动能力）
- 某种形式的记忆
- 生产环境中还需要：可观测性、评估、护栏

Agent 的行为特征是：**动态地指导自己的流程和工具使用，而不是沿着你硬编码好的路径走。** 你给它的是目标和工具集，而不是脚本。

## 三类系统的区别

| 类型 | 描述 | 谁控制流程 |
|---|---|---|
| **Chatbot（聊天机器人）** | 文本进、文本出。模型回答，人决定接下来做什么，它不会自行改变系统。 | 人 |
| **Workflow（工作流）** | LLM 和工具由预定义的代码路径编排，步骤事先确定。 | 开发者 / 代码 |
| **Agent（智能体）** | LLM 动态决定走多少步、调用哪些工具、如何追求目标。 | LLM 在运行时 |

从 Chatbot 到 Agent 的关键一步，是**给模型工具**；而这一步也正是权限与护栏开始变得重要的地方。

## 实践准则：用能解决问题的最不动态的系统

> 使用能解决问题的最不动态的系统。

- 如果任务能分解成固定的子任务 → 构建 **Workflow**（可预测、可测试、更便宜）。
- 把真正的 Agent 留给**开放式问题**——你无法预先预测需要多少步。

Anthropic 的指导很直接：**只有在能明确改善结果时才增加复杂度**，因为每增加一分自主性，就增加一分你需要测试和监控的不可预测性。

**最便宜的 Agent，是你根本不需要构建的那个 Agent。**

### 适合用 Agent 的场景

- 研究 / 调研
- 分类分流（triage）
- 数据收集
- 草拟内容
- 路径会变化的多步骤自动化

### 不适合用 Agent 的场景

- 必须保证正确性的任务
- 流程已经确定性的任务
- 能被 Workflow 更好处理的固定序列

在写代码前先做压力测试：

- 任务真的开放吗，还是固定序列？
- 有没有清晰、可检查的"成功"定义？
- 错误行动的代价是否可控？会不会自动犯错造成严重后果（转账、删数据、给客户发邮件）？

## Agent 的核心组件

**基本构建块是"增强型 LLM"（augmented LLM）**：一个具备检索、工具和记忆增强能力的 LLM。当前模型能主动使用这些能力——自己生成搜索查询、选择合适的工具、决定保留什么信息。实现时有两件事最重要：让这些能力贴合你的具体场景，以及为 LLM 提供易于使用、文档清晰的接口。实现这些增强的一种方式是通过 MCP（Model Context Protocol），它让开发者用一个简单的客户端实现即可接入不断增长的第三方工具生态。

在此之上，把 Agent 想成微服务架构，而不是一次 API 调用。它有路由层、执行层、记忆存储，以及连接它们的严格护栏。

1. **模型（推理）**：读取任务与上下文，决定下一步。它的能力大体决定了 Agent 处理模糊或异常输入的上限。
2. **工具（行动）**：把文本生成器变成能行动的系统。搜索、代码执行、数据库查询、API 调用、RAG 检索工具等。
3. **记忆（上下文）**：
   - 短期记忆：当前会话与任务历史（上下文窗口内的草稿纸）。
   - 长期记忆：持久化存储的事实、偏好、过往决策（向量库 / 数据库）。
4. **指令与护栏（控制）**：清晰的角色说明、步骤上限、审批点，让 Agent 在真实系统附近运行时可预测、安全。
5. **可观测性与评估**：追踪每一次模型调用、工具调用，持续测量表现。

> 一旦掌握了架构，具体用哪个 LLM 模型就变成可替换的了。

## 认知循环：Observe → Think → Act

每个 Agent 系统本质上都在运行某种 OODA 循环（Observe, Orient, Decide, Act），在 AI 领域通常简化为 **观察 → 思考 → 行动**：

1. **观察（Observe）**：接收初始提示，或上一个行动的输出。
2. **思考（Think / Reason）**：LLM 分析观察结果，决定下一步——用工具，还是返回最终答案。
3. **行动（Act / Execution）**：若决定用工具，后端执行相应调用（如 `search_database("user_id_45")`）；结果成为新的"观察"，循环再次开始。

示例场景（自动化 QA Agent 检查预发布环境）：

- **思考**："我需要检查状态。"
- **行动**：调用 `ping_server` 工具。
- **观察**：得到 502 Bad Gateway。
- **思考**："服务器挂了，我该查最近的提交日志看是谁弄坏的。"

循环持续进行，直到模型给出最终答案，或触发停止条件（完成目标 / 达到步数上限）。

一个健康的生产循环还需要：硬性的停止条件（迭代数、token、时间上限）、状态传递策略（摘要 / 裁剪，避免永久传递全部历史）、错误处理（捕获失败、把干净的错误反馈给模型重试），以及尽可能在非确定性的模型调用周围包裹确定性的、可测试的代码。

## 两类高价值应用场景

Anthropic 特别指出两个最有前景的应用方向：

**客服**：把熟悉的聊天界面与工具集成带来的增强能力结合。对话天然是流程化的，同时需要访问外部信息和执行动作——工具可以拉取客户数据、订单历史、知识库文章，也能以编程方式处理退款或更新工单。成功可以通过用户定义的"解决"来清晰衡量；已有多家公司采用"只为成功解决付费"的用量定价模式，说明对其 Agent 的有效性有信心。

**编码 Agent**：软件开发是从代码补全演进到自主解决问题的天然土壤。代码方案可通过自动化测试验证，Agent 能以测试结果为反馈迭代；问题空间定义明确、结构清晰；输出质量可客观衡量。Anthropic 的实现已经能仅凭 PR 描述解决 SWE-bench Verified 中的真实 GitHub issue。注意：自动测试能验证功能，但人工审查对确保方案符合更广泛系统要求仍然关键。
