# 抓取去重

去重不是在入库前做一次“看起来一样”的判断，而是两层工程：先把同一页面的多个 URL 收敛成一个，再把同一内容的不同载体合并成一份。去重做不好，索引会被重复文本灌满，检索结果反复命中同一段。

## 第一层：URL 去重

在请求之前做，成本最低：

- 主机名小写、去掉默认端口、统一 scheme；
- 解析 `.`/`..`、合并重复斜杠、去掉片段；
- 去掉明确的跟踪参数（`utm_*`、`gclid` 等），保留有业务含义的查询参数；
- 跟随重定向后，用最终 URL 作为主键；
- 尊重页面里的 `rel=canonical`，但不要盲目相信；要与最终 URL 和内容比对。

规范化要保守：把不同页面合并成一个，比留下少量重复更难恢复。

## 第二层：内容去重

在解析之后做：

- **精确哈希**：对规范化正文做 SHA-256；同哈希即同内容，适合完全重复。
- **近重复指纹**：SimHash、MinHash 或 shingle 集合，识别转载、轻微改版、模板差异；阈值要按业务调，过低会误合并。
- **结构指纹**：标题 + 正文骨架 + 关键字段的哈希，能区分“同一模板下的不同详情页”。
- **版本链**：同一 URL 内容变化时保留旧版本与 `content_hash`，不要直接覆盖；否则无法回溯“什么时候变了”。

## 去重键怎么选

| 场景 | 主键 | 备注 |
|---|---|---|
| 列表/详情页 | 最终 URL + 正文哈希 | URL 先规范化 |
| 转载/镜像 | 正文 SimHash + 标题 | 允许保留来源不同 |
| 同一文档多格式 | 标题 + 作者 + 日期 + 正文指纹 | PDF/HTML 可能同源 |
| 频繁更新页 | URL + 版本时间 + 哈希 | 保留版本链 |

## 常见失败

- **只按 URL 去重**：同一内容有打印版、AMP 版、带参数版，仍会重复入库。
- **只按正文哈希**：转载改了标点或加了免责声明，哈希就不同；需要近重复。
- **阈值过松**：把不同产品页合并，召回时丢失关键差异。
- **没有保留来源**：合并后不知道原文从哪来，无法溯源与删除。

## 一句话主线

先在请求前做保守的 URL 规范化，再在解析后做精确哈希与近重复指纹；去重必须保留来源与版本，宁可少量重复，也不要错误合并。
