# RAG 数据源

取数的第一决定不是“用什么爬虫”，而是“从哪里取”。同一个知识库，来自官方 API 的数据与来自页面抓取的数据，在结构、时效、授权与维护成本上完全是两件事。

## 五层数据源

| 层级 | 典型来源 | 优点 | 代价 |
|---|---|---|---|
| 官方 API | 平台开放接口、企业系统连接器 | 结构稳定、字段齐全、可增量 | 配额、鉴权、覆盖有限 |
| 批量导出 | CSV/JSON 导出、数据库只读副本、备份 | 一次拿全、可离线处理 | 时效差、可能含敏感字段 |
| 站点地图 / RSS | sitemap.xml、Atom/RSS、新闻订阅 | 发现成本低、更新信号明确 | 只覆盖愿意公开的站点 |
| 搜索发现 | 搜索引擎结果、站内搜索 | 能发现长尾页面 | 结果不稳定、有配额与合规限制 |
| 页面抓取 | 直接请求 HTML、渲染后取 DOM | 覆盖最广 | 解析脆弱、反爬与合规成本高 |

## 选择顺序

> 判断：官方 API > 批量导出 > 站点地图/RSS > 搜索发现 > 页面抓取。每降一层，维护成本与不确定性都上一个台阶。

先问五个问题：数据是否已有官方出口；是否允许批量获取；更新频率多高；需要多深的历史；出问题谁负责。答案决定了取数层，而不是反过来由爬虫能力决定。

## 一个数据源是否合格

- **覆盖**：目标实体与字段是否齐全，缺的能否从第二源补齐。
- **时效**：更新延迟是否满足业务；有没有“最后更新时间”。
- **结构**：字段是否稳定、类型是否明确；还是只能从版式里猜。
- **授权**：服务条款、许可证、个人信息与数据库权利是否允许当前用途。
- **成本**：配额、带宽、渲染与人力维护，按每千条有效记录算。

## 常见误判

- **有 API 却抓页面**。页面结构一变就断，API 通常更稳；抓页面只应补 API 覆盖不到的部分。
- **把搜索结果当数据源**。搜索负责发现，不负责给出一手事实；最终仍要回到原始页面或官方数据。
- **忽略增量**。每天全量重抓既慢又贵，还会把未变化的内容反复送进索引。

## 一句话主线

先按覆盖、时效、结构、授权与成本给数据源分层，再决定要不要爬；数据源选对，后面的抓取与解析才有意义。
