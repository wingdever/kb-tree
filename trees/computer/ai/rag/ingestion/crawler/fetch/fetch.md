# 抓取执行

抓取执行层把 URL 变成响应。它看起来只是“发一个 GET”，实际要处理的是 HTTP 语义、会话状态、失败分类、重试边界与每站限速；这些细节决定抓取是稳定运行还是不断被封、不断重试。

## 一次请求要定什么

- **方法与语义**：抓取优先用 GET；GET 应当幂等，不因重试产生副作用。需要提交表单时，先确认站点条款与是否真的需要。
- **请求头**：明确的 `User-Agent`、`Accept`、`Accept-Encoding`、`Accept-Language`；需要条件请求时带 `If-None-Match` 或 `If-Modified-Since`。
- **会话**：需要登录态或 CSRF 的站点用会话保持 cookie；但不要把个人登录态用于批量抓取，除非明确授权。
- **超时**：连接超时与读取超时分开设；长尾站点要有总预算，避免一个请求拖住整个 worker。

## 状态码怎么处理

| 状态 | 含义 | 抓取动作 |
|---|---|---|
| 200 | 正常 | 解析；仍要判断是否软 404 或空页 |
| 301/302/308 | 重定向 | 跟随有限次数，记录最终 URL |
| 304 | 未修改 | 保留旧版本，更新检查时间 |
| 401/403 | 未授权/禁止 | 停止重试；检查授权或改用官方 API |
| 404/410 | 不存在/已删除 | 标记失效，不反复重抓 |
| 429 | 限流 | 按 `Retry-After` 退避，降低并发 |
| 5xx | 服务端错误 | 有限次指数退避；持续失败则熔断 |

## 重试与限速

重试只适用于可能 transient 的错误：连接失败、超时、429 与部分 5xx。校验失败、401/403、404 不应重试。

退避用指数增长加抖动，并设上限；同一 host 的并发与请求间隔独立控制，不要把全局并发当成每站配额。遇到 429 先降速，不要换代理继续打。

## 缓存与条件请求

保存 `ETag`、`Last-Modified` 与响应哈希；下一次用条件请求换 304，能显著降低带宽与解析成本。缓存的是原始响应与最终 URL，不只是正文，否则重定向与编码问题无法复查。

## 常见失败

- **把 403 当临时错误**：不断重试只会加重封禁；应停止并检查授权。
- **重试非幂等请求**：提交、下单、发消息类请求重试会重复副作用；抓取层只应处理只读 GET。
- **忽略字符集与压缩**：不按 `Content-Type` 与响应头解码，正文会出现乱码。
- **没有最终 URL**：重定向后仍用原 URL 做去重，导致同一页被当成多个页面。

## 一句话主线

抓取执行要把请求语义、状态码、会话、超时、重试与每站限速当成一套协议来设计；只读、可缓存、可退避，才能稳定而不过界。
