# 分布式爬虫

单机爬虫受 CPU、带宽与并发限制；分布式爬虫把 URL 分给多个 worker。但它不会自动变快：调度、去重、限速与失败恢复都要跨进程协调，协调成本常常吃掉并行收益。

## 三个核心部件

- **共享 frontier**：集中式队列或分区队列，保存待抓 URL、优先级、重试次数与租约状态。
- **worker 池**：每个 worker 领取任务、抓取、解析、回写结果；可水平扩展，但要按站点配额限流。
- **共享去重**：URL 集合与内容指纹要在 worker 之间共享；否则同一页面会被多个 worker 重复抓取。

## 分片与调度

- **按 host 分片**：同一站点的 URL 固定到一个队列或一组 worker，便于执行每站并发与间隔。
- **按优先级分片**：高价值详情页与低价值列表页分开，避免互相阻塞。
- **租约与确认**：worker 领取任务时加租约；完成后确认，超时则重新入队。失败重试要有上限与死信队列。
- **背压**：队列积压或下游解析变慢时，降低领取速率；否则内存与磁盘先崩。

## 一致性边界

分布式抓取通常只能做到 **at-least-once**：worker 崩溃时任务会重跑。因此抓取与写入必须幂等：同一 URL 的重复结果按最终 URL + 内容哈希合并，而不是产生多条记录。

不要承诺“每条 URL 只抓一次”这种 exactly-once；网络超时与确认丢失会让它变成不可能。工程上接受重复，再用去重与幂等把影响压到可接受。

## 监控

- 每站吞吐、成功率、429/403 比例；
- 队列长度、租约超时率、死信数量；
- 每 worker 的抓取延迟与解析失败率；
- 重复抓取率与去重命中率。

没有这些指标，扩容只会把“一个站点被打爆”变成“多个 worker 一起打爆”。

## 常见失败

- **全局并发替代每站配额**：worker 越多，单站压力越大，封禁越快。
- **共享去重缺失**：同一 URL 被多次领取，重复率随 worker 数量上升。
- **确认丢失**：任务完成后未确认，租约到期后重跑；没有幂等就会写重。
- **队列无界**：发现阶段灌入无限 URL，内存先于抓取崩掉。

## 一句话主线

分布式爬虫把 frontier、worker 与去重拆开共享，按 host 分片与限流，用租约和幂等处理 at-least-once；先控住单站压力与队列背压，再谈扩容。
