# 动态页面渲染

很多页面在原始 HTML 里只有脚本壳，正文要等 JavaScript 执行后才出现。渲染层要判断“值不值得上浏览器”，以及“什么时候算加载完成”；不做这两步，抓到的就是空壳。

## 先判断是否真的需要渲染

按成本从低到高尝试：

1. **原始 HTML**：直接请求，检查正文是否已经在 HTML 中；SSR 与传统页面通常足够。
2. **接口响应**：页面通过 XHR/fetch 取 JSON；找到公开接口往往比渲染整页更稳、更省。
3. **无头浏览器**：前两条都不行时才用；它执行脚本、构建 DOM，成本与失败率都更高。

判断依据是“内容在不在首屏 HTML”，而不是“页面看起来是不是动态”。很多页面有 JavaScript，但正文仍是服务端渲染的。

## 无头浏览器的关键设置

- **等待条件**：等目标选择器出现、等网络空闲、或等某个文本出现；不要用固定 `sleep` 赌加载时间。
- **资源裁剪**：拦截图片、字体、媒体与无关脚本，降低带宽与渲染时间；但不要裁掉正文依赖的接口。
- **视口与滚动**：懒加载内容需要滚动触发；无限滚动要有页数或时间上限。
- **超时与重试**：渲染超时与抓取超时分开计；失败时回退到原始 HTML 或接口，而不是无限重开浏览器。
- **并发**：浏览器实例昂贵，按 CPU/内存设并发；每个页面用独立上下文，避免 cookie 串页。

## 从渲染到数据

渲染后的 DOM 可以按 CSS/XPath 抽正文，也可以从网络面板里拿到 XHR 返回的 JSON。后者通常更结构化，但需要确认接口是否公开、是否稳定、是否允许批量调用。

截图 + OCR 只能作为最后手段：它丢失结构、难去重、对版式变化敏感；只适合没有 DOM 可用的图像型内容。

## 边界与失败

- **登录墙与付费墙**：不要用浏览器自动化绕过访问控制；改用授权账号、官方 API 或采购数据。
- **验证码与挑战页**：遇到挑战就停止并联系站点，不用指纹伪装或代理池对抗。
- **渲染陷阱**：页面永远不 idle、脚本报错、接口 401、弹窗遮挡；需要明确的成功判定与失败回退。
- **成本失控**：每个 URL 都开浏览器，吞吐会降到原来的几分之一；先做“是否需要渲染”的分流。

## 一句话主线

渲染是抓取里最贵的一层：先用原始 HTML 与公开接口，确认必要才上无头浏览器，并用明确的等待条件、资源裁剪与失败回退控制成本。
