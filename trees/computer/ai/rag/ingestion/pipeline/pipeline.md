# 增量抓取流水线

一次性抓全只是开始。知识库要长期可用，必须回答：哪些页面变了、多久重抓一次、旧版本留不留、删除怎么处理。增量流水线把这些问题变成可调度、可观测的规则。

## 变化检测

- **HTTP 条件请求**：`ETag` / `If-None-Match`、`Last-Modified` / `If-Modified-Since`；304 表示未变，成本最低。
- **内容哈希**：对规范化正文做哈希；响应头不可信或没有校验头时，用哈希兜底。
- **结构信号**：列表页新增链接、RSS 新条目、sitemap `lastmod` 变化；用于发现“可能有新内容”。
- **抽取字段变化**：标题、正文长度、关键字段变化；适合监控“页面还在但主体换了”的情况。

只靠 `lastmod` 不可靠：很多站点不更新或乱写；只靠内容哈希又要先抓一遍。通常是条件请求 + 哈希 + 结构信号组合。

## 重抓调度

按内容类型分频率，而不是所有页面一个周期：

- **高频**：新闻、价格、库存、公告；分钟到小时级。
- **中频**：博客、文档、产品页；天到周级。
- **低频**：法规、归档、静态介绍；月到季度级。
- **事件驱动**：收到变更通知、sitemap 更新或用户反馈时才重抓。

调度要受抓取预算约束：高频页面多，低频页面就要让步；不能所有页面都“每天一次”。

## 版本与存储

至少保存三层：

1. **原始响应**：状态码、头、最终 URL、抓取时间；用于复算与排查。
2. **解析结果**：正文、字段、解析器版本；用于重建索引。
3. **版本索引**：`content_hash`、首次/最近抓取时间、变更次数、过期标记。

同一 URL 内容变化时保留版本链，不要直接覆盖。删除的页面要有 tombstone（失效标记），否则索引会一直返回已删除内容。

## 重新处理

解析器升级、切块策略变化、字段规则调整时，需要能对历史原始响应重跑，而不是重新抓一遍。原始响应与解析结果分开存，才能做到“只重算、不重抓”。

## 常见失败

- **全量重抓**：每天把整个站点抓一遍，成本高且容易被限流。
- **没有版本**：内容变了直接覆盖，无法回答“什么时候变的、旧版是什么”。
- **删除不可见**：页面 404 后仍留在索引；需要失效标记与定期清理。
- **调度不受预算约束**：高频任务挤占低频任务，长期欠抓。

## 一句话主线

用条件请求、内容哈希与结构信号检测变化，按内容类型分频重抓，原始响应与解析结果分层保存并保留版本；增量的目标是“只抓该抓的、只算该算的”。
