# 知识库形态与存储要素

用于 Agent 知识检索的知识库，不是一个单一数据库。它先要回答“知识按什么单位组织”，再回答“用什么系统承载”。前者是形态，后者是存储要素；两者不是一一对应。

## 形态与存储不是一回事

- 形态是逻辑层：文档、块、表格、图谱、案例、工具说明，决定检索时召回什么单位。
- 存储是物理层：对象存储、关系库、倒排索引、向量索引、图库、KV，决定这些单位落在哪里、怎么查。
- 向量库、图数据库常被当作“知识库类型”，严格说它们是存储/索引要素；同一形态可以用不同存储，同一存储也能承载多种形态。
- 把“向量库”当成独立形态，会漏掉原文、元数据、权限和版本；向量只是给块或实体加的一层语义索引。

## 知识库的形态

- **文档/目录型**：目录树 + 整篇文档或章节。优点是上下文完整、可人工维护、可版本控制；适合手册、论文、Wiki、规范。
- **块型**：把文档切成 chunk，按块召回。RAG 最常见；关键是切块粒度、重叠、标题层级与元数据。
- **表格/结构化型**：行、列、字段、记录。适合参数、清单、指标、权限、配置和可精确过滤的事实。
- **图谱型**：以知识图谱的实体—关系—属性组织，按节点和边检索。适合多跳关系、组织关系、因果链和可解释路径。
- **案例/轨迹型**：任务步骤、工具调用、成功与失败记录。适合 Agent 复用经验、少走弯路。
- **工具/技能型**：API、函数、SOP、技能说明。适合“找到该用哪个能力”，而不只是“知道什么”。
- **规则/本体型**：术语表、分类体系、约束、schema。适合统一口径、校验与跨源对齐。
- **混合型**：文档 + 表格 + 图谱 + 向量路由。真实 Agent 最常用；单一形态往往覆盖不了查询类型。

> 判断：真实 Agent 多为混合形态，但混合是路由层的事，不等于所有存储都要独立部署。

## 存储要素

- **对象/文件存储**：S3、OSS、本地文件系统、Git。放原始 PDF、HTML、Markdown、图片和附件。
- **关系型数据库**：Postgres、MySQL、SQLite。放文档元数据、块表、权限、版本、问题表和来源记录。
- **文档数据库**：MongoDB 等。放半结构化的 chunk、JSON 记录和可变字段。
- **倒排索引/搜索引擎**：Elasticsearch、OpenSearch、Meilisearch。负责关键词、BM25、过滤和聚合。
- **向量索引/向量库**：Milvus、Qdrant、Weaviate、pgvector、FAISS。负责 embedding 与近似最近邻。
- **图数据库**：Neo4j、NebulaGraph、ArangoDB。负责节点、边、属性和多跳路径。
- **KV/缓存**：Redis 等。放热块、查询缓存和会话状态。
- **版本库**：Git。放可追溯的知识文件、变更历史和协作记录。

## 横切要素

元数据、权限和版本不是装饰，而是检索结果能不能被信任的前提。元数据记来源、时间、实体、标签与块位置；权限决定哪些内容对当前 Agent 可见；版本决定答案对应哪一版知识。三者通常落在关系库，但必须贯穿对象存储、倒排索引、向量索引和图存储，否则召回越准，越可能把过期或无权限的内容答出去。

## 常见组合与选型

- **轻量**：文件系统 + SQLite + FAISS。适合个人知识库、原型和离线资料。
- **中型**：对象存储 + Postgres + 向量库 + 搜索引擎。覆盖原文、元数据、语义召回与关键词召回。
- **图谱增强**：在中型组合上再加图数据库，用于多跳关系与路径解释。
- **低延迟**：加 Redis，缓存热块、查询结果和会话状态。
- **选型顺序**：先按查询方式选存储——关键词走倒排，语义走向量，多跳走图，精确字段走关系库；再按数据规模决定是否独立部署。不要一上来把七种存储全部装上。
