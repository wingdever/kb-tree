# 四步 RAG 基线流水线

一条能跑通、能评估、能解释失败原因的 RAG 基线，可以压缩成四步：

1. 文档按章节结构与语义边界切块，不用固定 512 字硬切。
2. 块转向量，连同原文、元数据与版本写入向量库。
3. 检索时向量召回与 BM25 关键词召回并行，融合成一份候选。
4. 用 Cross-Encoder 对候选逐条重排，取少量高置信块交给生成。

这四步不是四个孤立技巧，而是一条有接口的链：切块决定检索单元，入库决定可召回范围，混合召回决定候选上限，重排决定最终上下文。任何一步坏了，后面的昂贵步骤都只是在给错误排序。

## 为什么四步

朴素 RAG 常见三种坏法：

- **切块坏**：固定字符数把一节、一张表、一段代码从中间切断，块脱离上下文后语义不完整。
- **召回窄**：只跑向量，专有名词、型号、错误码、人名这类精确词容易漏；只跑 BM25，换个说法就找不到。
- **排序粗**：向量相似不等于答案相关，前几个候选里混进大量“主题相近但不回答问题”的块。

四步分别对应：**保语义、保覆盖、保精确、保排序**。它也是排查顺序：先看正确块有没有被切出来，再看有没有被召回，再看有没有被排到前面，最后才怪模型。

## 第一步：结构 + 语义切块

先解析文档结构，再在结构内部做语义分割：

- **按标题层级切**：章、节、小节是天然边界；标题路径写进块元数据，检索时能解释“这段来自哪一章”。
- **保留完整对象**：表格、代码块、公式、列表不拦腰切；宁可块长一点，也不要把表头和行拆散。
- **段内语义切**：在章节内部按句子嵌入或段落主题变化找边界，而不是数满 512 字就断。
- **父子粒度**：用小块做匹配，命中后把父块或相邻上下文一起送给生成；匹配精度与回答连贯性分开优化。
- **重叠要克制**：只在边界附近保留少量重叠，整块复制会制造重复候选与浪费。

切块产物至少带：`doc_id`、`chunk_id`、标题路径、原文、字符范围、版本、权限标签。没有这些字段，后面无法增量更新、无法引用、也无法定位错误。

## 第二步：转向量入库

把每个块送嵌入模型，得到稠密向量，写入向量库。关键不是“存进去”，而是“存得能更新、能过滤、能追溯”：

- **向量与原文同存**：向量库只存向量，生成时还要回表取原文；原文、元数据、向量要在同一逻辑记录里对齐。
- **元数据过滤**：按租户、权限、文档类型、时间、版本先过滤再检索，避免把无权内容召回给模型。
- **索引参数**：数据规模、更新频率、延迟预算决定 ANN 索引类型；小规模先暴力或轻量索引，别一开始就上复杂集群。
- **增量与版本**：文档更新要能按 `doc_id` 删除旧块、写入新块；块 ID 要稳定，否则评估与引用会对不上。
- **嵌入版本**：换模型意味着向量空间变了，旧向量不能和新向量混用；索引要记录嵌入模型与维度。

这一步的验收不是“写入成功”，而是：给定一个块 ID，能取回原文、元数据、向量与所属文档；文档更新后，旧块能被干净替换。

## 第三步：BM25 + 向量混合召回

查询同时走两路：

- **稠密向量**：负责语义相近、换述、跨语言与模糊描述。
- **BM25**：负责精确词、稀有词、编号、错误码、产品名与领域术语。

两路各取一批候选，再用融合策略合并。默认用 **RRF**：不看原始分数，只看排名，把两榜都靠前的文档抬上来，避免 BM25 分数与余弦距离量纲不同带来的校准问题。若业务有明确偏好，也可以用归一化加权，但权重要靠评估集调，不能拍脑袋。

混合检索的常见坑：

- 中文 BM25 需要合适的分词与停用词；按字切或错误分词会让关键词路形同虚设。
- 两路召回数量要接近，否则融合会被一路垄断。
- 先过滤元数据再融合，避免“先融合再过滤”把候选池打空。
- 查询改写可以放在这一路之前，但改写失败会同时伤害两路；保留原始查询作为兜底。

这一步的输出不是最终答案，而是一份**候选池**：数量足够、覆盖两种匹配方式、带有各路排名与分数，供重排使用。

## 第四步：Cross-Encoder 重排

Cross-Encoder 把查询与候选拼接后一起过 Transformer，让每个 token 互相注意，直接输出相关性分。它比双塔向量准，因为它在查询期才做细粒度交互；代价是无法预计算，候选越多越慢。

标准做法：

- 从混合召回取一个中等候选池，不要把所有召回结果都送重排。
- 对候选做长度截断，保留真正决定相关性的开头部分；送给生成的仍是完整块。
- 取重排后的少量块进入上下文，通常前五到前十，具体按答案长度与模型窗口调。
- 对稳定查询缓存重排结果；查询与候选集都相同才可复用。
- 先测召回：正确块根本没进候选池时，重排救不了；这时回到切块、嵌入或混合召回。

重排的价值是**把“相关”变成“可回答”**：候选主题都对，但只有一个块包含答案所需的条件、数字或限制；Cross-Encoder 更容易把这一块顶上来。

## 接口与验收

四步之间要有清晰契约：

| 阶段 | 输入 | 输出 | 关键验收 |
|---|---|---|---|
| 切块 | 原始文档 | 带元数据的块 | 结构完整、边界合理、可追溯 |
| 入库 | 块 + 向量 | 可过滤的索引记录 | 能更新、能删除、版本一致 |
| 混合召回 | 查询 | 候选池 + 两路排名 | 正确块在池内、精确词不漏 |
| 重排 | 查询 + 候选 | 少量高置信块 | 正确块排到前面、延迟可接受 |

评估要分层，不要只看最终答案：

- **切块**：抽查边界是否切断表格/代码；用问题反查正确块是否存在。
- **召回**：看 Recall@k，正确块有没有进候选池。
- **融合**：看两路各自贡献，避免一路完全主导。
- **重排**：看 nDCG 或人工相关性，正确块是否进入最终上下文。
- **生成**：看答案是否只依据给定块、引用是否对得上。

## 常见错误

- 按固定字符数硬切，切碎章节、表格与代码。
- 块没有标题路径和权限元数据，召回后无法解释、无法过滤。
- 只做向量检索，专有名词与编号大量漏召回。
- BM25 不做中文分词，关键词路实际上没工作。
- 混合后不融合排名，直接把两路结果拼在一起。
- 重排候选过多，延迟爆炸；或候选太少，重排没有选择空间。
- 没有分层评估，最终答案差却不知道是切块、召回还是排序的问题。

## 边界

- 四步是**基线**，不是唯一架构：GraphRAG、Agentic RAG、多模态 RAG 会在其上增加路由、迭代检索或关系推理。
- Cross-Encoder 只能重排已召回的内容；召回阶段没进来的正确块，它看不到。
- 结构切块依赖解析质量；PDF 版面、扫描件与复杂表格需要先做可靠解析。
- 混合检索与重排都会增加延迟与成本；低延迟场景要裁剪候选、缓存或跳过重排，但要用评估证明没有伤到质量。

## 一句话主线

**结构切块保住语义，向量库保住可召回，BM25 保住精确词，Cross-Encoder 保住最终排序；四步各守一段，失败才能被定位。**
