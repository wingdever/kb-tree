# RAG 生产实践

## 生产中的常见失败

- **单向量检索无重排序**：2022 vintage 架构，仍在多数企业生产；质量明显差于混合 + 重排。
- **黄金集过期**：PoC 期手工做的，六个月没更新，语料翻倍、查询分布漂移，面板数字无人相信。
- **数据质量**：垃圾进→幻觉出。策展语料、版本化、定期离线检查检索召回漂移。
- **陈旧信息**：给每块打发布日期和来源标签，检索器可对新鲜度打分，生成器可被指示标记过时证据。
- **延迟**：查询改写 +200~400ms；用改写缓存、GPU 加速重排器、ANN 索引缓解。
- **Token 浪费**：30 个工具的描述在工作时每请求序列化进提示词，可能花 3000~5000 token 描述从不调用的工具——按阶段过滤工具（见 `../../agent/context/`）。

## 安全与 RBAC

> 用户在 SharePoint 看不到的文档，不能通过 RAG 检索到其块。

**做法**：把 ACL 嵌入向量元数据，如：

```json
{ "content": "...", "allowed_groups": ["hr", "management"] }
```

向量搜索前先按用户组过滤。元数据过滤两种模式：

- **Pre-filter**：先过滤再检索——正确但选择性低时慢。
- **Post-filter**：先检索再过滤——快但可能返回不足 k 条。
- **自适应**：查询规划器估计选择性，按查询选 pre/post。

元数据富化还能提升质量：IEEE 研究显示带归属、血缘、质量分、分类的元数据检索精度 82.5% vs 仅内容 73.3%。

## 索引新鲜度

- 文档批量更新后索引没重建 → 新文档搜不到。靠数据同步流程解决。
- 嵌入模型变更必须重嵌，过渡期维护两个索引双写。
- HNSW 删除难 → tombstone + 定期重建。

## 参考架构（2026 企业栈）

1. 摄入：Unstructured.io（PDF/PPT 解析）
2. 编排：LlamaIndex / LangChain
3. 索引：混合（Pinecone + Elasticsearch）
4. 知识图谱：Neo4j
5. 检索：混合搜索 + Cohere 重排
6. 生成：vLLM 或云端模型
7. 评估：Ragas / Arize Phoenix

## 成本优化

- 量化 + Matryoshka 降维（见 `../embedding/`、`../vdb/`）。
- 缓存：嵌入内容哈希缓存、查询改写缓存、提示缓存。
- 分层存储：热/温/冷分区。
- 批处理 API、按步骤选模型。

## 上线检查清单

- [ ] 用混合搜索 + 重排序，而非单向量。
- [ ] 块元数据含时间戳、来源、ACL、溯源标记。
- [ ] 黄金集代表生产分布且定期刷新。
- [ ] 有失败模式目录并分类跟踪。
- [ ] 少量生产流量回流回归集。
- [ ] RBAC 在检索前按用户组过滤。
- [ ] 索引重建与数据同步机制就位。
- [ ] 延迟分解（改写/检索/重排/生成）已埋点。
