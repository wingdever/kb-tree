# 检索即工具：架构转变

Agentic RAG 背后更微妙的架构变化：**检索越来越多是 Agent 调用的工具，而非应用确定性地运行的预处理步骤**。

传统 RAG 是线性函数：嵌入查询 → 取 top-K → 塞进提示 → 生成，一次通过、一个结果。Agentic RAG 是循环状态机：Agent 收到问题 → 拆解 → 决定调哪些源（向量库、SQL、web、MCP server）→ 评估结果 → 质量不足就再来一轮，直到答案达置信阈值或迭代上限（典型 5–6 轮）。

## 为什么这个转变重要

用户很少把问题表述成可 trivially 嵌入的形式。能把"我们之前怎么处理 Q3 定价问题"改写成两三次针对性检索（针对不同索引、不同时间范围）的 Agent，胜过单次管道。额外 LLM 调用成本，通常被生产中错误答案的成本淹没。

循环中的每一步都能拿到**环境反馈**（工具结果、代码执行）——这正是 Agent 自我纠正的基础。LangGraph 的 checkpoint 让每步可追踪、可暂停（人工审批）、可重放——合规与调试的必备属性。

## 工程投入的转移

架构转变后，投入重心从"调提示词"移到：

- **索引质量**：块元数据（尤其时间戳、来源类型、溯源标记）——比把单次重排序再挤高一个百分点更重要。
- **每次检索延迟**：在多次循环的 Agent 里，单次检索延迟被放大。
- **工具设计**：每个检索动作是一个工具，工具的描述、schema、权限决定 Agent 选得准不准（见 `../../../agent/tool/`）。

评估问题也随之改变：从"检索到正确的块了吗？"变成 **"Agent 构造了正确的检索计划了吗？"**——多数 RAG 评估套件还没测好这个，轨迹级评估见 `../../eval/`。

## 成本与延迟的现实

Agentic RAG 不是免费升级：

- **Token 成本**：简单 RAG 的 3–10×——循环每轮、每次工具调用都加 token。
- **延迟**：从 1–2s 升到 4–15s（p95）。3–4 轮循环端到端常需 8–12s。
- 若 UX 要求 sub-3s，必须让 Adaptive 路由把简单查询分到快路。

因此**默认架构决策是路由**：让大部分简单问题走单次检索，只把难题送进 agentic 循环。团队常犯的错是用 FAQ bot（简单事实快路）去处理"对比最近五份合同第 4.2 条"这类昂贵查询——浪费预算。

## 从 Pipeline 到 Loop 的对照

| 维度 | 线性 RAG | Agentic RAG |
|---|---|---|
| 结构 | 预定序列 | 动态循环 |
| 自我纠正 | 无 | 高（可再检索） |
| 查询复杂度 | 简单（1 步） | 难（多步） |
| 延迟 | 低（固定） | 可变（多轮） |

**使用判断**：当查询需要的是"综合证明（Synthesized Proof）"而非"文档匹配（Document Match）"时，才用 Agentic RAG。

## 何时循环本身成了成本问题

有一类工作负载里，循环本身就是成本瓶颈——这时出现了"编译知识一次"的替代路线（把知识预编译成持久 Wiki，查询直接读成品），见 `../../llm-wiki/`。它与检索即工具是两种哲学：前者把决策放到运行时，后者把决策前移到摄入期。
