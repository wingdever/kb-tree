# IM 子生态

IM 是软件生态里第一个成形的子生态：它以「把人、机器人和 Agent 放进同一个会话」为核心，决定了对话发生在哪里、以什么身份发生、消息与事件怎么流动。本页写**跨平台共性**，具体平台见子知识点。

## 共性维度

| 维度 | 要解决的问题 |
|---|---|
| 身份体系 | 官方机器人账号 vs 真人账号接管；权限、实名、审核与封号风险 |
| 开放接口 | 消息 API、SDK、Webhook / 事件推送、频率限制 |
| 消息与事件模型 | 单聊/群聊/频道、指令类型、表单、流式消息、富媒体 |
| 机器人治理 | 官方与第三方机器人、准入、限流、审计 |
| 会话边界 | 账号、房间、群组如何映射成 Agent 会话 |
| 部署与数据 | 云端/自托管、多设备、消息留存 |

## 选择对话面：路径与生态位

封闭生态的问题是：官方机器人接口能力受限，而全能力方案要接管真人号、违反用户协议。可选路径分四类，但**生态位不同，不能混为一谈**：

1. **国内大陆可直连的消费级开放 IM** — 云湖：官方机器人账号、开放 API + Webhook、流式消息、Flutter 全平台。这是「大陆直连 + 消费级/技术社群 + 官方机器人身份 + 开放接口」这个组合里目前最完整的一个。
2. **企业协作平台** — 飞书、钉钉、企业微信：开放平台、长连接事件订阅、Webhook / 回调、富交互卡片，适合企业内部渠道。它们的官方定位是 AI 工作平台或企业协作套件，IM 只是其中一个模块，**不是消费级 IM 的同类产品**。
3. **海外 Bot API 平台** — Telegram（Bot API 完善、限额宽松）、Discord / Slack：开放度高，但**大陆访问有门槛**，不能作为国内 C 端渠道的默认基线。
4. **自建或自托管开放 IM** — Matrix + Element（联邦、端到端加密、可桥接其它平台）、Rocket.Chat / Mattermost / Zulip（自托管、API/Webhook/机器人框架）。Matrix 是**协议不是产品**：`matrix.org` 官方服务大陆访问不稳定；自托管 homeserver 能解决连通，但带来 PostgreSQL + TLS 运维、合规资质、以及联邦仍需访问外部节点三道门槛，基本是技术圈方案。

另外两条相关路径：**开放协议桥接**（Matrix 桥接、多通道网关 goim / nanobot / dsh-channels）让 Agent 只面对一套接口，但网关里的微信/QQ 通道往往仍走协议端，风险并未消失；**Agent 原生 IM**（内置 Matrix 服务器，Agent 作为房间成员协作、人类随时进房间监督）不申请平台机器人、不等审核，但同样继承自托管的运维与合规门槛。

纯协议端（NapCat / SnowLuma 等）不算「突破」——它仍留在原生态里承担封号与掉线风险，只是绕开了接口限制。

**生态位结论**：大陆可直连的消费级开放 IM 这个窄生态位里，云湖目前没有同量级的直接对手，可以称为最完整；但其用户规模为自报、厂商规模小、版本迭代快，「最好」不能无条件成立。企业协作平台、海外 Bot API、自托管开放协议分别属于另外的生态位。

## 平台条目

| 平台 | 身份路线 |
|---|---|
| 云湖（YunhuM3） | 官方机器人账号；开放 API + Webhook |
| QQ | 官方 Bot 账号 vs 真人号 + 协议端 |
| 飞书 / 钉钉 / 企业微信 | 企业协作套件，IM 是其中一个模块；非消费级 IM 同类 |
| Telegram / Discord / Slack | 官方 Bot API；大陆访问有门槛 |
| Matrix / Rocket.Chat / Mattermost / Zulip | Matrix 是协议；自托管解决连通但有运维、合规与联邦访问门槛 |

## 与 Agent 渠道的边界

本子生态是**平台视角的主宿主**：讲平台是什么、给谁什么身份、开放什么能力。两处文字不同是正常的，不互相复制。

## 一句话主线

**IM 子生态的核心是「身份 + 接口 + 会话边界」；在大陆可直连的消费级开放 IM 这一窄生态位，云湖目前最完整，而企业协作平台、海外 Bot API、自托管开放协议分别属于不同生态位。**
