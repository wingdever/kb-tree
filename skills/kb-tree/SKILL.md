# kb-tree — 树状离线知识库构建规范

把主题资料整理成一棵可离线阅览、可无限扩展的 Markdown 知识树。核心约定：**领域顶层目录 + 知识点自成一个目录 + 目录内同名 md + front matter 四字段 + 相对链接互引**。

## 适不适用

- **适用**：从网上抓取资料整理成离线学习库；一个主题需要拆成多个子知识点；资料需要长期增量扩展。
- **不适用**：单篇笔记、一次性文档、需要在线实时更新的内容。

## 心智模型

```
<树名>/
├── <树名>.md            根知识文档：本知识库主题本身 + 子领域导航
├── <领域>/                 顶层按领域分（英文短名）
│   ├── <领域>.md           领域知识文档：该领域是什么 + 子树导航（同目录名）
│   ├── <知识点>/           每个知识点一个目录
│   │   ├── <知识点>.md     该知识点介绍（同目录名）
│   │   └── <子知识点>/      可继续嵌套：子知识点也是目录+同名 md
│   └── ...
```

五条铁律：
1. **每个知识点 = 一个目录 + 目录内同名 md**。要展开某个单文件时，把它改成该目录的导航页（保留精华 + 指向子目录）。
2. **根也是知识，根节点同样有同名 md**（如根 `<树名>/` 配 `<树名>.md`）。
3. **区分两类文档，不要混淆**：
   - **知识文档**（同名 md，如 `<树名>.md`、`ai/ai.md`、`agent/agent.md`）：讲这个知识点/领域**本身是什么**——研究范畴、分支、核心概念，并附该节点的子树导航。
   - **组织与维护规则**（仓库根 `README.md`）：**只讲组织与维护规则**——命名、front matter、链接、子树导航、新增与扩展规则。**不说明某棵树讲什么（不描述知识领域或学科），不列举有哪些知识、领域或分支，不写目录树、现状清单或具体路径示例**——这些属于知识文档，且会随库演进失效。标题与 front matter 描述同样保持中性，不点名知识领域；易变事实举例也不指向具体领域。
   - 规则不进树：根 `<树名>.md` 是知识文档，规则统一放仓库根 README；各领域只有同名 md（知识 + 子树导航），树内任何层级都不建 README。
4. **子知识点可以继续是目录**，层级不限，只要父节点有介绍 md 作为入口。
5. **全部用相对链接互引**（如 `../rag/eval/eval.md`），保证整个库可整体搬迁、离线打开。

> 来源规则另见下节"来源标注"：第三方资料不写来源关系，官方互联网文档保留来源说明。

## 节点类型与挂载

节点的"类型"不是一个标签，而是四个独立坐标：**内容性质**（事实 / 概念 / 程序 / 元认知）、**功能内容**（what / why / how / when）、**写作目的**（参考 / 解释 / 教程 / 指南 / 决策）、**结构角色**（叶子 / 枢纽 / 导航 / 综述 / 规则）。前两项描述知识本身，后两项描述文档与它在树中的位置。不要用一个词概括多个坐标，也不要往 front matter 加 `type` 字段。

三个层面要分开：

- **知识点**：可断言、可判真假的抽象内容。
- **文档**：有路径、有版本、可寻址的载体。
- **容器**：目录拓扑，决定节点在树中的位置。

内容性质和功能内容属于知识点，写作目的属于文档，结构角色属于容器。同一知识点可由多份文档表达，同一文档可含多个知识点；"目录 + 同名 md"只是默认的一对一挂载策略，不是知识的本性。

**目录 = 对象，同名 md = 对对象的描述，小节 = 对象的一个方面，子目录 = 子对象。** 新建目录等于宣布一类对象存在，是实质性决定；只在现有文档里加一节，是给对象补一个方面，成本低得多。

关系与过程也是对象，可以有多重挂载：

- **挂载是视角，不是副本**。挂在不同宿主上时，从宿主的关注点出发写相关的方面即可，文字不同是正常的。
- 一致性要求是"对同一关系的核心断言不矛盾"，不是逐字相同。
- 横切知识的写法：选一个主宿主写完整内容，其余宿主只写视角化简述并用相对链接指回主宿主，不整段复制。
- "信息只在其所属节点出现一次"只禁止同一条断言被重复陈述，不禁止同一关系对象被多个宿主从各自视角挂载。

写作前先确定这页回答什么问题——是什么（参考）/ 为什么（解释）/ 怎么做（教程、指南）/ 什么时候用哪个（决策）——然后保持一种口吻，不在同一页来回切换。综述页天然是"解释 + 决策 + 横向枢纽"的组合，这是它的职责，不是类型混乱。

## 附属检索夹具 questions.jsonl

每个节点目录可放一份 `questions.jsonl`，把该节点能回答的问题列为机器可读的检索夹具。它是 C 层附属文件，不是知识节点，不套四字段，文件缺失合法。

编写或校验 `questions.jsonl` 时，用 Read 打开 `${CODEBUDDY_SKILL_DIR}/references/questions-jsonl.md`，按其中的字段规则与校验脚本执行。

## 来源标注（按资料类型区分）

引入、抓取、迁移或融合资料时，先判断资料类型，再决定是否标注来源：

### 第三方资料 —— 不写来源关系

第三方资料指非官方、个人整理的素材，典型如**用户自己的笔记**、个人博客、第三方解读文章。这类内容的文档要读起来像本来就是知识树的一部分，**不写它与来源的关系**。

禁止出现的表述：

- `迁移自原笔记 xxx`、`本目录从原笔记迁移`、`原笔记此文件……`、`原笔记未改动`
- `补抓 2026 资料`、`本页源于原笔记对……的思考`、`另一来源：xxx`（当指第三方时）

正确做法：

- "原笔记此文件为空/只有框架，这里补全"这类句子整句删除，正文直接以知识点陈述开头。
- "X 提出于某年某月"属于知识点自身的史实（如 Karpathy 2026 年提出 LLM Wiki），可以保留——这是知识内容，不是"本文档的来源"。

### 官方互联网文档 —— 保留来源说明

官方资料指一手权威文档，典型如产品/项目的**官方文档与规范**（OpenAI、DeepSeek、LangChain、MCP spec、Google Cloud 等）、**论文原文**、**标准文本**。这类内容**保留来源说明**，便于溯源与核对时效。

格式：在知识点简介处用引用行写明出处与版本/时效，例如：

```markdown
> 来源：Model Context Protocol 官方规范 2026-07-28 版，modelcontextprotocol.io/specification/2026-07-28/server/tools。
> 来源：docs.langchain.com 官方 Tools 文档。API 形态变化快，落地前以官方文档为准。
```

要点：写清**来源主体 + 版本/日期**，时效提醒（"API 变化快，以官方文档为准"）属正常；不写"抓取于何时、抓自何处"这类操作痕迹。

### 复查

融合完成后用 Grep 搜 `迁移自|原笔记|补抓|源于原笔记` 复查第三方资料是否残留来源关系；官方来源行保留属正常。技术语境里的"数据来源""词嵌入来源"（列举语料/模型）不算来源关系，保留。

## 命名规范

- **所有层级**（根、领域、知识点、子知识点）的目录与文件名一律用**英文短名/首字母缩写**，小写 kebab-case（如 `<树名>`、`ai`、`rag`、`vdb`、`plan-exec`、`self-correct`）。**不要用中文或大写命名目录/文件**——中文概念放进 front matter 的 `名称` 字段，不进路径。
- 目录名与其介绍 md 的基名**完全一致**（`chunking/` ↔ `chunking.md`；根 `<树名>/` ↔ `<树名>.md`）。根用同名 md，**树内不用 README.md**。
- 中文全称不放进路径，放进 front matter 的 `名称` 字段。
- 设计映射表时一次列全：旧路径段 → 新路径段；深度嵌套时按段替换，不要整串 replace（会误伤正文词汇）。

## front matter 四字段

每个 md 顶部必须有，值统一用双引号（防冒号解析错误）：

```markdown
---
description: "One short English sentence describing the topic"
描述: "一句简短中文描述这个知识点是什么"
name: "English Full Name"
名称: "中文全称"
---

# 正文标题
```

- `description` / `描述`：**说知识点是什么**，不说"本文档介绍……"；约 40 字内。
- `name` / `名称`：全称，英文与中文各一。
- 只保留这 4 个字段，不加 `title/status/updated`（title 可从文件名推，status/updated 是一次性离线库不必要的维护负担）。

## 构建流程

1. **定领域**：按主题划顶层目录（如 agent / rag / model / api）。
2. **拆知识点**：每个领域拆成知识点目录 + 同名介绍 md；有子知识的继续拆子树。
3. **抓资料**：用 WebFetch/WebSearch 抓权威一手资料，整理成自足文档（含数字、公式、代码、失败模式）。按"来源标注"规则处理：官方互联网文档保留来源说明，第三方资料不写来源关系。扩展子知识时优先补抓原文，而非只切分旧内容。
4. **写导航**：每个领域写 `<领域>.md` 总览（子目录表格 + 建议阅读顺序 + 一句话主线）；仓库根 `README.md` 只写组织与维护规则，不写知识主题与现状，树内不放 README。
5. **加 front matter**：按四字段规范，给全部文件写中英文描述与全称。
6. **维护链接**：正文用相对链接指向相关知识条目；用脚本批量校验断链。

## 扩展一个已有知识点的标准动作

1. 读原文件，识别可独立的子知识（小节、并列概念）。
2. 建子目录，每个子知识写一份自足 md；不足处补抓资料。
3. 把原文件改造成导航页：保留核心摘要 + 子目录表格 + "一句话主线"，去掉已下沉的重复细节。
4. 更新父级总览里该条目的说明（标注"已展开为子树"并指向入口 md）。
5. 跑一遍断链检查。

## 批量改名与链接重写（关键陷阱）

要把中文目录/文件名改成英文短名、并全量加 front matter 时，用一次性 Python 脚本：

- **先写临时目录**（如 `.staging_new`），全部处理完再整体替换旧树，避免中途失败留半拉子。
- **路径分段替换**：对路径按 `/` 切段逐段映射（`seg_replace`），不要整串 replace。
- **front matter 与改名同步**：脚本读旧路径文件 → 写正文处理 → 加 front matter → 写新路径。
- **代码块陷阱（必踩）**：inline 相对链接在反引号 `` `../x/` `` 里，但三反引号代码块 ```` ``` ```` 会让朴素正则 `` `([^`]+)` `` 错位配对，把代码块后的 inline 链接吞掉、漏替换。解决：先 `text.split("```")`，只在偶数段（正文）做 inline 替换，奇数段（代码块）原样保留。
- **导航页/总览**（各 `<领域>.md`、各 `<知识点>.md`、仓库根 `README.md`）正文里也含目录名引用，需对它们做全文替换（按映射 key 长度降序），其余文件只处理反引号内的相对链接。
- 处理后再全库校验：front matter 四字段齐全、无中文路径遗留、无临时目录残留、相对链接断链为 0。

## 断链校验脚本（可直接用）

```python
import os, re
broken=[]; total=0
for dp,_,fns in os.walk('.'):
    for fn in fns:
        if not fn.endswith('.md'): continue
        fp=os.path.join(dp,fn); text=open(fp,encoding='utf-8').read()
        parts=text.split('```')
        body=''.join(parts[i] for i in range(0,len(parts),2))   # 跳过代码块
        for m in re.findall(r'`(\.\./[^`]+)`', body):
            total+=1
            if not os.path.exists(os.path.normpath(os.path.join(dp,m))):
                broken.append((fp,m))
print(f"链接 {total} / 断链 {len(broken)}")
```
