# kb-tree — 树状离线知识库构建规范

把主题资料整理成一棵可离线阅览、可无限扩展的 Markdown 知识树。核心约定：**领域顶层目录 + 知识点自成一个目录 + 目录内同名 md + front matter 四字段 + 文档各自自足、互不引用**。

## 适不适用

- **适用**：从网上抓取资料整理成离线学习库；一个主题需要拆成多个子知识点；资料需要长期增量扩展。
- **不适用**：单篇笔记、一次性文档、需要在线实时更新的内容。

## 心智模型

```
<树名>/
├── <树名>.md            根知识文档：本知识库主题本身
├── <领域>/                 顶层按领域分（英文短名）
│   ├── <领域>.md           领域知识文档：该领域是什么（同目录名）
│   ├── <知识点>/           每个知识点一个目录
│   │   ├── <知识点>.md     该知识点介绍（同目录名）
│   │   └── <子知识点>/      可继续嵌套：子知识点也是目录+同名 md
│   └── ...
```

五条铁律：
1. **每个知识点 = 一个目录 + 目录内同名 md**。要展开某个单文件时，把它改成该目录的入口页（保留精华，子知识点各自成文）。
2. **根也是知识，根节点同样有同名 md**（如根 `<树名>/` 配 `<树名>.md`）。
3. **区分两类文档，不要混淆**：
   - **知识文档**（同名 md，如 `<树名>.md`、`ai/ai.md`、`agent/agent.md`）：讲这个知识点/领域**本身是什么**——研究范畴、分支、核心概念，自足成文。
   - **组织与维护规则**（仓库根 `README.md`）：**只讲组织与维护规则**——命名、front matter、节点互不引用、新增与扩展规则。**不说明某棵树讲什么（不描述知识领域或学科），不列举有哪些知识、领域或分支，不写目录树、现状清单或具体路径示例**——这些属于知识文档，且会随库演进失效。标题与 front matter 描述同样保持中性，不点名知识领域；易变事实举例也不指向具体领域。
   - 规则不进树：根 `<树名>.md` 是知识文档，规则统一放仓库根 README；各领域只有同名 md（知识自足陈述），树内任何层级都不建 README。
4. **子知识点可以继续是目录**，层级不限，只要父节点有介绍 md 作为入口。
5. **知识点之间不互相引用**：每份文档自足，不提及其他节点——不放相对链接、不列子树导航表、不写 `> 相关：…` 引用行，也不写「见某某节点」这类文字点名。层级靠目录结构表达，读者按目录浏览。

> 来源规则见下节「来源标注」：官方与第三方资料都要交代，统一写进文末「参考资料」。

## 节点类型与挂载

节点的"类型"不是一个标签，而是四个独立坐标：**内容性质**（事实 / 概念 / 程序 / 元认知）、**功能内容**（what / why / how / when）、**写作目的**（参考 / 解释 / 教程 / 指南 / 决策）、**结构角色**（叶子 / 枢纽 / 导航 / 综述 / 规则）。前两项描述知识本身，后两项描述文档与它在树中的位置。不要用一个词概括多个坐标，也不要往 front matter 加 `type` 字段。

三个层面要分开：

- **知识点**：可断言、可判真假的抽象内容。
- **文档**：有路径、有版本、可寻址的载体。
- **容器**：目录拓扑，决定节点在树中的位置。

内容性质和功能内容属于知识点，写作目的属于文档，结构角色属于容器。同一知识点可由多份文档表达，同一文档可含多个知识点；"目录 + 同名 md"只是默认的一对一挂载策略，不是知识的本性。

**目录 = 对象，同名 md = 对对象的描述，小节 = 对象的一个方面，子目录 = 子对象。** 新建目录等于宣布一类对象存在，是实质性决定；只在现有文档里加一节，是给对象补一个方面，成本低得多。

关系与过程也是对象，可以有多重挂载：

- **挂载是视角，不是副本**。挂在不同宿主上时，从宿主的关注点出发写相关的方面即可，文字不同是正常的。
- 一致性要求是"对同一关系的核心断言不矛盾"，不是逐字相同。
- 横切知识的写法：选一个主宿主写完整内容，其余宿主只写视角化简述、不整段复制，也不提及其他宿主节点。
- "信息只在其所属节点出现一次"只禁止同一条断言被重复陈述，不禁止同一关系对象被多个宿主从各自视角挂载。

写作前先确定这页回答什么问题——是什么（参考）/ 为什么（解释）/ 怎么做（教程、指南）/ 什么时候用哪个（决策）——然后保持一种口吻，不在同一页来回切换。综述页天然是"解释 + 决策 + 横向枢纽"的组合，这是它的职责，不是类型混乱。

## 附属检索夹具 questions.jsonl

每个节点目录可放一份 `questions.jsonl`，把该节点能回答的问题列为机器可读的检索夹具。它是 C 层附属文件，不是知识节点，不套四字段，文件缺失合法。

编写或校验 `questions.jsonl` 时，用 Read 打开 `${CODEBUDDY_SKILL_DIR}/references/questions-jsonl.md`，按其中的字段规则与校验脚本执行。

巡检脚本会顺带报告覆盖率：`python3 skills/kb-tree/scripts/lint.py <根>` 输出「覆盖 已配/总节点」。加 `--coverage` 可列出缺夹具且二级标题不少于三个的节点。`object.json` 的 `realm`/`kind`/`generality`/`volatility` 取值也由巡检校验，非法枚举直接报错。

## 附属对象坐标 object.json

每个节点目录可放一份 `object.json`，用三个坐标登记该节点所讲的对象：`realm`（`logical` 逻辑界 / `material` 物质界 / `symbolic` 符号界）、`kind`（`thing` 东西 / `event` 事件 / `relation` 关系）、`generality`（`particular` 这一个 / `type` 这一类）；再附 `canonical`、`volatility`、`verify` 供核实与复查。

它属于 C 层附属文件，不是知识节点，不套四字段，缺失合法。一个节点只给一个三元组，按节点回答的问题的主语判定；主语跨格就拆节点，不在一页混写。

编写或校验时，用 Read 打开 `${CODEBUDDY_SKILL_DIR}/references/object-json.md`，按其中的判定顺序、硬规则与字段取值执行。

## 附属词项链接 links.csv

每个节点目录放一份 `links.csv`，登记“本页正文里出现的词 → 它所指向的另一个节点对象”。它是 C 层附属文件，不是知识节点，不套四字段；没有可登记项时只写表头。

表头固定为 `term,target`：`term` 是本页正文原样出现的词，`target` 是对象所在节点的目录路径（相对仓库根，如 `trees/computer/ai/rag`）。它只表达“词指称哪个对象”，不表达上下位或因果关系，也不替代正文的自足规则——正文仍不写相对链接、不点名其他节点。

编写或校验时，用 Read 打开 `${CODEBUDDY_SKILL_DIR}/references/links-csv.md`，按字段、路径与校验规则执行。巡检脚本会检查文件存在性、表头、目标节点、自指、词是否出现在正文，以及重复项。

## 来源标注

引入、抓取、迁移或融合资料时，一律交代来源。区分的是**交代什么**，不是**是否交代**。

### 两类资料，两种写法

- **官方资料**（产品/项目的官方文档与规范、论文原文、标准文本）：写清来源主体 + 版本或日期。
- **第三方资料**（用户自己的笔记、个人博客、第三方解读文章）：写清作者或机构 + 原链接；借用他人的结构、措辞、图表时必须点名。

两类都放在**文末 `## 参考资料`**，每条一行 `- 名称：URL`：

```markdown
## 参考资料

- Model Context Protocol 官方规范（2026-07-28 版）：https://modelcontextprotocol.io/specification/2026-07-28
- 张三《Agent 记忆的三种实现》：https://example.com/post
```

要点：

- 官方条目带版本/日期，便于核对时效；第三方条目带作者或站点。
- 只有机构与文档名、拿不到固定链接时，条目就写机构与文档名，**不凭空补一个像样的 URL**。
- 正文里已嵌的接口地址（端点、SDK 调用）不必搬进参考资料；纯资源清单页不重复列出同一地址。
- 本页自己的归纳与工程判断用 `> 判断：…` 标出，不写成「官方认为」「业内共识」。
- 不再使用文档顶部的 `> 来源：…` 引用行——来源统一收到文末。

### 不写操作痕迹

来源交代的是知识从哪来，不是这份文档怎么做出来的。禁止出现：

- `迁移自原笔记 xxx`、`本目录从原笔记迁移`、`原笔记此文件……`、`原笔记未改动`
- `补抓 2026 资料`、`本页源于原笔记对……的思考`、`另一来源：xxx`（含糊指代）

做法：这类句子整句删除，正文直接以知识点陈述开头；「X 提出于某年某月」属于知识史实，可以保留。

### 复查

用 Grep 搜 `迁移自|原笔记|补抓|源于原笔记` 确认无操作痕迹；再确认每页有 `## 参考资料`，或该页确实无外部来源。技术语境里的「数据来源」「词嵌入来源」不算来源关系，保留。

## 命名规范

- **所有层级**（根、领域、知识点、子知识点）的目录与文件名一律用**英文短名/首字母缩写**，小写 kebab-case（如 `<树名>`、`ai`、`rag`、`vdb`、`plan-exec`、`self-correct`）。**不要用中文或大写命名目录/文件**——中文概念放进 front matter 的 `名称` 字段，不进路径。
- 目录名与其介绍 md 的基名**完全一致**（`chunking/` ↔ `chunking.md`；根 `<树名>/` ↔ `<树名>.md`）。根用同名 md，**树内不用 README.md**。
- 中文全称不放进路径，放进 front matter 的 `名称` 字段。
- 设计映射表时一次列全：旧路径段 → 新路径段；深度嵌套时按段替换，不要整串 replace（会误伤正文词汇）。

## front matter 四字段

每个 md 顶部必须有，值统一用双引号（防冒号解析错误）：

```markdown
---
description: "One short English sentence describing the topic"
描述: "一句简短中文描述这个知识点是什么"
name: "English Full Name"
名称: "中文全称"
---

# 正文标题
```

- `description` / `描述`：**说知识点是什么**，不说"本文档介绍……"；约 40 字内。
- `name` / `名称`：全称，英文与中文各一。
- 只保留这 4 个字段，不加 `title/status/updated`（title 可从文件名推，status/updated 是一次性离线库不必要的维护负担）。

## 构建流程

1. **定领域**：按主题划顶层目录（如 agent / rag / model / api）。
2. **拆知识点**：每个领域拆成知识点目录 + 同名介绍 md；有子知识的继续拆子树。
3. **抓资料**：用 WebFetch/WebSearch 抓权威一手资料，整理成自足文档（含数字、公式、代码、失败模式）。按"来源标注"规则处理：官方互联网文档保留来源说明，第三方资料不写来源关系。扩展子知识时优先补抓原文，而非只切分旧内容。
4. **写总览**：每个领域写 `<领域>.md` 自足总览（该领域是什么 + 一句话主线），不列子目录表格或阅读顺序链接；仓库根 `README.md` 只写组织与维护规则，不写知识主题与现状，树内不放 README。
5. **加 front matter**：按四字段规范，给全部文件写中英文描述与全称。
6. **不维护跨节点引用**：每份文档自足；不写 `> 相关：…` 行、不写指向其他节点的路径或文字点名，也不做断链校验。

## 扩展一个已有知识点的标准动作

1. 读原文件，识别可独立的子知识（小节、并列概念）。
2. 建子目录，每个子知识写一份自足 md；不足处补抓资料。
3. 把原文件改造成自足入口页：保留核心摘要 + "一句话主线"，去掉已下沉的重复细节，不列子目录表格。
4. 更新父级总览里该条目的说明（标注"已展开为子树"），不放路径链接。
5. 检查新文档没有指向其他节点的相对链接。

## 自检清单

- [ ] `tree` 查看结构，符合"目录 + 同名 md"，无空目录。
- [ ] **根节点有同名 md**（如 `<树名>/<树名>.md`），且组织与维护规则统一放在仓库根 `README.md`（纯规则，不说明某棵树讲什么，不含知识清单/目录树/现状描述，标题与 front matter 亦不点名知识领域）；树内无 README，知识文档与规则未混淆。
- [ ] 全部文件有四字段 front matter，值为双引号。
- [ ] **所有层级目录/文件名全为小写英文 kebab-case**，无中文、无大写（如按英文短名规范）。
- [ ] 领域总览与知识点入口页自足成文，无子目录表格、无阅读顺序链接；树内无 README。
- [ ] 文档内无指向其他节点的相对链接、无子树导航表、无 `> 相关：…` 引用行，也无「见某某节点」的文字点名。
- [ ] 新扩展的子知识点已补抓权威资料，不是空壳。
- [ ] 来源标注：第三方资料无来源关系残留（Grep 搜 `迁移自|原笔记|补抓|源于原笔记` 无命中）；官方来源行保留属正常。
- [ ] 每个节点明确它回答 what / why / how / when 中的哪一个，没有在同一页混用多种口吻。
- [ ] 横切知识有主宿主，其他挂载点是视角化简述、不放相对链接，没有整段复制。
- [ ] 新建目录前确认它代表一类对象；只是补一个方面时优先加小节。
- [ ] `questions.jsonl`（若有）每行可解析、字段齐全，`section` 与同级同名 md 的 H2/H3 标题逐字一致。
- [ ] `object.json`（若有）三轴取值在枚举内，一个节点一个三元组，`canonical` 与 md 所述对象一致。
- [ ] 每个节点都有 `links.csv`，表头为 `term,target`；每行的词能在正文找到，目标节点存在且不是自己。
- [ ] 同一问题全树只有一个 `primary`，每条 `perspective` 都有 `owner` 且路径存在。
