# 搜索 → 入库：把知乎检索结果变成知识树节点

这是本仓库的固定工作流：用 `tools/zhihu-search` 检索，把经得起复核的知识写成树节点，而不是把链接堆进文件。

## 一、先检索，别先动笔

```bash
cd tools/zhihu-search
./zhihu "关键词" --count 10          # 默认 10 条，站内经验贴密度最高
./zhihu --quota                      # 动手前先看当天还剩多少额度
```

检索词按知识树的节点名来定，而不是按你的口语问题来定：要写“上下文工程”，就搜“上下文工程”“context engineering”“上下文压缩”，而不是搜“Agent 怎么变聪明”。

## 二、给三类“不太可靠”的结果分档，而不是丢弃

粗筛丢弃很浪费：一篇二手综述里往往藏着五篇值得读的论文，一篇营销稿里往往有真实的版本号与价格。正确做法是按**它能承担什么角色**分档：

| 类型 | 能承担的角色 | 不能承担的角色 | 处理动作 |
|---|---|---|---|
| 二手转述（综述、解读、课程笔记） | 线索层：告诉你该读哪篇论文、哪个作者、哪个工具 | 证据层：不引用它给的数字与结论 | 顺藤摸瓜找到一手出处，入库时引用一手；找不到一手时，只写“存在这种说法，待核” |
| 版本过期（旧 API、旧框架） | 演进层：解释当年为什么这么做、现在为何改 | 现状层：不作为当前做法 | 只在“历史演进/迁移”段落使用，并标明版本与时间 |
| 营销稿、软文 | 事实碎片：版本号、额度、价格、入口、参数名 | 判断层：不采信其评价与对比 | 抽事实，逐条去官方页核对；核对不上的不进树 |

判断口径就一句：**它提供的是“去哪找”，还是“是什么”？** 前者可以放心用，后者必须先回到一手。

提炼率要有心理预期：10 条检索结果通常只产出 2–3 条可断言的句子，其余都作为线索或背景消化掉——这不是浪费，是检索的正常损耗。

## 三、抽取“可断言的知识”

不要摘抄段落。从每条结果里提炼一句话，形式是“条件 → 做法 → 代价”。举例：

- 错误不要清理：抹掉报错与重试记录会让模型失去修正依据 → 保留失败痕迹本身就是上下文资产。
- 长任务轨迹要折叠：把历史压成可递归的摘要，配合记忆卸载，才能撑住长周期任务。

如果一句话写不出“代价”，通常说明这条还不构成知识，只是观点。

## 四、写进树的正确姿势

1. **先找归属**：这条属于哪个域、哪个节点？优先补现有节点的一节，不轻易新建节点——新建节点意味着它要能独立成页（有定义、有边界、有取舍）。
2. **查重**：`grep -ril "关键词" trees/`，避免和已有页重复断言，lint 会逐句比对跨页重复。
3. **写作规范**：front matter 四字段、节点自足、不点名兄弟节点、数字有出处，详见 `skills/kb-tree/SKILL.md`。
4. **来源回填**：把知乎原文链接放进该页的「参考资料」，格式“名称：URL”，保留 `utm_medium=openapi_platform` 溯源参数，不要手动清洗成裸链。
5. **配问题**：在 `questions.jsonl` 增加 1–2 条，`section` 必须逐字命中该页的 H2/H3 标题。
6. **跑巡检**：`python3 skills/kb-tree/scripts/lint.py trees/computer/ai/agent`（或目标子树），必须 0 错 0 警。

## 五、标注可信度

知乎是**经验来源**，不是权威来源。写进树时分三档：

- **一手实践**（作者自述做过、给出参数或代码）：可以直接写成做法，注明“实践者复盘”。
- **论文/官方文档转述**：先找原始出处，参考资料优先给 arXiv 或官方文档，知乎链接作为二手佐证。
- **观点与预测**：只能写进“争议/演进”段落，且明确标注是观点。
- **只当线索的**：不入正文，最多以“待核”方式记一句，或直接留在检索笔记里。

## 六、一次完整示例

```bash
./zhihu "Agent 上下文工程" --count 5
```

拿到三条后，按上面的规则只保留两条可断言的（失败痕迹、上下文折叠），补进 `trees/computer/ai/agent/fundamentals/context/context.md` 的「实践者经验」一节，来源回填三条知乎链接，配两条问题，跑 lint，提交。
